## 0. 一句话裁决

**当前 dev 的 198/285 = 69.47% 里，至少 68 题（23.86%）不做任何检索就能拿到（回显题干），而把"答案"整个替换成 gold 本身只剩 171/285 = 60.00%。**
也就是说：**判据度量的不是答案正确性，而是答案的句式形状。** 任何在句式上做文章的改动都会涨分，而真正的检索/推理改进在这个判据下几乎不可见。这个结论在下面 §A 的 20 条里有 20 组数字支撑。

## A. 注水空间清单（20 条，全部实测）

> 每条格式：【机制】【代码位置】【实测可涨】【被判据哪一句挡住 / 挡不住】【建议防线】
> 基线一律为 dev 198/285 = 69.47%。

### A1 抄题干 —— 最严重的一条

- **机制**：把问句原样当答案输出。`single_chunk` / `alias` 的判据是"答案里出现 gold 串"，而 60.53% 的 single_chunk 题干里**书名号内就直接写着 gold**。
- **代码位置**：`src/arkrag/judge.py:157`（`if any(g in text for g in golds)`）；泄漏源在 goldset 构造，非判据。
- **实测可涨**：dev **68/285 = 23.86%**、holdout **50/195 = 25.64%**、clean **32/120 = 26.67%**。逐类 dev：single_chunk 46/76、alias 21/57、multihop 1/57、其余 0。
- **挡不住**。judge 只看"文本里有没有 gold"，完全不看这段文本是不是从题干复述来的。
- **防线**：①判据加"答案不得包含问句长度 ≥80% 的连续子串"；②评测前统计 question 含 gold 的题并单列，不计入改进分母（地板扣除，见 §D）。

### A2 放宽 `MAX_CLAIMS`（8 → 20 / 40）

- **机制**：答案能塞更多断言句，撞中 gold 的概率上升。
- **代码位置**：`src/arkrag/answer.py:85`（`MAX_CLAIMS = 8`）、`answer.py:796-800`（`accepted = accepted[: self.max_claims]`）。
- **实测可涨**：8→20 → **203/285 = 71.23%（+5 题）**；8→40 相同（饱和）；`dev_c12.json`（8→12）实测 **191/285 = 67.02%，比 8 还低 7 题**（说明这条不是单调，但在 20/40 档确实涨）。
- **挡不住**。judge 对句数无任何约束。
- **防线**：答案句数硬上限（≤ `MAX_CLAIMS`），并在报告里固定回显 `max_claims` 值。

### A3 放宽 token budget（12000 → 40000）

- **机制**：上下文更长 → 更多断言 → 更多 gold 命中。
- **代码位置**：`src/arkrag/retrieve.py:92`（`"max_context_tokens": 12000`）、`scripts/eval_answer_quality.py:189`（`--token-budget`）。
- **实测可涨**：12000→40000 → **207/285 = 72.63%（+9 题）**，其中 cross_chunk 19→26、direct_relation 50→51、multihop 8→9。
- **挡不住**。
- **防线**：预算作为**版本化常量**写死并在报告中回显；禁止扫描（理由见 §A21 / §E）。

### A4 放宽 `DEFAULT_MIN_TOP_SCORE`（0.05 → 0.0）

- **挡不住但也无收益**——只有和 A2/A3 组合才有效（见 A6）。

### A5 放宽 `MIN_EVIDENCE_CHARS`（4 → 1）

### A6 ★ 组合调参 —— 恰好卡在 80.00%

### A7 堆名字（soup）—— 一张嘴越过 80%

- **机制**：把全图 6583 个唯一实体名用「，」连成一句（30,659 字符，不含句号），拼在答案后面。
- **代码位置**：判据侧 `judge.py:192-202`（multihop 只要"每锚点各有一句与 gold 共现"）、`judge.py:157`（single_chunk/alias 子串）。
- **实测可涨**：
  | 变体 | dev |
  |---|---|
  | `answer + "。" + soup`（新起一句） | **235/285 = 82.46%** |
  | `answer.replace("。","，") + "，" + soup`（压成一句） | **238/285 = 83.51%** |
  | 只给"本来答错"的题补 soup | **254/285 = 89.12%** |
  | 只给"非 cross_chunk 的答错题"补 soup | **254/285 = 89.12%（+56 题）** |
- **逐类（基线 → 压一句）**：single_chunk 69→70、alias 52→57、direct_relation 50→54、**multihop 8→57（+49）**、**cross_chunk 19→0（−19，全 `extra_chapter_does_not_mention_entity`）**。
- **挡不住**。multihop 分支只要求"gold 与每个锚点共现"，**不要求中间实体参与、不要求锚点彼此共现**。一句 3 万字的话必然同时满足。
- **防线（实测有效）**：给"断言句"加**句长上限**。60/120/200/400 字四档结果完全相同：基线 198 一分不掉，攻击从 254 掉到 **204/285 = 71.58%**（杀掉 50 题里的 50 题）。另加"答案总长 ≤1000 字"，对基线**零代价**（生产答案 max=98 字）。

### A8 定点注水（掩耳盗铃版）

- **机制**：只对"判错了的题"追加 soup，判过的题原样保留。
- **实测**：**254/285 = 89.12%（+56 题）**，且 **cross_chunk 19→19 一分不掉**。

- **防线**：评测必须**单次前向**——答案生成阶段不得访问 `judge` 的输出；重跑必须整批重跑，禁止"逐题重试直到通过"。

### A9 `cross_chunk` 全列章节

- **机制**：把语料里全部 494 个章节代号一次性列出来，必然满足"gold ⊆ got"。
- **实测**：**0/38**。全部失败于 `extra_chapters_outnumber_gold`（额外章节数必须 ≤ gold 数）或 `extra_chapter_does_not_mention_entity`。**我原本的假设（全列即可通关）被证伪。**
- **变体**：只列"语料里真实提到该实体的全部章节"→ **25/38 = 65.8%**（不需要知道 gold，只要实体名 + 全语料检索）。列 `gold ∪ 任意 |gold| 个真实提及章` → 38/38（纯上界，需知 gold）。
- **挡住的句子**：`judge.py:179`（`len(extra) > len(want)`）+ `judge.py:176`（真实性）。这是**判据里唯一一处真正有效的上界约束**，应保留。

### A10 `chapter_texts` 宽松口径（裸子串）

- **机制**：`chapter_texts` 是"整章所有块正文用 `\n` 拼接"，真实性校验 = 裸子串匹配。
- **代码位置**：`scripts/eval_answer_quality.py:39-50`；消费点 `judge.py:176`。
- **实测可涨**：38 道 cross_chunk 中，**26 题（68.4%）的问句实体在 gold 之外的章节里也裸出现过**。也就是说，"额外章节真实性"这道校验对这 26 题**形同虚设**——随便列一个含该名字的章都能过。
- **建议防线**：把"本章提到该实体"从裸子串改成"该章内至少一个 assertion 的主语或宾语是这个实体"（图标注口径），这样能排除"正文里出现名字但实体未参与任何断言"的伪证据。

### A16 给答案加润色句 —— 实测**无收益**（反向证据，如实列出）

- **实测**：追加「以上内容整理自剧情原文。」/「详见相关章节。」/「（据剧情原文归纳）」

### A19 拒答策略被反向激励

- **代码位置**：`judge.py:147-149`（空答案 → `{"pass": False, "reason": "empty"}`）。
- **机制**：拒答永不算对 ⇒ **"多答"严格优于"少答"**。A7/A8 的 soup 攻击本质就是吃这个不对称。这也解释了为什么 `min_top_score` 调低（A4）没有收益、但 `max_claims` 调高（A2）有收益。
- **挡不住**（这是设计选择，不是 bug）。
- **防线**：若要报告"准确率"，必须同时报告"覆盖率"，并给出 F1 或 `pass − 误答惩罚`；否则任何"多说几句"的改动都被奖励。

### A20 ★ 判据的"形状天花板"与"错名地板" —— 决定性的一条

- **机制**：把一个**只含正确 gold（+ 锚点）但完全没有检索内容**的字符串喂给判据。
- **实测**：
  | 输入 | dev |
  |---|---|
  | 生产链路现状 | 198/285 = 69.47% |
  | **形状 oracle：锚点 + gold 拼成一句**（不含任何检索内容） | **285/285 = 100.00%** |
  | 同句式但 gold 换成随机错误实体名 | **1/285 = 0.35%** |
  | 答案 := gold answer 原文（`item["answer"]`） | **171/285 = 60.00%** ← 低于生产！ |
- **逐类（答案 := gold）**：single_chunk 76/76、alias 57/57、cross_chunk 38/38、**direct_relation 0/57**、**multihop 0/57**（全 `no_claim_links_gold_to_any_anchor`，因为 gold 只是关系词/实体名，不含锚点）。
- **含义**：判据对"gold 是否为真"的分辨力**是完美的**（错名 0.35%），但对"答案是否由检索支撑"的分辨力**是零**（形状 oracle 100%）。**任何只学句式的改动都能把分数推到 100%，而 `answer := gold` 反倒不及格。**
- **防线**：见 §D 的"形状对照臂"——每次报数必须同时给出形状 oracle 与错名地板两条基线，二者之间才是真实能力区间。

### A21（附）`token budget` 不是单调旋钮 —— 不能当调参维度

- **机制**：`retrieve.py:964-975` 的 kept 循环是"装不下就 continue 跳过、不回头重试"，顺序依赖 score 排序。
- **实测复现**：同一 hits，budget 300 保留 `obt/memory/story_chiave_1_1#008`（cost=269）；budget 600 反而丢掉它，换来 `activities/act34side/level_act34side_08_beg#011`（cost=431）。**预算变大，单元集合变小。** 同一 hits + 同一 budget 两次调用结果一致（确定性），所以是逻辑问题不是随机性。
- **含义**：任何"扫 budget 找最优点"的做法，既过拟合又建立在非单调函数上，"最优点"没有意义。
- **防线**：budget 冻结为常量；如需变更，必须附单调性测试（`tmp_adv_budget4.py` 的做法）。

### D3 bootstrap 用法（可直接跑）

脚本里已实现逐题配对 bootstrap（`scripts/audit_eval_recompute.py` 的 `_paired_bootstrap`）：

```powershell
# 1) 生成两条臂的逐题 0/1 向量（示例：baseline vs 你的改动）
py -3 -c @"
import sys, io, json
sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8', errors='replace')
a = json.load(open('data/eval_quality_dev.json', encoding='utf-8'))['rows']
b = json.load(open('data/eval_quality_YOURRUN.json', encoding='utf-8'))['rows']
SCOR = {'single_chunk','alias','direct_relation','multihop','cross_chunk'}
ka = {(r['question_id']): r for r in a if r['category'] in SCOR}
kb = {(r['question_id']): r for r in b if r['category'] in SCOR}
assert set(ka) == set(kb), '题集不一致，直接判失败'
va = [1 if ka[q]['arms']['prod']['pass'] else 0 for q in ka]
vb = [1 if kb[q]['arms']['prod']['pass'] else 0 for q in kb]
print(json.dumps({'a': va, 'b': vb}))
"@ > tmp_arms.json

# 2) 跑 bootstrap
py -3 -c @"
import sys, io, json, random
sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8', errors='replace')
d = json.load(open('tmp_arms.json'))
a, b = d['a'], d['b']
diff = [y - x for x, y in zip(a, b)]
n = len(diff); rnd = random.Random(7); idx = list(range(n)); B = 20000
stats = sorted(sum(diff[rnd.choice(idx)] for _ in idx) for _ in range(B))
obs = sum(diff)
lo, hi = stats[int(.025*B)], stats[int(.975*B)]
p = sum(1 for s in stats if s <= 0) / B          # 单侧 H1: 改动更好
print(f'Δ={obs:+d} 题 ({obs/n*100:+.2f}pp)  95%CI=[{lo:+d},{hi:+d}]  单侧 p={p:.4f}')
print('PASS' if (obs >= 1 and lo > 0 and p < 0.05) else 'FAIL')
"@
```

**判读规则**：`Δ ≥ +1` 且 CI 下界 > 0 且 `p < 0.05` 才算显著；**CI 跨 0 一律判不显著，不管 Δ 多好看**。
**已知反例（务必记住）**：桥接通路 bootstrap 结果 `Δ=+27 题(+9.47pp) CI[+16,+39] p<0.0001` —— **统计上极显著，但 §A7/§A11 已证明增益 100% 来自模板而非证据**。显著性检验只能排除噪声，**排除不了注水**。所以 D1 的第 1~8 条必须一起看。
