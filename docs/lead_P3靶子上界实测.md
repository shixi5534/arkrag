# P3 第三轮靶子上界实测

> 复算命令：`py -3 scripts/lead_p3_targets.py --json data/lead_p3_targets.json`
> 数据：`data/lead_p3_targets.json`（41,359 B，五溯源字段在位，0 处绝对机台路径）
> 世代：`g-20261103T132152Z-06a741`；数据集：`data/goldset/gold-v2.json`，只取 `split == dev` 且非 `should_abstain`

## §0 为什么写这份

P3 第一轮（整行引用）只救 `alias`-类 14 题的真实收益、第二轮（标题通路）只动 `single_chunk`，
其余七类增益**全是 0**。在决定第三轮往哪打之前，必须先用**在线可得的信息**
（问句 + 上下文 + 图，不用 gold）把候选方向的上界量出来。

不做这一步就开工，风险是拿一个「结构性不可达」的方向做一周——
比如「放宽准入判据」，实测覆盖率能涨但答案质量一题都涨不动（见 `docs/lead_引用覆盖五闸门实测.md`）。

本文件量四件事，每件都直接决定「值不值得投」：

| 节 | 问题 | 结论（一句话） |
|---|---|---|
| §1 | 「按题型路由」能不能用纯规则做 | **能，零误分类**（25 个骨架，跨类 0 个） |
| §2 | `cross_chunk` 的章节代号能不能机械生成 | **能，38/38 精确**，但必须读块字段不能截路径 |
| §3 | `multihop` 的共同中间实体能不能机械求 | **能，top1 45/57**，但**抬不动引用覆盖** |
| §4 | 闸门2 的 203 题该归谁 | **三层各 80/77/46，是三件不同的活** |

## §1 题型路由：问句骨架与 category 一一映射

把问句里的「…」替换成 `「Q」`、《…》替换成 `《T》`，得到骨架：

```
题 640 / 骨架 25 / 跨类骨架 0
每类骨架数：single_chunk 2 / alias 2 / direct_relation 2 / multihop 2 /
            cross_chunk 2 / time_conflict 2 / adversarial 2 / negative_abstain 11
```

**跨类骨架数 = 0** 意味着：同一个骨架 100% 只对应一个 category。
⇒ 路由不需要模型、不需要训练、不需要新依赖，纯字符串规则即可，且不会误分类。

`negative_abstain` 有 11 个骨架（其余七类各 2 个），因为「不可回答」这件事本身有十种问法。
这不影响路由（仍然零跨类），但意味着写触发词时**不能只写两三条**。

骨架示例（每个类的第一例）：

- `single_chunk`：`在剧情《T》的正文里，出现了这样一句话：「Q」。这句话出自哪个文本块？请给出该块的标题。`
- `multihop`：`从「Q」出发，经过一个中间实体可以到达「Q」。这个中间实体叫什么？`
- `cross_chunk`：`「Q」这个实体横跨了多个章节。请给出它出现过的章节代号。`
- `direct_relation`：`根据剧情，「Q」与「Q」之间的关系是什么？请用词表里的一个关系词回答。`

## §2 `cross_chunk`：章节代号可从块元数据机械拼出（38/38）

**答案形态**：`it["answer"]` 是 `act33side、main_ep14` 这种「、」连接的章节代号串；
`acceptable_answers` 另给空格版与逗号版。

| 生成方式 | 精确命中 |
|---|---|
| **读 gold 块的 `chapter` 字段，按 gold 块顺序用「、」连接** | **38 / 38** |
| 从 `chunk_id` 路径截第二段 | **7 / 38** |
| 用「实体在断言里作 subject/object」取章节集合 | 24 / 38（集合相等 24/38） |
| 上述断言法至少命中一个 gold 章节 | 38 / 38 |

**这一节的坑（值得单列）**：`chunk_id` 形如 `activities/act33side/level_act33side_01_end#003`，
路径第二段确实是 `act33side`；但 main 线是 `obt/main/level_main_14-11_beg#004`，
路径第二段只有 `main`，**真实章节字段是 `main_ep14`**；memory 线同理（路径给 `memory`，字段给 `memory_whitw2`）。
按路径截只能拿 7/38，读字段拿 38/38 —— **同一批题、同一个「章节」概念，两种取法差 31 题**。
这与「两个合法数据源选错一个」（13,786 vs 13,798）是同一族，但更隐蔽：这里两条路都能跑通、都返回非空字符串。

**不用 gold 时的上界 = 24/38**：用「实体在断言里作端点」取到的章节集合与 gold 集合相等。
候选章节数中位 2、最大 5 —— 数量级可控，不是「实体出现过的所有章节」（那样会到 47 个）。

**为什么不能用「实体在正文出现」当判据**：`q-cx-000001`「以勒什」正文出现于 47 个块，取到 3 个章节且含 `act17mini`；
`q-cx-000004`「海洋」覆盖 47 个章节。正文出现 ≠ 该实体的归属章节。

## §3 `multihop`：共同中间实体可机械求，但抬不动引用覆盖

邻接表结构是 `retriever.adjacency[entity_id] == {"out": [...], "in": [...]}`，
每个元素是含 `neighbor_id` / `relation` / `direction` / `weight` / `edge_id` / `assertion_ids` 的字典。
（我前两版脚本把它当成「list of dict」和「dict of set」，两次都报错 —— 见 §5 第 1 条。）

用「两端点各自的邻居求交」求共同中间实体（权重取两侧边权之和排序）：

```
题 57 / 可解析双端点 57 / 候选集含 gold 答案 57 / 候选唯一 25（全对）/ 加权 top1 正确 45/57
候选数中位 2 / 最大 6
```

**关键限定**：`required_in_context` 为真 **0 / 57**；当前 `answer_hits_gold` **25 / 57**。

⇒ 这条路能把「答案对了」从 25 拉到最多 45 题，**但引用覆盖一题都不会涨**，
因为 gold 块 57 题一个都没进上下文（它们在闸门2，见 §4）。
**答案质量和引用覆盖在这里是两条独立的线**，不能用一个数字汇报。

## §4 闸门2 的 203 题：三层等分，是三件不同的活

对「`required_in_context` 为假」的 203 题，逐题看 gold 在**前 20 命中列表**里排第几、
有没有进 `context.units`、有没有落在 `stats.truncated_chunks` 里：

| 层 | 题数 | 含义 | 该谁的活 |
|---|---|---|---|
| **容量层**：gold 在前 20，但全被预算截断 | **80** | 排序对了，6000 token 装不下 | 预算/填充（P2） |
| **检索层**：gold 不在前 20 | **77** | 排序没把它排上来 | 排序/召回（P2） |
| **部分层**：多块题只进了其中一部分 | **46** | 第一块进了、第二块没进 | 多块题的第二块名次（P2 专项） |

按类：

| 类 | 合计 | 容量层 | 检索层 | 部分层 |
|---|---|---|---|---|
| multihop | 57 | 26 | 20 | 11 |
| time_conflict | 36 | 12 | 7 | 17 |
| direct_relation | 33 | 13 | 20 | 0 |
| cross_chunk | 32 | 8 | 6 | 18 |
| adversarial | 18 | 6 | 12 | 0 |
| single_chunk | 15 | 8 | 7 | 0 |
| alias | 12 | 7 | 5 | 0 |

**这张表的意义**：把 203 合成一个「闸门2 太大」的结论，会得出「该去调排序」；
但 80 题排序已经对了、只差容量，46 题排序也对了、只差第二块 —— **126/203 不是排序问题**。
反过来只看「容量层 80」就以为加预算能全救，也不成立：`frontier` 实测（`docs/lead_预算容量与填充实测.md`）
表明 `6000 → 8000` 的代价比是 any 22:2、all 22:0，且 8000 仍会留下 `q-mh-000042` 这类非单调丢失。

## §6 对 P3 第三轮的直接影响（四条）

1. **题型路由应当采用，且成本近零**：25 个骨架、0 个跨类，纯规则分派。
   但触发词要把 `negative_abstain` 的 11 个骨架覆盖全，否则那 8 题会掉回通用路径。
2. **`cross_chunk` 章节包是性价比最高的一块**：不用 gold 的上界 24/38，
   且实现路径明确（读块 `chapter` 字段 + 引用发对应块），不碰 `retrieve.py`。
   **门槛按 24 定，不是 38**（38 是用了 gold 的数字，只能作「机制可行」的证明）。
3. **`multihop` 中间实体要单独立项，且不许与引用覆盖混报**：答案上界 45/57，
   但 `required_in_context = 0/57` 不变，所以它**只抬答案质量、不抬引用覆盖**。
   如果这一轮的目标写「提升引用覆盖」，做它就是方向错了。
4. **闸门2 拆分后，P2 的剩余价值要重新估**：容量层 80 + 部分层 46 = 126 题排序已对，
   只有 77 题是真的排序问题。这改变了「排序是主战场」的权重，但**不改变** P2 已有结论
   （`cooc` 只动 `direct_relation`、`hop_line` 是洗牌）。

## §7 六条限制

1. **只测 `dev` 350 应答题**，不外推到 `new-holdout 160`。dev 的类占比与验收集不同。
2. **`answer_hits_gold` 与 `correct_coverage` 都是子串判据**，未展开 `acceptable_answers`；
   本文件所有 base/cand 对比都在同一判据下做，故**差值**可信，**绝对值**偏低。
3. **`cross_chunk` 的 24/38 是「按断言端点取章节集合」的口径**，比的是集合不是顺序；
   真实实现要输出有序串，顺序上还会掉几题。**24 是上界不是承诺。**
4. **`multihop` 的共同中间实体只用了 1 跳共同邻居 + 边权和排序**，没有做路径约束
   （问句里「经过一个中间实体」不限定关系类型）。放宽到 2 跳会提高召回也提高候选数，本轮没测。
5. **闸门2 三层的判据依赖 `stats.truncated_chunks`**（`build_context` 的截断名单）。
   「部分层」是 `required ∩ units` 非空但非全含；若某题的 required 块既没进 units 也没进
   truncated 名单，会落进「其它」——实测该桶为 0，但这个 0 只对本世代成立。
6. **本轮没有真跑任何候选改动**，五个数全是结构量。任何一条要变成收益，都要过单变量、
   引用定位、拒答三道门，并在 `dev` 上真跑。

## §8 我在这一轮踩的坑（三条，都是「接错/读错但看不出来」）

1. **邻接表结构读了三次才对**：第一版当成 `{eid: {out: {...}, in: {...}}}` 里的集合处理报
   `TypeError: cannot use 'dict' as a set element`；第二版当成 list-of-dict 报
   `AttributeError: 'str' object has no attribute 'get'`（因为第一版把元素打印出来污染了判断）。
   正确形状：`adj[eid] = {"out": [dict, ...], "in": [dict, ...]}`，元素取 `nb["neighbor_id"]`。
   **教训：结构不确定时先 `type()` + 打印一层，不要先写循环。**
2. **章节代号从路径截 vs 读字段，差 31 题**（7/38 vs 38/38），两条路都能跑通、都返回非空字符串。
   这是「两个合法数据源选错一个」的第五次。
3. **第一次跑把 640 题全喂进 `cross_chunk` / `multihop` 两节**（应只喂 dev 350），
   得到「题 64 / 题 96」而正文引用的是 dev 数字。发现方式是数字对不上自己上一轮手算的 38/57。
   **教训：脚本里的种群过滤要和文档写的那一行同一个口径，且打印出来。**
