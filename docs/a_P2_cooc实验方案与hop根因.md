## 1. `cooc` 实验方案（0.1 / 0.3 两档，可执行、可复算、可回滚）

> 本轮真跑同时测了 `cooc0.3` 和 `cooc0.1`。两者的差别不是「增益大小」，是
> **覆盖面是否零回退**（见 §4）。方案主体对两档通用，权重只是常量取值。

### 1.1 唯一变量与确切改动位置

**信号定义**（已实现在 `scripts/a_hop_suppress.py` 的 `question_signals()`，`cooc` 字段）：

对深池第 `i` 个块，若其正文**某一行同时包含问句解析出的两个端点规范名**，则 `cooc[chunk_id] = 1`；否则 `0`。
端点取 `qa["entity_candidates"][:2]` 的 `entity_id` 对应规范名。

**加成落点**（P2 唯一允许改的位置，行号已核对）：

```
src/arkrag/retrieve.py:451-469  search() 里逐块汇总分数那一段
    现状（:452-460）：
        for cid, item in merged.items():
            total = 0.0
            for src in item["sources"]:
                if src["channel"] == SOURCE_BM25:      total += src["score"]
                elif src["channel"] == SOURCE_SPEAKER: total += SPEAKER_BOOST_WEIGHT * src["score"]
                else:                                  total += ENTITY_CHANNEL_WEIGHT * src["score"]
    目标：在内层循环之后、hits.append() 之前加一行
        if cooc.get(cid): total += COOC_BOOST_WEIGHT          # COOC_BOOST_WEIGHT = 0.3
```

三个必须注意的点（都核对过代码）：

1. **必须加在 `hits.sort()`（:468）之前**，不能做成「先切 top_k 再重排」——那样第 43 名的块永远进不来。
   `merged` 里装的是 `depth = top_k * CANDIDATE_POOL_MULT = 200` 的全部候选
   （`bm25` 就是 `index.search(top_k=200)` 归一化后的结果，见 `:410-411`），所以 200 名以内的块都能被抬进来。
   本轮实测 `q-mh-000044` 的第二块 gold 原始 rank 43 被抬动，正是这个原因。
2. **`top_score`（:472 `hits[0]["score"]`）会自动带上加成**，不用额外改。它被 `answer.py` 用作「检索不足」判据，
   带加成后会略微抬高 top1，需观察 `DEFAULT_MIN_TOP_SCORE = 0.05` 的拒答边界是否被踩到
   （`tests/test_answer.py` 有相关用例，跑一遍单文件）。
3. **建议给 hit 增一个 `"cooc_boost"` 字段**（additive，不改既有字段），否则事后无法从 `hits` 里看出哪块被加成了。
   本轮 `a_hop_suppress.py` 的补丁是直接改 `score`、把明细留在 `state` 里，正式实验建议落到 hit 上便于归因。

**三条硬约束（违反任一条则实验作废）**：

1. **加成必须折进 `hit["score"]`，不许只改 hits 顺序。**
   `src/arkrag/retrieve.py:850-853` 的 `build_context` 是
   `ordered = sorted(units.values(), key=lambda u: (0 if direct(u) else 1, -u["score"], u["chunk_id"]))`
   —— 它**只读 `score` 不读顺序**。只改顺序会得到「R@20 涨、下游一点不动」的假增益。
   本轮所有真跑已按此实现（`a_hop_suppress.py` 的 `make_patched_search` 里 `h2["score"] = score[cid] + boost(cid)`，
   且 `stats["top_score"]` 同步重算）。
2. **`cooc` 只在已进深池的块上算，不许引入新召回。** 本轮未改 `depth`、未改 `CANDIDATE_POOL_MULT`。
3. **不许同时改 `pair` 或 `hop` 权重。** `pair0.3+hop0.2+cooc0.1` 的净 +13（回放口径）虽优但违反单变量，
   本轮**不采纳**，只作为「三信号增益不重叠」的证据。

## 2. `hop_line` 失效根因（比「抑制不够」更根本）

### 2.1 先说结论：不是权重问题

Lead 的要求是「按 cn 倒数加权 + 抬分必须局部」。我按这两条都测了，**都不够**。真正的失效面是：

> **`hop_line` 在难题的候选块里几乎全亮。** 92 道「gold 不在前 5、两端点齐全、有共同邻居」的题里，
> 平均 **19.15 个块**同时满足「含任一端点 + 含任一共同邻居」——而这 19 个块里通常只有 1 个是真 gold。

| 变体 | 判定条件 | gold 命中 | 有对手命中 | 对手块均值 | 精确率代理 |
|---|---|---|---|---|---|
| **`line_any`（现行）** | 任一端点 + 任一共同邻居，**同一行** | 78/92 = **84.8%** | 87/92 = 94.6% | **19.15** | 0.042 |
| `line_all` | **两端点都**在同行 + 共同邻居同行 | 22/92 = 23.9% | 49/92 = 53.3% | 3.55 | 0.063 |
| `win1_any` | 端点在 3 行窗口内 + 邻居 | 83/92 = 90.2% | 91/92 = 98.9% | 22.15 | 0.039 |
| `win1_all` | 两端点 3 行窗口 + 邻居 | 39/92 = 42.4% | 61/92 = 66.3% | 10.22 | 0.040 |
| `win2_all` | 两端点 5 行窗口 + 邻居 | 42/92 = 45.7% | 61/92 = 66.3% | 11.26 | 0.039 |

（「精确率代理」= gold 命中数 / (gold 命中数 + 对手命中块总数)，越大越好）

**没有任何一个单行变体能同时保住 gold 和排除对手。** 变体 3 把对手块从 19.15 压到 3.55（好），
但 gold 命中从 84.8% 崩到 23.9%（更糟），精确率代理只从 0.042 升到 0.063——**靠牺牲召回来的轻微精确率提升**。

### 2.4 为什么「更局部」在对话体语料上失效（结构性原因）

`07_beg#003` 正文是**对话体**，「莫不服」与「煌」的每次出现都是**说话人前缀**：

```
L0  莫不服：都准备好了？          ← 端点
L1  煌：准......准备好了。         ← 共同邻居
L2  莫不服：你负责的这碗长寿面...   ← 端点
L3  煌：明......明白。             ← 共同邻居
```

**「煌」在这块里出现 8 次，8 次全部是行首说话人前缀**（`huang_1_1#003` 里 18 次中 16 次是前缀）。
两块 gold 的分子与分母**从不共现于同一行**，所以 `hop = 0`；而 rank7、rank8 的竞争块恰好把两者写进了一行。

⇒ **`hop_line` 判定的是「同一行共现」，而对话体语料的正确共现形态是「跨行交替」。**
这不是调权重能解决的：任何基于「同一行」的共现信号，在对话体里判真的时候往往判的是
「这两个人在这块里说过话」，而不是「这两个人有这个中间关系」。

**跨行共现的规模**（350 dev 里两端点齐全且有共同邻居的 148 题）：

| | 题数 | 说明 |
|---|---|---|
| gold 块内两端点都出现 | 93 | |
| 其中**跨行共现**（对话交替，同行判定为假） | **17** | `hop_line` 在这批题上必然漏判 |
| 其中同行共现（`hop_line` 能命中） | 87 | |

按类跨行占比：`time_conflict` **12/34 = 35.3%**（最高）、`multihop` 4/48 = 8.3%、`direct_relation` 0/41、
`single_chunk` 0/14、`adversarial` 0/6。

⇒ **`time_conflict` 的 `hop_line` 打坏集中（`q-tc-000005` cn=16、`q-tc-000019` cn=20）有结构原因**：
该类三分之一的 gold 是跨行共现，同行信号全落在错的地方。

## 7. 我这一轮踩的坑（供后续避免）

1. **`loaded` 是 dict 不是对象**：`pipeline.load_generation()` 返回字典，读图要 `loaded["graph"]["entities"]`，
   不是 `loaded.graph`。写归因脚本时先 `print(type(...))`。
2. **深池必须压 `CANDIDATE_POOL_MULT`**：`search(top_k=200)` 内部 `depth = top_k * 10 = 2000`，
   与生产 `top_k=20`（depth=200）的候选集与归一化分母不同，前 20 会漂移。
   正确做法是临时把 `retrieve.CANDIDATE_POOL_MULT` 压到 1（`try/finally` 还原），让 top_k 自己承担深度。
3. **补丁生效时 `retriever.search` 已被替换**：`deep_search()` 必须接收**原始** search 函数，
   否则无限递归（首跑撞 `RecursionError`）。
4. **对话体语料的「共现」有两层含义**：说话人前缀（`X：`）与正文提及。我最初怀疑 `hop_line` 全靠前缀凑成，
   实测 169 个命中块里 **0% 是纯前缀**（全含正文提及），真问题在**跨行**（§2.4），不是前缀。
5. **代理指标不能当验收**：§2.7 用 `rank ≤ 5` 代理「进上下文」，真跑是 189，代理是 193——**差 4 题**。
   代理只可用于策略筛选，判据必须用真跑。
