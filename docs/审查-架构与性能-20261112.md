**审查范围**：`src/arkrag/` 50 个模块（1.17 MB 源码）、`data/` 产物、`tests/` 74 个文件、仓库根目录。
**审查方式**：只读。全部数字为本机实测（Windows / CPython 3.14.7 / `.venv`），非引用文档。
**测量工具**：`ast` 静态分析、`cProfile`、`K32GetProcessMemoryInfo`（WorkingSet / PrivateUsage）、真实 HTTP 打 `server.serve()`。

> 说明：本报告只提出结论与证据，**未修改 `src/` 下任何文件**。唯一写入是本文件。

## 1. 【严重】A-1 每个请求白付一次 `Retriever` 克隆

| 项 | 内容 |
|---|---|
| **影响** | 严重（线上延迟 2.3–2.5×） |
| **证据** | `server.py:1257` / `server.py:1496(_with_budget)`；实测见下 |

**证据链**：

1. `pipeline.build_pipeline()`（`pipeline.py:192-199`）构造 `Retriever` 时**不传 `budget`**，于是 `Retriever.__init__` 用 `DEFAULT_BUDGET["max_context_tokens"] = 12000`（`retrieve.py:92`）。
2. `AppState.served()`（`server.py:460`）调的是 `build_pipeline(loaded, top_k=20, graph_depth=1)`，**没有** `apply_prod_profile()`。
3. `server.py:1257` 的判断：
   ```python
   if ctx_tokens != served.pipeline["retriever"].budget.get("max_context_tokens"):
   ```
   实测 `12000 != 24000` → **恒为真**，于是每个请求都走 `_with_budget()` 克隆。

**实测（`g-20261103T132152Z-06a741`）**：

```
served retriever budget max_context_tokens = 12000
server default ctx_tokens (Settings)      = 24000
=> mismatched: True   → 每请求都克隆

_with_budget 单次耗时：P50 = 257 ms，min 237 ms，max 754 ms（5 次）
克隆重建：chunks dict 复制 13,798 项 / assertions_by_id 62,924 项 /
          assertions_by_chunk 13,309 组各自 sorted + _pred_by_pair 62,924 条
```

**真实 HTTP 端到端**（`server.serve()` + `urllib`，同一问句 5 次）：

```
wall        P50 = 751 ms
server 自报 total_ms P50 = 301 ms
未记账差额 = 450 ms  => 服务端**少报 2.5 倍**
```

对照实验（把预算在 `served()` 里直接设成 24000，跳过克隆分支）：

```
WITH FIX  wall P50 = 326 ms   server total_ms P50 = 296 ms   （tokens=23726, units=19）
```

**收益**：P50 751 → 326 ms（**−56%**）；且服务端自报延迟与实际 wall 重新对齐。

**建议**（二选一，都很小）：
- 首选：`AppState.served()` 里 `build_pipeline(...)` 之后补一句 `pipeline_mod.apply_prod_profile(pipe)`——这是**已有函数**（`pipeline.py:248`），CLI/评测脚本都在用（`ask.py:254/545`、`eval_answer_quality.py:665`），只有服务端漏了。
- 备选：把 `_with_budget` 改成"复用父实例的派生表、只覆盖 budget 字段"的浅克隆，避免重扫 6.3 万条断言。

> 注：这是**接线缺失**，不是设计错误。`apply_prod_profile` 的 docstring 写明"服务端、CLI、评测脚本三处都要用生产档，各写一遍就是三份判定"——但服务端那一处没接上。

## 2. 【严重】A-2 候选块全量分词，只留 1/20

| 项 | 内容 |
|---|---|
| **影响** | 严重（单问 62–65% 耗时） |
| **证据** | `retrieve.py:1245(cost_of)` 在 `retrieve.py:1356/1365/1385/1396/1408` 的装填循环中被逐单元调用 |

**机制**：`build_context()` 先把 `ordered` 里**所有**候选（实测 181–519 个）逐个 `cost_of(unit)` 计价——`cost_of` 内部是 `estimate_tokens(f"{title} {chapter} {text}")` → `index.tokenize()`（`index.py:310`）→ 完整 t2 分词（`index.py:263`，含 `NameTable.spans_with` 专名扫描）。装填时只有装得下的才留下（实测 9–19 个），**其余 20 倍的计价全部丢弃**。

**实测（单问）**：

```
wall = 273 ms
estimate_tokens 调用 181 次 / 155,622 字符 / 178 ms  → 占 wall 65%
candidates = 181  kept_units = 9   →  浪费比 20.1×
若只计价被保留的单元：9 ms（省 95%）
```

24000 生产档下更糟：`candidates = 519, units = 19`（比值 **27×**）。

**已有记忆化但只覆盖窗口路径**：`charge_of()`（`retrieve.py:1316`）的注释明说"按 `chunk_id` 记忆化……`reserve` 路径会对同一单元调用两次"——但这个记忆化**只包住 `window_cost`**，不包 `tokenize` 本身，更不跨请求。

**建议**（按 ROI 排序，前两项互相独立）：

1. **`estimate_tokens` 加 `@lru_cache` 或实例级 `dict` 缓存**（键 = `(text, tokenizer_version)`）。
   实测同一世代内块正文不变，跨问重复率极高：
   ```
   无缓存          138 ms/query
   有缓存（暖）     60 ms/query   （省 56%，缓存 655 条文本）
   ```
   注意 `lru_cache` 不能直接套 `name_terms`（`frozenset` 可哈希，但 8,177 项做键会让每次哈希变贵）——建议键用 `(text, id(name_terms))` 或把 `name_terms` 固定到索引实例上。
2. **装填时惰性计价 + 剪枝**：`ordered` 已按 `-score` 排序，`cost_of` 只需对**前缀**求值。先用 `len(text)` 的粗估（字符数 × 已知 token/char 比）做预算剪枝，只对真正要装填的单元精算。粗估误差不影响正确性（最终 `tokens_used` 仍由精算得到），但能把 181 次降到 ~25 次。

## 3. 【严重】A-3 `lexical.json` 的倒排用 `dict[int,int]` 驻留 —— 795 MB

| 项 | 内容 |
|---|---|
| **影响** | 严重（占常驻内存 56%） |
| **证据** | `index.py:706(load_index)`、`index.py:396(postings: dict[str, dict[int,int]])` |

### 3.1 分阶段实测（`g-20261103T132152Z-06a741`，磁盘 288.4 MB）

`pipeline.load_generation()`（`pipeline.py:114-165`）严格按序全量载入，**无惰性**：

| 阶段 | 磁盘 | 耗时 | WS 累计 | Priv 累计 |
|---|---|---|---|---|
| import only | — | — | 27 MB | 18 MB |
| `graph.json` | 30.1 MB | 0.32 s | 98 | 90 |
| `adjacency.json` | 25.2 MB | 0.24 s | 159 | 151 |
| `assertions.jsonl` | 65.6 MB | 1.11 s | 460 | 452 |
| **`index/lexical.json`** | **101.7 MB** | **8.68 s** | **1252** | **1248** |
| `chunks.jsonl` | 65.7 MB | 2.52 s | 1361 | 1358 |
| `chunks→dict` | — | 0.01 s | 1361 | 1359 |
| `build_pipeline` | — | 0.47 s | 1390 | 1387 |
| **PEAK** | 288.4 MB | 13.3 s | **1475 MB** | — |

**膨胀 5.1×**（288 → 1475 MB），与你给的 1.0–1.5 GB 一致。

### 3.2 索引部分为什么这么贵

`lexical.json` 结构（实测）：

```
{ meta: 21 keys, tokenizer_version: "t2", name_terms: 8,177,
  doc_id: 13,798, doc_len: 13,798,
  postings: 390,508 terms × 平均 23.0 条 = 8,996,776 条 }
```

`load_index()` 的关键一行：

```python
index.postings = {k: {int(s): f for s, f in v.items()} for k, v in payload["postings"].items()}
```

**三种表示实测对比**（同一份 `lexical.json`）：

| 表示 | 构建耗时 | WS 增量 | 每条 posting |
|---|---|---|---|
| **A. 当前 `dict[int,int]`** | 6.05 s（json 2.5 + rekey 3.5） | **+795 MB** | **92.7 B** |
| B. 保留 str 键（不 rekey） | 5.21 s | +333 MB | 38.8 B |
| C. 平行 `array('I')` 两数组 | 6.96 s | +290 MB | 33.8 B |
| D. 三条扁平数组（offs|slots|tfs） | 5.93 s | **+182 MB** | 21.2 B |
| 理论上界（2×uint32/条） | — | 69 MB | 8.0 B |

**结论**：
- 光"把 str 键 rekey 成 int 键"这一件事，**多花 3.5 s 换 462 MB**（A vs B）。而 rekey 的必要性只是 `search()` 里 `self.doc_id[kv[0]]` 的列表下标——用 `array` 表示后这个优化仍然成立（方案 C/D 更快）。
- `content_digest()`（`index.py:351`）对每个 term 做 `"".join(...)` + `sorted(posting)`，实测占 `verify_generation` 的 15.7 s / 35 s（见 B-3）——这也是 dict 表示的连带成本。
- 8,996,776 × 92.7 B = 834 MB，与 795 MB 实测吻合。

### 3.3 `lexical.json` 全量载入是必须的吗？—— **不是，且已有现成替代**

`fts_backend.Fts5SearchBackend` 已实现同接口后端（`fts_backend.py:579`），`search_backend.open_backend(kind="auto")`（`search_backend.py:143`）已能切换。**实测**：

```
FTS sqlite 打开（mode=ro）        =   4.5 ms   内存 +5 MB
FTS backend 构造 + norm 表预建     =  27   ms   内存 +5 MB
单次 search top_k=20             = 28–36 ms
（对照：json 后端仅 postings 就 795 MB，单次 search 85–113 ms）
```

对照 `docs/h3-FTS5迁移.md` 的记录：FTS 后端在**单次检索**上更慢（P50 +27~60%），但实测这里的 28–36 ms 已经不慢于 json 的 85–113 ms——差异来自既有的 `norm_table` 预建（H2）已被 FTS 后端复用。

**可行性判断**：

| 方案 | 内存 | 冷启动 | 检索 | 改造成本 | 风险 |
|---|---|---|---|---|---|
| 现状 `dict[int,int]` | 795 MB | 8.7 s | 85–113 ms | 0 | — |
| **D. 扁平 `array` + `mmap`** | **182 MB** | ~6 s（可 mmap 至 ~0） | 需重写 `search` 内层循环 | 中（`index.py` 1 处 + `search` 1 处） | 中：`content_digest`/`probe_digest` 必须逐位不变，有测试钉住 |
| **FTS sqlite（已存在）** | **5 MB** | **27 ms** | 28–36 ms | **极低**（`open_backend(kind="fts")` 一行） | 低：`exact` 模式已断言与 json 后端 top-20 逐位相同 |

**建议**：
1. **立即可做**：把服务端/CLI 的 `load_generation` 接到 `search_backend.open_backend(kind="auto")`。这样只要 `data/arkrag/fts/<gid>.sqlite` 存在就自动走 FTS，**内存 −790 MB、冷启动 −8.7 s、检索不打折**，回滚只需删 sqlite。注意 `.gitignore` 已声明 fts 可重建（`scripts/build_fts_index.py`，36 s），且 `default_db_path` 刻意放在世代目录外以免污染摘要（`search_backend.py:186`）——设计已经为这一步准备好了。
2. **中期**：若坚持 json 后端，把 `postings` 改成方案 D。但既然 FTS 后端已存在且逐位等价有测试，**不建议**再投人力做 D。

> **为什么 `lexical.json` 不能"惰性加载"**：`search()` 需要任意 term 的完整 posting，访问模式是随机的，无法分批。惰性加载只在"每问只碰 ~74 个 term"这点上成立——但索引结构是 `dict[str, dict]`，要取第 N 个 term 的 posting 必须先把整个 JSON 解析完。**这正是 sqlite 存在的理由**，而不是 `mmap` + JSON（JSON 不支持随机访问）。

## 4. 【严重】A-4 测试总数精确断言 —— 当前是红的

| 项 | 内容 |
|---|---|
| **影响** | 严重（CI 恒红 → 门失去信号价值） |
| **证据** | `tests/test_suite_hygiene.py:1249(N=2403)`、`:1251-1270(test_declared_count_matches_actual)` |

**实测**：

```
$ pytest tests/test_suite_hygiene.py -q
FAILED tests/test_suite_hygiene.py::TestSuiteSizeIsMonotonic::test_declared_count_matches_actual
1 failed, 296 passed, 1 skipped in 8.21s
    AssertionError: 测试总数变了：登记 2403，实际 2481。
```
（另一次全量 collect 读数为 **2487**——见下方"更糟的一点"。）

### 成本与收益评估

**成本（可量化）**：
- 该文件 **1,271 行 / 99 KB**，其中**注释 1,038 行（82%）**，实际代码只有 **190 行（15%）**。
- `TestSuiteSizeIsMonotonic` 单个类占 **L212–1270，1,059 行**，只为维护一个整数 `N`。
- 每次增删测试都要：① 跑 `--collect-only`；② 手算 parametrize 增量（`TEST_FILES` 是 `glob("test_*.py")`，**每加一个测试文件就让 4 个 parametrize 各多一项**）；③ 改 N；④ 在注释里写一段"这次换来的门是什么"。
- 历史记录本身证明了这个成本：该文件的注释里记了 **40+ 次** N 的变更（936→948→1019→1056→1093→1146→1208→1248→1251→1269→…→2403）。其中一段自认：
  > "⚠️ 这两个数**在同一轮里变过四次**……**谁最后改谁负责重新实测这个数**，不许按增量手算"

**更糟的一点（新发现）**：`TEST_FILES = sorted(TESTS.glob("test_*.py"))`（`:38`）意味着 N 是一个**随目录内容变化的复合量**，而 N 又被写成常量。所以"登记值"实际上是一个**派生量被硬编码**——它无法只靠"新增 X 个测试"推出，必须实测。这让"精确等于"这个断言在最常见的操作（加测试）上**必然失败**，而不是"偶尔失败"。

**收益**：
- 真实收益只有一条：**防止测试被静默删除**。
- 但这条收益**用错了工具**：断言"总数不变"既抓不到"删了 A 加了 B"（净零），也抓不到"某个测试被 skip 掉了"。它只在"净减少"时报警——而"净减少"恰恰是最容易被 git diff 看见的事。

### 替代方案（按推荐度）

1. **【首选】改成"每文件基线 + 允许增加"的单调断言**
   ```python
   BASELINE = {  # 文件 -> 用例数，只在"减少"时失败
       "test_answer.py": 120, "test_identity.py": 340, ...
   }
   def test_no_test_file_shrank():
       for path, n in collect_per_file().items():
           assert n >= BASELINE.get(path, 0), f"{path} 用例数减少 {BASELINE.get(path,0)}→{n}"
   ```
   收益：`git diff` 能审核"删了哪个文件的哪条测试"；不再需要在注释里写 40 段说明；新增测试零摩擦。
   成本：约 30 行代码，替换掉 1,059 行。

2. **【次选】用 `pytest --collect-only -q` 的 per-file 计数生成基线文件**（`tests/.test_baseline.json`），由一个脚本更新，测试只读它。把"人肉维护常量"变成"生成物 + 一次 diff"。

3. **【必做，无论选哪个】删除"精确等于"这一条**。它当前是红的，等于本项目最核心的纪律（"门必须能变红"）被一条永远红的门自己破坏了——而报告里的其他门（`TestEveryFileIsCollected`、`TestAssertionsActuallyRaise`、`TestNoCwdRelativeRepoPaths`）仍然有价值，应当保留。

### 5.1 `answer.py` —— 关注点确实混装，但**不是**你猜的那四样

**真正的混装在 `answer()` 函数体内**（L1205–1757，553 行）。按注释锚点，这一个函数里顺序执行了 **7 个互斥通路/判据**：

```

L1325  别名规范化答案通路（默认关）
L1363  标题型答案通路（默认开）
L1394  章节包答案通路（默认开）
L1463  收集候选 claim（每条都从断言的证据偏移来）
L1640  判据 5：冲突材料不无条件合并
L1648  multihop 多锚点合取装配（默认关）
```

**因此准确的说法是**：
- ❌ "检索策略 + 预算装配 + 引用校验 + 章节排序都在 `answer.py`" —— 检索策略和预算装配在 `retrieve.py` / `pipeline.py`，**不在** `answer.py`。

## 6. 【中等】B-2 引用校验三份实现，语义已分叉

**这是"Manifest 是唯一接口事实源"在代码里唯一没做到的地方。**

`src/` 里有三处各自实现"引用是否合格"：

| 位置 | 检查内容 | 遇 `start=None` 的行为 |
|---|---|---|
| `answer.verify_citations`（`answer.py:839`） | chunk 存在 / evidence 长度 / **偏移逐字比对** | **抛 `TypeError`** |
| `judge.citations_support`（`judge.py:206`） | 同上 + 章节覆盖 | 返回 `offsets_missing` |
| `gates.l5_evidence_gates`（`gates.py:1636`） | 断言（不是引用）的偏移逐字比对 | N/A |

**实测分歧**（同一输入 `{"chunk_id":"c1","evidence":"abcd","start":None,"end":5}`）：

```
answer.verify_citations   → RAISES: TypeError int() argument must be ... not 'NoneType'
judge.citations_support   → ok: [{'index':0,'chunk_id':'c1','reason':'offsets_missing'}]
```

原因：`answer.py` 用 `int(cite.get("start", -1))`——`get` 的默认值只在**键缺失**时生效，键存在且值为 `None` 时 `int(None)` 抛异常。而 `judge.py` 显式做了 `if start is None or end is None: reason = "offsets_missing"`。

**为什么这是真缺陷**：`answer.verify_citations` 是**服务端 `/query` 的必经之路**（`server.py:1285`）。一条来自 LLM 通路（`LLMAnswerer`）或未来新形态的引用，只要带 `"start": null`，就会让整个请求 500，而不是"剔除这条引用并降置信度"。

**修复的现状提示**：`judge_v2.normalize_citations`（`judge_v2.py:324`）的 docstring 已经写明纪律：
> "**不校验偏移**：偏移是否逐字对上……是 `judge.citations_support` 的职责（**单一事实源，不许在这里再写一份**）"

——即项目**已经意识到**这个问题并在 `judge_v2` 里守住了，但 `answer` 与 `judge` 之间的分叉没被处理。

**建议**：
1. 立即：`answer.verify_citations` 加 `if not isinstance(start, int)` 守卫（2 行），与 `judge` 对齐。
2. 中期：把"偏移逐字比对"提成模块级 `assert_span(text, start, end, evidence) -> reason`（纯函数，无 I/O），三处都调它。`answer` 保留"剔除 + 降置信度"的策略层，`judge` 保留"章节覆盖"的判定层——**策略可以有两份，判据只能有一份**。

## 11. 【不建议改】D 类 —— 防过度重构

### D-1 不拆 `gates.py`
**理由**：7 个 `lN_gates` 之间零共享状态，结构已是最扁平形态。拆成 `gates/l1.py … gates/l6.py` 只是把 1 个文件变 8 个，**没有降低任何复杂度**（每个函数还是那么长），反而破坏"所有门在一个文件里可通读"的审查便利。`l4_gates` 306 行可以抽 helper 降 20%，但**不值得**为一个 stage 单独重构。

### D-2 不换 FTS5 原生 `bm25()` 打分
`fts_backend.py` 的 docstring 已经做完了这项实验并给出结论：
> "已实现，但实测两头都不占：与 exact 模式同进程交替实测 P50 110–116 / P95 214–219，比 exact（P50 132–139 / P95 200–203）P50 略快、P95 更慢，且 **idf 公式与现有实现不同**……top-20 平均重合率仅 **0.5919**。结论：不作默认，也不作推荐。"

这是**对抗审查的正面案例**：测得"新功能不划算"就诚实记录并不采纳。**不要**因为"SQLite FTS5 是官方推荐"就去换——那会静默改变排序口径。

### D-3 不建统一配置层 / 不引入 pydantic-settings
当前 16 个可调检索参数 + 24 个环境变量，全部有实测出处注释，且**刻意不开放环境覆盖**（防止线上/评测分叉）。建一个配置层会：(a) 引入第三方依赖（违反"零第三方运行时依赖"一等约束）；(b) 把"这个数为什么是 4"的注释从常量旁搬走，反而丢失信息。**B-4 的修法应该是"让 3 处从 1 处派生"，不是"建配置系统"。**

### D-4 不降低注释密度
`answer.py` 注释 25%、`retrieve.py` 16%，含大量实测数据（如 `retrieve.py:71-91` 的 6000/12000/18000/24000 四档通过数与回滚指令）。这些注释是**决策依据的唯一载体**——`DEFAULT_BUDGET` 那 20 行注释解释了"为什么 12000 不是 24000"，删掉后没人能安全改这个数。**这 100 KB 里相当一部分是有价值的**，不是膨胀。

### D-5 不动 `tmp_*` 里被 docs 引用的 90 个（保持原位可直接跑）
