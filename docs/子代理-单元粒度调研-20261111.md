## 0. 结论先行：**前提有一半是错的**

任务书里那句「粒度减半 → 24000 能装 37.6 个 → 覆盖 rank≤37」在算术上对，**但它隐含了一个前提：gold 自身的 token 也会减半。这个前提不成立。**

| # | 结论 | 性质 |
|---|---|---|
| 1 | 单元 = **chunk**，定义是「同一场景文件内、按轮次贪心装箱到 900 **字符**」——是**设计值**，不是自然结果。参数确实存在：`ARKRAG_CHUNK_CHARS` | 读代码确认 |
| 2 | 切碎**不会**破坏「一句话同时含两个锚点」的判据——断言 99.99% 落在单个轮次内，而轮次是原子单位，永不切开 | **实测确认** |
| 3 | 但切碎**会**把 gold 的证据劈成两半：**83.7% 的 gold 块，两个半块里都有断言**。要让证据不丢，两个半块都得进上下文 → **单元数 ×2，token 一克没省** | **实测确认** |
| 4 | 与此同时候选池也跟着翻倍。**覆盖率（可装/候选）从 19.7/55.4=35.5% 变成 37.6/110≈34%——基本原地不动** | 算术，候选池倍数是估计 |
| 5 | 因此「粒度减半救预算」的净收益 ≈ **0 题**，而不是 +3.54 pt 的上界 | 我基于 3+4 的推断 |
| 6 | **有一个更便宜、等价、且不碰索引的替代**：证据窗口装配。**2.59–4.97 倍 token 压缩、断言零损失、不用重抽** | **实测** |
| 7 | 真正的成本不是「改一个数字」，而是 **13,798 块全部重抽**。而本机**没有 LLM 端点**（`answer.py:1086-1094` 直接抛 `RuntimeError`）⇒ 这条路过不去 | 读代码确认 |

**一句话**：粒度这个杠杆的算术没算错，但**它省的不是 gold 的 token，省的是「非 gold 的陪衬文本」的 token**。而「只给陪衬文本打折」这件事有更便宜的干法（证据窗口），不需要动粒度。

## Q1：单元是什么？粒度由什么决定？

### 1.1 一个「单元」= 一个 chunk = 一个场景文件内的一段连续轮次

**不是段落，不是句子，不是章节。** 链路是三层，逐层读代码确认：

| 层 | 定义 | 代码 |
|---|---|---|
| 文档 → 场景 | **一个剧情 JSON 文件 = 一个场景**（签字四）。场景是分块的**硬边界** | `model.py:36-47`（`Scene` docstring：`"一个剧情文件即一个场景（签字四）；场景是分块的硬边界。"`） |
| 场景 → 轮次 | `storyList` 每个节点按 `prop` 分类成四类之一：`dialogue`/`narration`/`quote`/`title_card` | `model.py:7`（`KINDS`）、`parse.py:128-185` |
| 轮次 → 块 | 场景内**按轮次贪心装箱**：累加到超 `TARGET` 就开新块，可带 1 轮重叠 | `chunk.py:137-167`（`split_scene`） |

**轮次是原子单位，永不切开。** 这不是偷懒，是刻意写死的：

> `chunk.py:158-159`：「单轮本身超上限：轮次是原子单位，不许切成半句（切了就定位不到证据），只能显式登记，让门去判它。」
> `chunk.py:254-255` 同义复述。

### 1.2 长度由什么决定：**字符数**，不是 token 数

```python
# config.py:120-126
# L2 参数（决策推荐区间：目标 800-1000 / 最小 100-150）
CHUNK_TARGET_CHARS = int(os.environ.get("ARKRAG_CHUNK_CHARS", "900"))
CHUNK_MIN_CHARS    = int(os.environ.get("ARKRAG_CHUNK_MIN_CHARS", "120"))
CHUNK_MAX_CHARS    = int(os.environ.get("ARKRAG_CHUNK_MAX_CHARS", str(2 * CHUNK_TARGET_CHARS)))
CHUNK_OVERLAP_TURNS = int(os.environ.get("ARKRAG_CHUNK_OVERLAP_TURNS", "1"))
```

**→ 现成的粒度参数是存在的**，而且是两个：`ARKRAG_CHUNK_CHARS`（目标）与 `ARKRAG_CHUNK_MAX_CHARS`（硬上限，默认 2× 目标）。注释里还写着「决策推荐区间：目标 800-1000」——**900 是一个被选定的设计值**。

装箱条件是**纯字符**（`chunk.py:146`：`if buf and size + len(line) + 1 > TARGET`），与 token 无关。

### 1.3 平均 1216 token 是怎么来的：设计值的直接后果

实测 `chunks.jsonl` 全量 13,798 块：

| 量 | 值 |
|---|---|
| chars mean / median | **826.8 / 883** |
| chars p10 / p25 / p75 / p90 / p99 | 630 / 866 / 892 / 897 / 924 |
| **750–900 字符区间占比** | **86.28%** |
| > 1200 字符 | **0 块** |

**86% 的块挤在 750–900 这一个区间**，因为贪心装箱总是把块填到「再放一轮就超 900」为止。不是语料自然长度，是装箱器的特征。

token 换算（用建库同一套 `t2` 分词器，抽 300 块精算，`index.py:263-307`）：

| 量 | 值 |
|---|---|
| tokens/chars | **1.405**（中文单字 + 双字，所以 >1） |
| `title+chapter+text` 的 token 中位 | **1228** |
| 全库总 token（title+chapter+text） | **16,135,149**，均值 **1169.4** |
| `diag_rank_24000.json` 实测 `ctx_tokens/n_units` | **1215.9**（均值 1215.9，中位 1233） |

两个数差 4%（1169 vs 1216），原因可解释：`build_context` 的 `cost_of()` 调用 `estimate_tokens(..., name_terms=self.index.name_terms)`（`retrieve.py:1011-1016`），**运行时注入了专名表**，会把专名整词额外计 token；我离线精算时没注入。**1216 是真的，而且有 4% 是专名表的开销。**

> **纯数学提分空间文档 §6.1 表里「1276（现状，gold 单元中位）」是 gold 专属的中位数**，全库均值是 1169–1216。两个数不冲突，只是分母不同。

**记录一个文档缺陷**：`docs/分析-纯数学提分空间-20261111.md` §6.2 的表格用 1276 当「现状粒度」，而 §6.1 用 1216 当「token/单元」。**同一个文档里两个数指同一个量**，读的人会以为矛盾。建议统一成「全库均值 1216 / gold 中位 1276」并写清分母。

## Q2：改粒度的代价

### 2.1 【关键风险，实测：**威胁不成立**】切碎会不会破坏「一句话同时含两个锚点」？

**不会。** 三层证据：

**(a) 断言证据 99.99% 落在单个轮次内。** 全量 62,924 条断言，按 `evidence_start/end` 对 `turn_spans` 做包含判定：

| 量 | 值 |
|---|---|
| 落在**单个轮次**内 | **62,842 / 62,924 = 99.870%** |
| 跨轮次 | **82**（0.130%） |
| 非法偏移 / 块缺失 | 0 / 0 |

跨轮那 82 条长这样（都是两行相邻台词被当成一条证据）：

```
'obt/main/level_main_14-02_beg#007'
  evidence = '这些年，阿米娅的变化很大。\nLogos：血魔仪式的核心发生了改变。'
```

**(b) 在轮次边界切，断言几乎零损失。** 模拟在中位轮次切（不是任意字符切，而是**轮次边界**切）：

| 切法 | 子块 chars 中位 | 断言落在单段内 | **跨切点的断言** | 0 断言子块 |
|---|---|---|---|---|
| 2 段 | 432 | 99.995% | **3 / 62,924** | 15.34% |
| 3 段 | 286 | 99.987% | 8 / 62,921 | 27.10% |
| 4 段 | 212 | 99.992% | 5 / 62,913 | 36.67% |

**跨切点从 82 条降到 3 条**——因为切点被吸到轮次边界上，而跨轮证据原本就是 82 条噪声。

**(c) 判据的「句子」是合成出来的，不读原文.** `judge.py:117-118` 的 `_sentences()` 只是 `text.split("。")`，而 `answer_text` 是 `claim` 列表 `f"{subject}{predicate}{object}。"` 拼起来的（`answer.py:963`）。**「一句话同时含 gold + 全部锚点」这句话，是 claim 拼出来的，不是从块正文里切出来的。** 所以块怎么切，都影响不到判据的句子边界。

> **结论：任务书担心的「切碎破坏断言句完整性」这个风险，在「按轮次边界切」的实现下不存在。** 但注意——**这只在按轮次切时成立**。如果有人按字符数硬切（`text[:450]`），就会切开轮次，`_line_bounds` 会断行，`verify_citations` 的 `text[start:end] == evidence` 会整批失败。**这个区分必须写进任何实施方案里。**

### 2.2 【真正的风险，实测：**威胁成立且致命**】gold 的证据会被劈成两半

这是粒度方案真正的成本，也是前提算错的地方。

**实测：gold 块分半后，两半里都有断言的比例是 83.7%。**

| gold 块（823 个唯一） | 数量 | 占比 |
|---|---|---|
| 分半后**两半都有断言** | **689** | **83.7%** |
| 只有一半有断言 | 129 | 15.7% |
| 无断言 | 5 | 0.6% |

**后果**：`build_context` 的单元是 chunk 粒度的，一个单元带的是 `assertions_by_chunk[chunk_id]`（`retrieve.py:946`）。如果 gold 被切成两半，而只有一半进了上下文，**另一半的断言在回答层根本不存在**——`ExtractiveAnswerer` 只能从 `unit["assertions"]` 里取候选（`answer.py:811-813`）。

multihop 判据要求「gold 与**每个** anchor 各有一条共现断言」。实测 C 桶 24 道 multihop 题：

| 两条 anchor 的 gold↔anchor 断言住在哪 | 题数 |
|---|---|
| **两条都在 gold 块内** | **24 / 24** |
| 分散在别的块 | 0 |
| 有 anchor 无边 | 0 |

**所以 multihop 完全依赖「gold 块整块进上下文」**。分半之后，这 24 题里约 83.7%（≈20 题）需要**两个半块都进上下文**才能保住两条断言。

**⇒ 单元数 ×2，token 不变。** 这就是前提算错的地方：粒度减半并没有让 gold 变小，只是把 gold 从一个「1276 token 的单元」变成两个「638 token 的单元」。**要装下的 gold token 总量是守恒的。**

实测验证：

| 粒度 | gold 单元数 mean | **gold token mean / median** | token 能装下的题 |
|---|---|---|---|
| 1×（现状） | 1.45 | **1734 / 1257** | 588/588 |
| 1/2 | 2.89 | **1734 / 1257** | 588/588 |

**gold 的 token 一克没变。** 全部 gold 块字符合计 725,690（≈1,019,594 token），这个数**与粒度无关**。

### 2.3 【算术，候选池倍数是估计】覆盖率基本原地不动

粒度减半之后，同样的信息量摊到 2 倍数量的块上：

| 量 | 现状 | 减半后 | 说明 |
|---|---|---|---|
| 单元 token | 1216 | ≈638 | 前提给的数 |
| 24000 可装单元 | 19.7 | 37.6 | **前提给的数，对** |
| 候选池 `n_candidates` | **55.4** | **≈110**（估计） | 信息量不变，块数翻倍 |
| **覆盖率 = 可装/候选** | **19.7/55.4 = 35.6%** | **37.6/110 = 34.2%** | **基本不变，甚至略降** |
| 装下全部候选需 | 67,356 token | **≈70,000 token** | 前提给的「×2.8」，减半后仍是 ×2.9 |

**这是整个调研最重要的一张表。** 「装下 37.6 个单元」听着是 2 倍容量，但**候选池也变成了 2 倍**。「能装的比例」没变。

而 gold 的**名次**会变差：现在 gold 在 55 个候选里排 14，减半后在 110 个候选里大约排 28。**覆盖 rank≤37 只覆盖到 34% 的候选，与现在 rank≤19.7 覆盖 36% 是同一件事。**

> **诚实边界**：候选池「≈110」是**我的估计，未实测**。真实值取决于 `top_k`（命中条数被 `top_k=20/40` 卡死，不随粒度变）与 `expand` 的图扩展规模（会随证据块变化）。但即使候选池只涨到 80，覆盖率也只有 47%，且 gold 名次仍会退。**方向不依赖这个估计的精度。**

### 2.4 断言与 chunk 的绑定关系：**会全部断掉，需要重抽**

不是「可能断」，是**必然全断**。三条键都在 `chunk_id` 上：

| 绑定 | 位置 | 断了会怎样 |
|---|---|---|
| `chunk_id` 本身 | `chunk.py:232`：`f"{scene['doc_id']}#{index:03d}"` | 切碎后 `index` 重排，**每个场景第一个块之后的所有 `chunk_id` 全变** |
| `content_key` | `chunk.py:251`：`sha256(text)[:24]` | 正文变了 → key 变 → **缓存全部 miss** |
| 缓存键 | `cache.py:88-98`：`key_for(content_key, chunk_id, scene_id, ...)` | 双份变化 → **13,798 条 raw 抽取结果全部作废** |

历史已经演过一遍：D 阶段 13,781 → 13,798（**只多 17 块**），就有 34 块缓存 miss，而台账写明「**0 块可证明复用**」：

> `docs/升级台账.md:226`：「**34 块全部是 `changed_content`，`identical_content = 0`。** 原因是它们正是那 17 个尾块被切开后的「新两块」：旧记录抽的是 992 字整块，切开后每一半正文都不等于它。」
> 同文件 `:228`：「34 块完整清单（17 doc × 2 块…），**必须等重抽**」

**⇒ 粒度减半 = 13,798 块全部变成「changed_content」= 全部重抽。** 增量 34 块的教训直接乘以 400 倍。

### 2.5 引用（citation）定位精度：**变好，但 goldset 要重建**

分两面看：

**(a) 运行时精度会变好。** 引用是 `text[start:end]`，`verify_citations` 要求逐字相等（`answer.py:551`）。块越小，同一句台词在块内重复的概率越低，`find_all_occurrences` 取 `occurrences[0]` 的歧义就越小（`assertion.py:266-274`）。实测：断言证据区间长度 **中位 14 字符、p99 32 字符**，而所在整行中位 25 字符——**证据本身就是整行的子串，块变小不影响这一点**。

**(b) 但 goldset 的 `required_citations.chunk_id` 会全部失效。** gold-v2 有 588 题带 `required_citations`，共 850 条，每条都是 `{chunk_id, evidence}`：

| 分半后 `required_citations.evidence` 落在哪 | 条数 | 占比 |
|---|---|---|
| **唯一落入一个子块** | **847** | **99.65%** |
| 落入多个子块（歧义） | 3 | 0.35% |
| 找不到 | 0 | 0% |

**好消息**：证据串本身 99.65% 能机械重映射到唯一子块，`required_citations` 可以程序化重建。
**坏消息**：`gold_chunk_ids` 与 `gold_assertion_ids` 必须跟着重算，而 `multihop` 的 24 题全部需要「两个子块都在 hits」这一新条件——**goldset 的语义会变，不是一次字符串替换**。823 个 gold 块 × 平均 2 个子块 = 约 1,646 个新 gold id，每题从「1–2 个 gold」变成「2–4 个 gold」。**判据本身要跟着改。**

> 这一条是**我的判断，未实测**：我没有重建 goldset，也没有验证「gold 变成 2 个子块」之后 `judge.py` 的 `gold = golds[0]`（`judge.py:183`）会取哪一个。**这是个真问题**——`judge_answer` 只取第一个 gold 字符串，gold 变多值后判据语义未定义。

## Q3：不改粒度，有没有等价但更便宜的替代？

### 3.1 排序（按 预期收益/成本）

| # | 方案 | 预期收益 | 成本 | 判据 | 依据 |
|---|---|---|---|---|---|

### 3.2 【推荐】证据窗口装配：把「陪衬文本」从预算里去掉，而不是把「块」切小

**机制**：`build_context` 现在已经算出每个单元要装什么了——`unit["evidence_spans"]` 记录的就是「这块里哪些断言和问句相关」（`retrieve.py:946-949`）。但是装填时，`cost_of()` 计的是**整块正文**（`retrieve.py:1011-1016`）。

**所以 5/6 的 token 花在了和问句无关的文本上。** 实测：

| 装填口径 | token 均值 | 总 token | 24000 可装 | 覆盖 rank |
|---|---|---|---|---|
| **整块（现状）** | **1169.4** | 16,135,149 | **20.5 个** | ≤21 |
| 证据所在轮（±0 轮） | **235.4** | 3,248,172 | **102.0 个** | ≤102 |
| 证据所在轮 ±1 轮 | **450.9** | 6,221,527 | **53.2 个** | ≤53 |

**压缩 2.59–4.97 倍**，而这是**同一批块、同一份索引、同一份断言**——**零重抽**。

**断言零损失**（这一点是关键，与粒度方案相反）：

| 量 | 现状 | 证据窗口 |
|---|---|---|
| 每单元保留的轮次 | **31.5 轮** | **5.1 轮**（丢 83.7%） |
| 每单元保留的字符 | 827 | **155**（5.33×） |
| **块内断言损失** | — | **0**（窗口按「含证据的轮」取，块内**全部**断言仍在） |

**为什么粒度方案做不到这一点**：粒度方案把断言**分到不同的块里**，装不下的那一块连带断言一起消失。证据窗口方案把断言**全留在同一个单元里**，只裁掉没有断言的文本。**后者不损失任何证据，前者损失一半。**

**代价（我实测的，不是猜的）**：

| 通路 | 依赖 | 影响 |
|---|---|---|
| `title` 通路（引文定位） | `unit["text"].splitlines()`（`answer.py:415`） | 题干「」引文在窗口内命中 **942 次**，只在被丢弃的轮里 **159 次** ⇒ **约 14.4% 的引文定位会失败** |
| `chapter` 通路（跨块章节） | `unit["text"]` 里找焦点实体（`answer.py:302`） | 同理会漏，未单独量化 |
| `claim` 通路（主通路） | `unit["assertions"]` + `evidence_spans` | **零影响**（断言和偏移都在） |

**⇒ 正确的落法不是「全裁」，是分层**：
- 前 N 个直接单元（比如 N≈10，覆盖现在 19.7 个格子里最有用的那半）：**装整块**，保住 title/chapter 通路；
- 其余长尾单元：**只装证据窗口**，用 235 token 而不是 1169 token 换一个候选位。

这样把「19.7 个整块」变成「10 个整块 + ~60 个证据窗口」，**长尾覆盖率提升 3 倍，而主要通路一字未改**。

> **诚实边界**：收益是**结构量（token 容量）实测**的，**端到端分数我没跑**（任务书禁止跑端到端）。结构量 → 分数的转化率可以参照 `lead_预算三档真跑实测.md` 的实测漏斗：**9 题进上下文 → 4 题发对引用 → 2 题答案也对**。按这个转化率，容量翻 3 倍不等于分数翻 3 倍。

### 3.3 【否证】「只对截断题动态放大预算」——**这是最诱人但最贵的一条**

任务书猜的这条，数学文档 §8 已经否了，我这里给出更硬的证据。

先把 C 桶（gold 在 hits 但不在上下文）的题**逐题对上评测判决**（`data/w3_evidence/cap4_{dev,holdout,clean}.json`）：

| 机检 C 桶 | 27 题 |
|---|---|
| 其中 **cap4 实测已通过** | **9 题** |
| 其中 **cap4 实测失败** | **17 题** |
| 无判决（`time_conflict` 结构类） | 1 题 |

**「27 减 9 等于 17」正好对上分析文档的 17 题。** 这是个干净的交叉验证。

**但这条路的成本被低估了**：

1. **上界只有 +3.54 pt**，而 17 题 × multihop 的 ctx 转化率 0.569 ≈ **9.7 题 ≈ +2.0 pt**。
2. **已被真跑否证两次**：
   - 预算 6000→8000（+33%），`any_gold` 净 +20 题，但 **`correct_coverage` 只 +4 题**，主判据 K1（门槛 ≥10）**FAIL**。
   - 且实测**两道题在高预算下 gold 反而被挤出去**（`q-mh-000042`、`q-tc-900022`）——贪心首适配在预算边界上「多装一个更大的块，把原有的小块顶掉」。**加预算会让 `any_gold` 一救一丢。**
3. **7 道题已经证明「进上下文 ≠ 答对」**：同级实测 9 题进上下文，只有 4 题发对引用，只有 2 题答案正确（`lead_预算三档真跑实测.md` §3）。

**⇒ 动态放大预算买的是最贵的那 2 分。** 而且 24000 token 的成本是实打实的（分析文档 §8：「加预算必须配粒度，否则是买最贵的那 3.5 分」）。

---

### 3.4 【否证】「提高 search top_k 让更多候选进 hits」

**已实测为负，不必再试**：

> `pipeline.py:216-217`：「`bridge_search_top_k=40` —— 只对桥接题抬候选数。**全局抬到 40 会让 single_chunk 掉 1 题**（逐字定位命中的块被挤到后面），只对桥接题抬则三份都涨。」

机制：`n_hits` 均值 23.3 < `n_candidates` 55.4，**而且 `n_truncated` 均值 35.9 已经证明「hits 里也装不下」**。抬 top_k 只是把更多块塞进 hits，而 hits 里已经在丢东西了。**在漏水的桶里多加水。**

---

### 3.5 「混合粒度」（multihop 单独小单元）为什么也不划算

理论上对：multihop 是唯一整类被预算打击的（C 桶 24/27 是 multihop）。但：

1. **它不解决 §2.2 的劈半问题**——gold 块劈成两半后，83.7% 需要两半都在上下文，单元数 ×2、token 不变。
2. **它要付出 §2.6 的全部重建成本**（因为 `chunk_id` 是全局连续的 `{doc_id}#{index:03d}`，你不能只对 multihop 相关的块改编号——那会让同一场景内编号不连续，`fingerprint.py:83` 的 `chunk_id/content_key` 指纹和 `release.py:146` 的清单摘要全部对不上）。
3. **收益与 #1 重叠**：multihop 真正需要的不是「更小的块」，是「gold 的两条断言都在上下文里」。证据窗口方案能做到这一点且不丢断言。

---

### 3.6 我想到但没测的：把 gold 的「断言」直接当上下文单元（极激进）

既然回答器是抽取式的、只吃 `unit["assertions"]` 和 `evidence_spans`，理论上上下文可以只发「断言三元组 + 证据行」，完全不带块正文。token 会降到 ~30 token/断言，24000 能装 800 条。

**但我不推荐，而且不建议把它当备选**：
- `title` 通路和 `chapter` 通路会**整个失效**（两者都 `splitlines()` 读正文）；
- `verify_citations` 的 `text[start:end] == evidence` 会失去「块正文」这个校验基准；
- 这与证据窗口方案的差别只在于「窗口取多大」，而证据窗口已经把 ±0 轮压到 235 token 了，**极端化收益递减而风险陡增**。

## 4. 明确的推荐：**如果只能做一个，做证据窗口装配（分层版），不做粒度**

### 为什么

| 判据 | 粒度减半 | **证据窗口装配** |
|---|---|---|
| token 压缩 | 2×（名义） | **2.59–5.0×（实测）** |
| **gold 的 token 缩减** | **0（§2.2 实测：1734→1734）** | **不适用（gold 本来就是重点，整块进）** |
| 断言损失 | **可能丢一半（83.7% 需两半都在）** | **0（实测）** |
| 候选池 | ≈×2（估计） | **不变** |
| **覆盖率** | **35.6% → 34.2%（§2.3）** | **35.6% → 约 3 倍长尾** |
| 要重抽 13,798 块吗 | **是**（阻塞：本机无 LLM 端点） | **否** |
| 要重建 goldset 吗 | **是**（823 个 chunk_id 全失效） | **否** |
| 要改判据吗 | **是**（gold 变多值，`judge.py:183` 取 `golds[0]` 语义未定义） | **否** |
| 要跑多久 | 约 1,104 次子代理运行（**做不到**） | 改 `retrieve.py::build_context` 装填段，分钟级 |
| 可回滚 | 几乎不可能（产物换代） | 一个开关（照 `max_direct_units` 的既有范式） |

**核心逻辑**：粒度这个杠杆想解决的问题是「格子里装不下」。但它**没有增加格子，只是把格子改小了——而每个格子里该装的东西也一起改小了**。真正的浪费不是「块太大」，是「块里 83.7% 的文本与问句无关，却按整块计价」。**直接修这个浪费，不需要动粒度。**

### 具体落地（只是方案，不是代码）

1. 在 `build_context` 的 `cost_of()` 旁边加一个「窗口成本」路径，装填时按 `evidence_spans` 折叠成证据轮；
2. 对前 N 个直接单元（N 建议 8–12，覆盖现状 19.7 个格子里最有用的那半）走**整块**，保住 `title` / `chapter` 通路；
3. 对其余长尾单元走**证据窗口 ±0 轮**（235 token），把 24000 从「19.7 个」扩到「10 个整块 + ≈60 个窗口」；
4. **必须同时保留**：`unit["text"]` 的**原始完整正文**供 `verify_citations` 校验（偏移不变），只在**预算计价**和**发给回答器的文本**上用窗口。这两件事要分开——`retrieve.py:1119` 的 `stats.tokens_used` 有测试钉着（`tests/test_context_budget.py`）。
5. **预登记判据**：照 `lead_预算三档真跑实测.md` 的范式，主判据必须是 `correct_coverage` 净增 ≥10 题，不是 `any_gold`。**`any_gold` 涨 20 而 `correct` 涨 4 的教训已经付过学费了。**
