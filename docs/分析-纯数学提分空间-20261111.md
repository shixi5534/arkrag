## 0. 结论先行

**有空间，但不在 W1–W4 那条路上。** 三个层面要分开，混在一起谈就会得出错误结论：

| 层面 | 空间 | 性质 |
|---|---|---|
| **A. 报告口径内的真实空间** | 上界 **+19.79 pt**；现实可达 **+5～+10 pt** | 工程问题，机制清楚，但被**测量分辨率**卡住 |
| **B. 口径本身的自由度** | **+9.47 pt（判据）** ／ **+14.7 pt（分母）** | 会计问题，比任何工程改动都大，**不是能力** |
| **C. 口径之外的空间** | **108 题 = 18.4%** 整类 0 分 | 判据未实现，当前完全不计 |

三条硬结论：

1. **W1–W4 已把「参数旋钮」这条路测完了。** cap 3–6、direct cap 14/16、bridge margin、章节截断，全部净效应 ≤6 题、配对检验 p ≥ 0.25（判据 v2 除外）。继续在同一族里调，期望收益 ≈ 0。
2. **在 judge v1 下，「减少内容」的改动方向在结构上就不可能为正。** v1 只问「答案里有没有 gold」，实测 claims 5→12 得 **+15 题 / 0 题损失**（`data/diag_max_claims.json`）——即 v1 对"多写"零惩罚。所以 W1 的 −2 不是偶然，是**方向的必然**；W2/W3 只能拿到 ±1～6 题的残差。
3. **真正的物理约束是「单元粒度 × 预算」，不是排序。** 24000 token ÷ 1216 token/单元 = **19.7 个单元**，而候选池均值 **55.4 个**，**64.8% 的候选单元被预算丢掉**，**95.6% 的题有截断**。任何 cap / margin / chapter_cap 都只在这 19.7 个格子里挪动，不改变格子数。

## 1. 先把分母钉死（后面每个 pt 都在这个分母上算）

### 1.1 三份 split 不是三份独立样本

| split | 题数 | 可判 | 通过 | 率 |

- 本文一律用 **N = 480** 报 pt；凡引用文档的"三份合计"数字，都要先除以约 1.25 才是真实效应。

**直接后果**：`W2` 的 +1(holdout)/+2(clean) 是同一批题。把 holdout 拆成 clean 子集(120) + 真新题(75)：

| 臂 | clean 子集 Δ | rest(75 新题) Δ | holdout 总 Δ |
|---|---|---|---|
| cap3 | −3 | 0 | −3 |
| cap5 | −1 | 0 | −1 |

| w1cap14 | 0 | +2 | +2 |

W2 在 clean 上 +2、在同为 holdout 的另外 75 题上 **−1**，符号相反。所谓"clean 独立确认了 holdout"**不成立**——它是同一批题被计了两次。

### 1.2 108 题（18.4%）整类不计分，且 100% 失败

`time_conflict` / `negative_abstain` / `adversarial` 三类共 dev 65 + holdout 43 = **108 题**，占 588 的 **18.37%**。逐题 `judge.reason = "structural:not_supported"`，`pass = null`——**判据根本没实现这三类，直接排除出分母**。

- 报告口径：385 / **480** = **80.21%**

**差 14.7 pt，全部躺在"被判据拒绝计分"的那 18.4% 里。**

## 4. ★ 判据的自由度比所有工程效应加起来还大（本文最重要的数学事实）

### 4.1 v2 是 v1 的严格子集，差额 9.47 pt，且全部单向

dev 285 题逐题比对（`data/w4_evidence/judge_both_dev.json`）：

| | v2 pass | v2 fail |
|---|---|---|
| **v1 pass** | 204 | **27** |
| **v1 fail** | **0** | 54 |

- 不一致 **27/285 = 9.47%**，且 `v1=0,v2=1` 的次数为 **0** ⇒ 两套判据是**嵌套关系**，不是两种独立口径。
- κ = 0.741（po=0.905，pe=0.634）。

**含义**：把判据从 v1 换成 v2，分数从 81.05% 掉到 71.58%，**掉了 9.47 pt = 27 题**。这个数字比 W1+W2+W3+W4 所有工程改动之和（净 6 题 = 1.25 pt）**大 7.5 倍**。

### 4.2 v2 把 multihop 整体归零

dev 逐类（`judge_both_dev.json`）：

| 类别 | n | v1 通过 | v2 通过 | cardinality 轴失败 | 其中"只"被基数轴否掉 |
|---|---|---|---|---|---|
| single_chunk | 76 | 76 | 76 | 0 | 0 |
| alias | 57 | 52 | 52 | 3 | 0 |
| direct_relation | 57 | 50 | 50 | 0 | 0 |
| **multihop** | 57 | 27 | **0** | **57** | **26** |
| cross_chunk | 38 | 26 | 26 | 3 | 0 |

multihop 57 题里 **57/57 的 `cardinality_ok = False`**：v2 要求"答案里不同值的个数不超过 gold 个数"，而现行答案是 claim 列表，必然多值。**26 道题是"只被基数轴否掉"**（value 与 support 都过）。

⇒ **在 v2 口径下，multihop 的全部 57 题都是 0 分**，一切 multihop 讨论（W2、no_common_neighbor）在 v2 下都无意义。

### 4.3 v1 对"多写"零惩罚 ⇒ 结构性地奖励散弹枪

`data/diag_max_claims.json`（350 题）：claims 5 → 12，正确 **196 → 211**，**loss 列表为空**，且 `gain_gold_not_first = 0`。

**v1 是一个"gold 是否出现"的检出器，不是质量判据**。于是：

$$\frac{\partial\, \text{score}_{v1}}{\partial\, (\text{含 gold 的文本量})} \;\ge\; 0$$

由此可以**先验推出**四项实测结果的方向，不需要跑：

| 改动 | 方向预测 | 实测 | 一致 |
|---|---|---|---|
| W1 砍直接单元（cap 14/16） | **必然 ≤ 0** | dev −2 | ✅ |
| W2 重排桥接候选（不加内容） | ≈ 0 | 0 / +1 / +2 | ✅ |
| W3 砍章节（只砍 cross_chunk） | 只能靠"消除 \|O\|>\|W\| 这一类失败"为正 | +3/+2/+1 | ✅ |
| 任何"加更多候选" | 弱正 | 未测 | — |

W3 的机制我核对过，**双向都成立，不是纯噪声**：

| cap 档 | `chapter_set_missing`(fail) | `extra_chapters_outnumber_gold`(fail) | 通过 |
|---|---|---|---|
| 3 | 11 | 0 | 15 |
| **4** | **8** | **0** | **18** |
| 5 | 8 | **1** | 17 |
| 6 | 7 | **1** | 18 |

（holdout，26 题 cross_chunk）cap=3 太低 ⇒ 缺章节 +3 失败；cap=5/6 太高 ⇒ 多余章节压过 gold +1 失败。**cap=4 是内生最优，机制成立。**

但幅度必须说清：**cap=4 相对 cap=3 只多 3 题，相对 cap=5 只多 1 题**。见 §5。

## 6. 物理约束：容量算术

### 6.1 预算与粒度

| 量 | 值 |
|---|---|
| token / 单元 | 1216（dev 1216 / holdout 1205 / clean 1211） |
| 预算 24000 可装单元 | **19.7 个** |
| 候选池均值 `n_candidates` | **55.4 个** |
| 实际进 hits 均值 `n_hits` | 23.3 个 |
| 被预算丢掉的单元均值 `n_truncated` | **35.9 个 = 候选的 64.8%** |
| 有截断的题 | **562/588 = 95.6%** |
| 装下全部候选需 | **67 356 token（×2.8）** |
| 装下 rank ≤ 40 的 gold 需 | **48 640 token（×2.03）** |

**关键**：`hit_rank > 20` 的题只有 **13 道**。也就是说——**排序没那么糟，是格子太少。**

### 6.2 粒度：**已被实测否决**（原判断作废，见 §7.3）

原判断："粒度是唯一不改 token 成本就能多装"的杠杆。**这个判断是错的**——粒度减半不增加格子，只是把格子改小，里面该装的东西也一起变小了。84.0% 的 gold 块两半都有断言 ⇒ token 不省。**详见 §7.3。**

真正成立的那条杠杆是**证据窗口**：不改块、不重抽，只把没有断言的文本从预算计价里去掉，实测压缩 **5.72×**、24000 可装单元从 **19.7 → 115 个**、断言零丢失。

$$\text{可装单元数} = \frac{\text{预算}}{\text{单元计价 token}},\quad \text{而单元计价 token 可以由 } 1243 \text{ 降到 } 208$$

### 7.1 为什么 #3（多锚点合取）仍是最先该做的

- **#3 多锚点合取**：23 道题 gold 已在上下文，只差"一句话同时含 gold 和全部锚点"。这是**纯实现问题，不需要任何新的检索/排序/预算**。上界 +4.79 pt，已过 MDE。

原 #1（粒度）已作废，替换为**证据窗口**（§7.3）。证据窗口不救特定题，它把容量从 19.7 提到 115 个格子，同时改善 A 桶与 C 桶——但它**必须走端到端实测**才能知道转化率（§7.4）。

### 7.3 ★ 修正：粒度减半被实测否决，「证据窗口」才是那个杠杆（2026-11-11 复核）

**§6.2 和 §7 表原先的"粒度减半 → 装 37.6 个 → +3.54 pt"是错的。** 错在一个隐含前提：**假定 gold 自身的 token 也跟着减半**。实测不成立。

#### 否决证据（Lead 独立复核，非子代理单方结论）

读 `data/arkrag/generations/g-20261103T132152Z-06a741/` 的 13,798 块 + 62,924 条断言：

| 量 | 实测 |
|---|---|
| gold 块（有断言的 818 个）中，**两半都有断言** | **687 = 84.0%** |
| 只有一半有断言 | 131 = 16.0% |
| gold 块字符合计（分半前 / 分半后需保留） | 702,064 / 697,911 |

断言按 `assertions_by_chunk[chunk_id]` 绑定（`retrieve.py:946`）。**84% 的 gold 块分半后，两半都必须进上下文**，否则丢一半断言 ⇒ **单元数 ×2、token 一克不省**。而候选池也会 ×2（55.4→~110）⇒ **覆盖率原地不动**。

⇒ **粒度减半净收益 ≈ 0 题。** 且代价是 13,798 块全部重抽 + 823 个 `gold_chunk_id` 失效 + 判据语义未定义。

#### 替代方案：证据窗口装配（实测压缩 5.72×，断言零损失）

同一批块、同一份索引、零重抽。只裁掉**没有断言的文本**，断言全留在同一个单元里：

| 装填口径 | 保留字符 | 压缩比 median | 24000 可装单元 |
|---|---|---|---|
| 整块（现状） | 100% | 1.0× | **19.7 个** |
| **证据所在轮（±0）** | **17.5%** | **5.72×** | **115 个** |

压缩比分布：p10=3.09× / p25=4.23× / p50=5.72× / p75=8.12× / p90=11.83×。**断言零丢失**（0/818 块出现断言无处安放）。

块结构事实：13,798 块，字符 median 883（上限 900，`config.py:120-126`），**每块 median 32 轮而相关证据通常只在 5 轮**。`turn_spans` 提供逐轮字符偏移，`evidence_start/end` 提供断言偏移——两个都在现成数据里。

#### 必须分层的理由

`title` 通路用 `unit["text"].splitlines()`（`answer.py:415`），窗口会漏：**942 次引文命中里有 159 次落在被丢弃的轮里（14.4%）**。所以正确落法是：

- 前 10~12 个直接单元：**装整块**，保住 title/chapter 通路；
- 其余长尾单元：只按窗口计价，用 ~208 token 换一个候选位。

#### 与 §7 表的关系

原表第 1 项（粒度减半）**作废**，其 +3.54 pt 上界**给错了对象**——那是"C 桶 17 题全救"的上界，而粒度减半救不了那 17 题。新的第 1 项应为「证据窗口装配」，收益性质不同：**它不是直接救某 17 题，而是把 19.7 个格子的容量提到 ~115 个**，从而同时改善 A 桶（召回后的装填）与 C 桶（预算挤出）。

诚实边界：**压缩比与断言归属是实测**；"容量 ×5.7 → 分数提升多少"**是推断**，需端到端实测（见 §7.4）。

### 7.4 端到端转化率不可直接外推（已知漏斗）

历史上同级别实测（`docs/lead_预算三档真跑实测.md` §3）：**9 题进上下文 → 4 题发对引用 → 2 题答案正确**。所以容量提升 5.7× **不等于**分数提升 5.7×。任何基于容量的收益预测都必须打折。预登记判据应当用 `correct_coverage` 而不是 `any_gold`。

在 v2 口径下 multihop 是 **0/57**。若答案形态从"claim 列表"改成"单值抽取"，v2 的 dev 上限是 204 + 57 = **261/285 = 91.58%**：

- 相对 **v2 现状 71.58%** ⇒ **+20.0 pt**
- 相对 **v1 现状 81.05%** ⇒ **+10.5 pt**

这是本文算出来的最大单项空间，**但它同时在两个口径下都是正的**——这一点和前四项不同。

但它要求**换一种答题哲学**：v1 奖励多写（5→12 得 +15/0），v2 惩罚多写（57/57 挂基数轴）。**两个指标的梯度方向相反。**

$$\text{v1: } \text{score} \uparrow \text{ as } |\text{claims}| \uparrow \qquad \text{v2: } \text{score} \downarrow \text{ as } |\text{claims}| \uparrow$$

这是**必须先做的决定**，不是工程任务：**你要优化哪个指标？** 在没决定之前，任何改动都是在两个相反梯度之间随机游走——这也解释了为什么 W1–W4 的读数全是 ±1～6 题的乱跳。
