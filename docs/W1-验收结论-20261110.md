# W1 验收结论：直接单元 cap —— **不采纳**

- 日期：2026-11-10
- 环境：conda `arkrag` / Python 3.13.18（`docs/基线-环境标准化与测试基线-20261110.md`）
- 世代：`g-20261103T132152Z-06a741`
- 生产档：`max_context_tokens=24000`，`quote_locate+bridge+bridge_search_top_k=40+graph_reserve_tokens=12000`
- 依据：W0 实测（`docs/W0-实测结论-20261110.md`）否决了 cap=10，cap 候选收敛为 12/14/16
- **结论标签：不采纳（反证条件 1 触发）**

---

## 1. 一句话结论

**三个候选 cap 全部触发反证条件 1（`Δ < 0`），W1 按预登记规则回滚。**

dev 上 cap=14 与 cap=16 都是 **226/285 = 79.30%**，比基线 **228/285 = 80.00%**
低 **2 题**。且失败集中在 `direct_relation`，机制清楚：cap 砍掉的那个直接单元里
**正好带着 gold 的关系断言句**，答案因此凑不出"一句同时含两个锚点 + gold"。

这不是实现 bug（cap 确实生效了：答案有 128–136 题变化），
**是 cap 这个方向本身在这个语料上不划算**。

## 2A. 三份 split 完整读数（口径已对齐）

**重要：** 本节的基线是**含 `chapter_cap=4` 的当前生产档**（231/154/98），
不是 W1 首轮那时的 228/152/97。两者不可混比——首轮测 W1 时 W3 还没上线。

| split | 当前基线 | cap=14 | Δ |
|---|---|---|---|
| dev | 231/285 = 81.05% | 229/285 = 80.35% | **−2** |
| holdout | 154/195 = 78.97% | 156/195 = 80.00% | **+2** |
| clean | 98/120 = 81.67% | 98/120 = 81.67% | **0** |
| **合计** | — | — | **0** |

### 2A.1 这个结果改变了什么、没改变什么

**没改变结论**：仍是不采纳。理由见下。

**改变了论据的完整性**：W1 首轮只有 dev 一个负读数（−2），当时是按
「任一 split Δ<0 即回滚」的规则停下的，因此**无法排除「dev 的 −2 是偶然」**。
现在三份都有数了：

- dev −2、holdout +2、clean 0，**三份合计恰好 0**；
- 这是一个**零和的振荡**，不是稳定的收益，也不是稳定的损失。

### 2A.2 为什么不采纳（三条独立理由）

1. **反证条件 1 已触发且未撤销。** 计划书原文：「任一份 split 出现 `Δ < 0`
   （哪怕 −1）→ 立即回滚」。dev 是 −2，规则要求回滚，**不因 holdout 涨了 2 而改判**。
   改判就等于把预登记判据变成「三份合计 ≥ 0 即可」，那是**事后移动门槛**。
2. **合计 0 的收益不构成采纳理由。** 一个三份合计恰好零和的开关，
   换来的是「上下文从 23643 token 降到约 14×1276 ≈ 17.9k」的成本下降。
   但 K3 要求的 `≤15000` **仍未达标**（17.9k > 15k），所以连成本目标也没完全兑现。
3. **holdout 的 +2 与 dev 的 −2 机制相同**：都是「gold 断言所在单元是否落在前 14 名」。
   同一机制在不同 split 上一个赚一个亏，说明它是**噪声**，不是可泛化的改进。

### 2A.3 诚实边界

若将来有人主张「按三份合计看，W1 至少不亏」，本文件不反对这个读法——
但必须同时说明：**预登记的判据是「每份 Δ≥0」（K1），不是「三份合计≥0」**。
按 K1 判定，W1 是 FAIL。改判据需要重新预登记并在未见的 split 上验证，
不能拿已经看过的三份读数回头改门槛。

## 4. 失败机制（这是本次真正的收获）

掉分的两题：

| question_id | 类别 | base 判据理由 | cap 后判据理由 |
|---|---|---|---|
| `q-dr-000006` | direct_relation | `one_claim_all_anchors_and_gold` | `no_single_claim_with_all_anchors` |
| `q-dr-000022` | direct_relation | `one_claim_all_anchors_and_gold` | `no_single_claim_with_all_anchors` |

题目是「『乌尔比安』与『海嗣』之间的关系是什么？请用词表里的一个关系词回答」。

基线答案里有 8 句，**第一句就是 `乌尔比安交谈海嗣。`**——这句同时含两个锚点。
cap=14 之后，答案里**这句没了**，只剩 `乌尔比安交谈乔迪`、`乌尔比安交谈阿玛雅`
这类不相关句。判据要求"存在一条 claim 同时含两个锚点"，于是落空。

**根因**：cap 按 `(-score, chunk_id)` 取有序前缀。分数最高的 14 个直接单元里，
`乌尔比安—海嗣` 那条断言所在单元**排在第 15 名之后**。它的分数不高，但它
恰好是唯一能回答这道题的证据。

这正是 W0 §7 那张代价表的现实版：W0 预测 cap=14 会丢 6.1% 已进上下文的 gold
（dev 261/278），实测确实丢了，而且丢的那部分**在 `direct_relation` 上直接变成了分数**。

- W0 说 cap=14 保留 93.9% 的 gold → 看起来"只丢 6%"；
- 实测 Δ = −2 → 那 6% 里恰好有本该答对的题。

**教训：`gold 是否还在上下文` 不等于 `这道题还能不能答对`。** 这两个指标在
W0 里被明确分开标注过（`ctx_pos ≤ cap` vs 分数），W1 的实测证实了分开标注是对的。

## 5. 已证实的部分（这些是正面结果，值得记下）

### 5.1 门控正确
`cross_chunk` 与 `multihop` 的答案**没有变化**（反证条件 3 未触发）。
证明 `pipeline.ask_once` 里的门控确实按设计生效：

```python
if max_direct and (bridge.is_bridge_question(question)
                   or is_chapter_question(question)):
    max_direct = 0
```

### 5.2 默认路径逐位等价
`cap=0` 精确复现 228/285，且 `--option` 不传时 `run()` 的 `extra_options=None`
→ `options` 与改造前完全相同。这是 K5 的核心部分（非触发题零差异）。

### 5.3 cap 真的生效了，不是空操作
答案有 **128（cap=16）/ 136（cap=14）题**发生变化、开口数 347 → 348。
若 cap 没接上，答案变化数会是 0。所以这**不是**"开关没接到入口"那一类事故。

### 5.4 K2 的实现形态正确（未实测但代码可查）
cap 路径用「有序前缀 + 首个超预算即停」（`break`），默认路径仍用 `continue`，
两条路径在 `src/arkrag/retrieve.py` 的 `build_context` 里显式分开。
`tests/test_w1_direct_cap.py` 的 `test_cap_path_stops_at_first_over_budget_unit`
钉住了这个区别：构造「预算装得下 2 个大单元、第 3 个超预算、第 4 个又变小」的语料，
断言第 4 个**不许**进上下文。该测试全绿。

## 7. 回滚

`max_direct_units` **默认 0**，且 `PROD_PROFILE` **没有**加入这个键
（`tests/test_w1_direct_cap.py::test_prod_profile_does_not_enable_cap` 钉着）。
所以回滚 = 什么都不做：生产档本来就没开它。

实现在仓库里保留（`retrieve.build_context(max_direct_units=...)`），
因为：
1. 它是 W2/W3 的共享基础设施（`bridge_candidates` 机制）；
2. 将来若换语料或换预算，这个旋钮可以再测；
3. 删掉它会让 `tests/test_w1_direct_cap.py` 的 13 条门失去对象。

**但记录必须写明：这个开关的实测结论是负的，不要在生产档打开。**
