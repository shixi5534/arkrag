## 实施记录

### A 基线冻结（完成）

**交付物**：`src/arkrag/legacy.py`（写保护）、`scripts/snapshot_baseline.py`（快照与校验）、`data/releases/legacy-baseline/manifest.json`、`gates.snapshot.json`、`metrics.json`、`docs/baseline-metrics.md`。

**为什么要有写保护**：A 阶段的核心承诺是"冻结现场"，而冻结只写在文档里等于没冻结——下一次跑 L5 就把 `graph.json` 覆盖了，基线从此无法复现。所以 `legacy.guard_write()` 在**代码层**拦住对 `graph.json` / `index/lexical.json` / `gates.json` / `circuit_open.json` / `cache/` 的写入，除非显式设 `ARKRAG_ALLOW_LEGACY_WRITE=1`。

**一次数据来源纠错**：`corpus_fp` 首次生成为 `None`。查明 `l0_manifest.json` 顶层键是 `['schema_version','source_dir','corpus_source','baseline','encoding','props','top_level_keys','reconciliation','dropped_files']`，**不含** `corpus_fp`；权威来源是 `data/arkrag/corpus_meta.json`。已改为从 corpus_meta 取，并让 markdown 渲染源仓库、release tag、ZIP sha256、源分类分布、丢弃文件清单。

### B 数据契约与严格回收（完成）

**B1 契约**（`src/arkrag/contracts.py`）：`ark-rag-task-2` / `ark-rag-extraction-2` 两套 schema，21 个机器可读错误码带字段路径。

关键修复：`entities` 不再用 `or []` 兜底。旧代码 `raw = {"entities": rec.get("entities") or [], ...}` 会把 `entities=""`、`entities=False`、`entities=None` **静默洗成空数组**，而空数组在旧校验里完全合法——于是"模型返回了坏数据"和"这一段确实没有实体"在收据上长得一模一样。现在 `""`/`False` → `WRONG_TYPE`，空 list → `EMPTY_COLLECTION`，两者都拒收。

**B2 严格回收**（`src/arkrag/agent_tasks.py`）：`HarvestResult` 十七口径，`hard_errors = conflicts + quarantined`，`complete = hard_errors==0 and missing==0`。

关键修复：旧代码 `got[cid] = rec` 让**同 id 的重复行"最后一行覆盖"**，`duplicates += 1` 只计数不报错。现在同 id 同内容记 `deduped`（合法），同 id 不同内容记 `conflicts` 并**两版都不入库**、写进隔离报告、退出码非零。

**B4 缓存身份**（`src/arkrag/cache.py`）：新键含 `content_key/chunk_id/scene_id/model/prompt_sha256/schema_version/generation`；`prompt_sha256()` 由实际提示词内容算出，不再靠人工改 `PROMPT_VERSION`。

旧键 `sha256(content_key|model|prompt_version)` 的失效形态：overlap 的两块正文相同 → `content_key` 相同 → 同一个键 → **用 A 块的抽取结果去建 B 块的边**。legacy 记录通过 `_legacy_record_is_safe()` 逐项核对身份后才复用，不相符返回 `layer="invalid"` 并带原因，不静默删除。

**风险 1 的处置证据**：`scripts/shadow_cache_check.py` 全量跑 13,786 块 → current 0 / legacy 13,781 / miss 5 / invalid 0，**可复用 99.9637%**。换键不会造成重抽灾难。5 个 miss 是全量 13,786 与 T1 13,781 的差集（`obt/guide` 5 块，D-18 已申报排除）。

**B3 状态口径**：所有"已入库"判断从"缓存文件存在"改为 `cache.is_cached_for_chunk()`（带 chunk_id 身份核对）。改动波及 `run_l3_agent.py --status`、`run_l5.py`、`run_l6.py`、`queue_status.py`、`prune_inbox.py`、`pack_pending.py`、`make_repair.py`、`qa_alignment.py`、`qa_evidence.py`、`qa_offenders.py`、`run_trial.py`。回归证据：`run_l3_agent.py --status` 输出 `合计 13781/13786 块已入库`，与 A 阶段基线一致。

### C 事务式构建与原子发布（完成）

**C3 原子写**（`src/arkrag/atomic.py`）：同目录 `.{name}.{pid}.{uuid12}.tmp` → flush → fsync → `os.replace` → fsync(dir)；`append_jsonl` 用 `O_APPEND` 单次写；`file_lock` 用 `<target>.lock`，超时抛 `TimeoutError` 而**不静默跳过**。

`gates.write_report()` 整段读-改-写包进文件锁。旧版无锁，两个 stage 并发写会各自读到旧内容、各自合并、后写者覆盖——先写者的行静默消失，报告看起来完整却少了一整个 stage 的门。报告损坏时改名 `{name}.corrupt.{ts}` 而非当空重来。

**C1/C2 Generation 与发布**（`src/arkrag/release.py`）：`generations/<gid>/` + `runs/<run_id>/` + `current.json`；状态机 `PREPARING→BUILDING→VALIDATING→READY→PUBLISHED`，任何状态→`FAILED`，只有 `READY` 能发布。

发布顺序固定：固定输入快照 → 建候选 → 算门禁 → **回读**候选产物 → 校验身份与内容摘要 → 全部硬门通过 → 原子替换 `current.json`。

**回读为什么不只比数量**：`index.content_digest()` 摘的是倒排内容本身（不是文件字节，因为 JSON 键序/缩进会让同一份索引有两份字节）；`index.probe_digest()` 用 10 条固定探针把检索排序摘要成一个值——数量全对、词条全对、但 slot 串了或分词错了，只有这一层能发现。

**C5 错误分类**（`src/arkrag/llm.py`）：旧代码 `fatal = exc.code in (401,402,403,429) or any(marker)` 把 **429 与鉴权错误归为一类**——一次限流就把整批任务判死。现在七类分开：AUTH 不重试+permanent 熔断；RATE_LIMIT 听 `Retry-After` + 第 3 次 transient；SERVER 第 4 次 transient；**NETWORK/CONTENT 重试但永不熔断**；RESOURCE 不重试。`circuit_state()` 过期返回 `None`（旧版读到文件就永久阻塞）。

**C5 有界队列**（`src/arkrag/extract.py`）：`futures = {pool.submit(...) for c in chunks}` 一次性提交 13,781 个任务，内存与在途峰值都不受控，且熔断后无法停止投喂。现在 `window` 是待处理队列上限，熔断立即停止补充，剩余块记 `skipped_circuit`（「没跑」与「跑失败」在收据里分开）。

**故障注入覆盖**（`tests/test_release.py::TestFaultInjection`）：构建半途中断 / 门禁 FAIL / 回读损坏 / 写 Manifest 中断 / 发布前终止 / 发布后写报告失败，六种全部验证 `current` 仍指向旧有效 Generation 或根本不存在。

### 一次测试设计纠错（记录在案）

`tests/test_build_generation.py` 首版用**真实门禁**跑人造四块数据，结果 L5.2 平均度数 0.67（要求 > 6）、L5.3 孤立率 33%（要求 ≤ 0.20）、L6.3 检索探针 0/0 全 FAIL，7 个测试失败。

处理方式不是放松门线（那是计划第 5 条明令禁止的"门禁越来越松"），而是认清测试对象：这些测试要证明的是**发布顺序**（快照 → 候选 → 门禁 → 回读 → READY → 指针），不是 L4/L5/L6 的判据。真实判据要求全量语料的规模，四块人造数据永远过不了。故改为**门禁替身**（返回构造好的 PASS/FAIL 行），并在 docstring 与 `_wire()` 注释里写明"门禁语义由真实语料上的 `run_l5`/`run_l6` 与 A 阶段 75 行快照负责"。这样"门禁 FAIL 不发布"仍然被真实测试（注入 FAIL 行），而门线阈值一个都没动。

## 偏差记录

（执行过程中出现与计划的差异一律追加在此，并说明理由。）

暂无与计划冲突的偏差。两处**实现选择**需要记录，因为它们是计划没说死、但会影响后续阶段的地方：

1. **门禁替身**（见上「一次测试设计纠错」）：C1/C2 的端到端测试用替身门禁，真实门线阈值未动。这不是放宽验收，是划清测试边界。
2. **`normalizer_version` 不进缓存键**：`cache.py` 记录它但不参与 `key_for()`。理由：缓存存的是**归一化前**的 raw 抽取结果，归一化版本改变不影响 raw 的可用性；若进键，D-24 那次 n1→n2 就会让 13,781 条 raw 缓存全部作废，而它们本来完全可复用。此判断需在 E 阶段（Assertion 图重建）复核——如果 Assertion 层要把归一化结果也缓存，那时它必须进键。
