## 实施记录

### A 基线冻结（完成）

**交付物**：`src/arkrag/legacy.py`（写保护）、`scripts/snapshot_baseline.py`（快照与校验）、`data/releases/legacy-baseline/manifest.json`、`gates.snapshot.json`、`metrics.json`、`docs/baseline-metrics.md`。

**为什么要有写保护**：A 阶段的核心承诺是"冻结现场"，而冻结只写在文档里等于没冻结——下一次跑 L5 就把 `graph.json` 覆盖了，基线从此无法复现。所以 `legacy.guard_write()` 在**代码层**拦住对 `graph.json` / `index/lexical.json` / `gates.json` / `circuit_open.json` / `cache/` 的写入，除非显式设 `ARKRAG_ALLOW_LEGACY_WRITE=1`。

**一次数据来源纠错**：`corpus_fp` 首次生成为 `None`。查明 `l0_manifest.json` 顶层键是 `['schema_version','source_dir','corpus_source','baseline','encoding','props','top_level_keys','reconciliation','dropped_files']`，**不含** `corpus_fp`；权威来源是 `data/arkrag/corpus_meta.json`。已改为从 corpus_meta 取，并让 markdown 渲染源仓库、release tag、ZIP sha256、源分类分布、丢弃文件清单。

### B 数据契约与严格回收（完成）

**B1 契约**（`src/arkrag/contracts.py`）：`ark-rag-task-2` / `ark-rag-extraction-2` 两套 schema，21 个机器可读错误码带字段路径。

关键修复：`entities` 不再用 `or []` 兜底。旧代码 `raw = {"entities": rec.get("entities") or [], ...}` 会把 `entities=""`、`entities=False`、`entities=None` **静默洗成空数组**，而空数组在旧校验里完全合法——于是"模型返回了坏数据"和"这一段确实没有实体"在收据上长得一模一样。现在 `""`/`False` → `WRONG_TYPE`，空 list → `EMPTY_COLLECTION`，两者都拒收。

**B2 严格回收**（`src/arkrag/agent_tasks.py`）：`HarvestResult` 十七口径，`hard_errors = conflicts + quarantined`，`complete = hard_errors==0 and missing==0`。

关键修复：旧代码 `got[cid] = rec` 让**同 id 的重复行"最后一行覆盖"**，`duplicates += 1` 只计数不报错。现在同 id 同内容记 `deduped`（合法），同 id 不同内容记 `conflicts` 并**两版都不入库**、写进隔离报告、退出码非零。

**B4 缓存身份**（`src/arkrag/cache.py`）：新键含 `content_key/chunk_id/scene_id/model/prompt_sha256/schema_version/generation`；`prompt_sha256()` 由实际提示词内容算出，不再靠人工改 `PROMPT_VERSION`。

旧键 `sha256(content_key|model|prompt_version)` 的失效形态：overlap 的两块正文相同 → `content_key` 相同 → 同一个键 → **用 A 块的抽取结果去建 B 块的边**。legacy 记录通过 `_legacy_record_is_safe()` 逐项核对身份后才复用，不相符返回 `layer="invalid"` 并带原因，不静默删除。

**风险 1 的处置证据**：`scripts/shadow_cache_check.py` 全量跑 13,786 块 → current 0 / legacy 13,781 / miss 5 / invalid 0，**可复用 99.9637%**。换键不会造成重抽灾难。5 个 miss 是全量 13,786 与 T1 13,781 的差集（`obt/guide` 5 块，D-18 已申报排除）。

**B3 状态口径**：所有"已入库"判断从"缓存文件存在"改为 `cache.is_cached_for_chunk()`（带 chunk_id 身份核对）。改动波及 `run_l3_agent.py --status`、`run_l5.py`、`run_l6.py`、`queue_status.py`、`prune_inbox.py`、`pack_pending.py`、`make_repair.py`、`qa_alignment.py`、`qa_evidence.py`、`qa_offenders.py`、`run_trial.py`。回归证据：`run_l3_agent.py --status` 输出 `合计 13781/13786 块已入库`，与 A 阶段基线一致。

### C 事务式构建与原子发布（完成）

**C3 原子写**（`src/arkrag/atomic.py`）：同目录 `.{name}.{pid}.{uuid12}.tmp` → flush → fsync → `os.replace` → fsync(dir)；`append_jsonl` 用 `O_APPEND` 单次写；`file_lock` 用 `<target>.lock`，超时抛 `TimeoutError` 而**不静默跳过**。

`gates.write_report()` 整段读-改-写包进文件锁。旧版无锁，两个 stage 并发写会各自读到旧内容、各自合并、后写者覆盖——先写者的行静默消失，报告看起来完整却少了一整个 stage 的门。报告损坏时改名 `{name}.corrupt.{ts}` 而非当空重来。

**C1/C2 Generation 与发布**（`src/arkrag/release.py`）：`generations/<gid>/` + `runs/<run_id>/` + `current.json`；状态机 `PREPARING→BUILDING→VALIDATING→READY→PUBLISHED`，任何状态→`FAILED`，只有 `READY` 能发布。

发布顺序固定：固定输入快照 → 建候选 → 算门禁 → **回读**候选产物 → 校验身份与内容摘要 → 全部硬门通过 → 原子替换 `current.json`。

**回读为什么不只比数量**：`index.content_digest()` 摘的是倒排内容本身（不是文件字节，因为 JSON 键序/缩进会让同一份索引有两份字节）；`index.probe_digest()` 用 10 条固定探针把检索排序摘要成一个值——数量全对、词条全对、但 slot 串了或分词错了，只有这一层能发现。

**C5 错误分类**（`src/arkrag/llm.py`）：旧代码 `fatal = exc.code in (401,402,403,429) or any(marker)` 把 **429 与鉴权错误归为一类**——一次限流就把整批任务判死。现在七类分开：AUTH 不重试+permanent 熔断；RATE_LIMIT 听 `Retry-After` + 第 3 次 transient；SERVER 第 4 次 transient；**NETWORK/CONTENT 重试但永不熔断**；RESOURCE 不重试。`circuit_state()` 过期返回 `None`（旧版读到文件就永久阻塞）。

**C5 有界队列**（`src/arkrag/extract.py`）：`futures = {pool.submit(...) for c in chunks}` 一次性提交 13,781 个任务，内存与在途峰值都不受控，且熔断后无法停止投喂。现在 `window` 是待处理队列上限，熔断立即停止补充，剩余块记 `skipped_circuit`（「没跑」与「跑失败」在收据里分开）。

**故障注入覆盖**（`tests/test_release.py::TestFaultInjection`）：构建半途中断 / 门禁 FAIL / 回读损坏 / 写 Manifest 中断 / 发布前终止 / 发布后写报告失败，六种全部验证 `current` 仍指向旧有效 Generation 或根本不存在。

### 一次测试设计纠错（记录在案）

`tests/test_build_generation.py` 首版用**真实门禁**跑人造四块数据，结果 L5.2 平均度数 0.67（要求 > 6）、L5.3 孤立率 33%（要求 ≤ 0.20）、L6.3 检索探针 0/0 全 FAIL，7 个测试失败。

处理方式不是放松门线（那是计划第 5 条明令禁止的"门禁越来越松"），而是认清测试对象：这些测试要证明的是**发布顺序**（快照 → 候选 → 门禁 → 回读 → READY → 指针），不是 L4/L5/L6 的判据。真实判据要求全量语料的规模，四块人造数据永远过不了。故改为**门禁替身**（返回构造好的 PASS/FAIL 行），并在 docstring 与 `_wire()` 注释里写明"门禁语义由真实语料上的 `run_l5`/`run_l6` 与 A 阶段 75 行快照负责"。这样"门禁 FAIL 不发布"仍然被真实测试（注入 FAIL 行），而门线阈值一个都没动。

### 口径更正（2026-10-31，以下两条以实测为准）

**更正 1：`tests/test_vocab.py` 已经是 pytest 用例，不再是"脚本式自检"。** 本表此前记它为"脚本式自检……不是 pytest 用例，故不计入"，此说法**已过时**。该文件现被重构为**判据只有一份**的结构：

| 部件 | 现在的职责 | 说明 |
|---|---|---|
| `check(cond, message)` | 失败即 `raise AssertionError(message)` | 旧写法是 `if not cond: FAILURES.append(message)`——只往模块级列表记一笔 |
| `_check_all()` | **唯一判据**，全部词表检查都在这里 | `main()` 与两个 pytest 用例都只调它，不重复实现 |
| `main() -> int` | 命令行入口，捕获 `AssertionError` 后打印 FAIL、返回 1 | 干净时打印 PASS 摘要并返回 0 |
| `test_vocab()` | pytest 入口，直接调 `_check_all()` | 不做任何重复实现 |
| `test_vocab_cli_exit_code_is_zero_on_clean_vocab()` | 断言 `main() == 0` | CI 常靠退出码判成败，这一条单独覆盖 |

实测：`py -3 -m pytest tests/test_vocab.py -q` → **`2 passed`**；`py -3 tests\test_vocab.py` → 仍输出同样的 `词表自检 PASS 关系名 48 条 / 逆谓词对 11 / 对称 9 / 互斥 6 / 同义词 211 条 / 实体类型 6`，退出码 **0**。

**为什么要改**：旧写法只把失败记进模块级 `FAILURES` 列表、由 `main()` 读，于是 **pytest 收集到 0 个用例却报成功**——文件能被导入、能显示"完成"，但没有任何一条断言真正生效。这与 `tests/test_negative.py` 的 `expect()` 是同一形态的缺陷（见「D 阶段两个隐形缺陷」2 节），也是 `tests/test_suite_hygiene.py` 建门的直接动因。

**更正 2：合计不再是 337 或 338，而是 405 collected / 404 passed / 1 skipped。** 337 保留为提交 `30a8ed5` 时口径（那是真的，不改写历史）；338 一类的中间观测值作废，不再引用。当前值：

| 命令 | 结果 | 退出码 |
|---|---|---|

## D 阶段：解析分块指纹与证据身份（候选已构建，未发布）

### 为什么必须先修两个"不报错"的 bug

D1/D2 改的不是风格，是**旧代码会把内容丢掉而门照样 PASS** 的两处：

**D1 轮次实例身份**。旧 `chunk.py` 拿 `node_id` 当轮次唯一键（`if turn["node_id"] in seen: continue`）。`node_id` 会缺失（实测 **201 轮 id 为 0，分布 201 个场景**），也会重复；同编号不同正文的两轮只剩一轮，且没有任何一处报错。更糟的是旧 L2 覆盖率门也用 `node_id` 当基准，分子分母一起少，门恒 PASS。现在实例身份改用**场景内序号 `ordinal`**，块记录带 `turn_ordinals` / `node_ids` / `turn_spans`；新增 `L1.8`（缺失，仅申报）与 `L1.8b`（同场景同编号且正文不同 → FAIL）把「缺失」与「身份冲突」分开报，`L2.1c` 按轮次实例逐轮核对块内顺序与正文。

**D2 超长尾块**。旧尾块长度用 `"".join(line for line, _ in buf)` 测量（**不含 `\n`**），而落盘用 `"\n".join(...)`。两把尺子差「行数-1」个字，于是每行都参与计费的短行数量被系统性低估。后果：**17 个文档各有一块本应独立的合格尾块（真实 121–125 字，均 ≥ `MIN_CHARS`=120）被误判为短块并合进前块**。新代码统一用 `_render_len()`（= `len("\n".join(...))`）测量，并新增 `MAX_CHARS`（= 2×TARGET = 1800）硬上限，尾块处置写进块记录 `tail_action` ∈ {`merged`/`rebalanced`/`kept_short`}、短块必须写 `short_reason`。配套门：`L2.2 短块必须有书面原因`（无原因短块必须为 0）、`L2.3 最大块 <= 硬上限`。

### 可证明复用层（能力已实现，本轮无对象可复用）

`cache.adopt_legacy(src_record, chunk, model, *, generation=0)`：仅当 **content_key + scene_id + model + prompt_sha256 四项逐项相等**、且 raw 过 `contracts.validate_extraction()` 时才写一条新键记录，记录里写明 `adopted_from=<legacy 缓存键>` / `adopt_reason="identical_content"` / `adopted_at`。`Lookup.layer` 因此多一层 `"adopted"`，**单独上报，不混进 `current` 冒充本轮抽取产出**。

## D4 阶段：关闭线上世代的 provenance 缺口（已发布）

### 缺口是什么

`py -3 scripts\release_cli.py current` 在本次修复前 **exit 1**，自检 FAIL 1 项：

```
索引 meta 缺 graph_artifact_id：无法证明这份倒排对着哪一份图产物
```

线上世代 `g-20261030T114823Z-606ea9` 建于 D3 **之前**，它的 index meta 只有
`graph_fp=f90a78f6df41f564`，缺 `graph_artifact_id` / `prompt_sha256` / `vocab_sha`。
这不是判据写错了，是判据收紧后**暴露出来的真实审计缺口**：

- `graph_fp` 是"建图配置指纹"——同一份配置重建两次图，指纹相同，**产物未必相同**。
  所以 `graph_fp` 相等**不能**证明这份倒排挂在某一具体图文件上。
- 缺 `graph_artifact_id` 就意味着：若图文件在盘上被替换（哪怕只是重新 dump 一次、
  键序变化、某条边被人工修正），没有任何字段能发现索引已经对不上了。
  线上服务会拿旧倒排去查新图，答案错而无人知晓。
- `prompt_sha256` / `vocab_sha` 同理：它们证明"这批倒排是这份提示词与这份词表抽出来的"。
  缺了它们，事后无法回答"这条检索结果为什么长这样"。

所以这个缺口必须关——它不是格式洁癖，是**线上产物无法自证身份**。

**本次重建用的是旧分块（冻结的 `data/arkrag/chunks.jsonl`，13,781 块），不是 D 阶段的新分块。**

### 代码改动

**1. 来源状态的单一事实源（`src/arkrag/source.py`、`scripts/build_generation.py`）**

`build_generation.py` 原本 `source_status` 从 `corpus_meta.json` 读。但冻结的
`corpus_meta.json`（153 B，D4 之前的产物）**没有这个字段**，于是
`corpus_meta.get("source_status", "source_unverified")` 把一份实际已验证的语料判成未知来源、
拒绝构建。**缺字段 = 这个文件里没写，不等于"没验证过"。**

改为：权威取 `source.status_for_build()`（读 `data/arkrag/source_verification.json`，
即**产出验证的地方**写的那份记录），`corpus_meta.json` 里的同名字段只作兜底与交叉核对。
理由是副本不配当权威：它会过期（L0 重跑后不更新）、会串味（产物搬家时副本跟着走而记录没跟着）、
**会缺字段（就是这次的 bug）**。

两份不一致时**不许静默取一边**：新增 `source.resolve_for_build()` 把它当成一次需要登录的事件——
`conflicts` 列出两边的原值，结论取**更保守**的那侧（`strength` 表定义 `source_unverified < verified_tree < verified_zip`），
调用方把冲突打到 stderr 并写进 run 事件的 `snapshot` 阶段。取保守的理由：两边不一致本身
就说明有一个产物在说谎，在能证明之前按弱的申报不会高估来源可信度。

顺带修了一处同源缺陷：`VERIFICATION_PATH` 原是模块级常量（`config.DATA_DIR / …`），
import 时就把路径烧死了，**测试把 `DATA_DIR` 重定向到临时目录也对它无效**——
读到的永远是真实仓库那份记录，于是"来源状态"在测试里成了真值的回声。
已改为 `verification_path()` 函数，跟随重定向。

**2. 状态强度用精确匹配，不用 `strip()`**

`strength()` 起初写成 `_STRENGTH.get(status.strip(), 0)`，新测试当场抓到它把
`"verified_zip "`（尾空格）算成强度 2——一个笔误就能把状态抬成"已验证"。
改为精确匹配，不 strip、不 casefold：未知拼写、大写、缩写、尾空格一律按 0（最保守）。
要用宽容归一化的话该在**写入端**做，并且归一化本身也得有记录，不是在读取端猜。

## 来源门的白名单修复（D4 收尾）

### 漏洞：发布门只拒绝了一个字面量

`src/arkrag/release.py` 的 `verify_generation()` 里，D4 的来源检查原先写成：

```python
if (manifest.get("source_status") or "") == "source_unverified":
```

**它只拒绝这一个拼写。** 而 `src/arkrag/source.py` 的 `strength()` 是保守的**白名单**：
只认 `verified_zip`（强度 2）、`verified_tree`（强度 1），其余一律按 0（未验证）。

于是两个模块对"什么算已验证"各有一套判据：`source` 用白名单，`release` 用黑名单（且只列一项）。

### 机检证明的不一致（逐值对照）

`release拒绝` = `verify_generation()` 是否报出 `source_status` 问题；`source认定已验证` = `strength()` 是否 > 0：

```
'source_unverified'  release拒绝=True   source认定已验证=False  一致=True
'verified_zip'       release拒绝=False  source认定已验证=True   一致=True
'verified_zip '      release拒绝=False  source认定已验证=False  一致=False
'VERIFIED_ZIP'       release拒绝=False  source认定已验证=False  一致=False
''                   release拒绝=False  source认定已验证=False  一致=False
'verified'           release拒绝=False  source认定已验证=False  一致=False
'bogus'              release拒绝=False  source认定已验证=False  一致=False
```

只有两行一致，其余五行全部错位。即：把 `source_status` 写成**空串、大写、尾空格（笔误）、缩写、或任何瞎写的值，都能通过发布门**。

### 为什么这不是理论风险

`resolve_for_build()` 在副本与权威不一致时**取更保守的一侧，并把原值原样带出**。实测
`resolve_for_build({"source_status": "verified_zip "})` 返回 `status='verified_zip '`、`verified=False`，
且 `conflicts` 里记了这次不一致。

也就是说：这个带尾空格的值会**一路写进 Manifest**，而旧门看到它不是 `"source_unverified"` 就放行。
**保守判断在上面，宽松判断在下面，两者正好抵消**——D4 建立的那层保护被下面这道门原地作废。
这也说明单靠"某一处判得严"不构成保证：只要链路上有一处松，结论就是那处最松的。

### 修法：改成白名单，与 `source` 共用常量

```python
_source_status = manifest.get("source_status") or ""
if _source_status not in (source.VERIFIED_ZIP, source.VERIFIED_TREE):
    problems.append(
        f"source_status={_source_status!r}：语料来源未能验证，"
        f"按计划 D4 不得作为 Release 发布"
    )
```

- `release.py` 的导入加 `source`，判据直接引用 `source.VERIFIED_ZIP` / `source.VERIFIED_TREE`，
  **不再手抄字面量**——表只有一张，改一处即两处同时生效。
- 报错信息用 `{!r}` 把实际值原样露出。尾空格、换行这类**看不见的字符必须能被看见**，
  否则收据上只会看到"来源未验证"却查不出到底是哪个拼写。

### 新增测试

`tests/test_release.py::TestVerify` 加两个参数化用例：

- `test_any_unrecognized_source_status_blocks_release`，参数
  `["source_unverified", "", "VERIFIED_ZIP", "verified_zip ", "verified", "verified_zip\n", "bogus"]`
  —— 7 个取值全部必须被拒。
- `test_recognized_verified_status_passes`，参数 `["verified_zip", "verified_tree"]` —— 必须放行。

`test_any_unrecognized_source_status_blocks_release` 的 docstring 写明判据：

> 门必须是白名单。只拒绝字面量 `"source_unverified"` 的写法等于没有门：把状态写成
> `""`、`"VERIFIED_ZIP"`、`"verified_zip "` 这些同样**不是已验证**的取值，全都绕得过去。
> 判据与 `source.strength()` 必须是同一张表。

### 一类反复出现的缺陷模式（本阶段第三次）

这一阶段已经出现三次同类问题，三次的形态不同、机理相同：

| 次数 | 同一判定被写了两份 | 后果 |
|---|---|---|
| A 阶段 | 冻结清单与写保护清单各写一份 | 漂移（11 项 vs 4 项），**冻结产物被覆盖** |
| D4 | `corpus_meta.json` 副本与 `source_verification.json` 权威各算一次 | 副本缺字段 → 被当成"未验证" |
| D4 收尾 | `release.py` 与 `source.py` 对"已验证"各有一套判据 | 门只守一个拼写 → **门形同虚设** |

**共同机理：同一个判定在两处各写一份，只要有任意一处较宽松，整套检查就等于那处最松的。**
两份拷贝不会互相校验，它们只会各自漂移；而执行路径上先遇到哪一份，就按哪一份的宽严执行。

对应的纪律：**判定只能有一处事实源，其余地方必须引用它而不是重写它。**
能不能引用是设计问题（常量放在无依赖的模块里），愿不愿引用是纪律问题——写了引用就改不动另一份，这才是可机检的约束。

### 本节遗留：**已关闭**（2026-10-31）

原来的遗留项是：

> 上述三项回归只覆盖"当前状态"，没有为"来源门"补一条**长期**机检：
> `release.py` 里若有人再次手抄字面量而非引用 `source.VERIFIED_*`，现有测试仍会通过
> （因为取值恰好相等）。要拦住这种回归需要一条静态检查（如扫描 `release.py` 中
> 出现 `"verified_zip"` 字面量即失败），本轮未做。

**现已关闭。** 关闭方式是静态检查，不是再加一条行为测试——行为测试根本拦不住这类回归：
把 `source.VERIFIED_ZIP` 改回手抄的 `"verified_zip"`，取值恰好相等，所有行为断言照样通过。

新的守卫位置：`tests/test_single_source_of_truth.py::TestSourceStatusHasOneDefinition::test_only_source_module_declares_status_literals`，
扫描 `src/arkrag/*.py` 与 `scripts/*.py`（`source.py` 除外）中是否出现
`"verified_zip"` / `"verified_tree"` / `"source_unverified"` 字面量。

关闭过程本身也抓出了真实残留（下一节第 1 项）：`release.py` 的两处**默认值**仍是手抄字面量。

**这条静态门只看代码、不看注释。** 注释里提到历史字面量是必要的、不该被判违规——
`gates.py` / `release.py` 现在都留着一句"手抄的后果已经发生过"的注释，那是解释判据为什么长这样，
删掉它才是损失。测试用 `_code_part()`（按 `#` 切分取左半）只检查代码部分。

唯一被放行的代码形态是"把字面量当**数据值**记录"（`reason=` / `note=` / `message=` 位置上，
例如 `run.finish(reason=...)`），那不是判定，是写原因文本。

## 单一事实源加固与门禁可失败性（D4 收尾续）

上一节把"判定只能有一处事实源"写成了纪律，并把"没有静态检查拦住手抄字面量"列为遗留。纪律靠人守，人会被进度和"就这一处应该没事"说服；于是本轮把纪律换成机检（第 1–3、6 项），并补上一件更基础的事：**门禁本身要能被证明会失败**（第 4–5 项）。一条恒 PASS 的门比没有门更糟，它会让人以为这件事被检查过了。

### 1. 静态防回归测试，首次运行就抓出两个真实遗漏

新建 `tests/test_single_source_of_truth.py` 后首次运行，2 项失败，报出：

```
release.py:185: source_status: str = "source_unverified"
release.py:208: source_status: str = "source_unverified",
```

两处都是**默认值**仍在手抄字面量。默认值恰恰是最容易漏的地方：它决定了"没写等于什么"，写错方向就是让未知冒充已验证。已改为引用 `source.UNVERIFIED`（现 `release.py:187` / `release.py:210`）。

同一轮还有一项失败是**测试自己的判定写错了**：先剥掉注释、却又拿原行去比对，于是把注释里解释历史缺陷的文字当成了违规。已改为只检查代码部分 `_code_part()`。测试自己也会错，这条一并记下——否则下一轮的人会以为"静态门红了就一定是代码错"。

### 2. 另外两处判定一并统一到常量

`gates.py` 的 `L0.8 来源已验证`：原来 `status in ("verified_zip", "verified_tree")` 手抄两份字面量，改为

```python
status = sv.get("status") or manifest.get("source_status") or source.UNVERIFIED
verified = status in (source.VERIFIED_ZIP, source.VERIFIED_TREE)
```

默认值改 `source.UNVERIFIED`，`gates.py` 的导入加 `source`（现 `gates.py:18`，判据在 `:212` / `:215`）。

`fingerprint.py` 的 `source_fingerprint()`：三个分支各写字符串，改为引用 `source` 常量（`fingerprint.py:198/200/202`，函数内 `from . import source as _source` 避免导入环）。

**该函数当前没有调用方**——D4 的真实判定在 `source.verify()`。留着两份独立判定就是隐患：今天没人调用，明天有人调用时它就是第二个事实源。这种情况删不掉（怕以后要用），就应该让它**无法写错**。

### 3. `build_generation.py` 的失败记录改为记实际值

原来：

```python
run.finish("failed", reason="source_unverified", source_status=source_status)
```

`reason` 写死成固定标签。若来源状态是 `"bogus"` 这类笔误，收据上照样记成 `source_unverified`，就把"写错了"和"确实没验证"混成一件事——事后查不出到底是判据失效还是拼写错误。改为（现 `scripts/build_generation.py:167-171`）：

```python
run.finish("failed", reason=f"source_not_verified:{source_status}", source_status=source_status)
```

实际取值原样进收据，字面量信息不再丢失。

### 5. 新建 `tests/test_gates_l0.py`（25 项）：把"门禁必须能失败"机械化

关键设计是 `TestEveryL0GateCanFail` 持一张 `FAILING_INPUTS` 清单，逐条列出每扇 L0 门的"能让它 FAIL 的 manifest 覆盖"；`test_no_uncovered_gates` 断言**实际存在的每条 L0 门都在清单里**，否则失败并提示补上。这样"新增一条门"这个动作本身被纳入检查，而不是靠评审时有人想起。

首次运行该元测试当场点出 **5 条没有任何触发输入的门**：`L0.6`、`L0.6a`、`L0.6b`、`L0.6c`、`L0.7`。逐条核查后的结论与处置：

| 门 | 核查结论 | 处置 |
|---|---|---|
| `L0.6 对话/旁白比（多口径一致性）` | 能失败，是最小 manifest 不触发 | 补真实触发输入：轮次口径 10:1 而字数口径 100:1000，制造两口径剧烈分叉 |
| `L0.6a 探针：narration 数>0` | 能失败 | 补 `narration_turns=0` |
| `L0.6b 探针：narration 占比<0.30` | 能失败 | 补 `dialogue_turns 5 / narration_turns 5`，占比 0.5 |
| `L0.7 文件<->索引缺口逐条有解释` | 能失败 | 补 `reconciliation={"some_index": {"unexplained": ["a.json"]}}` |
| `L0.6c 含无说话人轮次的文档数（仅申报）` | **确实恒 PASS**，是纯申报门 | 单列 `INFORMATIONAL` 集合 |

- 被声明为"只申报"的门**必须真的恒 PASS**（用多个 manifest 覆盖试一遍，出现 FAIL 就说明它其实是判定门）；
- 门名里**必须能看出"申报"字样**（`assert "申报" in name`）。

这样没人能用这个集合藏一条本该能红的门：要藏进去的前提是它真的恒 PASS，而且名字得自己说清楚。

### 8. 两轮做的是同一件事：把"纪律"换成"机检"

上一节的纪律是"判定只能有一处事实源"。本轮把它换成三类可执行约束：

| 约束 | 形态 | 拦住什么 |
|---|---|---|
| 状态字面量只在 `source.py` 出现 | 静态扫描 `test_only_source_module_declares_status_literals` | 有人再次手抄 `"verified_zip"` 而不是引用常量 |
| 来源门必须是白名单 | 静态扫描 `test_no_blacklist_comparison_in_gate_modules`、`test_run_l0_exit_code_is_whitelist_based` | 有人把白名单改回"只拦 UNVERIFIED" |
| 每条门都要有能红的输入 | 元测试 `test_no_uncovered_gates` + 反向验证 `test_declared_informational_gates_are_actually_always_pass` | 有人新增恒 PASS 的门，或把判定门藏进申报清单 |

三条约束的共同点：**它们检查的是"形状"，不是"某次运行的结果"**。取值恰好相等的回归，行为测试拦不住，形状检查能。

一个仍然存在的限制照实写下：`_code_part()` 靠按 `#` 切分来剥注释，字符串里含裸 `#` 的行会被切错。这里刻意**宁可少判**（漏掉一行注释）也**不误判**（把注释当违规）——误判会让人学会忽略这条测试，那比漏判更糟。仓库当前没有这种怪例，测试文件里也写明了这个取舍。

## D 阶段两个隐形缺陷（2026-10-31）

本轮复核的两个缺陷都不是"功能少做了一块"，而是**校验机制本身在给出错误结论**：一个让身份字段静默退化，一个让测试套件在 CI 里报绿。二者叠加的后果是"线上看着全绿、覆盖实际大面积塌陷"。记在此处，避免后当成小修小补。

### 1. 缺陷一：ordinal 退化成块内下标

**机制（读码 + 实测）。** `src/arkrag/chunk.py` 的 `turn_ordinal(turn, fallback)` 在轮次上找不到 `ordinal` 时退回调用方传入的 `fallback`；而 `_dedupe()` 与 `turn_spans` 两处都用 `enumerate(buf)` 的结果当 `fallback`——那是**块内下标**，不是场景级轮次序号。

**触发条件（实测）。** 冻结基线 `data/arkrag/scenes.jsonl` 的轮次键集实测为 `['kind','masked','node_id','prop','speaker','text']`，**没有 `ordinal` 字段**（该文件由旧版 `parse.py` 生成）。于是 `fallback` 路径是常态而非例外：每一块的轮次序号都从 0 重新起数。

**后果（实测规模）。** 停用补齐后重跑冻结语料：**2,291 个场景中 2,127 个轮次覆盖不全，占 92.8%**。典型例 `activities/a001/level_a001_01_beg` 共 89 轮，结果只覆盖 47 轮。切块越碎、场景越长塌陷越重——块内 `turn_ordinals` 恒落在 `0..块长-1`，前后块的序号互相重叠。

**修复。** `chunk.py` 新增 `_with_ordinal(turn, index)`，`split_scene` 在入口一次性补齐**场景级** ordinal：

```python
items = [(render_turn(t), _with_ordinal(t, i)) for i, t in enumerate(scene["turns"])]
```

`_with_ordinal` 返回浅拷贝，不改入参；上游已写 `ordinal` 时以其为准。`turn_ordinal` 的 docstring 补记了这次踩坑，写明 `fallback` 必须是场景级序号而非块内下标。

**修复后（实测）。** 2,291 场景覆盖不全降为 **0**。与冻结基线逐块比对：13,786 个同 `chunk_id` 的块中 **13,769 个正文与 `content_key` 完全一致**；余下 17 个正是 D2 尾块硬上限修正所改（新正文均为旧正文的严格前缀，旧约 978–1008 字符、新约 853–894 字符），另新增 17 个 `chunk_id`，故块数 13,786 → 13,803（其中 `obt/guide` 5 块，非 guide 13,798）。

> 口径说明：曾表述为"分块文本与冻结基线完全一致（差异 0）"，实测只对**剔除 D2 修正这 17 块后的 13,769 块**成立；D2 的 17 块是**有意**的正文变化，不是回归。

### 2. 缺陷二：`tests/test_negative.py` 在 pytest 下假通过

**机制（读码）。** 该文件的 `expect(cond, message)` 原实现只做 `if not cond: FAILS.append(message)`，`FAILS` 仅在 `main()` 结尾被读取打印。pytest 收集到的每个 `test_*` 都正常返回，**不产生任何断言失败**，于是全部计为通过。

**症状（实测，同一份代码）。**

| 调用方式 | 结果 |
|---|---|
| `py -3 -m pytest tests/test_negative.py` | **11 passed** |
| `py -3 tests\test_negative.py` | **1 条 FAIL**（「有轮次未被任何块覆盖」） |

即 CI 长期是绿的，而缺陷就躺在被断言保护的路径上。**上面那个 ordinal 缺陷能躲这么久，一半原因在这里**：唯一能抓住它的负例，在 pytest 口径下根本不发声。

**修复。** `expect()` 改为 `raise AssertionError(message)`；`main()` 逐个 `try/except AssertionError` 收集，保证单文件直接运行时一次看到全部失败，而不是首个失败即中断。

**反向验证（实测）。** 临时把 `if not cond:` 改成 `if True or not cond:` 注入失败：pytest 报 **11 failed**、直接运行 **退出码 1**，两者口径一致。修复后 `py -3 tests\test_negative.py` → 「负例测试 10/10 PASS」，退出码 0。

### 3. 新增回归门 `tests/test_chunk_ordinal.py`（9 项）

三个测试类守三件不同的事：

| 测试类 | 守什么 | 关键断言 |
|---|---|---|
| `TestOrdinalIsSceneScoped` | ordinal 必须是场景级 | 多块场景覆盖等于 `set(range(40))`；每块 ordinals 是场景级连续区间；`split_scene` 不得就地改入参；上游已写 ordinal（用 100/101/102 验证）必须尊重；同 `node_id` 不同正文的两轮都要保留 |
| `TestCoverageGateCatchesDegradation` | 门自己不能跟着一起错 | 正常块喂 `L2.1a` 必须 PASS 且 `measured` 含 `漏 0 篇`；把每块 `turn_ordinals` 人为改成块内下标后，`L2.1a` 必须 **FAIL** |
| `TestFrozenScenesShape` | 触发条件必须一直被覆盖 | 断言冻结 `scenes.jsonl` 的轮次**没有** `ordinal` 字段；抽样前 50 个真实场景跑分块，覆盖必须完整 |

`TestCoverageGateCatchesDegradation` 是其中最要紧的一条：只测"好数据能过"的门，会在门与实现一起变错时照样绿灯；必须同时测"坏数据必须被拦"。

**反向验证（实测）。** 以 `chunker._with_ordinal = lambda turn, index: turn` 停用补齐后，该文件 **3 failed / 6 passed**，失败项为 `test_multi_chunk_scene_covers_every_turn`、`test_good_chunks_pass`、`test_first_fifty_scenes_fully_covered`——门确实挡得住。

## 测试套件卫生门（2026-10-31）

> 一句话结论：**测试代码在，不等于判定在。** 这个门不是为了让测试变多，是为了让"绿"这个字有内容。

### 1. 触发原因：从一个假通过查到一类假通过

起因是修 `tests/test_negative.py` 的假通过：它的 `expect()` 只做 `FAILS.append(message)`、不抛异常，于是 **pytest 报 `11 passed`，而单文件直接运行报 1 FAIL**——两个口径给出相反的结论。

修完立刻意识到：**同类问题可能不止一处**。于是不再逐个人工看，而是系统性核查了 `tests` 目录下全部 **15 个** `test_*.py` 文件的 pytest 收集数（核查当时为 15 个；本门落地后 `tests` 下现存 16 个 `test_*.py`，多的那个就是 `test_suite_hygiene.py` 本身。另有 `conftest.py` 为夹具，始终不在其列）。核查结果：`tests/test_vocab.py` 是 **0 个用例**——它当时只有 `main()`，pytest 收集到 0 项，却和"全部通过"看起来一样。

这正是卫生门存在的理由：**0 个用例的报告与 100% 通过的报告，长得一模一样。**

### 2. 新建 `tests/test_suite_hygiene.py`：四类检查

| 类 | 测什么 | 判据 |
|---|---|---|
| `TestEveryFileIsCollected` | 每个 `tests/test_*.py` 必须能被 pytest 收集到用例 | 文件里必须有 `def test_` 或 `class Test`；`conftest.py` 作为夹具由 `HARNESS_FILES` 显式排除，不参与该判定 |
| `TestAssertionsActuallyRaise` | 断言必须真能失败 | 两层判据，见下 |
| `TestNoCwdRelativeRepoPaths` | 测试不得依赖 cwd | 正则扫相对仓库路径字面量；该文件对自己 skip 并写明理由 |
| `TestSuiteSizeIsMonotonic` | 用例总数不能静默变少 | 登记常量 `N = 405`，用子进程跑 `pytest --collect-only` 数实际值比对 |

`TestAssertionsActuallyRaise` 的两层判据是关键，缺一层都会漏：

1. **辅助函数层**：名字像断言辅助的函数（`expect` / `check` / `verify` / `require` / `assert_*`）函数体必须有 `raise` 或 `assert`。这一层抓的是 `expect()` 那种"只记不抛"的形态。
2. **调用层**：每个 `def test_*` 要么自己含 `assert`/`raise`，要么调用了**能抛异常的**模块级函数。且该判定要做**传递闭包**——`test_vocab()` 本身没有 `raise`，它调 `_check_all()`，`_check_all()` 调 `check()`，`check()` 才 `raise`。**只看一层会把这个正当结构误报成违规**。

`TestNoCwdRelativeRepoPaths` 的来历也是一次实测教训：`test_vocab.py` 原用 `Path("src/arkrag/vocab.py")`，从别的目录运行就 `FileNotFoundError`。现在改成 `ROOT = Path(__file__).resolve().parents[1]` 拼绝对路径。

### 3. 反向验证：证明这道门真能红

只证明"好代码能过门"的门，会在门与实现一起变错时照样绿灯。故做了注入实测：

| 注入 | 做法 | 结果 |
|---|---|---|
| A | 新建一个只有 `main()`、没有 `test_*` 的 `tests/test_inject_empty.py` | `test_file_has_pytest_visible_tests` 与 `test_declared_count_matches_actual` **双双 FAILED** |
| B | 把 `tests/test_negative.py` 的 `raise AssertionError(message)` 改回 `FAILS.append(message)` | `test_every_test_function_can_fail` 与 `test_assertion_helpers_raise` **双双 FAILED**；恢复后 **65 passed, 1 skipped** |
| C（词表单测） | 把 `check()` 的 `if not cond:` 改成 `if True or not cond:` | 该文件 pytest 转红（`assert 1 == 0`）；恢复后 **2 passed** |

三门都真的会红，不是装饰。

### 4. 本节遗留（如实申报，**未**完成）

- **`TestSuiteSizeIsMonotonic.N` 是人工登记的常量。** 新增测试忘了改它就会红——这是**有意的摩擦**（用例数变化必须有人签字，不能静默增加或减少），代价是并行改动时这个数会短暂失配。当前值 **405** 是 2026-10-31 01:05 前后实测的。
- **`TestNoCwdRelativeRepoPaths` 的正则只覆盖以 `Path(` 开头的字面量**，`os.path.join("src", ...)` 或字符串拼接绕得过去。这是**已知盲区**，取舍是宁可少判也不误判——误判会让人学会忽略这条门，那比漏判更坏。
- **`_raising_helpers` 的传递闭包靠字符串匹配 `f"{name}("`**。若辅助函数是经变量间接调用（`fn = check; fn(...)`），会漏判。同样是宁可少判的取舍。
- **本门只覆盖 `tests/test_*.py`**，`scripts/` 下的自检脚本不在范围内。

### 5. 纪律总结

> **测试代码在，不等于判定在。** 一个文件能被 pytest 导入、能显示 `passed`，和它真的在断言，是两件不同的事。
>
> 装门的成本远低于发现「门根本没通电」的成本。
