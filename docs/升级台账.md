## 实施记录

### A 基线冻结（完成）

**交付物**：`src/arkrag/legacy.py`（写保护）、`scripts/snapshot_baseline.py`（快照与校验）、`data/releases/legacy-baseline/manifest.json`、`gates.snapshot.json`、`metrics.json`、`docs/baseline-metrics.md`。

**为什么要有写保护**：A 阶段的核心承诺是"冻结现场"，而冻结只写在文档里等于没冻结——下一次跑 L5 就把 `graph.json` 覆盖了，基线从此无法复现。所以 `legacy.guard_write()` 在**代码层**拦住对 `graph.json` / `index/lexical.json` / `gates.json` / `circuit_open.json` / `cache/` 的写入，除非显式设 `ARKRAG_ALLOW_LEGACY_WRITE=1`。

**一次数据来源纠错**：`corpus_fp` 首次生成为 `None`。查明 `l0_manifest.json` 顶层键是 `['schema_version','source_dir','corpus_source','baseline','encoding','props','top_level_keys','reconciliation','dropped_files']`，**不含** `corpus_fp`；权威来源是 `data/arkrag/corpus_meta.json`。已改为从 corpus_meta 取，并让 markdown 渲染源仓库、release tag、ZIP sha256、源分类分布、丢弃文件清单。

### B 数据契约与严格回收（完成）

**B1 契约**（`src/arkrag/contracts.py`）：`ark-rag-task-2` / `ark-rag-extraction-2` 两套 schema，21 个机器可读错误码带字段路径。

关键修复：`entities` 不再用 `or []` 兜底。旧代码 `raw = {"entities": rec.get("entities") or [], ...}` 会把 `entities=""`、`entities=False`、`entities=None` **静默洗成空数组**，而空数组在旧校验里完全合法——于是"模型返回了坏数据"和"这一段确实没有实体"在收据上长得一模一样。现在 `""`/`False` → `WRONG_TYPE`，空 list → `EMPTY_COLLECTION`，两者都拒收。

**B2 严格回收**（`src/arkrag/agent_tasks.py`）：`HarvestResult` 十七口径，`hard_errors = conflicts + quarantined`，`complete = hard_errors==0 and missing==0`。

关键修复：旧代码 `got[cid] = rec` 让**同 id 的重复行"最后一行覆盖"**，`duplicates += 1` 只计数不报错。现在同 id 同内容记 `deduped`（合法），同 id 不同内容记 `conflicts` 并**两版都不入库**、写进隔离报告、退出码非零。

**B4 缓存身份**（`src/arkrag/cache.py`）：新键含 `content_key/chunk_id/scene_id/model/prompt_sha256/schema_version/generation`；`prompt_sha256()` 由实际提示词内容算出，不再靠人工改 `PROMPT_VERSION`。

旧键 `sha256(content_key|model|prompt_version)` 的失效形态：overlap 的两块正文相同 → `content_key` 相同 → 同一个键 → **用 A 块的抽取结果去建 B 块的边**。legacy 记录通过 `_legacy_record_is_safe()` 逐项核对身份后才复用，不相符返回 `layer="invalid"` 并带原因，不静默删除。

**风险 1 的处置证据**：`scripts/shadow_cache_check.py` 全量跑 13,786 块 → current 0 / legacy 13,781 / miss 5 / invalid 0，**可复用 99.9637%**。换键不会造成重抽灾难。5 个 miss 是全量 13,786 与 T1 13,781 的差集（`obt/guide` 5 块，D-18 已申报排除）。

**B3 状态口径**：所有"已入库"判断从"缓存文件存在"改为 `cache.is_cached_for_chunk()`（带 chunk_id 身份核对）。改动波及 `run_l3_agent.py --status`、`run_l5.py`、`run_l6.py`、`queue_status.py`、`prune_inbox.py`、`pack_pending.py`、`make_repair.py`、`qa_alignment.py`、`qa_evidence.py`、`qa_offenders.py`、`run_trial.py`。回归证据：`run_l3_agent.py --status` 输出 `合计 13781/13786 块已入库`，与 A 阶段基线一致。

### C 事务式构建与原子发布（完成）

**C3 原子写**（`src/arkrag/atomic.py`）：同目录 `.{name}.{pid}.{uuid12}.tmp` → flush → fsync → `os.replace` → fsync(dir)；`append_jsonl` 用 `O_APPEND` 单次写；`file_lock` 用 `<target>.lock`，超时抛 `TimeoutError` 而**不静默跳过**。

`gates.write_report()` 整段读-改-写包进文件锁。旧版无锁，两个 stage 并发写会各自读到旧内容、各自合并、后写者覆盖——先写者的行静默消失，报告看起来完整却少了一整个 stage 的门。报告损坏时改名 `{name}.corrupt.{ts}` 而非当空重来。

**C1/C2 Generation 与发布**（`src/arkrag/release.py`）：`generations/<gid>/` + `runs/<run_id>/` + `current.json`；状态机 `PREPARING→BUILDING→VALIDATING→READY→PUBLISHED`，任何状态→`FAILED`，只有 `READY` 能发布。

发布顺序固定：固定输入快照 → 建候选 → 算门禁 → **回读**候选产物 → 校验身份与内容摘要 → 全部硬门通过 → 原子替换 `current.json`。

**回读为什么不只比数量**：`index.content_digest()` 摘的是倒排内容本身（不是文件字节，因为 JSON 键序/缩进会让同一份索引有两份字节）；`index.probe_digest()` 用 10 条固定探针把检索排序摘要成一个值——数量全对、词条全对、但 slot 串了或分词错了，只有这一层能发现。

**C5 错误分类**（`src/arkrag/llm.py`）：旧代码 `fatal = exc.code in (401,402,403,429) or any(marker)` 把 **429 与鉴权错误归为一类**——一次限流就把整批任务判死。现在七类分开：AUTH 不重试+permanent 熔断；RATE_LIMIT 听 `Retry-After` + 第 3 次 transient；SERVER 第 4 次 transient；**NETWORK/CONTENT 重试但永不熔断**；RESOURCE 不重试。`circuit_state()` 过期返回 `None`（旧版读到文件就永久阻塞）。

**C5 有界队列**（`src/arkrag/extract.py`）：`futures = {pool.submit(...) for c in chunks}` 一次性提交 13,781 个任务，内存与在途峰值都不受控，且熔断后无法停止投喂。现在 `window` 是待处理队列上限，熔断立即停止补充，剩余块记 `skipped_circuit`（「没跑」与「跑失败」在收据里分开）。

**故障注入覆盖**（`tests/test_release.py::TestFaultInjection`）：构建半途中断 / 门禁 FAIL / 回读损坏 / 写 Manifest 中断 / 发布前终止 / 发布后写报告失败，六种全部验证 `current` 仍指向旧有效 Generation 或根本不存在。

## D 阶段：解析分块指纹与证据身份（候选已构建，未发布）

### 为什么必须先修两个"不报错"的 bug

D1/D2 改的不是风格，是**旧代码会把内容丢掉而门照样 PASS** 的两处：

**D1 轮次实例身份**。旧 `chunk.py` 拿 `node_id` 当轮次唯一键（`if turn["node_id"] in seen: continue`）。`node_id` 会缺失（实测 **201 轮 id 为 0，分布 201 个场景**），也会重复；同编号不同正文的两轮只剩一轮，且没有任何一处报错。更糟的是旧 L2 覆盖率门也用 `node_id` 当基准，分子分母一起少，门恒 PASS。现在实例身份改用**场景内序号 `ordinal`**，块记录带 `turn_ordinals` / `node_ids` / `turn_spans`；新增 `L1.8`（缺失，仅申报）与 `L1.8b`（同场景同编号且正文不同 → FAIL）把「缺失」与「身份冲突」分开报，`L2.1c` 按轮次实例逐轮核对块内顺序与正文。

**D2 超长尾块**。旧尾块长度用 `"".join(line for line, _ in buf)` 测量（**不含 `\n`**），而落盘用 `"\n".join(...)`。两把尺子差「行数-1」个字，于是每行都参与计费的短行数量被系统性低估。后果：**17 个文档各有一块本应独立的合格尾块（真实 121–125 字，均 ≥ `MIN_CHARS`=120）被误判为短块并合进前块**。新代码统一用 `_render_len()`（= `len("\n".join(...))`）测量，并新增 `MAX_CHARS`（= 2×TARGET = 1800）硬上限，尾块处置写进块记录 `tail_action` ∈ {`merged`/`rebalanced`/`kept_short`}、短块必须写 `short_reason`。配套门：`L2.2 短块必须有书面原因`（无原因短块必须为 0）、`L2.3 最大块 <= 硬上限`。

### 可证明复用层（能力已实现，本轮无对象可复用）

`cache.adopt_legacy(src_record, chunk, model, *, generation=0)`：仅当 **content_key + scene_id + model + prompt_sha256 四项逐项相等**、且 raw 过 `contracts.validate_extraction()` 时才写一条新键记录，记录里写明 `adopted_from=<legacy 缓存键>` / `adopt_reason="identical_content"` / `adopted_at`。`Lookup.layer` 因此多一层 `"adopted"`，**单独上报，不混进 `current` 冒充本轮抽取产出**。

线上世代 `g-20261030T114823Z-606ea9` 建于 D3 **之前**，它的 index meta 只有
`graph_fp=f90a78f6df41f564`，缺 `graph_artifact_id` / `prompt_sha256` / `vocab_sha`。
这不是判据写错了，是判据收紧后**暴露出来的真实审计缺口**：

- `graph_fp` 是"建图配置指纹"——同一份配置重建两次图，指纹相同，**产物未必相同**。
  所以 `graph_fp` 相等**不能**证明这份倒排挂在某一具体图文件上。
- 缺 `graph_artifact_id` 就意味着：若图文件在盘上被替换（哪怕只是重新 dump 一次、
  键序变化、某条边被人工修正），没有任何字段能发现索引已经对不上了。
  线上服务会拿旧倒排去查新图，答案错而无人知晓。
- `prompt_sha256` / `vocab_sha` 同理：它们证明"这批倒排是这份提示词与这份词表抽出来的"。
  缺了它们，事后无法回答"这条检索结果为什么长这样"。

所以这个缺口必须关——它不是格式洁癖，是**线上产物无法自证身份**。

### 代码改动

**1. 来源状态的单一事实源（`src/arkrag/source.py`、`scripts/build_generation.py`）**

`build_generation.py` 原本 `source_status` 从 `corpus_meta.json` 读。但冻结的
`corpus_meta.json`（153 B，D4 之前的产物）**没有这个字段**，于是
`corpus_meta.get("source_status", "source_unverified")` 把一份实际已验证的语料判成未知来源、
拒绝构建。**缺字段 = 这个文件里没写，不等于"没验证过"。**

改为：权威取 `source.status_for_build()`（读 `data/arkrag/source_verification.json`，
即**产出验证的地方**写的那份记录），`corpus_meta.json` 里的同名字段只作兜底与交叉核对。
理由是副本不配当权威：它会过期（L0 重跑后不更新）、会串味（产物搬家时副本跟着走而记录没跟着）、
**会缺字段（就是这次的 bug）**。

两份不一致时**不许静默取一边**：新增 `source.resolve_for_build()` 把它当成一次需要登录的事件——
`conflicts` 列出两边的原值，结论取**更保守**的那侧（`strength` 表定义 `source_unverified < verified_tree < verified_zip`），
调用方把冲突打到 stderr 并写进 run 事件的 `snapshot` 阶段。取保守的理由：两边不一致本身
就说明有一个产物在说谎，在能证明之前按弱的申报不会高估来源可信度。

顺带修了一处同源缺陷：`VERIFICATION_PATH` 原是模块级常量（`config.DATA_DIR / …`），
import 时就把路径烧死了，**测试把 `DATA_DIR` 重定向到临时目录也对它无效**——
读到的永远是真实仓库那份记录，于是"来源状态"在测试里成了真值的回声。
已改为 `verification_path()` 函数，跟随重定向。

**2. 状态强度用精确匹配，不用 `strip()`**

`strength()` 起初写成 `_STRENGTH.get(status.strip(), 0)`，新测试当场抓到它把
`"verified_zip "`（尾空格）算成强度 2——一个笔误就能把状态抬成"已验证"。
改为精确匹配，不 strip、不 casefold：未知拼写、大写、缩写、尾空格一律按 0（最保守）。
要用宽容归一化的话该在**写入端**做，并且归一化本身也得有记录，不是在读取端猜。

## 来源门的白名单修复（D4 收尾）

### 漏洞：发布门只拒绝了一个字面量

`src/arkrag/release.py` 的 `verify_generation()` 里，D4 的来源检查原先写成：

```python
if (manifest.get("source_status") or "") == "source_unverified":
```

**它只拒绝这一个拼写。** 而 `src/arkrag/source.py` 的 `strength()` 是保守的**白名单**：
只认 `verified_zip`（强度 2）、`verified_tree`（强度 1），其余一律按 0（未验证）。

于是两个模块对"什么算已验证"各有一套判据：`source` 用白名单，`release` 用黑名单（且只列一项）。

### 机检证明的不一致（逐值对照）

`release拒绝` = `verify_generation()` 是否报出 `source_status` 问题；`source认定已验证` = `strength()` 是否 > 0：

```
'source_unverified'  release拒绝=True   source认定已验证=False  一致=True
'verified_zip'       release拒绝=False  source认定已验证=True   一致=True
'verified_zip '      release拒绝=False  source认定已验证=False  一致=False
'VERIFIED_ZIP'       release拒绝=False  source认定已验证=False  一致=False
''                   release拒绝=False  source认定已验证=False  一致=False
'verified'           release拒绝=False  source认定已验证=False  一致=False
'bogus'              release拒绝=False  source认定已验证=False  一致=False
```

只有两行一致，其余五行全部错位。即：把 `source_status` 写成**空串、大写、尾空格（笔误）、缩写、或任何瞎写的值，都能通过发布门**。

### 为什么这不是理论风险

`resolve_for_build()` 在副本与权威不一致时**取更保守的一侧，并把原值原样带出**。实测
`resolve_for_build({"source_status": "verified_zip "})` 返回 `status='verified_zip '`、`verified=False`，
且 `conflicts` 里记了这次不一致。

也就是说：这个带尾空格的值会**一路写进 Manifest**，而旧门看到它不是 `"source_unverified"` 就放行。
**保守判断在上面，宽松判断在下面，两者正好抵消**——D4 建立的那层保护被下面这道门原地作废。
这也说明单靠"某一处判得严"不构成保证：只要链路上有一处松，结论就是那处最松的。

### 修法：改成白名单，与 `source` 共用常量

```python
_source_status = manifest.get("source_status") or ""
if _source_status not in (source.VERIFIED_ZIP, source.VERIFIED_TREE):
    problems.append(
        f"source_status={_source_status!r}：语料来源未能验证，"
        f"按计划 D4 不得作为 Release 发布"
    )
```

- `release.py` 的导入加 `source`，判据直接引用 `source.VERIFIED_ZIP` / `source.VERIFIED_TREE`，
  **不再手抄字面量**——表只有一张，改一处即两处同时生效。
- 报错信息用 `{!r}` 把实际值原样露出。尾空格、换行这类**看不见的字符必须能被看见**，
  否则收据上只会看到"来源未验证"却查不出到底是哪个拼写。

### 新增测试

`tests/test_release.py::TestVerify` 加两个参数化用例：

- `test_any_unrecognized_source_status_blocks_release`，参数
  `["source_unverified", "", "VERIFIED_ZIP", "verified_zip ", "verified", "verified_zip\n", "bogus"]`
  —— 7 个取值全部必须被拒。
- `test_recognized_verified_status_passes`，参数 `["verified_zip", "verified_tree"]` —— 必须放行。

`test_any_unrecognized_source_status_blocks_release` 的 docstring 写明判据：

> 门必须是白名单。只拒绝字面量 `"source_unverified"` 的写法等于没有门：把状态写成
> `""`、`"VERIFIED_ZIP"`、`"verified_zip "` 这些同样**不是已验证**的取值，全都绕得过去。
> 判据与 `source.strength()` 必须是同一张表。

### 一类反复出现的缺陷模式（本阶段第三次）

这一阶段已经出现三次同类问题，三次的形态不同、机理相同：

| 次数 | 同一判定被写了两份 | 后果 |
|---|---|---|
| A 阶段 | 冻结清单与写保护清单各写一份 | 漂移（11 项 vs 4 项），**冻结产物被覆盖** |
| D4 | `corpus_meta.json` 副本与 `source_verification.json` 权威各算一次 | 副本缺字段 → 被当成"未验证" |
| D4 收尾 | `release.py` 与 `source.py` 对"已验证"各有一套判据 | 门只守一个拼写 → **门形同虚设** |

**共同机理：同一个判定在两处各写一份，只要有任意一处较宽松，整套检查就等于那处最松的。**
两份拷贝不会互相校验，它们只会各自漂移；而执行路径上先遇到哪一份，就按哪一份的宽严执行。

对应的纪律：**判定只能有一处事实源，其余地方必须引用它而不是重写它。**
能不能引用是设计问题（常量放在无依赖的模块里），愿不愿引用是纪律问题——写了引用就改不动另一份，这才是可机检的约束。

### 本节遗留：**已关闭**（2026-10-31）

原来的遗留项是：

> 上述三项回归只覆盖"当前状态"，没有为"来源门"补一条**长期**机检：
> `release.py` 里若有人再次手抄字面量而非引用 `source.VERIFIED_*`，现有测试仍会通过
> （因为取值恰好相等）。要拦住这种回归需要一条静态检查（如扫描 `release.py` 中
> 出现 `"verified_zip"` 字面量即失败），本轮未做。

**现已关闭。** 关闭方式是静态检查，不是再加一条行为测试——行为测试根本拦不住这类回归：
把 `source.VERIFIED_ZIP` 改回手抄的 `"verified_zip"`，取值恰好相等，所有行为断言照样通过。

新的守卫位置：`tests/test_single_source_of_truth.py::TestSourceStatusHasOneDefinition::test_only_source_module_declares_status_literals`，
扫描 `src/arkrag/*.py` 与 `scripts/*.py`（`source.py` 除外）中是否出现
`"verified_zip"` / `"verified_tree"` / `"source_unverified"` 字面量。

关闭过程本身也抓出了真实残留（下一节第 1 项）：`release.py` 的两处**默认值**仍是手抄字面量。

**这条静态门只看代码、不看注释。** 注释里提到历史字面量是必要的、不该被判违规——
`gates.py` / `release.py` 现在都留着一句"手抄的后果已经发生过"的注释，那是解释判据为什么长这样，
删掉它才是损失。测试用 `_code_part()`（按 `#` 切分取左半）只检查代码部分。

唯一被放行的代码形态是"把字面量当**数据值**记录"（`reason=` / `note=` / `message=` 位置上，
例如 `run.finish(reason=...)`），那不是判定，是写原因文本。

## 单一事实源加固与门禁可失败性（D4 收尾续）

上一节把"判定只能有一处事实源"写成了纪律，并把"没有静态检查拦住手抄字面量"列为遗留。纪律靠人守，人会被进度和"就这一处应该没事"说服；于是本轮把纪律换成机检（第 1–3、6 项），并补上一件更基础的事：**门禁本身要能被证明会失败**（第 4–5 项）。一条恒 PASS 的门比没有门更糟，它会让人以为这件事被检查过了。

### 1. 静态防回归测试，首次运行就抓出两个真实遗漏

新建 `tests/test_single_source_of_truth.py` 后首次运行，2 项失败，报出：

```
release.py:185: source_status: str = "source_unverified"
release.py:208: source_status: str = "source_unverified",
```

两处都是**默认值**仍在手抄字面量。默认值恰恰是最容易漏的地方：它决定了"没写等于什么"，写错方向就是让未知冒充已验证。已改为引用 `source.UNVERIFIED`（现 `release.py:187` / `release.py:210`）。

同一轮还有一项失败是**测试自己的判定写错了**：先剥掉注释、却又拿原行去比对，于是把注释里解释历史缺陷的文字当成了违规。已改为只检查代码部分 `_code_part()`。测试自己也会错，这条一并记下——否则下一轮的人会以为"静态门红了就一定是代码错"。

### 2. 另外两处判定一并统一到常量

三条约束的共同点：**它们检查的是"形状"，不是"某次运行的结果"**。取值恰好相等的回归，行为测试拦不住，形状检查能。

一个仍然存在的限制照实写下：`_code_part()` 靠按 `#` 切分来剥注释，字符串里含裸 `#` 的行会被切错。这里刻意**宁可少判**（漏掉一行注释）也**不误判**（把注释当违规）——误判会让人学会忽略这条测试，那比漏判更糟。仓库当前没有这种怪例，测试文件里也写明了这个取舍。

## D 阶段两个隐形缺陷（2026-10-31）

本轮复核的两个缺陷都不是"功能少做了一块"，而是**校验机制本身在给出错误结论**：一个让身份字段静默退化，一个让测试套件在 CI 里报绿。二者叠加的后果是"线上看着全绿、覆盖实际大面积塌陷"。记在此处，避免后当成小修小补。

### 1. 缺陷一：ordinal 退化成块内下标

**机制（读码 + 实测）。** `src/arkrag/chunk.py` 的 `turn_ordinal(turn, fallback)` 在轮次上找不到 `ordinal` 时退回调用方传入的 `fallback`；而 `_dedupe()` 与 `turn_spans` 两处都用 `enumerate(buf)` 的结果当 `fallback`——那是**块内下标**，不是场景级轮次序号。

**触发条件（实测）。** 冻结基线 `data/arkrag/scenes.jsonl` 的轮次键集实测为 `['kind','masked','node_id','prop','speaker','text']`，**没有 `ordinal` 字段**（该文件由旧版 `parse.py` 生成）。于是 `fallback` 路径是常态而非例外：每一块的轮次序号都从 0 重新起数。

**后果（实测规模）。** 停用补齐后重跑冻结语料：**2,291 个场景中 2,127 个轮次覆盖不全，占 92.8%**。典型例 `activities/a001/level_a001_01_beg` 共 89 轮，结果只覆盖 47 轮。切块越碎、场景越长塌陷越重——块内 `turn_ordinals` 恒落在 `0..块长-1`，前后块的序号互相重叠。

**修复。** `chunk.py` 新增 `_with_ordinal(turn, index)`，`split_scene` 在入口一次性补齐**场景级** ordinal：

```python
items = [(render_turn(t), _with_ordinal(t, i)) for i, t in enumerate(scene["turns"])]
```

`_with_ordinal` 返回浅拷贝，不改入参；上游已写 `ordinal` 时以其为准。`turn_ordinal` 的 docstring 补记了这次踩坑，写明 `fallback` 必须是场景级序号而非块内下标。

**修复后（实测）。** 2,291 场景覆盖不全降为 **0**。与冻结基线逐块比对：13,786 个同 `chunk_id` 的块中 **13,769 个正文与 `content_key` 完全一致**；余下 17 个正是 D2 尾块硬上限修正所改（新正文均为旧正文的严格前缀，旧约 978–1008 字符、新约 853–894 字符），另新增 17 个 `chunk_id`，故块数 13,786 → 13,803（其中 `obt/guide` 5 块，非 guide 13,798）。

> 口径说明：曾表述为"分块文本与冻结基线完全一致（差异 0）"，实测只对**剔除 D2 修正这 17 块后的 13,769 块**成立；D2 的 17 块是**有意**的正文变化，不是回归。

### 2. 缺陷二：`tests/test_negative.py` 在 pytest 下假通过

**机制（读码）。** 该文件的 `expect(cond, message)` 原实现只做 `if not cond: FAILS.append(message)`，`FAILS` 仅在 `main()` 结尾被读取打印。pytest 收集到的每个 `test_*` 都正常返回，**不产生任何断言失败**，于是全部计为通过。

**症状（实测，同一份代码）。**

| 调用方式 | 结果 |
|---|---|
| `py -3 -m pytest tests/test_negative.py` | **11 passed** |
| `py -3 tests\test_negative.py` | **1 条 FAIL**（「有轮次未被任何块覆盖」） |

即 CI 长期是绿的，而缺陷就躺在被断言保护的路径上。**上面那个 ordinal 缺陷能躲这么久，一半原因在这里**：唯一能抓住它的负例，在 pytest 口径下根本不发声。

**修复。** `expect()` 改为 `raise AssertionError(message)`；`main()` 逐个 `try/except AssertionError` 收集，保证单文件直接运行时一次看到全部失败，而不是首个失败即中断。

**反向验证（实测）。** 临时把 `if not cond:` 改成 `if True or not cond:` 注入失败：pytest 报 **11 failed**、直接运行 **退出码 1**，两者口径一致。修复后 `py -3 tests\test_negative.py` → 「负例测试 10/10 PASS」，退出码 0。

### 3. 新增回归门 `tests/test_chunk_ordinal.py`（9 项）

三个测试类守三件不同的事：

| 测试类 | 守什么 | 关键断言 |
|---|---|---|
| `TestOrdinalIsSceneScoped` | ordinal 必须是场景级 | 多块场景覆盖等于 `set(range(40))`；每块 ordinals 是场景级连续区间；`split_scene` 不得就地改入参；上游已写 ordinal（用 100/101/102 验证）必须尊重；同 `node_id` 不同正文的两轮都要保留 |
| `TestCoverageGateCatchesDegradation` | 门自己不能跟着一起错 | 正常块喂 `L2.1a` 必须 PASS 且 `measured` 含 `漏 0 篇`；把每块 `turn_ordinals` 人为改成块内下标后，`L2.1a` 必须 **FAIL** |

## 测试套件卫生门（2026-10-31）

> 一句话结论：**测试代码在，不等于判定在。** 这个门不是为了让测试变多，是为了让"绿"这个字有内容。

### 1. 触发原因：从一个假通过查到一类假通过

起因是修 `tests/test_negative.py` 的假通过：它的 `expect()` 只做 `FAILS.append(message)`、不抛异常，于是 **pytest 报 `11 passed`，而单文件直接运行报 1 FAIL**——两个口径给出相反的结论。

修完立刻意识到：**同类问题可能不止一处**。于是不再逐个人工看，而是系统性核查了 `tests` 目录下全部 **15 个** `test_*.py` 文件的 pytest 收集数（核查当时为 15 个；本门落地后 `tests` 下现存 16 个 `test_*.py`，多的那个就是 `test_suite_hygiene.py` 本身。另有 `conftest.py` 为夹具，始终不在其列）。核查结果：`tests/test_vocab.py` 是 **0 个用例**——它当时只有 `main()`，pytest 收集到 0 项，却和"全部通过"看起来一样。

这正是卫生门存在的理由：**0 个用例的报告与 100% 通过的报告，长得一模一样。**

### 2. 新建 `tests/test_suite_hygiene.py`：四类检查

| 类 | 测什么 | 判据 |
|---|---|---|
| `TestEveryFileIsCollected` | 每个 `tests/test_*.py` 必须能被 pytest 收集到用例 | 文件里必须有 `def test_` 或 `class Test`；`conftest.py` 作为夹具由 `HARNESS_FILES` 显式排除，不参与该判定 |
| `TestAssertionsActuallyRaise` | 断言必须真能失败 | 两层判据，见下 |
| `TestNoCwdRelativeRepoPaths` | 测试不得依赖 cwd | 正则扫相对仓库路径字面量；该文件对自己 skip 并写明理由 |
| `TestSuiteSizeIsMonotonic` | 用例总数不能静默变少 | 登记常量 `N`（**当前 `936`**，未提交，对应 2026-10-31 16:57 实测的 `936 tests collected`），用子进程跑 `pytest --collect-only` 数实际值比对。`N` 追的是「collected」，测试基线表追的是「passed」，两者必须同时更新，只改一个就会红 |

`TestAssertionsActuallyRaise` 的两层判据是关键，缺一层都会漏：

1. **辅助函数层**：名字像断言辅助的函数（`expect` / `check` / `verify` / `require` / `assert_*`）函数体必须有 `raise` 或 `assert`。这一层抓的是 `expect()` 那种"只记不抛"的形态。
2. **调用层**：每个 `def test_*` 要么自己含 `assert`/`raise`，要么调用了**能抛异常的**模块级函数。且该判定要做**传递闭包**——`test_vocab()` 本身没有 `raise`，它调 `_check_all()`，`_check_all()` 调 `check()`，`check()` 才 `raise`。**只看一层会把这个正当结构误报成违规**。

`TestNoCwdRelativeRepoPaths` 的来历也是一次实测教训：`test_vocab.py` 原用 `Path("src/arkrag/vocab.py")`，从别的目录运行就 `FileNotFoundError`。现在改成 `ROOT = Path(__file__).resolve().parents[1]` 拼绝对路径。

### 3. 反向验证：证明这道门真能红

只证明"好代码能过门"的门，会在门与实现一起变错时照样绿灯。故做了注入实测：

| 注入 | 做法 | 结果 |
|---|---|---|
| A | 新建一个只有 `main()`、没有 `test_*` 的 `tests/test_inject_empty.py` | `test_file_has_pytest_visible_tests` 与 `test_declared_count_matches_actual` **双双 FAILED** |
| B | 把 `tests/test_negative.py` 的 `raise AssertionError(message)` 改回 `FAILS.append(message)` | `test_every_test_function_can_fail` 与 `test_assertion_helpers_raise` **双双 FAILED**；恢复后 **65 passed, 1 skipped** |
| C（词表单测） | 把 `check()` 的 `if not cond:` 改成 `if True or not cond:` | 该文件 pytest 转红（`assert 1 == 0`）；恢复后 **2 passed** |

三门都真的会红，不是装饰。

### 4. 本节遗留（如实申报，**未**完成）

- **`TestSuiteSizeIsMonotonic.N` 是人工登记的常量。** 新增测试忘了改它就会红——这是**有意的摩擦**（用例数变化必须有人签字，不能静默增加或减少），代价是并行改动时这个数会短暂失配。git 里的登记史是 `425 → 676 → 680 → 717 → 826 → 936`，**每变一次都随一次真实交付**，没有一次是静默增加的。当前 **936** 是未提交状态（对应 2026-10-31 16:57 实测的 `936 tests collected`）。**本行只报告从 git 读到的事实，不声称观察过某次变红的过程**——注入 A 才是这条门变红的实测证据（见上表）。若哪天真要靠调低 `N` 才绿，那是有人在删测试，不是这条门错了。
- **`TestNoCwdRelativeRepoPaths` 的正则只覆盖以 `Path(` 开头的字面量**，`os.path.join("src", ...)` 或字符串拼接绕得过去。这是**已知盲区**，取舍是宁可少判也不误判——误判会让人学会忽略这条门，那比漏判更坏。
- **`_raising_helpers` 的传递闭包靠字符串匹配 `f"{name}("`**。若辅助函数是经变量间接调用（`fn = check; fn(...)`），会漏判。同样是宁可少判的取舍。
- **本门只覆盖 `tests/test_*.py`**，`scripts/` 下的自检脚本不在范围内。

### 5. 纪律总结

> **测试代码在，不等于判定在。** 一个文件能被 pytest 导入、能显示 `passed`，和它真的在断言，是两件不同的事。
>
> 装门的成本远低于发现「门根本没通电」的成本。

## G 阶段：最小可用检索问答闭环（2026-10-31）

> 一句话结论：**闭环通了，指标没达标。** 这两件事必须分开写——「能跑通」证明链路存在，「达标」证明链路的每一环都对，而本轮只证明了前者。

事实源：`docs/g阶段实测.md`（本节所有数字的出处，本机实测，非估算）。

### 1. 做了什么：无向量六步闭环

`查询理解 → BM25 词法检索 → 有界图扩展 → 上下文组装 → 抽取式回答 → 引用校验`，对应 `src/arkrag/query.py` / `retrieve.py` / `answer.py` 加 CLI `scripts/ask.py`（单问 + `--evaluate --gold-set`）。

**为什么先不做向量**——两个硬约束，不是偷懒：

1. **本机没有 LLM 端点**（`ARKRAG_LLM_BASE_URL` / `ARKRAG_LLM_MODEL` 均为空，`arkrag.llm` 缺配置直接抛 `RuntimeError`），也没有 embedding 后端（`index.py` 至今写着 `vector_channels=not_built_no_embedding_backend`）。
2. **抽取式回答器保证离线可测**：只把已抽出的断言拼成句子、不生成新文本，于是整条链路可以在无网络、无模型的条件下被真实数据反复跑。`LLMAnswerer` 已写好但**默认不可用**。

这个选择有代价，且代价记在 §5 遗留第 1 条：方向题判据对抽取式偏松，接 LLM 后要重新定义并重跑基线。**先落地一个能在离线环境里被证伪的闭环，好过一个只能靠外部服务才能验证的「架构已就绪」。**

### 2. 首个真实基线（320 题，世代 `g-20261031T035231Z-4eafae`）

| 指标 | 实测 | F4 目标 | 达标 |
|---|---|---|---|
| Recall@20（精确块） | **0.6575** | ≥ 0.90 | ✗ |
| Recall@5（精确块） | **0.4658** | ≥ 0.75 | ✗ |
| MRR | 0.4123 | 建基线 | — |
| 引用定位正确率 | **1.0000**（1543/1543） | ≥ 0.98 | ✓ |
| 关键事实引用覆盖率 | **0.1567** | ≥ 0.95 | ✗ |
| 无依据拒答正确率 | **0.8406** | ≥ 0.90 | ✗ |
| 方向题正确率 | **0.6667** | ≥ 0.95 | ✗ |
| 引用校验硬失败 | **0** | 0 | ✓ |

**未达标是五项，不是「个别指标待优化」。** 按目标行计：R@20、R@5、引用覆盖率、拒答、方向题共 **5 个 ✗**（若把 R@20/R@5 合并算作「Recall 一项」，则是 4 项未达标——两个口径我都写出来，避免下一个人拿「四项」去对表时以为漏了一行）。达标只有两项：**引用定位 1.0000**（1543 条引用全部逐字命中，说明证据偏移是可定位的）和 **引用校验硬失败 0**。

### 3. Recall 未达标的归因：两条都要写，缺一条就是甩锅

#### 3.1 gold 块粒度口径能解释一部分，但不足以解释全部

Gold Set 的 `gold_chunk_ids` 取「断言所在的块」。同一 doc 被切成多块时，人看相邻块是同一条证据，指标算 0。把口径改成「同 doc 任一命中即算该 gold 块被覆盖」（**分母仍是 gold 块数，不是命中数**）后，合计 R20 从 **0.6575 → 0.7644**。

**但 0.7644 仍低于 0.90。** 所以不能把未达标归咎于判据——判据最多解释约 0.11 的差距，剩下的 0.14 必须记在检索头上。分类对照表（八类 × 6 列）见 `docs/g阶段实测.md` §3.1，这里只留结论。

#### 3.2 主因是检索本身（同 doc 口径下仍低的三类）

| 类别 | R20（同 doc） | 为什么低 |
|---|---|---|
| `multihop` | **0.5000** | 多跳题的自然证据常在**中间实体**的块，不在查询实体所在块。而当前图扩展**只走 `out`**，且 `max_degree_per_entity=20` 在稠密实体上很快耗尽 |
| `adversarial` | **0.3125** | 问的是「两个名字是不是同一实体」，自然目标是实体/别名表，不是剧情块。用块级 BM25 检索这个通道**本质上是错的** |
| `direct_relation` | **0.7500** | 两端实体常在大量块中共现，块级打分被热门块主导 |

三类低分**恰好是同一类**：都需要图扩展或实体精确通道。处置是**等 I 阶段手段**——`adversarial` 走 I1 的 entity/name exact matches，`multihop` 走 I1/I2 的多跳路径加权与 RRF 融合。

**在此之前不调 F4 阈值、不放宽「相关」定义。** 那两件事都是计划明令禁止的，而且它们的效果是「指标好看、系统没变好」。

#### 3.3 `q-dr-000001` 逐层取证：排序问题，不是数据问题

问「凯尔希」对「伊利亚」是什么关系，gold 块 `obt/main/level_st_17-01#001`。实际 `hits[:8]` 里**同一 doc 的 `#002` / `#003` 都在，`#001` 不在前 20**。图里该关系存在、断言证据可逐字定位、邻接也在前 20 内。

这条取证的用处是**排除掉一类错误归因**：如果只看到「gold 块没进前 20」就去查抽取、查分块、查图，会白查——数据是好的，是排序把它排下去了。**「检索没捞到」不等于「库里没有」，这两句必须分开验证。**

### 4. 三个真缺陷（本节的正文，机理 + 修法 + 修复前后实测）

这三个都不是「代码跑不起来」，而是**代码跑得起来、结果看着合理**的缺陷。这类缺陷只能靠「喂坏输入必须变红」抓出来。

#### 4.1 `retrieve.py`：单实体预算耗尽，终止了整个图遍历

```python
if per_entity_taken[node_id] >= max_degree:
    truncated_reason = ...; stopped = True; break
```

`stopped = True` 本意是「这个节点不展开了」，但它同时让外层 `while frontier` 退出——**第二个种子实体的边从未被展开**，`nodes_visited = 1`。单实体问句碰不到，**多实体问句必踩**。

修法：只 `break` 当前节点的循环，不置 `stopped`。修复前后实测：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `nodes_visited` | 1 | **2** |
| 边数 | 20 | **40** |
| 断言数 | 100 | **194** |

#### 4.2 `answer.py`：claim 排序完全不看问句问的是谁

原排序键 `(-unit_score, -support_count, assertion_id)`，而 `unit_score` 是**块级** BM25 分——热门块里的所有断言被同一个高分一起抬高。实测 `凯尔希 隶属 罗德岛`（`support_count` = 54）排到第 **12**，被 `max_claims=5` 截掉，答案里全是同一块带来的旁支闲聊。

修法：新增 `focus_tier` 三档——**0** = 两端都是问句候选实体、**1** = 只有一端、**2** = 都不是；排序键改为 `(focus_tier, -support_count, -unit_score, assertion_id)`。

**必须强调这是排序不是过滤。** 第 2 档仍留在 `accepted` 里、引用照旧给出。若把它当过滤砍掉，「问 A 与 B 但答案需要 C 作中间人」的多跳题会被直接砍断——那就从「排序不准」升级成「答案缺失」，更难被发现。

#### 4.3 `scripts/ask.py --limit`：局部评测只覆盖了一个类别

原实现是 `items[:limit]`，而 `gold-v1.json` 里 `single_chunk` 排最前（64 条）。于是 `--limit 40` / `--limit 50` **只测到 `single_chunk`**，报告照常打印七项指标，看起来是「局部很好」，实际多跳/对抗/时间冲突**一条都没跑**。

**少跑类别不会报错，只会让数字变好看。** 这是最危险的一类缺陷：没有异常、没有警告、没有红。

修法：改为分层配额抽样（`_stratified_sample`，**固定种子**保证可复现）。实测分布：

| `--limit` | 取到 | 类别数 | 分布 |
|---|---|---|---|
| 1 | 1 | 1 | single_chunk 1 |
| 8 | 8 | 8 | 每类 1 |
| 40 | 40 | 8 | sc 7 / al 6 / dr 6 / mh 6 / cc 4 / tc 4 / na 4 / ad 3 |
| 120 | 120 | 8 | sc 23 / al 18 / dr 18 / mh 18 / cc 12 / tc 12 / na 12 / ad 7 |
| 320 | 320 | 8 | 与池完全一致 |

**边界取舍**：`limit` 小于类别数时**不每类保底**——否则 `--limit 1` 会返回 8 条，评测规模不再等于用户要的规模。按池大小取前 `limit` 个类别各 1 条。

### 5. 我自己的一个判断错误（如实记录）

第一次量「同 doc 口径 Recall」时，我把分子算成**命中数**而非**被覆盖的 gold 块数**，得出 **1.9489** 这种不可能的值（Recall > 1）。

发现的路径不是查代码，是**看见 1.9489 这个数不合理**。改成「分母 = gold 块数、分子 = **被覆盖的 gold 块数**」（同一个 gold 块被多个 hit 命中只算一次）之后，才得到 0.7644。

**教训写在这里**：指标出现 > 1，就是口径错了，**不要当成「检索很好」**。一个带着 1.9489 的基线如果被当成好消息存档，后面所有基于它的判断（包括「要不要调阈值」「要不要改通道」）全是错的。这条和本轮另外两个陷阱（`--limit` 只测一类、`focus_tier` 排序被当成过滤）是同一族：**数字看着对，于是没人查。**

### 6. 本节遗留（五条，如实申报）

1. **抽取式 ≠ 生成式。** `--evaluate` 的「方向题正确率」判据是「标准谓词是否出现在答案文本里」，对抽取式**偏松**（谓词本来就是抽出来的）。接入 LLM 后该指标含义会变，**必须重新定义并重跑基线**，不能拿 0.6667 直接和历史对比。
2. **Recall 只在 300/320 题上可算。** 20 条 `negative_abstain` 没有 gold 块，如实跳过、未做任何填充。
3. **`adversarial` 与 `multihop` 的低 Recall 不是调参能解决的。** 要等 I 阶段的实体精确通道与多跳路径加权（§3.2）。本轮不做临时补丁。
4. **引用覆盖率的瓶颈是上下文 token 预算，不是 `max_claims`（这条原写错了，实测推翻后已改）。** 原判据写「`max_claims=5` 只陈述 5 条事实，所以覆盖不全」——听起来合理，实测是错的：`max_claims` 从 5 提到 12、30，覆盖率只从 0.1567 变成 0.1600 / 0.1600。逐层追踪 428 条 `required_citations`：出现在 `hits[:20]` 260 条（60.75%）、进入上下文 `units` 只有 **158 条（36.92%）**、最终被引用 122 条（28.50%）。**从 260 掉到 158 就是瓶颈**：题干平均产生 **42.6 个候选单元**，而 `max_context_tokens=6000` 只容得下平均 **4.7 块**（80 题样本被预算砍掉 3,034 块）。预算放大效果显著但成本同涨：20000 → 上下文含全部 required 0.3933→0.5400、60000 → 0.7000（平均 35.8 块）。**处置**：不在本轮调大预算（延迟与成本同步上涨），正确做法是 I 阶段先用 RRF + 重排把 42.6 个候选压到 10–15 个高相关的，再定预算；在此之前该指标如实记未达标、`max_context_tokens` 保持默认值。
5. **`required_citations` 与引用的「证据粒度」定义不一致。** 判据是「块 id 相符**且** required 的 evidence 是引用 evidence 的子串」。实测大量失败是**同一块、同一句话、只是切口不同**——required 存带说话人前缀的整行（`角峰：我也是奉命办事…`），引用存抽出的片段（`前方是机密仓库…`）。这是 F3 生成侧与 G6 抽取侧的口径分歧，需在 F4 层统一，不是检索缺陷。

### 7. 纪律总结

本轮**四次**「数字看着对」的陷阱——**Recall 口径算错（算出 1.9489）、`--limit` 只测一类、`focus_tier` 排序被当成过滤、覆盖率归因到 `max_claims`**——没有一次是代码跑不起来。四次都是**结果看起来合理，于是没人查**。第四次尤其值得记：归因错误比数字错误更难发现，因为一个自洽的解释会让人停止追问，而它只需改一个参数就能证伪。

所以每条修复都配了「喂坏输入 → 必须变红」的用例，而不是只测「好输入能过」：

| 缺陷 | 反向用例 | 证明什么 |
|---|---|---|
| Recall 口径 | 分母/分子定义写进文档并要求可复算 | 指标 > 1 即口径错，必须能被发现 |
| `--limit` 只测一类 | `test_ask_sampling.py::test_small_limit_does_not_collapse_to_one_category`、`::test_rarest_category_is_never_dropped` | 小 `limit` 不许塌缩到单一类别；最稀有类别不许被丢 |
| `focus_tier` 被当过滤 | `test_answer.py::TestFocusTierOrdering::test_non_focus_claims_are_not_discarded` | 第 2 档仍在 `accepted`，多跳不断链 |

> 与「测试套件卫生门」同一句话：**指标能算出来，不等于口径是对的。** 一个能打印七个数字的评测脚本，和一个口径正确的评测脚本，是两件不同的事。

## H 阶段：性能基线、低风险优化与 FTS5 迁移（2026-11-03）

> 完整数据与复现命令见 `docs/h阶段实测.md`。本节只记**做了什么、验证了什么、哪里没做到**。
> 基准世代 `g-20261031T035231Z-4eafae`（ark-rag-3，13,781 块 / 6,582 实体 / 28,625 边 / 62,910 断言，READY）；
> 题集 `data/goldset/gold-v1.json` 全 320 题。

### 1. H1：先造一把量尺，再谈优化

H1 的交付不是数字，是 `scripts/bench_h1.py`——一把以后每次优化都要重跑的尺子。
口径五条写死在代码里，因为**同一次测量换一种口径就能得到完全不同的结论**：

| 口径 | 定法 | 不定死的后果 |
|---|---|---|
| 冷 / 热查 | 冷 = 本进程首遍；热 = 其后各遍取中位数 | 取平均会把解释器预热抹平，冷启动成本就此消失 |
| 分位数 | nearest-rank `rank = max(1, min(len, ceil(pct*len/100)))` | `statistics.quantiles` 的插值会造出样本里不存在的值 |
| 空样本 | 返 `null` | 返 `0.0` 会让「没测到」看起来像「极快」 |
| 构建耗时 | 读真实 run 的 `events.jsonl` | 重跑会写新 Generation，污染被测产物清单 |
| LLM token / 成本 | `null` + 原因 | 本机无 LLM 端点；**估算值会被下一轮当成实测引用** |

峰值内存用 `GetProcessMemoryInfo` 的 `PeakWorkingSetSize`，不是"当前 RSS 的最大采样值"（采样必漏峰），
也不用 psutil（运行时零第三方依赖）。

### 2. H1 基线（优化前，如实记）

* 冷加载 **12,077.7 ms**，其中 `index/lexical.json` **9,972.5 ms = 82.6%**。
* 峰值 RSS **1,717.59 MiB**，是计划参照值 692.4 MiB 的 **2.48 倍**。
* 热查 P50 **239.281** / P95 **366.750** / P99 417.489 ms。
* 分阶段热查 P95：`query` 161.505、`search` **251.383**、`context` 54.831、`expand` 2.792、`answer` 0.583 ms。
  **两项占 412.9 ms，其余三项加起来不到 60 ms——优化后三项没有意义。**
* Top-K 成本：k=5/20/50/100 的 P50 是 180.9/204.8/198.2/209.4 ms，**与 top_k 几乎无关**，
  而候选数从 28 涨到 537。结论：成本在「扫全部倒排 + 打分」，不在排序截断。
  **所以调小 top_k 省不了时间**——这条推翻了"先降 top_k 试试"的直觉。
* 图扩展实际只走 2 节点 / 20 边，预算（80 节点 / 200 边）远未用满 → 瓶颈在上游种子实体的质量，不在扩展本身。

### 3. H2：七项只做两项，其余四项早已落地

计划列了七项低风险优化。**逐项核查后只有两项真的需要做**，这个结论本身比改动更重要：

| 计划项 | 结论 | 依据 |
|---|---|---|
| 预计算 `avg_doc_len` / 避免每次扫全部文档长度 | **已落地** | `LexicalIndex.avg_len` 是 `@property` 惰性缓存，`add()` 时失效 |
| 名称合并分桶前缀索引 | **已落地** | `NameTable` 的「两字前缀 ∩ 块内 bigram」求交 + trie 最长匹配 |
| QA 预建 `chunk_id -> index` | **已落地** | `answer.py:128` 的 `by_id` |
| L3 有界队列 | **已落地** | `extract.run_shard` 的 `window` + 熔断停补料，`skipped_circuit` 与 `miss_fail` 分开计 |
| 预建 `(category, chapter) -> chunks` | **不在查询热路径** | 只用于建库期分片（`chunk.py`），查询时不走 |
| 流式分片序列化 | **现状可接受** | `save_index` 已用 `atomic_write_json` 流式 dump 后原子替换 |
| 避免重复读取全部缓存 | **真缺口，本阶段做掉** | 见 3.1 |

> 一条经验：**计划里的优化清单是"猜想"，不是"事实"。** 逐项核查花了不到一小时，
> 省掉了四项本该写的代码（其中两项还会引入新的失效面）。

#### 3.1 `query.QueryContext`：问句解析从 161.5 ms 降到 1.15 ms

先量化，再动手。320 题 × 3 轮：

| 步骤 | 每问 | 说明 |
|---|---|---|
| 全量 `analyze_query` | 92.3 ms | — |
| 其中 `_alias_owner_map` | 48.2 ms | 遍历 6,582 实体 / 8,254 文本 |
| 其中 `NameTable` 建表 | 49.8 ms | 构建 8,177 项 trie |
| `_relation_lookup` | 0.1 ms | 真工作 |
| `_normalize` | 0.02 ms | 真工作 |

**96% 花在反复重建只依赖图、与问句无关的结构上。** 这三样在一个世代内不变（由 Manifest 锁定），
"每问重建"没有一处是为了正确性。

改法：`QueryContext` 显式只读容器持 `claims`/`name_table`/`rel_table`，生命周期跟 `Retriever` 走。

**为什么不用模块级 `lru_cache`**：key 要可哈希。把 6,582 个 dict 转内容指纹的代价与本函数相当（等于没省）；
用 `id(entities)` 作 key 会在对象回收后**命中另一个世代的图**——静默错配，比慢更坏。

结果：`query` P95 **161.505 → 1.154 ms（−99.3%）**，端到端热查 P95 366.750 → 303.905 ms。
代价：`Retriever` 构造 164.8 → 227.8 ms（一次性）。

#### 3.2 `index.norm_table()`：检索打分 251.4 ms → 167.5 ms

真实规模（先量准，这三个数常被混为一谈）：**词项数 694,304 / postings 条目总数 10,525,428 /
文档数 13,781**，每问命中 56.7 个 query term、内层循环迭代 **19.3 万次**（占条目总数 1.84%）。
这 19.3 万次每次重算 `k1*(1-b+b*length/avg_len)`，而这个除法**只与文档有关，与问句无关**。

改法：按 slot 预建扁平 `list[float]`，`add()` 时与 `_avg_len` 一同失效；内层循环只剩一次列表索引与一个乘加。
用 `list` 而非 `dict`：slot 由 `enumerate(sorted(...))` 连续分配，下标即 slot；有空洞时按原实现的
`doc_len.get(slot, 1)` 落 `len=1` 默认值补齐。

另把 `k1, b = 1.5, 0.75` 从函数局部变量提为模块常量 `BM25_K1`/`BM25_B`——H3 的 FTS5 后端必须用同一组参数，
让别的模块 import 函数内部的名字不可能，只能复制字面量，那又成了「同一判定写两处」。**数值未改动。**

结果：`search` P95 **251.383 → 167.523 ms（−33.4%）**，端到端热查 P95 303.905 → **211.785 ms**。
裸 `LexicalIndex.search` 的 A/B（320 题，同进程预热）P50 150.789 → **93.378 ms（−38.1%）**、
P95 228.979 → **138.992 ms（−39.3%）**——与端到端口径不同，不能互相引用。

> **本节初版的数字错误，如实记。** 初版把「694,304」（**词项数**）写成「postings 条目数」，
> 并把 `818,941` 当作"全部 postings 条目数"——那是 `cProfile` **20 次迭代**的累计调用次数。
> 词项数 694,304、条目总数 10,525,428、每问迭代 193,403，三个数差两个数量级，混用会让
> "为什么优化有效"的解释变成编出来的。发现路径不是复查代码，是**在真实索引上做 A/B 时
> 顺手把这三个数重新量了一遍**，发现与文档里的对不上。处置：改正文档与 `norm_table` 的
> docstring，并在文档里固定「词项数 / 条目数 / 迭代数」三种写法，不允许混称。

#### 3.3 顺带：`extract.run_shard` 的 `list.pop(0)`

每块搬动整个剩余队列，13,781 块累计约 9,500 万次元素搬移，且全在持锁判断之间。
改 `deque.popleft()`。不是瓶颈，但没理由留着。

### 5. 等价性门怎么写的（这轮的主要工程产出）

两项优化都是"改计算方式、不改结果"，失效形态全都**不抛异常、不打日志、评测分数只掉一点点**：

* `avg_len` 与 `norm_table` 是两份缓存，`add()` 若只失效前者，新文档会用旧平均长度打分 → 分数差千分之几，召回掉一两个位置。
* 别名表少一个两字前缀或建错一条别名 → 某问句候选少一个，召回 20 掉到 19。

所以两个测试文件都不测"能跑"，测的是**与冻结的旧实现逐位相等**：

* `tests/test_index_norm_table.py`（40 项）：把改动前 `search()` 的**逐字副本** `_legacy_search` 留在测试里当标尺，
  8 问句 × 3 top_k 逐位比对（连 float 的 `repr` 都比），另覆盖空洞 slot、单文档、空索引、`add()` 后缓存失效、落盘往返。
* `tests/test_query_context.py`（23 项）：用生产形状语料（一对多别名、别名与规范名同文、前缀嵌套名、拉丁名、
  与否定词同位置的实体）对 11 问句断言复用与就地重建**整个返回结构深度相等**（含候选顺序、`score` 取值、`stats` 每项计数）。

**真实数据核查（不进测试套件，因为要加载 121 MB 索引，一次性脚本跑）**：在 `g-4eafae` 的真实索引上

| 核查 | 规模 | 结果 |
|---|---|---|
| `QueryContext` 复用 vs 就地重建，整个 `analyze_query` 返回结构 | 320 题，真实 6,582 实体 / 8,254 别名文本 / 257 关系 | **0 处不等**（深度相等） |
| 新 `search` vs 旧 `search` 的 `(chunk_id, score)` 序列（含 float `repr`） | 320 题 × top_k=20，真实 13,781 文档 | **0 处不一致** |
| `norm_table()` 逐项按公式复算 | 13,781 项 | **0 项不一致** |

单元测试用合成语料（快、可控），真实数据核查用真实世代（慢、但证明生产形状下也成立）。
两者都要有：前者能进 CI，后者才叫"在生产上没坏"。

### 6. 又发现一个真实缺陷：默认世代静默取最旧

`scripts/ask.py::_latest_identity_generation()` 原本遍历 `release.list_generations()` 遇到第一个
ark-rag-3 就 `return`，而该方法按目录名升序返回（**最旧在前**）。于是"取最新"实际取到最旧。

**为什么一直没暴露**：磁盘上三个 ark-rag-3 世代（`b22ca8`/`348206`/`4eafae`）内容完全一致——
`index_content_digest`、`probe_digest`、`graph_build_fp`、`chunk_manifest_hash` 全同，跑谁的数字都一样。

**这是最坏的缺陷形态：结论正确，机制错误。** 只要出现第四个内容不同的世代，`--evaluate` 不带
`--generation` 就会静默评测旧数据，而报告里没有一个字段会变红。

已改为跳过无 Manifest / Manifest 损坏的目录，只留 `graph_schema == GRAPH_SCHEMA_IDENTITY`，
按 `(created_at or gid, gid)` 排序取最后一个。`tests/test_ask_generation_selection.py`（8 项）守门：
`test_returns_newest_not_oldest` 在旧实现下必红，`test_directory_order_does_not_decide` 防"改成 `list[-1]` 就行"。

## H3 阶段：SQLite FTS5 检索后端（2026-11-03）

> 完整数据见 `docs/h3-FTS5迁移.md`。本节记**结论、代价与复核过程**。
> 实施由子代理 `h3-fts5` 完成，**所有关键数字由 Lead 在独立进程里复测过**。

### 9.1 交付物

| 文件 | 作用 |
|---|---|
| `src/arkrag/search_backend.py` | `SearchBackend` Protocol（只含 `tokenizer_version`/`name_terms`/`size`/`avg_len`/`search`）+ `JsonSearchBackend` 纯转发 + `open_backend()` 工厂 |
| `src/arkrag/fts_backend.py` | `FtsSearchBackend`，`FTS_SCHEMA_VERSION="ark-rag-fts-1"` |
| `scripts/build_fts_index.py` | 从已发布 `lexical.json` **翻译**建库（不重新分词） |
| `scripts/bench_h3.py` | 双后端对比台（复用 `bench_h1.percentile()`） |
| `tests/test_search_backend.py`（9）+ `tests/test_fts_backend.py`（20） | 守门 |
| `data/arkrag/fts/<gid>.sqlite` | 产物 212.2 MiB，**刻意不放世代目录内**（否则世代摘要变化会让 `snapshot_baseline.py` 与 `release_cli verify` 变红） |

`SearchBackend` 接口**刻意不含 `postings`/`doc_len`**：放进去就迫使新后端在内存里造一份倒排，等于没换存储层。
`open_backend(kind="fts")` 在库缺失时抛 `FileNotFoundError`，**不静默降级到 json**——静默降级会让
「切过去了」和「没切」跑出同一个数字。

### 9.2 排序逐位不变（H3 成立的硬前提）

`SCORE_MODE_EXACT`（默认）：FTS5 只当倒排存储，**打分仍用本项目自己的 BM25 实现**，
`idf`、长度归一化、同分次序全部逐字复刻。三处刻意为逐位相同：查询词按 `tokenize()` 首现顺序、
同 token 内按槽位升序、乘除结合顺序照抄 `idf * (freq * k1p1) / (freq + norm)`。

**实测：320 题 `(chunk_id, score repr)` 0 处不一致**（Lead 独立复测，与子代理结论一致）。
因此七项召回指标、`expand`/`context`/`answer` 全部自动相同。

另有 `SCORE_MODE_FTS5`（用 SQLite 原生 `bm25()`）：**不采用**。它的 idf 是
`log((N-df+0.5)/(df+0.5))`，本项目是 `log(1+(N-df+0.5)/(df+0.5))`，两者不是同一个公式。
实测 top-20 与 json **重合度仅 0.5919**，且比 `exact` 还慢。**不许把它当作"等价且更快"的选项。**

### 9.3 收益与代价（Lead 独立实测，各自独立进程）

**收益（站得住的两条）**

| 项 | json | fts | 变化 |
|---|---|---|---|
| `index_ms`（加载索引） | 5,467.2 ms | **18.4 ms** | **−99.7%** |
| 冷启动 `total_ms` | 7,317.7 ms（多次运行 7.3–12.9 s） | **1,750.0 ms** | **−76.1%** |
| 内存 `after_load` | 1,499.32 MiB | **532.64 MiB** | **−64.5%** |
| 内存峰值高水位 | 1,719.37 MiB | **532.64 MiB** | **−69.0%** |

峰值这一项特别值得看：json 的 peak 恒等于解析那一刻的高点（**之后降不下来**），
fts 的峰值就等于当前值——**没有解析尖峰**。532.64 MiB 已低于计划里 692.4 MiB 的参照线。
冷启动剩余 1.75 s 的构成：`assertions_ms` 937.5 + `chunks_ms` 296.1 + `graph_ms` 288.0，
是**图与块正文**，不在 H3 范围内。

**代价（必须写清楚，不许含糊）**

| 口径 | json | fts | 变化 |
|---|---|---|---|
| 交替 A/B `search` P50 | 49.778 ms | 68.901 ms | **+38%** |
| 交替 A/B `search` P95 | 150.899 ms | 217.607 ms | **+44%** |
| 跨进程 `search` P50 | 103.934 ms | 138.917 ms | +33.7% |
| 跨进程 `search` P95 | 160.306 ms | **205.456 ms** | +28.2% |

**「检索阶段 P95 < 200 ms」在 FTS 后端上未达标（205.456 ms，超出 5.5 ms）。**
这不是 H2 的退步——H2 的 json 侧是 167.5 ms，本次 json 列 160.3 ms，**H2 成果仍在**——
是换后端把它顶出去了。若生产切 FTS，须接受这一项回退。

**原因**：json 后端装好后 `postings` 就是热 dict，`dict.get(term)` 直接命中，Python 层零反序列化；
FTS 后端每题要为命中的 ~74 个 term 各做一次 `array("I").frombytes()` 重建数组再读 BLOB，
这笔开销超过了「少扫一点」的收益。

### 9.4 一次差点写进文档的错误结论

子代理首版 `docs/h3-FTS5迁移.md` §5.2 写的是「search json 180.994 → fts 150.155，**−17.0%**，
P95 达标余量 49.8 ms」——方向完全相反。三处证据推翻它：

1. 文件 mtime：`fts_backend.py` 12:57:10、`bench_h3.py` 12:58:51，而文档 12:30:50——
   **文档比它描述的代码早 28 分钟，记的是一次已不复现的运行**。
2. 与它自己刚改对的 `fts_backend.py` 模块 docstring 直接矛盾（docstring 说「实测比内存 dict 慢」，
   §5.2 说「快了 17%」）——**正是 `tests/test_single_source_of_truth.py` 记录过的同型事故：
   同一判定在两处各写一份，读者取最想信的那份**。
3. Lead 用三种独立口径（跨进程、完全预热连跑、同进程交替 A/B）复测，方向一致：fts 一直更慢。

改正后 §5.2 贴的是实际运行输出，§5.3 标题改成「**检索延迟：H3 没有收益，实际更慢**」。
教训：**给子代理派活时必须要求"把实际运行输出原样贴进文档"，否则它会写一个自洽的、好看的、
但与代码不同步的结论。** 文档与代码的 mtime 关系是最便宜的检查手段。

### 9.5 建库只翻译、不重新分词

`build_fts_index.py` 从已发布的 `lexical.json` 读出 `postings`/`doc_id`/`doc_len`/`name_terms` 写进 SQLite，
**不复用分块文本重新分词**。理由：重新分词等于在第二处实现「哪些块进索引 / 用哪个分词器版本 /
用哪份整词名表 / 文本怎么拼」这四件事，任何一处偏差都会造出一份**静默不同**的索引，而没有任何门能发现它。

已知偏差：`meta.tokenizer_version` 记为 `"t1"`、`name_terms` 长度为 0（该世代的 index 就是 t1 建的）。
`tokenize()` 依赖 `name_terms`，两边都是 0 故 `context_ms` 本该完全等价——实测也确实等价
（18.003 → 18.519 P50、52.867 → 61.615 P95，**基本持平、FTS 略高**），
**不许把这一阶段算成任何一方的功劳**。

### 9.6 本节遗留（四条）

1. **检索延迟仍不达标（FTS 205.456 ms > 200 ms）。** 下一步方向：避免每 term 重建 `array` 对象
   （复用 buffer、或用 `sqlite3.Binary` + `memoryview.cast` 视图），或把倒排换列存。
   **本轮到此为止，不为了凑达标而换 `SCORE_MODE_FTS5`**（那会改排序口径）。
2. **图与块正文仍以 JSON 加载**（冷启动剩余 1.75 s 的主体，`assertions` 937.5 ms 最大）。
   H3 只迁了倒排层；`assertions.jsonl` 68.7 MB 也该进 SQLite。
3. **FTS 后端尚未接入生产默认。** `open_backend()` 默认 `AUTO`（有 .sqlite 就用 fts），
   但 `scripts/ask.py` 尚未改用它。灰度前需先解决第 1 条，否则默认一切换就丢掉 P95 余量。
4. **sqlite 产物不在世代摘要内**（`data/arkrag/fts/`），意味着它损坏或过期时，
   `release_cli verify` 与 `snapshot_baseline.py` 都不会变红。需要一条独立的
   「sqlite 与 lexical.json 的 `index_content_digest` 是否一致」的检查，本轮未做。

## I 阶段：向量召回、融合否证与检索增强（2026-11-03）

完整实测记录见 **`docs/i阶段实测.md`**（口径、逐轮扫描、复现命令）。本节只记结论与
"为什么这样做、为什么不那样做"。

### 1. 口径（先定尺）

| # | 口径 | 为什么 |
|---|---|---|
| Ⅰ | 输出窗固定 `top_k=20` | 改输出窗同时改分子与分母，两组数不可比 |
| Ⅱ | "生产口径"必须走 `top_k=20` | `search` 内部按 `top_k*MULT` 拉候选，`search(50)` 再截 20 ≠ `search(20)`（0.6858 vs 0.6575） |
| Ⅲ | 只有 R@20 与 MRR **同时**不劣才算改进 | 上下文只装 4.7 块，"多捞到但排不进前几"对答案无价值 |
| Ⅳ | 不显著就不采纳 | n=300 时等价配置光凭运气也差十几题 |
| Ⅴ | 先量 gold 命中率，再谈排名质量 | 连 gold 都捞不进的通道在融合里只能是噪声 |

### 2. 向量通道（I1）

- **后端**：本机 Ollama 的 `bge-m3:latest`（1024 维 / 8192 context / 566.70M / Q4_K_M，
  `digest=85c47f4ff97c9a8c…`）。`nomic-embed-text`（768 维 / 2048）更慢更短故不采用。
  输出已 L2 归一化（`norm=1.000000`），查询侧仍重新归一化一次。
- **扫描必须用 numpy**：13,781×1024 全量点积 `M @ q` + `argpartition` **2.82–5.18 ms**，
  stdlib 最快的 `math.sumprod` 938.5 ms，朴素 zip 1,826–2,195 ms。**差 300 倍以上。**
  二值量化 5.9 ms 但 top-20 只重合 1/20 → 否决。`math.sumprod` 与朴素实现逐位相同，
  说明 938.5 ms 已是纯 Python 极限。
- **numpy 是可选依赖**：缺 numpy 必须申报 `not_built_no_numpy`，**绝不静默退化成纯 BM25**。
- **建库**：13,781 条 × 1024 维，**610.3 s（44.3 ms/条）**，56.4 MB。落盘用
  「模型 slug + 索引内容摘要」命名（三个 ark-rag-3 世代内容全同，应共用一份）。
- **唯一的文本定义**：`chunk_text_for_embedding` = `title + chapter + text`，必须与
  `index.build()` 喂词法索引的字符串逐字相同，否则两通道在看两份不同文本。

### 3. RRF 三轮否证（**结论：彻底放弃**）

| 轮次 | 范围 | 结果 |
|---|---|---|
| ① 标准 RRF k=60 | 四模式对比 | R@20 +0.0361 但 **MRR −0.0753** |
| ② 扫 k 60→1 | 7 个 k | **无任何 k 让两指标同时不劣**（k=1 最好仍 ΔMRR −0.0071） |
| ③ 通道子集 × k | 7×6=42 组合 | **无解** |
| ④ 加权 RRF × head_lock | 4×4×2×4=128 组合 | **无解**（最好 ΔR@20 −0.0173） |

机理：k=60 时 rank1 贡献 0.01639、rank30 贡献 0.01099，只差 0.0054，而"多一路命中"
直接加一整份 ≈0.016 → 两路各排第 30 的块能压过单路排第 1 的块。

**根因在分通道质量差距**（n=300，channel_k=100）：

| 通道 | R@20 | MRR | **gold 命中率** |
|---|---|---|---|
| baseline（两路加权） | 0.6575 | 0.4123 | 0.7400 |
| bm25 单独 | 0.6478 | **0.4248** | **0.9367** |
| vector 单独 | 0.3892 | 0.2101 | 0.6467 |
| entity 单独 | 0.4650 | 0.2255 | 0.8367 |

**bm25 gold 命中率 0.9367 而 R@20 只有 0.6478** → gold 基本都在池里，问题是排不进前 20。
vector 单独只捞到 1 道独有题（`vector` 1 题 / `bm25` 17 题 / 三路 162 题）。
RRF 给弱通道与强通道同等话语权，等于让 vector 否决 bm25 的排序。

`src/arkrag/fusion.py` 保留（有测试、完整可用），**但不接入生产默认**——它是
"已证否方案"的证据载体。若将来换了 embedding 模型使 vector 的 gold 命中率大幅提升，
这套代码可直接重测。

### 4. 实际收益一：候选池深度

**发现路径是一次我自己的口径错误**：`diagnose_ranking.py` 把「`search(100)` 再截 20」
标成生产口径（R@20 0.6850），而真实口径是 0.6575。差 0.0275 全来自候选深度。

| 内部倍数 | R@20 | MRR | 判定 |
|---|---|---|---|
| 3（原值） | 0.6575 | 0.4123 | — |
| 5 | 0.6775 | 0.4221 | — |
| **10** | **0.6842** | **0.4392** | **唯一同时最大化，采纳** |
| 20 | 0.6817 | 0.4385 | 略回落 |
| 50 | 0.6817 | 0.4384 | 略回落 |

延迟代价**为零**：`index.search` P50 恒 67 ms（top_k 60/200/1000 → 67.6/68.2/66.8 ms）。
**成本在扫倒排，不在排序截断。**

### 5. 实际收益二：说话人结构化加成

剧情是对话体，`chunks.jsonl` 的 `speakers` 列出该块真正开口的人（13,786 行中 97.1% 有值），
问句命中 speakers 的题 **206/320**。这是 bm25 与 entity 两通道都没用上的结构化信号。

| 权重 | R@20 | MRR | 判定 |
|---|---|---|---|
| **ws=0.1** | **0.7019 (+0.0177)** | **0.4394 (+0.0002)** | **12 组合里唯一两者都不劣** |
| ws=0.2 | 0.7003 | 0.4336 (−0.0056) | MRR 降 |
| ws=0.5 | 0.6819 (−0.0023) | 0.4076 (−0.0316) | 两者都降 |
| wt(title) / wc(chapter) | 只降不升 | 只降不升 | 不实现 |

显著性（n=300，配对符号检验 + bootstrap 2000）：
- **R@20**：更好 8 / 更差 1 / 持平 291，**p=0.0391**，区间 **[+0.00167, +0.03611] 不跨 0 → 显著**。
- **MRR**：更好 22 / 更差 12 / 持平 266，p=0.1214，区间 [−0.00458, +0.00432] 跨 0 → **不显著**。

**准确说法：召回显著提升，头部精度无显著变化（没变差）。不许说成两项都提升。**

同类扫描里实体权重也做过：w=0.4 的 0.6858/0.4406 看似优于 w=0.5 的 0.6842/0.4392，
但更好 12 / 更差 24 / p=0.0652 / 区间跨 0 → **不显著，维持 0.5**。

### 6. 一处被测试抓出的真实缺陷（含一次我自己的错误判断）

`tests/test_retrieve_speaker.py` 断言"归一化落在 (0,1]"失败，实测能到 **2.0**（生产 323 个块）。
追下去是两个不同的问题：

1. **同一实体的规范名+别名重复计票**（`["凯尔希","凯尔希医生"]` 拿两票）→ **真缺陷，已按实体去重修掉**。
2. **超过 1.0 主要来自多实体同时在场** → 这不是缺陷，是真实信号。

拆解证据（`scripts/diagnose_speaker_clamp.py`）：

| 实现 | ws=0.1 时 R@20 |
|---|---|
| 按别名累加、无夹紧（原版） | 0.7019 |
| 按实体去重、**无夹紧** | **0.7019**（去重零影响） |
| 按实体去重 + 夹到 1.0 | 0.6919（**掉 0.0100**） |

**我一开始做错了**：为了让一句从未兑现的 docstring（"(0,1]"）变成真的，我把分数夹到
1.0，把真实收益砍掉一半。正确做法是**把契约改成实情**——现在 docstring 明写上界是
"问句里同时命中该块的实体数"，并附这张表。

**教训**：文档与代码不一致时，先查哪个是实测支持的，不要默认"代码错了"。
这次是文档错、代码对（只是有一处别名重复计票需要单独修）。

### 7. 重排两条路都不通（I2）

**本机 CE（bge-reranker-base-onnx int8，279 MB）**：
- 正确性 PASS（相关块 4.9951/1.2328，无关块 −7.6255/−10.1868）。
- 短文本 27–32 ms/对，但**真实块正文（832 字截到 512 token）95.1 ms/对**；
  重排 20 候选 **1.9 s**，预算 P95<200 ms 差一个数量级。
- 截断权衡：384 token ρ=0.8671（排序已变）、256 仍 816 ms、192 ρ=0.7832、128 ρ=0.5524。
  **截到能进预算的长度时排序已不可信。**
- 前项目对同一模型有独立读数：int8「快 6 倍但增益完全消失」（fp32 0.5→int8 0.4231）。
  **我方手里正是这个 int8 版本**，那条负结果直接适用。

**离线盲特征线性重排**（按前项目 §3.3 实现，9 特征，类别分层 train/holdout 各 160）：

| 集合 | 基线 MRR | 拟合后 | Δ |
|---|---|---|---|
| train | 0.4200 | 0.4361 | +0.0161 |
| **holdout** | 0.4622 | 0.4531 | **−0.0091 → 判据未通过** |

坐标上升只走 3 步（`bm25→0.5`、`speaker→0.5`、`len→0.5`）。**train 上的 +0.0161
全是拟合出来的。** 不采纳。

可能原因（未验证，仅作下一步假设）：我方已有 entity/speaker 两个结构化通道，
盲特征里最有价值的那些与它们高度重叠，边际信息少；前项目 10 个特征含 `ppr` /
`has_vec` / `log_deg` 等图侧特征，我方图规模（6,582 实体 / 28,625 边）未必支撑同样信号。

### 11. 纪律总结

- **否证也是交付。** 四轮 RRF 扫描与两条重排路径的负结果，每一条都有可复现的数字，
  并且都写清了"为什么必然失败"（不只是"试了不行"）。这比一个说不清来源的微小提升值钱。
- **过拟合防线必须是结构性的**，不能靠自觉：类别分层切分 + 只在 train 上拟合 +
  holdout 只跑一次 + 判据事先写死。盲特征重排就是被这条防线拦下的（train +0.0161 / holdout −0.0091）。
- **口径错误要先怀疑自己。** 候选池深度这个真实收益，是从我自己算错的 0.6850 里发现的；
  夹紧掉 0.0100 那次也是我先怀疑代码、实际是文档错。
- **一处改动一次复测。** 去重与夹紧是两个改动，必须分别测（`diagnose_speaker_clamp.py`），
  否则会得出"去重有害"的错误结论。
