# W0 实测结论：24000 档「名次 → 上下文」转化

- 产物：`data/diag_rank_24000.json`（schema `arkrag.diag_rank_24000/1`）
- 生成：`scripts/diag_rank_24000.py`，经 `scripts/run_guarded.py` 运行
- 世代：`g-20261103T132152Z-06a741`
- 环境：conda `arkrag` / Python 3.13.18（见 `docs/基线-环境标准化与测试基线-20261110.md`）
- `run_digest`：`cb39ca592a32cfeb1784fb447100d9804c4361c67ad0bab1a110c61b9e0cd284`
- 耗时：131.9 s（588 题）；熔断峰值 1383 MB / 2048 MB
- 结论标签：**证据充分，且触发反证条件 2 —— W1 不得直接 cap=10**

## 1. 一句话结论

**24000 档下，深名次不是"进不来"，而是"基本都进来了"。**
rank>10 的 gold 有 **65%** 进了上下文，远超计划书预登记的 16.25% 门槛
（反证条件 2）。因此 **不能 cap=10**，必须重新评估 cap=12/14/16。

同时首次拿到一个此前没有的数：**k≤10 的累计转化率在三份 split 上都是 100%**，
说明 24000 档的预算已经足以装下 rank 1–10 的全部 gold ——
这在 12000 档是不成立的（当年 top-10 捕获率虽也是 100%，但分母只有 203 题、
rank>10 的 32 题全军覆没）。

## 2. 分母（A3：逐个报出，不许只给比率）

`clean` 不是 `gold-v2` 里的一个 `split` 值，而是「holdout 里、有 gold、
且题号不在 gold-v1 里」的题（口径逐字对齐 `eval_answer_quality.py::pick_items`）。
首跑时按 `split=="clean"` 过滤得到 0 题，已修正。

| split | 全部输入 | 有 gold | 应答题 | gold 在 hits | gold 进上下文 |
|---|---|---|---|---|---|
| dev | 350 | 350 | 350 | **287** | **278** |
| holdout | 238 | 238 | 238 | **206** | **195** |
| clean | 144 | 144 | 144 | **127** | **122** |

注：`gold-v2` 的 `dev`/`holdout` 分区里**不含**结构类题（`time_conflict` /
`negative_abstain` / `adversarial`），所以"有 gold" = "应答题" = 全部输入。
`no_gold` 计数为 0 与此一致。W0 脚本仍保留 `no_gold` 状态分支，
以便将来换 gold set 时不静默丢分母。

### 7.1 可复算性实测（A2 + 反证条件 3）

同一命令连跑两次全量（两次都经 `run_guarded.py`，峰值内存均约 1383 MB）：

| 项 | run 1 | run 2 |
|---|---|---|
| `run_digest` | `cb39ca592a32cfeb1784fb447100d9804c4361c67ad0bab1a110c61b9e0cd284` | **同左** |
| 行数 | 588 | 588 |
| 逐字段差异 | — | **0** |
| `ctx_tokens` 序列 | — | **完全相同** |

`run_digest` 相等且 588 行逐字段零差异 ⇒ **A2 通过、反证条件 3 不触发**。
digest 的稳定性也由此得到实证：脚本把 `elapsed_ms` / `generated_at` 排除在
`_VOLATILE` 之外，这一处置被证明有效（两次跑的耗时不同，digest 仍相等）。

### 条件 2 的后果（这是本次最重要的产出）

计划书原文：

> 24000 档 `rank>10` 的进上下文数 > 本次实测分母的 5/32 等价比例（16.25%）：
> 不得直接 cap=10，W1 重新评估 cap=12/14

实测 65% ≫ 16.25%，**cap=10 被明确否决**。

### cap 各档的代价（本文实测，供 W1 决策）

"cap=N 后 gold 是否还在上下文里"——即 gold 的位置 `ctx_pos ≤ N`：

| cap | dev 保留 | holdout 保留 | clean 保留 |
|---|---|---|---|
| 10 | 247/278 = **88.8%** | 173/195 = 88.7% | 107/122 = 87.7% |
| 12 | 251/278 = 90.3% | 177/195 = 90.8% | 109/122 = 89.3% |
| 14 | 261/278 = **93.9%** | 182/195 = 93.3% | 113/122 = 92.6% |
| 16 | 272/278 = **97.8%** | 186/195 = 95.4% | 116/122 = 95.1% |

**cap=10 会丢掉约 11% 已进上下文的 gold**；cap=16 只丢约 2–5%。
这直接支持计划书的方向："上调至 12 或 14"，而数据表明 **16 更保守**。

但注意：这里算的是"gold 是否还在上下文"，不是"cap 后分数是否不降"。
cap 换来的是 23643 → 约 N×1276 token 的成本下降，收益与风险要在 W1 实跑后才有数。

## 9. 首跑踩到的两个坑（记录，防复发）

1. **`clean` 分区为空**：`clean` 不是 `gold-v2` 的 `split` 值，而是
   "holdout 里且不在 gold-v1 里"。按 `split=="clean"` 过滤得到 0 题。
   已改为逐 split 调 `pick_items`，并给每道题打 `selected_by` 标记
   （`clean ⊂ holdout`，同题会同时属于两个分区）。
2. **`rank_bucket` 函数被误删**：一次编辑替换掉了它，导致 588 题全部
   `NameError`。因为脚本对单题异常是 `except` 后记 `run_error` 而不中断，
   **表面"跑成功了"、实际一行有效数据都没有**。
   这是"错误被兜底吞掉"的典型形态，值得记住：`status` 分布必须每次核对，
   不能只看退出码 0。

## 10. 下一步（W1）

按反证条件 2 的要求，W1 的 cap 不得取 10。基于 §7 的代价表，候选是
**12 / 14 / 16**。W1 的预登记判据 K1（三份 `pass` Δ ≥ 0）必须在实跑后判定，
不能从本文的"gold 是否在上下文"推出分数结论。
