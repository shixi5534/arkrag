## 结论摘要

线上可被远程触发的实质问题集中在三处，均**不是**教科书式的泛泛而谈：

1. **`/ready` 把内部绝对路径直接吐给任何未鉴权调用方**——`sanitize_text()` 只挂在 `_fail()` / `_log_internal()` / `_clip_text()` 上，`readiness()` 里 7 处 `f"...：{exc}"` 全部是 `str(exc)` 直拼，**一次都没过清洗**。已实测打印出 `E:\图rag\data\arkrag\generations\...`。
2. **超时不占用并发名额，但会让执行器队列无界增长**：`run_bounded()` 在 `finally` 里**无条件** `release()` 信号量，而超时后工作线程仍在跑。信号量因此不构成 docstring 声称的"滞留线程上限"，请求以 504 返回后仍排队执行。
3. **`publish()` 的"这里再自己查一遍"是自证**：`verify_generation()` 从不读 `gates.json` 的 `verdict`，只比对它的 sha256。已实测一份 `verdict:"FAIL"` 的门禁报告可以 100% 通过 `verify_generation()`，`publish()` 会照发。

另有两项**与安全无关但会真出事故**的：

- **`atomic.append_jsonl` 在 Windows 并发写下静默丢记录**（实测 8 线程丢 13–19%）。`server.py` 的审计日志正是多线程写它 → **管理操作的可追溯性被静默破坏**。
- **`sanitize_text()` 的正则过度匹配**，把 `100/200/300` 这类文本与所有 `https://` URL 改写成 `<path>`；`/chunks` 的正文过它一次就被篡改（真实语料 13,798 块中 1 条命中）。

严重级口径：P0＝可远程触发且后果不可接受（数据损坏/鉴权绕过/不可用）；P1＝真实可利用或必然导致生产误判；P2＝有条件触发/纵深防御缺口；P3＝卫生问题。

## 我认为是误报 / 已正确处理的项

对抗审查也要防虚报。以下是我一开始怀疑、核查后判定**没问题**的：

- **M-01 `X-Forwarded-For` 伪造绕过限流 —— 误报。** `_client()`（`server.py:954-955`）只读 `self.client_address[0]`，即 TCP 对端地址。全文件 `grep 'X-Forwarded-For'`/`x-forwarded` **零命中**。不信任 XFF 是**正确**默认（信任它才是漏洞）。限流的真实问题在别处（A-05 无界、A-06 探针不豁免）。
- **M-02 `_require_admin` 不是 timing-safe —— 误报。** `server.py:1022` 用的是 `secrets.compare_digest`，**就是**标准库的 timing-safe 比较（`hmac.compare_digest` 的别名语义，同为 C 实现常数时间）。不是 `==`。真实问题是非 ASCII 令牌抛 `TypeError`（A-13），属可用性而非时序。
- **M-03 `git_revision()` 漏传 `child_env` —— 误报（已被测试白名单正确覆盖）。** 输出是 `git rev-parse HEAD` 的 40 位 hex，无中文、不参与任何中文匹配。`tests/test_subprocess_encoding.py:263-266` 白名单条目的理由成立。**唯一建议**是那条白名单的 `owner` 写的是 `"git_revision"`，实测 `_missing_env` 扫描用函数名匹配——已验证对得上（测试 `test_whitelist_points_at_real_calls` 会红）。
- **M-04 `admin_token` 未配置时 fail-open —— 误报。** `_require_admin`（`1016-1018`）在 `not token` 时**直接 raise 503 `admin_disabled`**，且 `from_env()` 用 `os.environ.get("ARKRAG_ADMIN_TOKEN","")` 无默认值（`212`）。`tests/test_server.py:297 test_settings_never_defaults_admin_open` 钉着这条。**确实是 fail-closed**。
- **M-05 `_BodyReader` 不做 body 超限即拒 —— 误报。** `read()` 在 `872-884` **先**比 `length > settings.max_body_bytes` 才决定读多少，绝不"读到内存再判断"；超限时 `_drain` 只读掉至多 `DRAIN_CAP=1 MiB`，超出 `can_drain=False` 就 `skipped_too_large` + `Connection: close`（`977-981`）。逻辑正确。缺陷另有两条：**没有读超时**（A-04）、**所有拒绝路径都先读完**（A-14）。
