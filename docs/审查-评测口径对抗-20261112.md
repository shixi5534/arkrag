## B. 严重：口径名不符实

### B1 判据实质是「gold 是否出现在答案文本里」—— 这是 retrieval/containment 指标，不是问答准确率

| 项 | 内容 |
|---|---|
| **攻击点** | `judge.py` 逐类判据全部是**子串/集合包含**，没有任何一项检验"答案是否真的回答了问题"。480 池的列联表证明判据与"gold 在答案里"近乎等价 |
| **证据** | `src/arkrag/judge.py:154-159`（single_chunk/alias）：`if any(g in text for g in golds): return pass=True, "gold_in_answer"`<br>`src/arkrag/judge.py:160-180`（cross_chunk）：纯 `chapter_set` 集合比较<br>`src/arkrag/judge.py:185-191`（direct_relation）：`all(a in s for a in anc) and gold in s`<br>`src/arkrag/judge.py:192-202`（multihop）：`any(a in s and gold in s for s in sents)`<br>我实测 480 池列联表（gold 是否出现在答案 → 是否判过）：<br>· `(True, True) = 445`　`(True, False) = 17`<br>· `(False, False) = 18`　**`(False, True) = 0`**<br>· 一致率 **96.5%**，`gold 在答案里 = 462/480 = 96.25%` |
| **若成立的影响** | 判据**从不在 gold 不在答案时放行**（0 例），也**只在 gold 已在答案却排错句时拦截**（17 例，全是 multihop 的形态）。所以 92.71% ≈ "答案里出现了 gold 字符串"的比例。这个量在 IR 里叫 **gold containment / hit rate**，是**检索侧指标**，与 answer accuracy（答案语义正确）不是一回事。项目自己的 `judge.py:22` 已经承认过类似性质（"超集判据在奖励换个定义作答"），但**92.71% 这个数字对外仍以"问答准确率"流通**。 |
| **定量** | 贡献 50.1% 分子的两类（single_chunk+alias，224/480 = 46.7% 的题）判据原文就是一句 `any(g in text)`。这两类通过 223/224。**445 份"答对"里有 223 份（50.1%）是"答案里出现了一个短专名"。** |
| **验证方法** | 纯离线：读 `data/l6f_cooc_{dev,holdout}.json` 的 `rows`，对每题算 `gold in answer`，与 `arms.prod.pass` 做列联表。零重跑。 |
| **状态** | 【已核实】 |

**对照外部标准**：RAG 评测里 retrieval 与 generation 必须分开报（参见 [RAGAS 式分层的做法](https://github.com/sudhir13s/ai-ml-learning-resources/blob/5cdb9a21253e538de9ac9d227e5bb0322dc03d89/11.%20RAG_and_LLM_Applications/11-RAG-Evaluation/code/rag_evaluation.py)、[检索层指标与答案层指标不可互相替代](https://github.com/LoveOrange/coding101/blob/main/docs/ai/evaluation/rag-evaluation.mdx)）。本项目把两者压成"一个数"，且这个数落在检索侧。
