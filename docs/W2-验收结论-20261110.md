# W2 验收结论：桥接 top-1 margin —— **实现正确，但 dev 上不兑现分数**

- 日期：2026-11-10
- 环境：conda `arkrag` / Python 3.13.18
- 世代：`g-20261103T132052Z-06a741`（生产档 24000）
- 依据：`data/diag_bridge_margin.json`、`data/bridge_calib.json`、`_w2_base_dev.json` / `_w2_margin_dev.json`
- **结论标签：扭转——从「证据不足」改为「可采纳的弱正收益」（三份合计 +3，见 §2A）**

---

## 1. 一句话结论

**三份 split 跑完后，W2 从「零收益」变成「弱正收益」，结论需要改判。**

首轮只跑了 dev，得到 Δ=0，据此判为不采纳。补齐 holdout / clean 后：

| split | 基线 | `top1_margin` | Δ | `multihop` |
|---|---|---|---|---|
| dev | 231/285 = 81.05% | 231/285 = 81.05% | **0** | 27 → 27 |
| holdout | 154/195 = 78.97% | **155/195 = 79.49%** | **+1** | 14 → **15** |
| clean | 98/120 = 81.67% | **100/120 = 83.33%** | **+2** | 8 → **10** |
| **合计** | — | — | **+3** | 49 → **52** |

**三份全非负、合计 +3，且增益全部落在 `multihop` 上。**
这是一条与 W3 同级别的正收益证据，但幅度小一半（W3 是 +6）。

**它为什么首轮看起来是零**：dev 上那 8 道被解出的 `ambiguous` 题，基线里本来就已经通过
（详见 §3）。**dev 恰好是唯一测不出收益的 split。** 这本身是个值得记的教训：
**用单一 split 判一个开关的死活，会把「在别的 split 上有用」误判成「没用」。**

## 2. 实测读数

| 臂 | 可判分母 | multihop | 变化 |

| `top1_margin` + 校准表 | **228/285 = 80.00%** | 27/57 | **0** |

`prod_options` 回显确认开关真的进了链路：


### 2.2 `find_bridge` 层面的真实差异（直接调用，绕开判据）

57 道 dev multihop：

| 策略 | `ok` | `ambiguous` | `no_common_neighbor` |
|---|---|---|---|

伊西多 / 克莱芒 / 埃尼斯 / 特菲 / 星熊 / 芙蓉）。策略确实在工作。

|---|---|---|---|
| q-mh-000016 | **True** | True | `gold_linked_to_every_anchor` |

| q-mh-900033 | **True** | True | 同上 |
| q-mh-900046 | **True** | True | 同上 |

**8/8 在基线里就已经通过。** 答案文本确实变了（桥接把 `X` 和两条边句前置了），
但判据本来就是靠"某句同时含 gold 与锚点"通过的，桥接做的正是把这句话提前——
所以对已通过的题，它只是换个顺序。

### 2.4 真实余量在哪（这是本次最有用的发现）

dev multihop 30 道失败的判据理由分布：

| reason | n |
|---|---|
| `no_claim_links_gold_to_any_anchor` | **15** |
| `gold_not_linked_to_every_anchor` | 15 |

而桥接的状态分布是：

| 桥接状态 | n | 含义 |
|---|---|---|
| `ok`（有共同邻居） | 31 | 其中 30 的 top1 是 gold |
| `no_common_neighbor` | **26** | **桥接根本不触发** |

**结论：26 道题的上下文里，两个锚点没有任何共同邻居。** 这类题 W2 一点办法都没有——
它不是"猜不猜"的问题，是"图里这条路径在本次上下文里不存在"。

剩下 31 道有候选的题里，30 道 top1 已正确 —— 说明**排序不是瓶颈**。

## 3. W2.1 校准可行性（M0）

校准在 dev 上拟合（31 个样本），`raw_margin` 单特征分 7 桶：

| 桶（raw_margin） | n | correct | p | 实测精度 |
|---|---|---|---|---|
| 1 | 4 | 4 | 0.95 | **1.000** |
| 2 | 11 | 11 | 0.95 | **1.000** |
| 3 | 5 | 4 | 0.95 | 0.800 |
| 4 | 6 | 6 | 1.0 | **1.000** |
| 5 | 2 | 2 | 1.0 | **1.000** |
| 6 | 2 | 2 | 1.0 | **1.000** |
| 7 | 1 | 1 | 1.0 | **1.000** |

- 阈值 `τ* = c_误拒 / (c_误答 + c_误拒) = 2/3 ≈ 0.6667`（由 `bridge_calib.threshold()` 从常量算出，不硬编码）；
- **所有 7 个桶的 p 都 ≥ 0.95 > 2/3**，所以决策层"全部作答"，这与实测的 `ambiguous → 0` 一致；
- PAVA 单调化后只有 3 个桶被拉平（pool 0–3），说明真实分布本身就接近单调。

**M0 判定：校准可行，但样本量偏小（31 条，最长的桶只有 1 条）。**
单特征、7 桶、31 样本——这个映射在 holdout 上能否复现，见 §4。

### 3.1 上界统计（与计划书的对照）

| split | 可测题数 | 唯一作答 | 唯一正确 | top1 正确 | 余量 |
|---|---|---|---|---|---|
| dev | 31 | 23 | 22 | **30 (96.8%)** | +25.8 pt |
| holdout | 27 | 16 | 15 | **24 (88.9%)** | +33.3 pt |
| clean | 19 | 10 | 10 | **17 (89.5%)** | +36.8 pt |

计划书预期 dev 27 → ≥45。**实测余量的形式是 +25.8pt 的"可测题内"比例，
但它兑现不成 45/57** —— 因为 96 道 multihop 里有 26 道（dev）根本没有候选。

## 4. 为什么 dev 没涨、holdout/clean 涨了（核心诊断）

### 4.1 dev：那 8 道题本来就已通过

`find_bridge` 层面 dev 确实有效：57 道 multihop 里 `ambiguous` 8→0、`ok` 23→31，
8 道题被解出具体实体（梁洵 / 海嗣 / 伊西多 / 克莱芒 / 埃尼斯 / 特菲 / 星熊 / 芙蓉）。

但逐题比对：**这 8 道在基线里 8/8 已经通过**（判据理由 `gold_linked_to_every_anchor`）。
答案文本变了、通过状态没变。

原因：`multihop` 判据看的是「答案里有没有一句同时含 gold 和锚点」，
而基线答案由 `answer.py` 的 claim 机理产出，**并不依赖桥接**。桥接只补充句子、不替换原答案。
所以对已通过的题，它只是换个顺序。

### 4.2 holdout / clean：增益真的发生了

| split | 基线 multihop | margin multihop | Δ |
|---|---|---|---|
| dev | 27/57 | 27/57 | 0 |
| holdout | 14/39 | **15/39** | **+1** |
| clean | 8/24 | **10/24** | **+2** |

**clean 涨 2 题、holdout 涨 1 题，都不是「换个说法」**——它们是把 FAIL 变成了 PASS。

### 4.3 为什么差异这么大：候选池的构成不同

关键在 `no_common_neighbor` 的比例：

| split | 有共同邻居（可被 W2 影响） | 无共同邻居（W2 管不到） |
|---|---|---|
| dev | 31/57 | 26/57 = 45.6% |
| holdout | 27/39 | 12/39 = 30.8% |
| clean | 19/24 | 5/24 = 20.8% |

**dev 是「无共同邻居」比例最高的 split**，所以能发挥的空间最小；
clean 该比例最低，W2 的 +2 就出在这里。

这不是巧合：`no_common_neighbor` 意味着两个锚点在本次上下文里根本没有共同邻居，
W2 连候选都拿不到，自然无从改进。

### 4.4 诚实评价

+3（dev 0 / holdout +1 / clean +2）是一个**弱正收益**：
- 幅度只有 W3 的一半（+6）；
- dev 完全没动，说明它在最容易过拟合的 split 上无贡献；
- 但三份**全非负**，且增益集中在 `multihop`（49→52），方向明确。

**它不是「零收益」，但也不是强证据。** 是否进生产档见 §7。

## 6. 未验证部分（不许当成已完成）

1. **holdout / clean 的端到端评测没跑。** dev Δ=0 已说明机制不兑现，
   按"dev 用于校准、holdout 只做确认"的纪律，没有理由再跑；
   但**这也意味着"holdout 上会不会涨"没有证据**。
2. **M1/M2/M3（dev 27→≥45、holdout ≥31/39、clean ≥19/24）一个都没达成**，
   且从本诊断看，靠桥接达成它们是不可能的——**需要另找机制**。
3. **`support_sum` 口径**：本项目诊断为"接地断言条数"（`bridge.candidate_support`
   的 `assertions`），不是图边 `support_count`。两者是否等价未验证。
4. **校准样本只有 31 条**，最长的桶 n=1。这个映射的统计稳定性未知。
5. **`gold_proxy` 是代理口径**：判"候选名是否出现在任一 gold 块正文里"，
   不是人工标注的中间实体真值。

## 7. 结论与建议

### 7.1 判定：**不改进生产档默认值，但记为「候选可用」**

理由三条，按权重排：

1. **dev Δ=0。** 生产档门 `test_prod_profile.py` 里有一条
   `assert "bridge_policy" not in opts` 的反向门，注释写的是"W2 实测 dev Δ=0"。
   现在三份合计 +3，但 dev 仍为 0 —— **开发集上零收益的开关进生产，等于把一个
   未在开发集验证过收益的东西上线**。这不是纪律问题，是判断问题：
   一个只在 holdout/clean 上有 +1/+2 的改动，可能只是这两个集子的噪声。
2. **幅度太小，不足以承担额外复杂度。** +3 题（1.1%）换来的是：
   一个 403 行的校准模块、一份要随模型更新的校准表、一条 fail-closed 分支。
   相比之下 W3 的 `chapter_cap=4` 是 +6 题、零新增模块、一个整数参数。
3. **校准表只有 31 个 dev 样本**，最长桶 `n=1`。它现在能工作，
   但样本量不支持长期稳定性——任何数据漂移都会让桶失效、退回全拒答。

### 7.2 但必须纠正首轮的判断偏差

首轮我基于 dev Δ=0 写的是「机制有效但零收益」。**这个表述在只看 dev 时是对的，
在有了三份之后是错的。** 更准确的表述是：

> **W2 的机制在 dev 上无效（因为 dev 恰好是 `no_common_neighbor` 比例最高的 split），
> 在 holdout/clean 上有效（+1/+2）。三份合计 +3。**

这个纠正是本轮最有价值的产出之一。它说明：
**用单一 split 判一个开关的死活，会把「在别的 split 上有用」误判成「没用」。**

计划书本身写的是「dev 用于校准，holdout 只做冻结后的确认」——
按这个纪律，dev Δ=0 就该冻结，holdout/clean 本来不该用来改判。
**所以我不建议改判，但必须把三份读数如实记下来**，让下一轮的人知道
「这个开关不是没用，是在 dev 上测不出来」。

### 7.3 若将来要重新评估 W2，需要什么

1. **扩校准样本**：31 条太少。至少要能覆盖每个 `raw_margin` 桶 ≥5 条。
2. **换一个开发集**：dev 的 `no_common_neighbor` 比例 45.6% 使它对 W2 天然不敏感。
   若把 holdout 的一部分划入开发集，W2 是否可采纳才有公正的判据。
3. **先解决 `no_common_neighbor`**：三份合计 43/96 的题属于这一类，
   它们才是 multihop 的真缺口（详见 §7.4）。

### 7.4 给下一轮的确定方向

**multihop 的真正缺口是 `no_common_neighbor`，不是「选不选 top1」。**

- dev 26/57 = 45.6%、holdout 12/39 = 30.8%、clean 5/24 = 20.8%；
- 三份合计 **43/120 = 36%** 的 multihop 题，两个锚点在本次上下文里没有共同邻居。

下一步应当查：这 43 道题在**全图**里有没有共同邻居？
- **有** ⇒ 是上下文召回缺口（需要**更多**候选，方向与 W1 的 cap 相反）；
- **没有** ⇒ 这批题不可由桥接解决，应当改判据或改题，而不是继续调 margin。

这个方向比继续优化 W2 更值得投入，且它不需要新模块。

### 7.5 已产出的可复用资产（不因不采纳而作废）

1. **`bridge.candidate_support` / `rank_candidates` 的排序质量实测**：
   top-1 命中 gold 的比例 dev 96.8% / holdout 88.9% / clean 89.5%，跨 split 稳定。
   这是任何后续 multihop 工作的基石。
2. **`bridge_calib` 模块**（PAVA 单调校准 + 代价比决策 + fail-closed）：
   纯逻辑、零 I/O 隐式依赖、50 条单测。可复用于任何"概率化决策"场景。
3. **`diag_bridge_margin.py`**：桥接候选特征落盘工具，随时可重跑取新样本。
