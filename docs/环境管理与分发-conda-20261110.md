# 环境管理与分发（conda）

- 编写时间：2026-11-10
- 对应事故：`docs/事故-内存耗尽与熔断器-20261110.md`
- 规格文件：`environment.yml`、`pyproject.toml`、`requirements.lock.txt`

## 1. 为什么需要这份文档

本项目此前一直是**在全局 Python 上裸跑**的。这带来三类实际损失：

1. **说不清跑的是哪个解释器。** 两次 `0xC00000FD`（STATUS_STACK_OVERFLOW）
   崩溃与三次整机提交内存被打满，排查时都卡在同一处：没有环境声明，
   "跑一次看看"的结果无法归因到具体解释器版本。
2. **换机器即不可复现。** 没有 `pyproject.toml`、没有锁文件，
   新机器上装到的 pytest 版本可能不同，测试行为随之漂移。
3. **临时目录行为被当成项目缺陷。** 本机沙箱拒绝写系统临时目录，
   29 个 `tmp_path` 用例全数 ERROR——看起来像代码坏了，其实是环境问题。

conda 解决的正是第 1 条与第 2 条；第 3 条靠文档写清 `--basetemp`。

## 2. 分发方式

### 2.1 从规格创建（跨平台，推荐给使用者）

```powershell
conda env create -f environment.yml
conda activate arkrag
```

`environment.yml` 只钉两件事：`python=3.13` 与 `pytest>=9.0,<10`。
**刻意不钉更多**——项目运行时零第三方依赖，多钉一个包就等于放宽那条约束。

### 2.2 导出精确锁定（分发方做一次）

```powershell
# 同平台精确复现（含 build string）
conda env export > environment.lock.yml

# 跨平台可读（只留显式请求的项，去掉 build 与传递依赖）
conda env export --from-history > environment.min.yml
```

两份都该入库：`environment.lock.yml` 用于"一模一样地复现"，
`environment.min.yml` 用于"在别的平台重建"。

### 2.3 更新环境

```powershell
conda env update -f environment.yml --prune
```

`--prune` 会移除规格里已不存在的包。不加它，环境会随时间漂移成
"规格之外还有一堆东西"，那正是要避免的状态。

### 2.4 删除与重建

```powershell
conda env remove -n arkrag
conda env create -f environment.yml
```

## 3. 必须记住的运行约束

### 3.1 `--basetemp` 已不再需要（迁移到 conda 后消失）

迁移前在沙箱内直接跑 pytest 时，系统临时目录被拒，所有 `tmp_path` 用例 ERROR。
**迁移到 conda 环境 `arkrag` 后该问题消失**：`test_retrieve.py` 的 29 个
`tmp_path` 用例全绿，不加 `--basetemp` 也能跑。

如果换台机器又出现，症状是 `test_retrieve.py` 一次 ERROR 29 个，
届时再加 `--basetemp=./_pytest_tmp` 即可。

### 3.2 重型任务必须走熔断器

```powershell
python scripts/run_guarded.py -- python scripts/eval_answer_quality.py --split dev --prod
```

`run_guarded.py` 提供三层防护，其中**内核硬上限是主机制**：
`JOB_OBJECT_LIMIT_JOB_MEMORY` 让超限分配根本不被满足，子进程当场
`MemoryError`，内存从没被真正占走。本机实测：Job 上限 64 MB、子进程要
200 MB → 退出码 42，`MEMORY_ERROR_CAUGHT`，整机 commit 稳在 10.6 GB。

### 3.3 跑前先报预估

```
磁盘 MB → 预估峰值 RSS → 占物理内存 % → 熔断阈值
```

本项目一次 `load_generation()` 读 302.4 MB 产物，常驻 1.0–1.5 GB。
**同时跑多个就是 5–8 GB**，这是那三次事故的共同成因。

### 3.4 不许用管道捕获输出

`pytest ... | Select-Object -Last 10` 这类管道会让读取永远等不到 EOF，
表现为"工具返回空、job 失踪"。输出重定向到文件再读，是唯一可靠形态。

### 3.5 全量测试约 21 分钟，必须后台跑

实测 1240.89 秒。前台跑会触发工具超时并被移到后台，而工具移到后台时
**熔断器不生效**。正确形态：重定向到文件 + 后台 job + 轮询读文件。

## 4. 环境规格的当前取值与理由

| 项 | 取值 | 理由 |
|---|---|---|
| `python` | `3.13` | 主线稳定版本，conda-forge 构建最全；项目只用到 3.10 就有的语法特性。想在 3.14 上跑改这一行即可，代码没有 3.14 专属依赖 |
| `pytest` | `>=9.0,<10` | 与 `requirements.lock.txt` 的 9.2.0 同一大版本 |
| `pip` | 有 | 仅为将来 `pip install -e .` 留路；当前不需要（`conftest.py` 已把 `src` 插进 `sys.path`） |
| 运行时依赖 | **空** | 项目一等约束，不是巧合 |

### 为什么不是 3.14

本机 3.14.3 与 3.14.7 **都**复现了 `0xC00000FD`，根因是沙箱临时目录限制，
不是解释器缺陷。所以"升级到 3.14 就能修好"这个判断不成立——把这条写进文档，
免得下次又有人（包括我）照这个思路再试一遍。

选 3.13 纯粹因为它更保守，不是因为 3.14 不能用。

## 5. 已知限制与实测更正

- **`conda env create -f environment.yml` 在本机走不通。** 不是文件写错，是
  `~/.condarc` 里 `defaults` 渠道的 ToS 未接受，conda 26.7.1 直接拒绝解析
  （`CondaToSNonInteractiveError`）。而 `conda env create` 不接受
  `--override-channels`，无法绕开。**实际可用命令**：

  ```powershell
  conda create -n arkrag --override-channels -c conda-forge python=3.13 "pytest>=9.0,<10" pip -y
  ```

  已实测通过（conda-forge 的 `python-3.13.18` + `pytest-9.2.0`）。
- **`environment.lock.yml` / `environment.min.yml` 尚未生成。** 需由
  `conda env export` / `conda env export --from-history` 在装好环境后导出并入库。
- **3.13 组合已实测**（不再是"未验证"）：全量 `pytest tests` 得
  2038 passed / 2 failed / 16 skipped / 1 xfailed，耗时 1240.89 s。
  见 `docs/基线-环境标准化与测试基线-20261110.md`。
- **`--basetemp` 已被证明不再需要**：迁移后 `test_retrieve.py` 的 29 个
  `tmp_path` 用例全绿。此处更正本文件早期版本的判断。
