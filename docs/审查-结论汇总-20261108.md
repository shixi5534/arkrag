## 1. 最重要的一件事：判据度的是「形状」，不是「正确」

这是全部七轮审查的根结论。三条实测（同一批 285 题 dev 可判）：

| 输入 | 通过 | 说明 |
|---|---|---|
| 生产链路现状 | 198/285 = 69.47% | 真实系统 |
| **只把「问句锚点 + 正确 gold」拼成一句**（零检索、零证据） | **285/285 = 100.00%** | 形状 oracle |
| 同句式但 gold 换成随机错误实体名 | **1/285 = 0.35%** | 错名地板 |
| **答案直接等于 gold 原文** | **171/285 = 60.00%** | **低于生产！** |

读法：
- 判据对「gold 是否真的是那个字符串」的分辨力**是完美的**（错名 0.35%）；
- 判据对「这个答案有没有检索支撑」的分辨力**是零**（形状 oracle 100%）；
- 所以：**任何只学句式的改动都能把分数推到 100%，而"给出标准答案原文"反而不及格**（因为 direct_relation / multihop 的 gold 是关系词或实体名，本身不含锚点，判据要求锚点与 gold 共现）。

后果：**dev 分数与「答案正确性」不是单调关系。** 这条结论必须写进 README 的评测章节，否则每一代改动都会继续往句式上使劲。

## 5. 五条最关键的技术发现

### 5.1 「只删不加 + allow ⊇ gold」⇒ 0 回退是定理，不是质量指标

第七轮实测：`gold 章节 ⊆ 锚点实体 chunks 章节` = 38/38 + 26/26 + 16/16 = **100%**。
因此任何"只删不加"且 allow 覆盖 gold 的过滤器，**在数学上不可能删掉 gold 章节**。
定理检验：取 30 道 got⊇gold 的题各删 1 个非 gold 章 → **掉分 0 次**。
⇒ 报"0 回退"等于报"我构造了一个不可能掉分的操作"。**这类改动必须报 `gold ⊆ 允许集` 的比例。**

### 5.2 把 gold 塞进对照组后，信息来源就归零了

同一批 cross_chunk 题，五种"允许集"：

| 允许集来源 | dev | holdout | clean |
|---|---|---|---|
| 真实体 `entity["chunks"]` 章节 | 30 | 21 | 13 |
| **随机实体章节 ∪ gold** | **30** | **21** | **13** |
| **gold ∪ 等量随机章**（完全不读索引） | **30** | **21** | **13** |
| oracle = gold 本身 | 30 | 21 | 13 |
| 按锚点名正文词频取等量章节（不读索引） | 20 | 16 | 11 |

⇒ **逐格相同。** 索引唯一在起的作用就是"盖住 gold"。这是识别"索引直读"最快的一刀。

### 5.3 判据退化的三条判据

一条通路若出现下列任一情形，判据对该通路已无独立信息：
1. **`pass` 集合 ≡ `top1==gold` 集合**（假正 0、假负 0）——第 6/7/11 号通路全部如此；
2. **`pass` ≡ (输出 == gold)**——第 4 号通路如此；
3. **真证据 vs 纯模板/AI 造句 边际 = 0**——第 6/7 号通路如此。

### 5.4 「引用可机检」有两个口径，差 10~30 个百分点

- `judge.citations_support()`（`judge.py:206`）**不检查 evidence 长度**，且 `judge_answer` 根本不消费 citations ⇒ 对得分 **0 约束力**。
- `answer.verify_citations()`（`answer.py:392`）额外检查 `len(ev) < MIN_EVIDENCE_CHARS(4)` → `evidence_too_short`，并会**清空答案转拒答**。
- 同一批 alias 引用：前者 102/102 ok，后者只保留 **68.4%/71.8%/70.8%**。
- **任何"引用 100% 可机检"的声明，必须说明用的是哪个函数。**

### 5.5 `token budget` 不是单调旋钮，不能扫描调参

`retrieve.py` 的装填循环是"装不下就跳过、不回头重试"，顺序依赖 score 排序。实测反例：budget 300 保留 cost=269 的块；**budget 600 反而丢掉它**，换成 cost=431 的另一个块——预算变大，单元集合变小。
⇒ 任何"扫 budget 找最优点"的做法既过拟合又建立在非单调函数上。且该旋钮**饱和于 73.68%**（抬到 200 万 token 也只到 210/285）。

## 6. 验收协议（必须执行的 8 条）

任何声称"提升 dev 分数"的改动，必须**同时**满足：

1. **dev 上 Δ ≥ +1 题**，且可判分母不变、题集不变、`judge.py` hash 不变；
2. **holdout 上 Δ ≥ 0 题**；
3. **逐题配对 bootstrap 单侧 p < 0.05**（CI 下界 > 0）；
4. **clean 上 Δ ≥ 0 题**；
5. **净增益 = pass − 零检索地板（§2.1）> 0**——地板上已过的题不计入改进；
6. 所有报告数字**必须能被 `scripts/audit_eval_recompute.py` 复现（0 条 DIFF）**，并附三份 SHA-256；
7. **必须并列形状 oracle 与错名地板两条基线**（§1）——若改动后分数逼近形状 oracle，判失败；
8. **单次前向**：答案生成阶段不得读取判据输出，禁止"逐题重试直到通过"。

补充三条（本轮新增，见红线 27–41）：
- 任何"通道/过滤器"类改动**必须单报该机制自身的边际贡献**，不得只报整体增益；
- 过滤型改动**必须报 `gold ⊆ 允许集` 比例**与"把 gold 塞进过滤器"的对照；
- **clean ⊆ holdout，禁止用 `/80` 这类把 clean 重复计入的分母**（逐题唯一分母是 dev+holdout = 64）。

### bootstrap 用法（可直接复制）

```powershell
$env:PYTHONPATH="E:\图rag\src"
py -3 -c @"

sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8', errors='replace')

assert set(ka) == set(kb), '题集不一致，直接判失败'
va = [1 if ka[q]['arms']['prod']['pass'] else 0 for q in ka]
vb = [1 if kb[q]['arms']['prod']['pass'] else 0 for q in kb]
d = [y - x for x, y in zip(va, vb)]
rnd = random.Random(7); idx = list(range(len(d))); B = 20000

print(f'Δ={obs:+d} ({obs/len(d)*100:+.2f}pp)  95%CI=[{lo:+d},{hi:+d}]  单侧 p={p:.4f}')
```

## 8. 给决策者的四条建议

**建议 1：把 80% 重新定义。**
当前 dev 80.00% 是**恰好在边界上**（285×0.8 = 228.0，整数解恰好 228），不是因为能力到了 80%。真实情况是：
- 零检索地板 **23.86%**；
- 单一通用检索路径（无任何类别通道）**71.93%**；
- 加三条通道后 80.00%，其中 single_chunk 全靠"字符串定位器"、multihop 靠"接地桥接"。
**建议把目标改成「不依赖类别特异门控的通用检索路径分」**，或至少两者并列。否则"80%"是"认出题型后换捷径"的产物。

**建议 2：先修判据，再谈分数。**
形状 oracle 100%、gold 原文 60% 这个悖论不修，任何后续优化都会继续奖励句式。最小可行的三条改动（都属于"收紧"而非"放松"）：
- 断言的证据必须能回指到本次活动内的 assertion；
- `multihop` / `direct_relation` 加"答案实体数 ≤ 锚点数 + 1"这类上界型约束；
- `cross_chunk` 的 extra 真实性校验目前恒真（227/227 都"含锚点名"），需要改成"该章内至少一条断言的主/宾是该实体"。

**建议 3：把两道零代价防线立刻加上。**
- **断言句长 ≤60 字**、**答案总长 ≤1000 字**。实测：基线 198→198 一分不掉，soup 攻击 254→204。这是全报告里唯一"零假阳性、能挡住 89% 级注水"的措施。

**建议 4：把"审查方独立复现"写进流程。**
七轮里有 4 次出现"lead 报数与复现数不一致"（第三轮 dev 230 vs 224；第五轮 baseline 跨预算 +31 vs 同预算 +26；第六轮 alias 53 vs 52、holdout 153 vs 152；第七轮 `E_eq_G` 报 chunk 级 10% 而章节级 96.2%）。这不是诚信问题，是**口径没有唯一实现**的结构问题。建议：任何进入台账的数字，必须由第二人用 `scripts/audit_*.py` 跑出相同结果。

## 10. 审查后发现的一个新问题（2026-11-08 12:10 复核）

**评测脚本与生产服务端的引用纪律不是同一套。**

| 位置 | 用哪个函数 | 是否检查 evidence 长度 | 后果 |
|---|---|---|---|
| `scripts/eval_answer_quality.py:143-145` | `judge.citations_support` | **否** | 引文再短也不影响得分 |
| `src/arkrag/server.py:1285`（生产） | `answer.verify_citations` | **是**（`< MIN_EVIDENCE_CHARS=4` → `evidence_too_short`） | 会被清空答案并**转拒答** |

**当前影响：0 题。** 我用 `PROD_PROFILE` 同配置实测（`verify_citations` 后再判 vs 原始判）：
dev 228 → 228、holdout 152 → 152、被清空 **0/0** 题。所以现有读数不受影响。

**但这是结构隐患，两个方向都会出问题：**
- 若将来某条通道产出短引文（第五轮 N2 就是：alias 的 22 条 2~3 字引文），**评测会算通过、生产会拒答** —— 评测虚高。
- 反之若 `judge` 侧收紧，历史读数会整体下移，台账失去可比性。

**建议（不改判据，只改接线）**：`eval_answer_quality.py` 在 `judge_answer` 之前加一次 `answer.verify_citations(ans, chunks)` 并用其 `answer` 字段作答；同时把"被清空题数"作为一个独立计数写进报告（本报告红线 33 已是同一条要求，只是此前只约束"报数口径"，没约束"判分路径"）。

**同时确认的一条好消息**：删掉 `chapter_narrow` 后，`--prod` 三份读数为 228 / 152 / 97，与我第六轮独立复算逐格一致；`judge.py` 与 `gold-v2.json` 的 SHA-256 七轮全程未变。**当前 80.00% / 77.95% / 80.83% 是可信的、可复现的，但含义仍须按 §1 读。**
