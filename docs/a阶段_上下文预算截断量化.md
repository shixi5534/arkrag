# A 阶段补充：上下文预算截断量化（纯分析）

- 工具：`scripts/a_context_budget_probe.py`（只用标准库 + 仓库既有模块，零新增依赖）
- 逐题结果：`data/a_context_budget_probe.json`
- 范围：`primary=上下文未采用` 的 **74 题**，世代 `g-20261103T132152Z-06a741`，`top_k=20 / graph_depth=1`
- **性质：账面估算，不是端到端实测。** 没有重跑检索、没有重新回答、没有验证回答层是否真的变好。

## 方法（为什么可信）

不重跑检索：对每题重放**同一批** hits/expansions，先用极大预算跑一次 `build_context`，
拿到「完整有序单元表 + 每单元 token 成本」，再用**同一个贪心循环**在不同预算下重算。

**自检**：预算 6000 的重算结果必须逐题等于 `data/a_triage_all320.jsonl` 里记录的 `context_units`。
→ **74/74 逐题相等，自检通过。** 说明重放路径与生产一致。

## 问题 1：预算提到 8000/10000 能救多少

| 预算 | 74 题里 gold 进上下文 | 占比 | 全库 gold 进上下文（分母 300） | 占 300 |
|---|---|---|---|---|
| **6000（现状）** | 0 | 0.000 | 162 | 0.5400 |
| 7000 | 11 | 0.149 | 173 | 0.5767 |
| **8000** | **19** | **0.257** | 181 | 0.6033 |
| 9000 | 27 | 0.365 | 189 | 0.6300 |
| **10000** | **34** | **0.459** | 196 | 0.6533 |
| 12000 | 41 | 0.554 | 203 | 0.6767 |
| 15000 | 49 | 0.662 | 211 | 0.7033 |
| 20000 | 66 | 0.892 | — | — |
| 25000 | 74 | 1.000 | — | — |

救回 1 题所需最小预算：**中位 9900**，最小 6100，最大 24400。

**换算成上下文余量**：候选单元 token 中位 **1262**。6000 预算只装得下 **约 4.8 块**；10000 装 **约 7.9 块**。

### ⚠️ 一个必须记下的反直觉结果：加预算**不单调**

逐 200 token 扫描 6000→20000，**19/74 题存在「预算加到某个值，gold 反而被挤出上下文」**：

| 题 | 掉 gold 的预算点 |
|---|---|
| q-dr-000026 | 6400 / 7200 / 7800 / 8400 / 9400（反复抖动） |
| q-al-000035 | 12400 / 16400 |
| q-sc-000014 | 7600 |
| q-sc-000027 | 10400 |

原因：贪心是「按序扫、装不下就跳过继续」，预算一变，前面某个大块从「装得下」变「装不下」，
它让出的位置会让后面若干个小块挤进来，整张单元表随之重排。

**最小复现（3 个块就够，与语料无关）**：成本 `[5000, 3000, 1000]`，
预算 6000 → 保留 `[0, 2]`；预算 8000 → 保留 `[0, 1]`。**预算变大，索引 2 的块反而丢了。**
⇒ 贪心 `continue` 填充在预算增大时**不保证单调**，这是算法性质，不是数据巧合。

⇒ **「8000 一定不差于 6000」这个假设不成立。** 所以预算变更**不能只报总体均值**，
必须同时报「多少题变好、多少题变差」，否则会把「平均涨了但若干题跌了」报成成功。

## 问题 2：截断按什么顺序？（读代码确认，`src/arkrag/retrieve.py:850-869`）

排序键是 `(0 if direct else 1, -u["score"], u["chunk_id"])` —— 直接证据（bm25/entity）优先于纯图扩展，同层按分数降序。**排序本身是按排名来的。**

但填充**不是**「排名靠后的先截」：

```python
for unit in ordered:
    cost = estimate_tokens(...)
    if used_tokens + cost > budget_tokens:
        truncated.append(unit["chunk_id"])
        continue          # ← 关键：continue，不是 break
    used_tokens += cost
    kept.append(unit)
```

**是 `continue`，不是 `break`。** 所以一个装不下的块被跳过之后，**扫描不停止，后面更小的块仍然会被装进来**。

**实测后果：47/74 题（63.5%）存在「被跳过的块之后仍有块被保留」，这类被跳过的单元共 951 个。**
例：q-sc-000024 跳过 `activities/a001/level_a001_06_end#001`（1239 tok），却保留了它后面的 `activities/a001/level_a001_01_end#001`。

⇒ 这意味着截断**不是纯预算问题**，而是「大块被小块顶掉」。你猜的第二种机制成立。

### 但「改成 break」在 6000 预算下**救不了任何一题**

| 策略（预算 6000，排序完全不动） | 74 题里 gold 进上下文 | 保留单元中位 |
|---|---|---|
| 现状 `continue` | **0** | 5 |
| 改为 `break` | **0** | 4 |

原因：74 题的 gold 在有序表里的位置分布是 —— **位置 0-4：8 条、5-9：39 条、10-19：38 条、20-49：16 条、50+：5 条，中位位置 11.0**。
改成 `break` 只会更早停（保留 4 块而不是 5 块），**gold 中位在第 11 位，break 之后根本走不到那里。**

⇒ **单改装配策略（continue→break）不解决问题。要救这 74 题，必须让 gold 进入前 ~5 名，或者加大预算。**
这条很重要：它否掉了一个看起来「很便宜」的方案。

## 问题 3：同 doc 兄弟块挤占

**74 题里 33 题（44.6%）是「gold 不在上下文内，但同 doc 的兄弟块在上下文内」。**
⇒ 确实存在这个具体机制，但只占 44.6%，**不是主因**（另外 41 题 gold 所在的 doc 整个都没进上下文）。

### 每 doc 名额上限试算（纯装配，排序不动）

| 预算 | 不设上限 | 每 doc ≤2 块 | 每 doc ≤1 块 |
|---|---|---|---|
| 6000 | 0 | 0 | **6** |
| 7000 | 11 | 10 | 12 |
| 8000 | 19 | 20 | 20 |
| 10000 | 34 | 32 | 29 |
| 12000 | 41 | 38 | 30 |
| 15000 | 49 | 45 | 36 |

⇒ 只在**很紧的预算**（6000）下 cap=1 才有小幅收益（+6 题）；预算一旦松到 8000 以上，设上限反而**变差**（挤掉了本来能装下的无关块，没换来 gold）。
**结论：每 doc 名额上限不值得单独做。**（这与 `scripts/diagnose_ranking.py` 的历史扫描方向一致，属于又一次负结果，应记台账。）

## 四、结论与 P2 排期建议（已按「每轮只改一类变量」改写）

1. **加预算有效但收益递减、且不单调**：6000→8000 救 19/74（25.7%），→10000 救 34/74（45.9%），→15000 救 49/74（66.2%）。救回 1 题所需预算中位 9900。**真实口子，但不是免费的：延迟与输入 token 成本要一起算。**
2. **「只改装配策略」这条便宜路走不通**：`continue→break` 在 6000 预算下救 0 题（gold 中位在第 11 位，break 更早停）。**「大块被小块顶掉」机制确实存在（47/74 题），但规模不足以救题。**
3. **真瓶颈是「gold 中位排在第 11 位」**：74 题里 85/106 条未进上下文的 gold 卡在第 5–19 位。要让它们在 6000 预算内进来，得把它们推进前 5 名 —— **这是排序问题，不是装配问题。**
4. **每 doc 名额上限是负结果**：只在 6000 紧预算下 cap=1 有 +6 题；预算松到 8000 以上反而变差（10000 时 34→29，12000 时 41→30）。不值得单独做。

### P2 排期（每轮只改一类变量，不得合并）

原稿曾建议「预算 8000 + 排序改进」一起上，**这违反「每轮只改一类变量」的计划纪律，已撤回**。正确排期：

| 轮次 | 只改什么 | 固定什么 | 判据 |
|---|---|---|---|
| **P2 第一轮** | **只改预算 6000→8000**（纯配置，零代码风险） | 排序、装配策略、graph_depth 全不动 | 七项指标 + **逐题盈亏表**（变好/变差各多少题） |
| **P2 第二轮** | **只改排序** | 预算固定在第一轮选定的值 | 七项指标 + 逐题盈亏表 |
| 叠加验证（第三轮） | 两者的组合 | — | 只在两轮各自都有独立增益后才做，用来确认不冲突 |

**为什么第一轮选预算**：它是纯配置变更、零代码风险、可秒级回滚；而且 6000→8000 这一段实测**变差 0 题**（见问题 1 风险登记表），是当前最干净的对照起点。

## 五、P3 方向粗估：按 evidence span 计费/装填的杠杆

Lead 指出 `cost` 按整块全文算（`retrieve.py:859-863` 的 `estimate_tokens(f"{title} {chapter} {text}")`），
但 payload 里同时带着 `evidence_spans`。**若按 span 计费，同样的预算能装多少？**

实测（世代 `06a741`，抽样 10 题 / 351 个候选单元）：

| 计费方式 | 单元中位成本 | 6000 预算可装单元数 |
|---|---|---|
| **现状：整块标题+章节+全文** | **1261 tokens** | **约 4.8 个** |
| 仅 evidence span 原文 + 标题章节 | 31 tokens（1 条 span 中位） | 约 193 个 |
| **命中行 + 标题章节**（更保守） | **68.5 tokens** | **约 87.6 个** |

参考：单条 evidence span 文本中位 **24 tokens**（62,924 条断言的 `evidence_text`，均值 24.8、P90 39、最大 76）。

**压缩比 18–41 倍。** 每单元 span 数中位 **1**（均值 1.0，最大 11）—— 也就是说**一个 1261 token 的块，被用上的通常只有一行话、约 24 token**。

⇒ 这是比继续加预算**更便宜**的方向：它不改预算、不改排序，只改「装什么」。
但它会改变回答器看到的输入形态（从整块正文变成证据行集合），`src/arkrag/answer.py` 的
`_claim_supported_by_line` 与引用校验 `text[start:end] == evidence` 都依赖整块正文，
**必须先解决「span 装填后引用定位还能不能成立」这个前置问题**，否则会打坏当前 1.0000 的引用定位。
**本项只做粗估，不立项。** 建议等 Gate 0 过、P2 两轮做完再评估。
