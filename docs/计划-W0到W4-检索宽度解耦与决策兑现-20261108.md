|---|---|---|---|---|---|---|---|---|---|---|---|
| 进上下文 | 100 | 124 | 144 | 159 | 171 | 182 | 188 | **197** | 202 | **203** | 203 |

## W1 · 把「检索宽度」与「上下文宽度」解耦（cap 直接单元）

### 作用

现状：`top_k=20`（桥接题 40）**全部**作为直接证据候选进入 `build_context`，谁进上下文由 token 预算贪心决定。这造成两个后果：

1. **预算被深层名次吃掉**。12000 档均 9.86 单元 × 1272 token ≈ 12500，预算正好耗尽 —— 而 rank>10 的 gold 转化率是 **0/32**，即那 10 个槽位买到的 gold 是 0 题。
2. **非单调**。超预算时 `continue` 而非 `break`，实测 **193/350 单调性违规**，出现「gold 被砍、名次比它差的块反而进了 context」共 21 题（`truncation_overtake`）。

**cap 的数学性质**是：`top-k` 是**嵌套族**（`S(k) ⊆ S(k+1)`），所以任何 cap 策略**在数学上不可能有单调性违规**。而 `break` 策略虽也单调但每档少 1~5 题；cap 不需要这个牺牲，因为被砍的尾部本身 gold 转化率是 0。

### 为什么必须门控（这条是本次核算最重要的发现）

逐类「gold 落在 rank 9–20 的占比」：

| 类别 | rank9-20 / rank≤20 | 是否可 cap |
|---|---|---|
| single_chunk | **1/60 = 1.7%** | ✅ 可 |
| alias | **4/44 = 9.1%** | ✅ 可 |
| direct_relation | **5/30 = 16.7%** | ✅ 可（但转化率 0） |
| cross_chunk | 5/29 = 17.2% | ⚠️ 暂不 cap（W3 单独处理） |
| **multihop** | **17/30 = 56.7%** | ❌ **绝对不可** |
| time_conflict | 4/25 = 16.0% | 结构类，不进分母 |

`multihop` 有 56.7% 的 gold 在深层名次，且 `bridge_search_top_k=40` 就是为它加的 —— 对它 cap 等于拆掉桥接通路。所以 cap **只对非桥接、非 `cross_chunk` 题生效**，与 `graph_reserve_tokens` 恰好互补（后者只对桥接题生效）。

### 改动面

`src/arkrag/retrieve.py::build_context` 新增形参 `max_direct_units: int = 0`（0 = 现状，逐位等价）；`pipeline.py` 在 `ask_once` 里按门控传入。

```
opts["max_direct_units"]  # 默认 0
门控（在 pipeline 里，与 reserve 同一处）：
  if bridge.is_bridge_question(q):  → 0      # 不 cap
  elif qa 命中 chapter 触发词:       → 0      # 不 cap（W3 管）
  else:                            → 10
```

**为什么实现成"cap 直接单元"而不是"cap 检索条数"**：桥接候选来自 `context["units"]` 的断言（`bridge.find_bridge(question, context.get("units"), ...)`），cap 检索条数会同时砍掉桥接的候选池。cap 直接单元只砍"进上下文的量"，不动"检索/候选的宽度"。这是 W1 与 W2 能共存的前提。

### 预登记判据

| # | 判据 | 门槛 | 口径 |
|---|---|---|---|
| K1 | **cap 不丢 gold** | dev/hold/clean 三份 `pass` 均为 **Δ ≥ 0** | `--prod` 三份 |
| K2 | **单调性违规归零** | 从 **193/350 → 0/350** | 12000↔24000 两档比较 |
| K3 | **成本真降** | `ctx_tokens` 均 **23667 → ≤15000**（dev） | `timings["context_tokens"]` |
| K4 | **延迟不升** | P95 不高于现状 **136.6 ms** 的 1.05 倍 | 同批三份 |
| K5 | 逐题硬保证 | 非触发题（未 cap 的题）**九字段逐题零差异** | 答案 SHA / 三闸 / 拒答 / 引用条数 / units |

**K1 的预登记值**（我从 W0 前的数据推的，W0 之后按实测修正）：

- 若 W0 显示 24000 档 rank>10 转化 ≤ 1/32 → cap=10，三份 **Δ ≥ 0**，dev 期望落在 228~232
- 若 W0 显示 2~5/32 → cap 上调至 12 或 14，再报三份

### 反证条件（W1 失败的定义）

任一成立即回滚并记录：

1. 任一份 split 出现 `Δ < 0`（哪怕 −1）→ 立即回滚，cap 值上调重测
2. 单调性违规没降到 0（说明 cap 没按预期成为嵌套族，实现有 bug）
3. `cross_chunk` 或 `multihop` 任一题答案发生变化 → 门控写错，属实现事故
4. 答案均长上升（`mean_chars` > 现状 52.7 + 2）→ 说明腾出的预算被 claim 层吃了，不是被图单元吃了

### 回滚

`max_direct_units` 默认 **0**，改回默认即与现状逐位等价（`used_tokens + cost > direct_cap` 的判据不变）。测试用 `xfail(strict=True)` 之外的方式钉住：`tests/test_context_budget.py` 新增一条「cap=0 时 `kept` 逐块相同」。

### 预期收益（诚实版）

**不承诺 pass 上升。** 这条的首要价值是：

1. **消灭 193/350 这个悬案**（台账现在的处理是"缺陷保留，不改"，因为 `break` 要付 1~5 题）
2. 成本从 23.6k token 降到 ~13k，**为 W3 提供确定性空间**
3. 让后续所有预算实验第一次可解释（嵌套族下"加预算"才有单调含义）

若 W0 显示腾出的预算能被图单元用上，才可能有 pass 增益 —— **W0 之前不给数**。

## W2 · `multihop`：从「唯一才答」到「top-1 by support + margin」

### 作用

这是**三条里唯一一个上界被实测确定、且跨 split 稳定**的改动。

`bridge.py` 现在的策略是 `len(cand) > 1 → ambiguous`（不猜）。但实测：

| 指标 | dev 57 | holdout 39 | clean 24 |
|---|---|---|---|
| gold ∈ 接地候选集 | **57 (100%)** | **39 (100%)** | **24 (100%)** |
| 候选唯一（现行作答条件） | 25 (43.9%) | 10 (25.6%) | 6 (25.0%) |
| **gold 按 support 排 top-1** | **50 (87.7%)** | **31 (79.5%)** | **19 (79.2%)** |
| gold 按 support 排 top-2 | 56 (98.2%) | 38 (97.4%) | 23 (95.8%) |
| 现行生产档实际通过 | 27 (47.4%) | 14 (35.9%) | 8 (33.3%) |

两件事：

1. **候选集从不缺 gold（96/96）**，缺的只是"敢不敢选"。
2. **候选唯一率 43.9% → 25.6% → 25.0% 逐份下降，而 top-1 稳定在 88%/80%/79%** ⇒ **现行策略的瓶颈恰好长在 v2 新题上**，这是最强的改造理由。

### 红线 23 的作用域过期（必须写进报告）

红线 23 的原文是"dev 上候选内随机 21 > 排序 top1 19 ⇒ 排序是负收益"，那是**全图公共邻居**候选集上的测量。在当前**接地候选集**上重算随机基线：

```
E[random top-1] = Σ_q 1/k_q
                = 25·1 + 17·(1/2) + 5·(1/3) + 6·(1/4) + 3·(1/5) + 1·(1/6)
                = 37.43
观测 support-rank1 = 50
```

⇒ **50 > 37.4，排序在接地集上是 +12.6 的正收益。** 候选集从"全图"缩到"接地"后，随机基线自己从 21 塌到 37.4 的位置关系（k 变小）—— 红线 23 的结论**不能平移**。报告中必须并列这个计算，否则就是在无证据地推翻一条红线。

### 改动面

`src/arkrag/bridge.py::find_bridge` 新增策略参数；`pipeline.py` 传 `opts["bridge_policy"]`（默认 `"unique_only"` = 现状）。

```
bridge_policy ∈ {"unique_only"(默认), "top1_margin"}
top1_margin 的判定：
  cand 按 (-support_sum, -assert_count, degree_asc, name) 排序
  n == 1                      → ok
  n > 1 且 margin ≥ τ*        → ok（选 top-1）
  n > 1 且 margin < τ*        → abstain（落回原链路，不猜）
margin 定义：top1.support_sum − top2.support_sum
```

### 为什么必须带 margin 而不是无脑 top-1

`unjudged` 的代价不对称：答错会同时打掉 `negative_abstain` 的正判（"不知道"变"看起来确定的错"，台账 P3 靶子一那 6 道题的教训）。所以 cap 必须由 margin 控制，τ* 由 §W2.1 的分布决定。

### W2.1 τ* 的定法（先测后用，不扫参）

**第一步只落盘、不作答**：跑一遍 `top1_margin` 但不改变 answers，只记 `{n_cands, support_top1, support_top2, margin, gold_is_top1}`。产出 `data/diag_bridge_margin.json`。

然后用**代价比**定 τ*，不用 0.5 也不用网格：

```
拒答 ⟺ margin < τ*,  τ* = c_误答 / (c_误答 + c_误拒)
```

`c_误答 : c_误拒` 是**业务决策，一次定死写进常量注释**。本计划预登记取 **`c_误答 = 2, c_误拒 = 1` ⇒ τ* = 2/3**（理由：答错比不答贵一倍，因答错同时破坏 abstain 侧判据），并在报告里并列 τ* ∈ {1/3, 1/2, 2/3} 三档的分数作为敏感性披露 —— **但这三档不作为选优依据**，τ* 就被上面那个式子钉死。

### 预登记判据

| # | 判据 | 门槛 |
|---|---|---|
| M1 | **dev 主判据** | `multihop` 类 **27 → ≥ 45/57**（不是总分，是该类；避免其他类抖动掩盖） |
| M2 | **holdout 不回退** | `multihop` **≥ 31/39**（= top-1 上界）且总分 `Δ ≥ 0` |

## W3 · `cross_chunk`：输出截断到校准帽（cap）

### 作用

15 道失败可**互斥穷尽**地劈成两半：

| 形态 | 题数 | R（召回） | 属性 |
|---|---|---|---|
| `chapter_set_missing`（`W ⊄ O`） | **8** | 0.00 ~ 0.75 | 真·召回失败 |
| `extra_chapters_outnumber_gold`（`W⊆O` 但 `\|O\|>2\|W\|`） | **7** | **全部 1.00** | **纯基数失败** |

那 7 道（`\|W\|` / 输出章节数）：`000006` 2/9、`000027` 2/5、`000032` 2/10、`900008` 2/6、`900018` 2/5、`900022` 2/10、`900030` 2/7。

**它们把 gold 章节一个不落地全找到了，只因为多列了几章被判错。**

### 数学依据（为什么"截断到 4"永远合法）

gold 章节数分布（全 64 题）：`|W|=2 → 35 题`、`3 → 20`、`4 → 9`。⇒ **`min|W| = 2`**。

判据的精度闸是 `|O−W| ≤ |W|`，配合 `W⊆O` 等价于 `|O| ≤ 2|W|`。既然 `|W| ≥ 2`：

> **`|O| ≤ 4` 时 `|O| ≤ 2|W|` 恒成立。**

⇒ 截断到 4 章**不可能**触发 `extra_chapters_outnumber_gold`。这是可证的，不是调出来的。

### ⚠️ 唯一必须命名的风险：排序键质量未知

截断要保住 gold 章节，依赖一个**章节排序键**。而 `nh`（该章内正文含焦点名的单元数）**只被测过"当阈值用"**（`nh≥2` 掉到 2/38、`nh≥3` 归零），**从没测过"当序用"**。

**这是 W3 唯一的未知量，必须先出一个排序键对照表**：`nh` / 该章断言数 / 该章单元数 / 混合分，各算「top-4 内保住全部 gold 章节的题数」，四者并列。产出 `data/diag_cx_rank_keys.json`。

### 改动面

`src/arkrag/answer.py::_chapter_answer` 新增 `chapter_cap: int = 0`（0 = 现状，不截断）；`pipeline` 传 `opts["chapter_cap"]`（默认 0）。截断发生在 `chapters = sorted(by_chapter)` 之后、拼答案之前。

**cap 值不硬编码 4**：由 W3.1 的**风险控制**定：

```
给定风险 α（未兑现题中「截断导致漏 gold 章节」的比例 ≤ 5%）
在 dev 上取满足该约束的最小 cap
输出不是单个数字，而是 cap → (漏 gold 风险, 平均精度) 的表，冻结落盘
```

这是 [Bates et al., *Distribution-free, Risk-controlling Prediction Sets*, ACM TOIS 2021](https://dl.acm.org/doi/fullHtml/10.1145/3478535) 的形式：不拍数、不扫参，而是在 dev 上把风险约束解成 cap。

### 预登记判据

| # | 判据 | 门槛 |
|---|---|---|
| C1 | **dev `cross_chunk`** | **23 → ≥ 29/38** |
| C2 | **holdout** | **16 → ≥ 20/26** |
| C3 | **clean** | **12 → ≥ 13/16** |
| C4 | **零回退** | 三份逐题：现 pass 的题**一题不许掉**（尤其 `q-cx-900027`，`\|O\|=8 \|W\|=4`，会受截断影响） |
| C5 | **顺序键对照已出** | 先交 `diag_cx_rank_keys.json`，四键 top-4 保 gold 率并列；**未交不出分** |
| C6 | **random-entity 对照** | 必须并列「随机实体也能拿到多少」——现测 `true_ent 30/38` vs `rand_ent 21/38`，若本方案的真实增益落在随机区间内，判注水 |
| C7 | **`gold ⊆ 允许集` 比例** | 报出截断后 `W ⊆ O` 的比例（红线 36），≥95% 一律判注水 |

### 反证条件

1. C5 的排序键表显示「任何键的 top-4 保 gold 率 < 90%」⇒ **cap 不成立**，W3 撤回（不能靠截断保住 gold）
2. C4 有任一题回退 ⇒ 回滚（说明 cap 命中了一道 pass 且 `|O|>4` 的题）
3. C6 显示真实实体与随机实体同分 ⇒ 判注水，撤回

### 回滚

`chapter_cap` 默认 0。且 `CHAPTER_ANSWER_PATH` 本身有开关，两道回滚点。

### 口径订正（必须写进报告）

台账写「`cross_chunk` 剩余缺口 **100%** 在容量层」。**这条对 8 道 `missing` 成立，对 7 道 `outnumber` 不成立** —— 它们缺的是精度不是容量。本工作项就是这个订正本身。

另：今早 `tmp_cxfilter` 用 `entity["chunks"]` 拿到 **+7/+5/+1**，被审查判为"索引直读"。**+7 这个数量级是对的，但机制用错了** —— 同样 +7 可以靠"输出截断"拿到，完全不需要读 `entity["chunks"]`。报告里应当把这两件事并列，说明"同一个数字可以由注水机制或合法机制产生，必须靠机制区分"。

## W4 · 判据 v2 双口径（不加分，但让分数有意义）

### 作用

这是唯一一件**必然让分数下降**的工作项，也是唯一一件让所有其他数字**可以被相信**的工作项。

现行判据的三处结构性缺陷（本次核算）：

1. **无精度项** ⇒ `multihop` 的最优策略是"全列候选"，唯一刹车是 `merge` 的 8 句。
2. **F1 非单调** ⇒ 实测 345 个配对里有 **5 个逆序对**：`q-cx-000011`（P=1.00, R=0.75, **F1=0.857**）被判 **FAIL**，`q-cx-900027`（P=0.50, R=1.00, F1=0.667）被判 **PASS**。
3. **基数闸退化** ⇒ `min|W|=2` 使 `|O|≤2|W|` 在 `|O|≤4` 时恒真，extra 真实性校验是空的。

### 三轴判据

```
judge_v2(category, ans, item) →
  value_ok        # 每类一个纯函数（集合/串运算），与 v1 同源
  support_ok      # 每条答案值必须有**本次 ctx** 的 assertion 支撑
  cardinality_ok  # multihop: |实体| ≤ 锚点数+1；cross_chunk: |O| ≤ cap
  loss = w1·¬value_ok + w2·¬support_ok + w3·cardinality_over   # 连续量
  pass = loss ≤ τ
```

三处收紧，全部是**收紧**不是放松：

| 轴 | v1 | v2 | 治什么 |
|---|---|---|---|
| support | `judge_answer` 不消费 citations | 每条值必须能回指本次 ctx 的 assertion | 形状 oracle 100% → 归零；"纯模板 vs 真三元组 marginal=0" 同型 |
| cardinality | `multihop` 无 | `\|实体\| ≤ 锚点数+1`（2 锚点 ⇒ ≤3） | "全列候选"从免费变有成本 |
| cardinality | `cross_chunk` `\|O\|≤2\|W\|`（恒真） | `\|O\| ≤ cap`（cap 由 W3 校准） | 从"永远满足"变"真约束" |

### ★ 内置证伪：判据 v2 必须让分数**下降**

> **若 `judge_v2` 跑出的 dev 分数 ≥ 当前的 228，说明它没有真正收紧，判 v2 设计失败。**

理由：现有 80% 里 23.86 点是泄漏地板、100% 是形状 oracle、7 道 `outnumber` 是纯基数送分。一个真带精度项 + 支撑项 + 基数项的判据，**在同一个答案集上必然打得更低**。分数掉下来是"判据变硬了"的证据。

**这一条把"改判据涨分"这个红线方向变成了自我否证 —— 涨分就是失败。**

### 评测口径同时升级

| 项 | 现在 | v2 |
|---|---|---|
| 主指标 | `pass / 可判分母` | `(pass − 泄漏地板)/(1 − 泄漏地板)`，归一化到 [0,1] |
| 次指标 | 无 | 每类 `P/R/F1` 曲线、`cap` 曲线、`margin→pass` 曲线 |
| CI | 配对 bootstrap（假设 iid） | **按模板聚类的 cluster bootstrap** |
| 分母 | 可判 / 全 | 再加「去重后唯一题数」（4 组题 gold 完全相同） |
| 地板 | 注脚 | **每次必报三行**：回显题干 23.86% / 形状 oracle 100% / gold 原文 60% |

**为什么必须换聚类 CI**：实测 `dev × holdout` 3-gram Jaccard ≥0.6 的近似重复 **1,802 对**（alias 739 / cross_chunk 493 / multihop 322），题面是模板生成的。按 `m̄≈2.5, ρ≈0.6` 估，**方差膨胀 ≈1.9，CI 宽度膨胀 ≈1.4**。用它复核已采纳的三条通路：`quote_locate` p=0.0021→仍显著、`bridge` CI[+5,+18]→下界 3.6 仍显著、`graph_reserve` hold p=0.1562 本来 FAIL。**三条都不会被推翻，但"显著"的强度要打折。**

### 判据 v2 的落地方式（守红线）

- `judge.py` **一字节不动**（红线 1）。新增 `src/arkrag/judge_v2.py`，`eval_answer_quality.py` 加 `--judge v1|v2|both`，默认 `v1`
- 双跑：同一批答案两套判据并行记分，**两套数并列报**
- `gold-v2.json` 一字节不动（红线 9）
- 结构类 65 题：仍剔分母，但**记为数据缺陷**（`time_conflict` gold 是常量）并进待办，不记作判据缺陷

### 验收

| # | 判据 | 门槛 |
|---|---|---|
| J1 | **分数必须是降的** | `judge_v2` 的 dev < 228，且降幅 = 「无支撑通过数 + 基数越界通过数」，两者之和必须能逐题对上 |
| J2 | **逆序对归零** | v2 在 `cross_chunk` 上的 F1 逆序对从 5 → 0 |
| J3 | **v1 不受影响** | `--judge v1` 的两份产物与提交前**逐题逐字段相等** |
| J4 | **聚类 CI 并列** | 三份同时报 iid CI 与 cluster CI，并写明方差膨胀倍数 |
| J5 | **地板三行必报** | 报告模板加硬性三行，缺一判失败 |

### 反证条件

1. `judge_v2` 的 dev ≥ 228 ⇒ **v2 没收紧，设计失败**，重做
2. 降幅对不上「无支撑 + 基数越界」的逐题计数 ⇒ 实现有 bug
3. `--judge v1` 与提交前有任何差异 ⇒ 违红线 1，立即回滚

### 回滚

`--judge` 默认 `v1`；`judge_v2.py` 是独立文件，删掉即完全恢复。

## 6. 外部依据（联网核过的部分）

本计划的三条设计不是自创，各自有一篇对应的工作：

| 本计划 | 外部依据 | 用它的哪一部分 |
|---|---|---|
| W1（cap） | [**Retrieval Saturation: Diminishing Returns of Top-k**](https://www.tmls.nyc/research/retrieval-saturation)（TMLS AI Research, 2026） | 它的核心模型是 `Q(k) = (1−e^{−αk})·e^{−λk}`，单峰，最优点 `k* = (1/α)·ln(1+α/λ)`。**它的 presence 项正是我这张累计表**；它给的 k* 闭式解说明"最优 k 由检索accrual率与读者derailment率共同决定"，而不是拍数。它同时给出一个**噪声注入探针**（Eq.13）用 log-accuracy 对注入干扰项的斜率估 λ —— 这正是 W0 之后可以补的一步 |
| W3（章节 cap） | [**Distribution-free, Risk-controlling Prediction Sets**](https://dl.acm.org/doi/fullHtml/10.1145/3478535)（Bates et al., ACM TOIS 2021） | 集值预测 + 基数惩罚 + 分布无关风险控制。本项目 `\|O\| ≤ 2\|W\|` 就是这类损失里最粗暴的阶跃型基数惩罚；用它把 cap 从"拍 4"变成"解风险约束" |
| W4（判据） | [**Why Language Models Hallucinate**](https://ar5iv.labs.arxiv.org/html/2509.04664)（Kalai / Nachum / Vempala / Zhang, OpenAI, 2025-09） | 论文原话：在 0-1 评分下"**awards 1 point for a correct answer and none for blanks or IDKs**"，则"永不表达不确定"的 Model B **必然胜过**"会表达不确定"的 Model A，形成"惩罚不确定性的流行病"。它的处方是**改现有 benchmark 的打分函数**而不是加新 benchmark。本项目四条判据全是 0-1 阈值、`abstain_accuracy` 的 Bayes 最优是永不拒答（基率 π=7.89%，Chow 规则要求似然比 ≥6.3，不可得）—— 逐条命中 |
| W4（CI） | [**Lost in the Middle**](https://sinoxiv.napstic.cn/article/5361320)（Liu et al., 2023） | 只借它的"位置影响被系统性低估"这条方法论。对**抽取式**读者没有文档级位置效应，但 **`MAX_CLAIMS=8` 的截断就是同一件事在 claim 粒度上的投影** —— gold claim 被"埋在中间" |

**免责**：`Retrieval Saturation` 那篇自己声明"we ran no experiments"，所有数字都是引用别人的。所以它的 k* 公式只能用作**框架**，α/λ 必须在本项目自己的数据上标定（这正是 W0 的用途）。不能把它的结论当"已验证有效"。
