# 引用覆盖的第五道闸门：抽到了，被准入判据挡掉

> 一句话结论：旧的四闸门把「gold 那句话**已经被抽成断言**、但被
> `retrieve._assertion_relevant()` 判成不相关而**根本没登记**」这一类，
> 合并记进了「抽取没抽到」。这两件事对 P3 是完全不同的活。
> 拆开之后：**改引用粒度救 38 题、补抽取救 68 题、改准入判据碰 19 题 —— 三者互斥。**
>
> **2026-11-05 二次更正（A 指出，我认）**：首版报闸门1b 29 题，其中 5 道 `multihop`
> 是**我自己的判定顺序错**——先判 `admit` 再判 `incl`，把「块根本没进上下文」
> 错记成「进了但被准入挡」。改成先判 `incl` 后，闸门1b = **19 题，全部 `single_chunk`**。
> 连带结论：**旧文档的 `51/72 = 0.7083` 是对的，首版宣布它作废是错的**（`82` 才是错的）。
> 详见 §5 与 §8。

生成命令：`py -3 scripts/lead_gate_recheck.py --json data/lead_gate_recheck.json`

## 0. 为什么写这份

`docs/lead_引用覆盖漏斗实测.md` 里那条四闸门漏斗（成功 51 / 闸门1 106 / 闸门2 122 / 闸门3 21）
被反复引用，还派生出了 `51/72 = 0.7083` 这个「条件口径」。但那次统计用的判据是
「required 句能不能在断言 `evidence_text` 里找到」，**没有区分「断言不存在」与「断言存在但被过滤」**。

`build_context` 的第 1 步在遍历 hits 的块时，对每条断言调
`retrieve._assertion_relevant(rec, focus_ids, hint_predicates)`：

```python
def _assertion_relevant(rec, focus_ids, hint_predicates):
    # 判据只有两条
    #   1) subject_id 或 object_id 落在焦点实体集合里
    #   2) predicate 命中关系提示 relation_hints
```

不合格的断言**根本不进 `unit["assertions"]`**。回答层不是「不发这条引用」，
是**连这条断言都没见过**。

## 1. 六态漏斗（v1 320 题里的 300 道应答题，现场代码真跑）

`pipeline.ask_once()` 逐题实跑，`retrieve.COOC_BOOST_WEIGHT` 两档对照：

| 闸门 | cooc0.0（基线） | cooc0.1（候选） |
|---|---|---|
| covered（成功覆盖） | 51 | 55 |
| 闸门3 块在手没发引用 | 2 | 1 |
| 闸门2 块没进上下文 | **122** | **119** |
| **闸门1b 断言在、但被相关度过滤** | **19** | **19** |
| 闸门1L 仅整行可救（断言在、只是切了片段） | 38 | 38 |
| 闸门1 抽取缺（那一行根本没被抽） | 68 | 68 |
| 合计 | 300 | 300 |

判据口径（逐题取**最坏一条 required**，六态互斥）：

- `frag_rescuable` / 可达层级：先问「required 句是不是某条断言 `evidence_text` 的子串」
  → 是则 **span 可达**；否则看「required 句是不是落在某条断言所在的**整行**里」
  → 是则 **仅整行可救**；否则 **抽取缺**。
- span 可达之后，**先问 required 那块进没进上下文**（没进 = 闸门2），
  再问那条断言**过没过准入判据**（没过 = 闸门1b），都过了但没发引用 = 闸门3。

**判定顺序为什么必须是「先 incl 后 admit」**：块没进上下文时 `_assertion_relevant`
根本没机会执行——那条断言不进 `unit["assertions"]` 是因为**块不在**，不是因为被判不相关。
先判 1b 会把 P2 的活算进 P3 的口径，分母跟着虚增（v1 上 29 vs 19）。

两档归类不同的题只有 5 道（`q-dr-000010` / `q-dr-000024` / `q-dr-000038` / `q-dr-000041`
闸门2→covered，`q-tc-000007` 闸门3→闸门2），其余 295 道完全一致。

## 2. 三集合互斥（这是本轮最有用的一条）

**口径必须统一到「最坏一条 required」**——第一版这里用了两个不同分母
（frag 用「任一 required 整行可救」、gate 用「全部 required 都 span 可达」），
算出来 `frag ∩ 闸门1 = 55`，看着像「整行可救的题大多也是抽取缺的」，
实际是口径错配，真值 **0**。

| 集合 | 题数 | 该改哪里 |
|---|---|---|
| frag（整行粒度可救） | **38** | 改 `src/arkrag/answer.py` 的引用粒度 |
| 抽取缺口（那一行没被抽） | **68** | 补抽取 / 改 gold 挖掘路径 |
| 闸门1b（span 可达、被准入挡） | **19** | 改 `retrieve._assertion_relevant` 的输入侧 |
| 已覆盖 | 51 | — |

`frag ∩ 闸门1b = 0`、`frag ∩ 抽取缺口 = 0`、`闸门1b ∩ 抽取缺口 = 0`，
三者合计 125；再加上闸门2 的 122、闸门3 的 2、已覆盖的 51，正好 300。

⇒ **三件不同的活，任何把它们合成一个「天花板」的说法都会导致修错地方。**
P3 第一轮做整行引用，预期收益上界就是 **38 题**（不是 55、也不是更早算的 21）。

## 3. 19 道闸门1b 的画像

| 维度 | 数 |
|---|---|
| 题数 | **19** |
| 按题型 | **`single_chunk` 19 / 其他 0** |
| `gold.answer` 恰等于 required 块的 `title` | **19 / 19** |
| `required.evidence` 被问句原样引用 | **19 / 19** |
| 问句里含「」引文 | **19 / 19** |
| 强行放行后 claim 层仍立不住（按含 gold 那句的那条断言判） | 3 / 19 |

机制：这类问句把「要引用的原句」直接放进「」里问，那句话里**既不是实体名、也不是关系词**。
典型 `q-sc-000001`：gold 那条断言是「导火索 —交谈→ 艾拉」，两个端点都不是问句的焦点实体，
谓词「交谈」又不在 `relation_hints`（问句里没有关系词）⇒ 判不相关。
`data/a_gate1b_diag.json` 的 `blocked_reason` 是 `{"endpoint_not_focus": 25, "predicate_not_hint": 25}`
（A 在 dev 350 上的口径），两个原因 100% 同时成立。

**被更正掉的 5 道 multihop**：`q-mh-000010`（罗德岛）/ `-000015`（凯尔希）/ `-000017`（煌）/
`-000021`（小黑）/ `-000043`（阿米娅），实测 required 块 `in_context = False`。
放行准入对它们零作用，它们要图扩展，是 P2 的活。

## 4. 最要紧的一条：准入放行后覆盖率能过，答案还是错的

| 维度 | 数 |
|---|---|
| required 块已在上下文 | 19 / 19 |
| 准入放行后 `required_citation_coverage` 会变真 | **19 / 19** |
| 准入放行后答案文本**仍不含** gold 答案 | **19 / 19** |
| **既会过覆盖率、又答不上** | **19 / 19** |

19 道**全部是 `single_chunk` 标题题**，答案文本含 gold 答案的是 **0 道**（多数是空答案或三元组）。

原因：这 19 道题的 gold 答案就是块 `title`，而抽取式回答器只会输出「主体 谓词 客体」。

⇒ **修准入判据能把 `required_citation_coverage` 抬 19 题，但抬不动一题答案质量。**
这条决定了报告口径：任何「引用覆盖涨了 X 题」的行，必须并列
「答案文本含 gold 答案的题数涨了没有」。只涨前者，只能记作**口径修正**，不能记作质量提升。

A 按同一思路在 dev 350 上真跑四条放行规则，得到同向结论（`data/a_gate1b_rules.json`）：
`quote` 覆盖 +17 / 正确覆盖 +0；`any_predicate` 与 `admit_all` 把拒答从 30 打穿到 **0**、
还打坏 5 道 alias ⇒ 后两条**判死，连备选都不算**。

## 5. 引用覆盖的分母全表（含一次「我自己宣布作废又撤回」）

| 口径 | 分子/分母 | 值 | 说明 |
|---|---|---|---|
| 混合（旧） | 51 / 300 | 0.1700 | 被三种失败稀释，只做对外汇报 |
| 断言层可达 | 51 / 194 | 0.2629 | 中口径 |
| **两道准入闸都过** | **51 / 72** | **0.7083** | **P3 盯这个**（72 = covered 51 + 闸门3 2 + 闸门1b 19） |
| ~~51 / 82~~ | ~~51 / 82~~ | ~~0.6220~~ | **首版分母算错，作废**（把 29 当成 19，多算 10 道闸门2） |

**必须写明这段**：首版我宣布 `51/72` 作废、改成 `51/82 = 0.6220`；A 用另一条路径
（先按因果顺序重排闸门判定）复现出 25 题（dev 350）并指出 5 道 multihop 属闸门2，
我据此修掉自己的判定顺序、重跑得 19 题。**19 + 2 + 51 = 72，旧分母本来就是对的。**
教训：当一个新拆出来的集合恰好让旧分母「变成错的」时，要先怀疑新集合本身，
用另一条独立路径复算一遍，再动手删旧数字。

`72` 的含义：断言层可达（`span` 或 `line` 能拿到 required 那句话）、
且没有被上游检索闸拦掉的全部题。这是 P3 真正的作业面。

## 6. 对 A 的 P3 第一轮（整行引用）与第二轮（标题通路）的影响

1. **整行引用的预期收益上界 38 题**，不是 55、也不是 21。19 道闸门1b 不在其中（`frag ∩ 闸门1b = 0`）。
2. **四数必须报**：引用总条数 / 逐条定位通过率 / 覆盖率 / 答案文本含 gold 答案题数。
   第三条会涨 38 题量级，第四条**可能几乎不涨**（整行引用不改变「只会三元组」这件事）。
3. **`_claim_supported_by_line` 的输入也会变**：它读 `claim["start"]` / `claim["end"]`。
   整行引用若只改 `citations` 里的 `evidence` 与 span、不传给 claim 层，这一层不受影响；
   若同时改，就不是单变量，要停下报告。
4. **标题通路的上界是 19+ 量级，且必须两档报**：闸门1b 这 19 道全部是标题题，
   而标题题里答案直接写在问句「」引文之外/之内的比例要单独统计（A 报 dev 350 上
   76 道标题题里 23 道答案泄露在问句里）。**只报含泄露的那一档会把「从问句抄答案」
   算成能力提升。**
5. **`51/72 = 0.7083` 恢复有效**，`51/82` 作废。

## 7. 限制

1. 本节所有数字都来自 v1 320 题（300 应答题）在**当前工作区代码**上的真跑，
   `src/arkrag/answer.py` 与 `src/arkrag/retrieve.py` 均有 A 的改动（cooc0.1 与整行开关）。
2. 六态归类依赖「整行」的边界定义（`_line_bounds`：`\n` 到 `\n`），换块切分方式会变。
3. `frag` 38 题是**结构上界**：改发整行之后能不能真的覆盖，还取决于回答层会不会把
   那条断言选进 claim（`answer.py` 的 `MAX_CLAIMS = 5` 与 `_claim_supported_by_line`）。
   上一轮已实测 P3 第一轮整行引用真跑：覆盖 63→82（救 19 丢 0），但答案质量 0 变化，
   且 `citations_distinct` 2103→2057（塌缩 46 条、受影响 42 题 = 11.1%）。
4. 闸门1b 里「claim 层立不住」只算了 3 道——这个数**依赖 `_claim_supported_by_line`
   的偏移输入**。第一版只喂 `subject`/`object`/`predicate` 时它恒返回 `False`
   （函数先校验 `start`/`end`，非法直接 `ok=False`），得出「25/29 立不住」的假结论。
   凡是给判据函数喂参数，**必须对照它的函数签名逐个字段确认**。
5. 分母 72 只在 `single_chunk` 题目上成立的部分较多：19 道闸门1b 全是 `single_chunk`，
   所以这个分母对 `multihop` / `cross_chunk` 是**偏乐观**的，分类别报时要另算。
6. 两档（cooc0.0 / cooc0.1）分母不能混用：cooc0.1 的对应分母是 `55 + 1 + 19 = 75`。
