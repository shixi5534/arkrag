## 0. 先看这一节：一个必须先接受的结构性事实

题目给的现状是：

| 类别 | 现状 | 分母 | 剩余空间 | 计入分母 |
|---|---|---|---|---|
| single_chunk | 69/76 | 76 | +7 | ✓ |
| alias | 52/57 | 57 | +5 | ✓ |

| **multihop** | **8/57** | 57 | +49（但见下） | ✓ |

而本项目台账已经把两个"洞"的真实天花板钉死了：

- **multihop 天花板 13/57 = 22.8%**。`docs/会话交接-20261107.md` 的逐环节漏斗：gold 在图里 57/57、gold 进 context 53；第一跳（边在/载块进 hits/断言挂上）= 57/39/34；第二跳 = 57/**35**/28/27；**两跳同时挂上只有 13 题**；claims=8 兑现 8 题。也就是说 multihop 最多再捞 **+5 题**。
- **cross_chunk 天花板由上下文容量决定**：`docs/分析-cross_chunk判据.md` 实测 B=6000 时"gold 全部章节都在 context 里"的可达题数 = **15/38**，B=12000 = **22/38**；而 `superset` 集合与这个 `ceiling` 集合逐题完全重合（对称差为空）。

**所以：multihop + cross_chunk 两个洞加起来现实可捞约 +5 ~ +11 题，离 +30 还差 20 题。剩下 20 题只能从前三类（single_chunk +7 / alias +5 / direct_relation +7 = +19）里挖。**

这条推导决定了第 6 节方案清单的排序：**不能把全部预算压在 multihop 上**。文献调研的价值在于告诉你哪些 multihop 手段值得做（第 1–3 节），以及哪些是已经被别处证否的坑（第 1.11、2.4、4.4 节）。

## 1. GraphRAG 家族的多跳检索策略：可抄的算法与超参

### 1.1 谱系速览

| 系统 | 多跳怎么走 | 路径/节点怎么打分 | 上下文怎么装 | 爆炸怎么控 | 关键超参 |
|---|---|---|---|---|---|
| **Microsoft GraphRAG** | 不走路径：预生成社区摘要，global search 逐社区出 partial answer 再 reduce | 无路径分；靠社区层级 + LLM 生成 | 单 context window 塞实体/关系/社区报告/text unit 五路候选 | 社区划分天然有界 | chunk 1200 token（GraphRAG-Bench 统一设定） |
| **GraphRAG Local Search** | **实体为入口**：命中实体 → 拉其 text unit / 关系 / 社区报告 / covariate | 各路各自 ranking + filtering | 五路候选全部塞进**单个** pre-defined size 的 context | 靠 candidate 数上限 | `context_builder`（mixed_context.py）、`context_builder_params` |
| **GraphRAG DRIFT** | global→local 交替：Primer 出 follow-up 问题 → 每个 follow-up 跑 local search 继续出问题 | **每个节点一个 glyph = 继续扩张该 query 的置信度** | 三层 question/answer 层级，按 relevance 排序输出 | **用 tokenizer 跟踪算法预算** | `tokenizer`、`query_state`、`drift_search_config.py` |
| **LightRAG** | dual-level：low-level 命中实体节点、high-level 命中关系边，取**一跳邻居并集** | 向量相似度（无路径分） | 实体 profile + 关系 profile + 原文 chunk | top_k 截断 | `top_k=60`、`chunk_top_k=20`、`max_entity_tokens=6000`、`max_relation_tokens=8000`、`max_total_tokens=30000`、`chunk_token_size=1200`、`overlap=100`、`gleaning=1`、`cosine_better_than_threshold=0.2`（二手整理） |
| **HippoRAG / 2** | **PPR 在 KG 上扩散**，种子 = query 里识别出的实体 | `p'·P`（PPR 稳态 × passage-node 关联矩阵）；种子乘 **node specificity `|P_i|^{-1}`** | 取 PPR top-k passage | PPR 本身衰减 | **damping/restart = 0.5**；synonymy 边阈值 **cos > 0.8**；MuSiQue 上语料 11,656 passage / 91,729 node / 21,714 edge |
| **RAPTOR** | 不走图：自底向上聚成树，查询时**跨层联合检索（collapsed tree）** | 余弦 | 全层一起取 top-k 直到 token 上限 | token 上限 | 叶节点 **100 token**、`multi-qa-mpnet-base-cos-v1`、GMM+UMAP 软聚类（BIC 选簇数）、**max 2000 tokens ≈ top-20 节点** |
| **PathRAG** | 关键词命中节点 → **资源流动剪枝**后枚举路径 | 节点资源 `S(v_i)=Σ α·S(v_j)/|N(v_j,·)|`；路径可靠性 `S(P)=(1/|E_P|)Σ_{v∈V_P} S(v)` | **最可信路径排最末**（利用 lost-in-the-middle 两端黄金区） | 早停：`S(v_i)/|N(v_i,·)| < θ` 剪掉；每节点资源最多更新一次 | α（衰减）、θ（剪枝阈值）、N（种子节点数） |
| **LinearRAG** | relation-free 三图（entity/sentence/passage）；**迭代激活 + 阈值剪枝**，n 跳需 n 次迭代（n≤4） | 式(5) `a_q^t = MAX(Mᵀ(σ_q ⊙ (M a_q^{t−1})), a_q^{t−1})`；再在 passage–entity 图上跑 **PPR d=0.85**；passage 初值式(7) | 激活到的 passage | **按分数阈值 δ 自动停**（无新实体超 δ 就停） | PPR d=0.85、阈值 δ、λ（式7 权衡） |
| **ConRAG** | **端点对端点**：确保两侧锚点各有 seed → **DFS 枚举 d→e→d′ 路径** → 无路径退化为单条最短路 | 式(3) `S(P) = (1/L)·Σ_i cos(v_q, v_{d_i})`（**长度归一**）；**按长度分桶、每桶各取 k_path** | `R_seed ∪ R_path` | `L ≤ L_max`、hub 抑制（度 > `p_hub` 分位数的实体从邻接表删除）、df<2 实体直接丢弃 | `k_seed`、`k_path`、`L_max`、`p_hub`、`n_max`（短语 token 上限）；平均检索 doc 数 **10.8** |
| **IndexRAG** | **入库期**识别跨文档 bridge entity，把 bridging facts 生成为**可独立检索单元** | 无路径分：单趟检索 + 单次 LLM 调用 | 原文 + bridging facts 同池竞争 | 靠索引设计 | 无训练；F1 比 Naive RAG 平均 **+4.6**（HotpotQA/2Wiki/MuSiQue） |

### 1.2 对本项目最直接的四条可抄机制

**(A) ConRAG 的"端点对端点"检索流程**——与本项目 multihop 的题面完全同构（已知两个锚点，问中间实体）。它的 Algorithm 3.4 只有 10 行，抄法：

1. 抽 anchor/target；
2. dense seed 取 top-`k_seed`；
3. **强制两侧锚点各有 seed**（原文点明"单边 seed 集是 dense top-k 的常见失败"）——缺哪侧就从语料注入含该实体的 doc；
4. DFS 枚举 `d→e→d′` 两跳路径；
5. 按 `S(P) = (1/L)·Σ cos(v_q, v_d)` 打分；
6. **按路径长度分桶，每桶各取 k_path**（避免短路径系统性压过长路径）；
7. 返回 `R_seed ∪ R_path`。

其中第 3 条对本项目的含义很直接：**`expand()` 目前是把两个锚点一起丢进 seed 集做 BFS，谁先被访问到谁就先占预算**，而"确保两侧都有承载块"这件事没有被显式保证。台账里"第二跳：边在 57 / 载块进 hits 只有 35"正是单边偏斜的症状。

**(B) ConRAG 的 `df(e) ≥ 2` 硬过滤**——原文理由：`a mention confined to one document cannot connect two documents`。落到本项目：**一个实体如果只出现在一个 chunk 里，它不可能当桥。**

**(C) ConRAG 的 hub 抑制 + LinearRAG 的阈值剪枝**——本项目 `expand()` 已有 `max_degree_per_entity`（同源机制），但它是**固定节点数上限**；LinearRAG 的做法是**按分数阈值 δ 停**（"没有新实体超过 δ 就自动停止"）。两种都在预算键里，差别是自适应 vs 固定。

**(D) DRIFT 的"用 tokenizer 跟踪预算" + "confidence glyph 决定是否继续扩张"**——本项目 `expand()` 的预算键是 `max_nodes / max_edges / max_degree_per_entity / max_assertions`，本来就是 token/节点双预算；缺的是"继续扩张值不值"的**边际收益判据**。PathRAG 的 `S(v_i)/|N(v_i,·)| < θ` 早停就是这个判据的最小实现。

### 1.3 GraphRAG-Bench 的冷水（必须写进结论）

GraphRAG-Bench（arXiv:2506.02404v2，2025，PolyU + 腾讯优图；1018 题 / 16 学科 / 20 本教材 / 7M 词；统一 k=5、chunk 1200 token、GPT-4o-mini）评了 9 个 GraphRAG 系统，生成准确率均值：

| 方法 | 准确率 | 检索耗时 |
|---|---|---|
| GPT-4o-mini 裸 | 70.68 | — |
| BM-25 | 71.66 | — |
| TF-IDF | 71.71 | — |
| DALK | **69.30 ↓** | 26.8s |
| G-Retriever | **69.84 ↓** | 23.77s |
| LightRAG | 71.22 | 13.95s |
| ToG | 71.71 | 70.53s |
| KGP | 71.86 | 89.38s |
| GFM-RAG | 72.10 | 1.96s |
| GraphRAG | 72.50 | 44.87s |
| HippoRAG | 72.64 | 2.44s |
| **RAPTOR** | **73.58（最佳）** | **0.02s** |

建图 token 成本：RAPTOR 10.1M 最省，LightRAG 83.9M / GraphRAG 79.9M 最贵。非孤立节点率：KG 类 ~90%，LightRAG 69.71%，GraphRAG 72.51%，KGP 46.03%。

**两条结论**：
1. **不是所有 GraphRAG 都能提升 LLM**——DALK 和 G-Retriever 反而比裸模型低，作者归因于"过度依赖结构信息丢了语义"。G-Retriever 恰恰是那个用了 PCST 精美子图优化的系统。

### 2.1 三个数据集的判据口径（与本项目判据同源）

| **MuSiQue** (TACL 2022, arXiv:2108.00573) | 25K 条 2–4 跳，bottom-up 组合 | 单跳模型 F1 **掉 30 点**；人机差距 ×3；另有 unanswerable contrast 集 | 与本项目「结构类不计分但必须不退化」的设计同构 |

### 2.2 迭代检索：IRCoT 与 MDR 的具体做法与数字

**IRCoT**（ACL 2023，arXiv:2212.10509）：把检索与 CoT 句子**交错**——每一步用当前推理句去检索，检索结果反过来改下一步 CoT。核心论点 "what to retrieve depends on what has already been derived"。GPT-3 上**检索 +21 点、下游 QA +15 点**（HotpotQA / 2Wiki / MuSiQue / IIRC）；小模型 Flan-T5-large 免训练也有收益。 [来源: https://arxiv.org/abs/2212.10509 ]

**MDR**（ICLR 2021，arXiv:2009.12756v2）：

```
P(P_seq|q) = Π_{t=1..n} P(p_t | q, p_1..p_{t−1})
P(p_t | ·) = exp(⟨p_t, q_t⟩) / Σ_{p∈C} exp(⟨p, q_t⟩)
q_t = g(q, p_1..p_{t−1}),  p_t = h(p_t)
```

推理用 **beam search 取 top-k 序列，beam 按内积和打分**；HotpotQA 固定 n=2。

HotpotQA 检索（R@2 / R@10 / R@20）：

| 方法 | R@2 | R@10 | R@20 |
|---|---|---|---|
| TF-IDF | 10.3 | 29.1 | 36.8 |
| TF-IDF + Linked | 17.3 | 50.0 | 62.7 |
| DrKIT | 38.3 | 67.2 | 71.0 |
| **MDR** | **65.9** | **77.5** | **80.2** |
| MDR + ELECTRA-large 重排 | SP EM 81.2 | Ans Recall 88.2 | — |
| Graph Rec Retriever | 75.7 | 87.5 | — |

消融（同一表）：去 linked negatives 64.6/76.8/79.6；去 memory bank 63.7/74.2/77.2；去 shared encoder 59.9/70.6/73.1；**去掉 hop 顺序信息 17.6/55.6/62.3（崩）**；单跳 DPR 25.2/45.4/52.1。

**"hop 顺序信息"这一项是本表最重要的一行**：告诉模型"这是第一跳还是第二跳"，R@2 从 17.6 涨到 65.9。映射到本项目：`expand()` 的 `depth` 字段已经存在，但在**边打分里没有用到**——tier1 只判 `node_depth == 0`，tier2/tier3 与 depth 无关。

[来源: https://arxiv.org/html/2009.12756 ]

### 2.3 路径定位（path finding）

**Asai et al., Learning to Retrieve Reasoning Paths over Wikipedia Graph**（ICLR 2020，arXiv:1911.10470）：graph-based recurrent retrieval——RNN 依次检索推理路径中的段落，条件于已检索文档；reader 对**整条 reasoning path 打分**并抽 span；HotpotQA 比之前最好模型 **+14 点以上**。这是"路径级打分而非段落级打分"的范式源头。 [来源: https://arxiv.org/abs/1911.10470 ]

**PropRAG**（EMNLP 2025，Wang & Han，pp.6212–6227）：把 KG 三元组换成 context-rich **propositions**（缓解 triple 的 "context collapse"），在线做 **LLM-free beam search over proposition paths**，显式发现多步推理链；2Wiki / HotpotQA / MuSiQue 上 zero-shot Recall@5 与 F1 双 SOTA。 [来源: https://aclanthology.org/2025.emnlp-main.317/ ]

**ConRAG**（见 1.1 / 1.2）是当前与本项目题面最贴合的一篇。它的指标定义值得直接搬：

- **BCM**（Bridge contains match）：gold 桥接实体被包含的比例 —— **这就是本项目 multihop 判据的严格版**；
- **CR**（chain recall）：gold 链被恢复的比例；
- **CP**（chain precision）。

即：把"答案里出现 gold"升级成"**答案里出现了 gold 并且路径上每段都被覆盖**"。本项目 multihop 判据恰好就是这个形状（gold 要与**每一个**锚点各有一句共现），所以 ConRAG 的结论可迁移性最高。

### 2.4 查询分解：一个必须知道的负结果

**MDR Table 4（100 条 bridge 题，用 QDMR 人工分解，且给分解法免掉了中间错误）**：

| 方法 | R@2 | R@10 | R@20 |
|---|---|---|---|
| MDR | 54.9 | 63.7 | 70.6 |
| Decomp (SubQ1; SubQ2) | 50.0 | 64.7 | 67.6 |
| Decomp (Q; SubQ2) | 51.0 | 64.7 | 68.6 |

**显式查询分解没有任何提升**，而且把第一跳换成原问句也不掉分。作者假设"一个子问题的信息对另一跳也有用"。这与 Wolfson et al. 2020 在 TF-IDF 上的结论相反。 [来源: https://arxiv.org/html/2009.12756 ]

对比之下，分解家族本身是有据的：**self-ask**（Findings EMNLP 2023, arXiv:2210.03350）定义了 **compositionality gap**，并指出"结构化 prompt 便于把搜索引擎插进 follow-up 环节"[来源: https://arxiv.org/abs/2210.03350 ]；**DecomP**（ICLR 2023, arXiv:2210.02406）证明可以在分解框架内嵌入 symbolic IR[来源: https://arxiv.org/abs/2210.02406 ]；**Least-to-Most**（ICLR 2023, arXiv:2205.10625）用 14 个 exemplar 在 SCAN 各 split ≥99%（CoT 仅 16%）[来源: https://arxiv.org/abs/2205.10625 ]。

**结论【推断】**：分解对**生成式 + LLM** 有效（它靠 prompt 里的中间答案传导），对**抽取式 + 无 LLM** 的系统没有直接通路——本项目没有"生成中间答案"这一步，分解出来的子问题无法把答案喂回下一跳。所以**不要浪费时间做查询分解**，要做的是"把第一跳的检索结果（而不是答案）喂给第二跳"，即 MDR/IRCoT 的机制而不是 DecomP 的机制。

**ChainRAG**（ACL 2025 long, pp.22362–22375）给了这个方向一个反面诊断：RAG 多跳 QA 存在 **"lost-in-retrieval"** —— 关键实体在子问题分解中被**丢弃**，导致检索断裂。它的解法是 progressive retrieval and rewriting：顺序处理子问题、**补全缺失的关键实体**、从**句子图**里检索相关句子；在 MuSiQue / 2Wiki / HotpotQA × 三种 LLM 上一致优于基线。 [来源: https://aclanthology.org/2025.acl-long.1089/ ]

### 2.5 桥接实体识别的三条实现路线

**路线一：入库期把 bridging facts 变成一等公民（IndexRAG，AACL 2026 Findings）**
在入库时识别跨文档共享的 bridge entities，把 bridging facts 生成为**可独立检索的单元**；无训练、单趟检索 + 单次 LLM 调用；F1 比 Naive RAG 平均 **+4.6**（HotpotQA/2Wiki/MuSiQue），与 IRCoT 组合后在所有对比方法（含 HippoRAG2、FastGraphRAG）中平均最好。

摘要里那句机制说明特别值得抄：**"The recall drops because bridging facts compete with original passages for retrieval slots"** —— 桥接事实和原始段落**争抢检索名额**。这句话正对得上本项目台账里"同 doc 兄弟块占掉前 20 名额的 25 题、共 46 个名额"。

[来源: https://aclanthology.org/2026.findings-aacl.175/ ]

**路线二：relation-free 二分图 + 实体激活（LinearRAG）**
只建 entity–sentence–passage 三类节点和两张二值矩阵（`passage×entity`、`sentence×entity`），**不做语义关系抽取**，索引时间降 >77%、零额外 token；然后做"迭代激活 + 阈值剪枝"。诊断部分给了本项目最需要的一句外部佐证：**LightRAG / HippoRAG 在 GraphRAG-Bench 上的 context relevance 只有 36.86%–54.61%，而 vanilla RAG 是 62.87%** —— 图召回扩了范围但灌进大量噪声。 [来源: https://arxiv.org/html/2510.10114v4 ]

**路线三：显式公共邻居/最短路打分**（见第 3 节，这是唯一能在零依赖纯 Python 上跑、且直接输出"哪个实体同时连接两个给定实体"的路线）

### 2.6 映射表：文献机制 ↔ 本项目模块

| 文献机制 | 本项目对应位置 | 现在的差距 |
|---|---|---|

## 3. 共现/桥接实体的显式打分：公式、复杂度、纯标准库可行性

这一节是整份报告里**最能在零依赖条件下直接落地**的部分。

### 3.1 公共邻居族（local indices）

设 `Γ(u)` 为 u 的邻居集（本项目已有 `adjacency.neighbors()`，且出/入分列、已按 `(-support_count, edge_id)` 稳定排序）。

| 指标 | 公式 | 出处 |
|---|---|---|
| **CN** 公共邻居 | `CN(u,v) = |Γ(u) ∩ Γ(v)|` | Lü & Zhou 综述 |
| **AA** Adamic-Adar | `AA(u,v) = Σ_{w∈Γ(u)∩Γ(v)} 1 / log|Γ(w)|` | Liben-Nowell & Kleinberg 2004 |
| **RA** Resource Allocation | `RA(u,v) = Σ_{w∈Γ(u)∩Γ(v)} 1 / |Γ(w)|` | Zhou, Lü, Zhang, Eur. Phys. J. B 71 (2009) 623；arXiv:0901.0553 |
| **Jaccard** | `|Γ(u)∩Γ(v)| / |Γ(u)∪Γ(v)|`（分母 0 返回 0） | — |
| **PA** 优先连接 | `|Γ(u)| · |Γ(v)|` | — |

以上五个公式的**逐字实现**可以直接从 NetworkX 2.8.4 的 `link_prediction.py` 读出来搬（它本身就是纯 Python，没有 numpy 依赖）：
- `RA(u,v) = Σ_{w∈Γ(u)∩Γ(v)} 1/|Γ(w)|`
- `AA(u,v) = Σ_{w∈Γ(u)∩Γ(v)} 1/log|Γ(w)|`
- `jaccard` 分母为 0 时返回 0
- `pa = |Γ(u)|·|Γ(v)|`

[来源: https://networkx.org/documentation/networkx-2.8.4/_modules/networkx/algorithms/link_prediction.html ]
[来源: https://arxiv.org/abs/1010.0725 ]（Lü & Zhou, *Link Prediction in Complex Networks: A Survey*, Physica A 390 (2011) 1150–1170）

**综述对 q 元共同邻居的正式定义**（这正是"哪个实体同时连接两个给定实体"的数学定义）：

```
Θ(V_q) = Σ_{t ∈ V − V_q}  δ( A_{v1,t} + A_{v2,t} + … + A_{vq,t} − q )
```

`q = 2` 时退化为普通共同邻居数；`q = 1` 时退化为度 `k_v`。对本项目：**Θ({u,v}) 的值就是同时连接两个锚点的实体个数；让它 > 0 的那些 t 就是候选桥接实体。**

### 3.2 CCPA：同时用"公共邻居数"和"最短路距离"

NetworkX 的 `common_neighbor_centrality`：

```
CCPA(u,v) = α · |Γ(u) ∩ Γ(v)| + (1 − α) · N / d_uv
```

- `d_uv` = 最短路长度（NetworkX 用 `bidirectional_shortest_path` 的长度）
- `N` = 图中节点数
- **默认 α = 0.8**（Ahmad et al., *Sci Rep* 10, 364 (2020)）

这是**唯一一个把"共享多少邻居"与"隔着多远"放进同一式子的现成指标**，正好对应本项目 multihop 需要的两种信号：中间实体 → CN>0 且 d=2；中间实体不好找 → d>2 但仍有共同邻居。

[来源: https://networkx.org/documentation/networkx-2.8.4/_modules/networkx/algorithms/link_prediction.html ]

### 3.3 零假设 λ：公共邻居多少算"显著"

**The Node-Similarity Distribution of Complex Networks and Its Applications in Link Prediction**（arXiv:1710.10738v3，2019，Pu/Li/Wang/Quek）证明：

- ER 随机网络中任意 **q 元节点集**的公共邻居数服从 **Poisson 分布**，期望
  ```
  λ = ⟨k⟩^q · N^{1−q}
  ```
  其中 `⟨k⟩` 为平均度、`N` 为节点数。
- 并且：**若连通对与非连通对的相似度分布相同，则 AUC 恒为 0.5**（即该指标无预测力）。

[来源: https://arxiv.org/html/1710.10738v3 ]

**这条 λ 是本项目最需要的那个"地板"**。用台账数字算一下【推断】：

- `N = 6483` 个实体、`E = 28234` 条关系 → 有向平均出度 `⟨k⟩ ≈ 4.36`。
- `q = 2` 时 `λ = ⟨k⟩² / N ≈ 19.0 / 6483 ≈ 0.0029`。

意思是：**在随机图里，两个实体共享 ≥1 个共同邻居的概率只有约 0.29%**。所以**任何"两个锚点有公共邻居"的观察都极度显著** —— 这解释了本项目台账里的那个反例：`hop_line` 信号在同一批候选块上几乎全亮（难题平均 19.15 块点亮但只有 1 个真 gold）。

**关键推论【推断】**：问题不在"公共邻居这个信号不准"，而在**"用公共邻居的个数而不是它的稀有度来排序"**。正确的用法是把 CN 除以零假设期望（或用 RA/AA 做度归一），并且**只对 `C(text)` 级别上真正独立的实体计数**。本项目已经踩过这个坑：更严的"两端点同行 + 共同邻居同行"把 gold 命中从 84.8% 打到 23.9% —— 说明**加严信号本身不是解，加权排序才是解**。

### 3.4 元路径 / PathSim

**PathSim**（Sun et al., VLDB 2011, PVLDB 4(11):992–1003）：

```
o(x, y) = 2 · |{ p_{x~y} : p_{x~y} ∈ P }| / ( |{p_{x~x}}| + |{p_{y~y}}| )
```

即"x 到 y 的对称元路径实例数的 2 倍"除以"x 到自身与 y 到自身的实例数之和"。论文里取 k=10 个 top 相似节点。

**限制**：PathSim 要求 **x、y 同类型**。本项目两个锚点可能不同类型（人物 vs 组织 vs 事件），需要放宽为"两侧路径实例数各自归一"的泛化版。

[来源: https://ar5iv.labs.arxiv.org/html/2310.15593 ]（RecipeMeta, ACM MMAsia 2023，逐字复核了 PathSim 公式）

### 3.5 PPR top-k

标准 personalized PageRank（HippoRAG 用法）：

```
p^{(0)} = s,  s_i = 1[ i ∈ 查询实体 ] · |P_i|^{−1}    （node specificity）
p^{(t+1)} = (1 − d) · s + d · A^T · p^{(t)}           （A 列归一化邻接）
```

- HippoRAG 的 **damping/restart d = 0.5**（在 MuSiQue 100 条训练样本上调出）
- passage 分数 = `p' · P`，其中 `P` 是 |N|×|P| 的 node–passage 共现矩阵
- LinearRAG 用 **d = 0.85**（更标准的取值）

[来源: https://arxiv.org/abs/2405.14831 ]、[来源: https://arxiv.org/html/2510.10114v4 ]

**node specificity `|P_i|^{-1}` 这一项是 HippoRAG 里最容易被忽略但最关键的**：它是"局部版 IDF"——出现在很多 passage 里的实体（本项目里的"阿米娅""罗德岛"）初始概率被压低，从而**天然抑制 hub**。这正好是 3.3 节 λ 那件事的另一种解法。

### 3.6 最短路（BFS）

两跳内最短路：以其中一个锚点为源跑 BFS，深度上限 2（或 3），命中另一锚点即停。复杂度 `O(V + E)`，本项目 `V+E ≈ 3.5 万`，纯 Python 毫秒级。

### 3.7 复杂度与可行性汇总

| 算法 | 单次复杂度 | 本项目实测量级 | 纯标准库可行？ |
|---|---|---|---|
| CN / AA / RA / Jaccard / PA | `O(min(|Γ(u)|,|Γ(v)|))`（把较小一侧建成 dict 再扫另一侧） | `⟨k⟩≈4.4` → 每次 < 10 次比较 | ✅ 直接可写 |
| 为**全部候选桥接实体**打 CN 分 | `O(Σ_{s∈seeds} |Γ(s)|)` | 两个 seed × 4.4 ≈ 9 | ✅ |
| CCPA | CN 的 `O(min deg)` + 一次 BFS 最短路 | BFS `O(V+E)=3.5万` | ✅ |
| q=2 的 Θ({u,v}) | 同上 | 同上 | ✅ |
| PPR（幂迭代） | `O(iter · E)` | `20 × 28234 ≈ 5.6×10⁵` 次浮点乘加 | ✅ 毫秒级 |
| k 跳 BFS（有界） | `O(V+E)`，受 `max_degree_per_entity` 剪枝 | — | ✅ 已实现 |
| 元路径实例枚举 | 路径长度指数 | 2 跳内可枚举，3 跳需上限 | ⚠️ 建议限 2 跳 |

**结论：第 3 节全部指标都能在"纯 Python 标准库 + 预建邻接表"上跑，本项目 `adjacency.py` 的 `{entity_id: {"out": [...], "in": [...]}}` 结构完全够用，不需要 numpy / networkx。**唯一要补的是把 `Γ(u)` 从 list 建成临时 dict 以做 O(1) 成员判断。

## 4. 章节/段落定位（section-level retrieval）与过度召回惩罚

### 4.1 TREC CAR：分级相关性就是"过度召回惩罚"的正统写法

**TREC Complex Answer Retrieval**（Dietz, Verma, Radlinski, Craswell, *TREC CAR Overview*, TREC 2017 / Y2 2018 / Y3 2019）：

- 任务：给定 outline（title + 层级 headings），为**每个 heading（section）**返回相关 (entity, passage) 排序。语料 20 million paragraphs（2016 Wikipedia 去重）。
- **分级相关性 5 档**：
  - `3` = must be mentioned (excellent)
  - `2` = should be mentioned (good)
  - `1` = could be mentioned (fair)
  - `0` = on topic but not relevant (**near miss**)
  - `-1` = not relevant，`-2` = trash
- section 唯一标识 = **section path**（`pageName/section1/section1.1`），qrels 用 trec_eval 格式 `$sectionId 0 $paragraphId $isRelevant`。
- **官方明确警告**（原文）："there have been many problems whenever participants have tried to 'parse' the text of the heading or query out of the heading id (or query id). Please do not do this, as the ID is a hashkey and does not perfectly preserve the text."

[来源: https://trec-car.cs.unh.edu/ ]

**这一段对本项目有两个直接用处**：

1. **`0 = on topic but not relevant (near miss)` 这一档就是本项目 cross_chunk 的 `unattributed_standalone`**。TREC 用 5 档加权（通常 NDCG）来惩罚 near miss，而不是二元判对错。本项目现在的判据是硬二元 + `|额外| ≤ |gold|` 的上限，本质上是把 5 档压成 2 档再用计数约束近似——**方向是对的，但可以更细**（见 4.5）。
2. **"章节名只准读 `unit["chapter"]` 字段、不要截 `chunk_id` 路径"这条本项目血泪教训，在 TREC 官方文档里有同源佐证。**（本项目实测：截 chunk_id 只有 7/38 对，读字段 38/38。）

### 4.2 DHR：document → passage 两级 + 文档级校准

**Dense Hierarchical Retrieval**（EMNLP 2021 Findings，arXiv:2110.15439，Salesforce）：

- **document-level retriever 先选文档 → passage-level retriever 在文档内选段 → 再用 document-level relevance 校准 passage 排序**；
- 利用层级标题结构；
- 两种负采样：**In-Doc negatives**（同文档内其他段落）、**In-Sec negatives**（同一节内其他段落）。

[来源: https://arxiv.org/abs/2110.15439 ]

**映射到本项目**：`chapter` → `chunk` 天然是两级。本项目已有一个"反向"版本的坑：**同 doc 兄弟块占掉前 20 名额的 25 题、共 46 个名额**（`docs/a阶段_失败样本分层.md`）。DHR 的 In-Sec negatives 思路给了一个正面用法：**同节内的兄弟块应该互相去重（它们通常是同一场景的连续对白），而不是各占一个名额。**

### 4.3 SECTOR / WikiSection：section 边界本身有噪声

**SECTOR**（TACL 2019，arXiv:1902.04793）：贡献 **WikiSection 数据集 = 242k 条已标注 section，英文+德文（diseases / cities 两域）**；任务 = 把文档切成连贯 section + 给每个 section 打 topic label（30 topics）；最好成绩 **71.6% F1**，比 SOTA CNN 基线 **+29.5 点 F1**。

[来源: https://arxiv.org/abs/1902.04793 ]

**含义【推断】**：71.6% F1 已是 SOTA，说明**section 边界判定本身就有 ~30% 的误差**。本项目如果要在章节级做打分，必须容忍边界噪声——**不要把 section 切分质量当成可以优化的杠杆**，本项目用现成的 `unit["chapter"]` 字段已经是最优选择（它来自语料本身，不需要预测）。

### 4.4 一个重要的负结果：层级结构≠收益

**"When Question-Based and Hierarchical Retrieval Don't Beat Flat Dense Retrieval"**（Santosh Majety, Zenodo preprint, 2026-07-03, DOI 10.5281/zenodo.21157390）：8 方法 × 5 数据集公平对比 + 受控 head-to-head（层级问题树 HQD vs flat question pool，共享同一 dense 引擎，2 个 embedding 模型跨 5 倍容量）：

1. **对全文索引的问题做词法检索会输给 dense 基线**，因为合取语义在排序前就丢掉大部分候选，**78–95% 的 query 出现空结果集**；
2. **层级结构相对 flat dense 检索毫无增益**：MRR 差最多 0.0072，模型容量 ×5 也不增长；
3. **多跳准确率在两个模型上都停在 ~0.64**，是结构性天花板；
4. 作者结论：缺的是**跨文档结构（图，而不是树）**。

[来源: https://zenodo.org/records/21157390 ]

**两条对本项目的直接含义**：

- **"给章节/块加层级树"不会自动涨分。** 想涨分必须做**跨章节的图**——这正是 cross_chunk 的形态（同一实体横跨多个 `chapter`）。
- **"合取式词法检索会大面空结果"这一条，解释了本项目 `_cooc_boost` 为什么点亮率不稳**：它要求 `all(n in line for n in names)`（同一行同时含前两个实体名），这是最严格的合取；要么几乎不亮，要么一旦放宽就全亮（台账：难题平均 19.15 块点亮但只有 1 个真 gold）。

### 4.5 过度召回的三种惩罚口径（可直接用）

**(a) 计数上限（本项目现行）**：`|额外章节| ≤ |gold|`。已证：只放开成"超集 + 额外真实"会被普通名词打满（`海洋` gold 3 章膨胀到 47 章 = extra/gold 14.7；`巫术` 15.0；`集市` 12.5；`银行` 11.0）。**这个上限必须保留。**

**(b) 分级加权（TREC CAR 式）**：给每章一个 `must / should / could / near-miss` 档，用 NDCG 式折扣。可行实现：`score = Σ_ch w(ch) / log2(rank_ch + 1)`，`w ∈ {3,2,1,0}`。

**(c) 集合覆盖目标（GeoRAG 式 facility location）**

**GeoRAG: Covering the Unseen**（arXiv:2606.29328，USST + SMU）给出了过度召回问题的正式诊断：

- 把 context selection 隐式当成 chunk-wise ranking：`S* = argmax_{S⊆C, |S|=k} Σ_{c∈S} f(c,Q)`，等价于假设"信息需求 = 单个 `emb(Q)` 点"。
- **实测 Dense retriever 上 top-5 选中块的平均两两余弦 = 0.82**（NQ/HotpotQA dev 均值），严重冗余。
- **失败在 selection 不在 recall**：6 个 retriever 的 Recall@200 已达 **88.7%–93.8%**，证据几乎总在候选池里，却在选 k 个时被丢掉。
- **Proposition 1（单点不可覆盖性）**：若存在 Peak A/B 划分且 `min_{a∈A} cos(a,Q) > max_{b∈B} cos(b,Q)`（且 |A|≥k），则**任何 query-proximity-monotone selector 都返回 S⊆A、S∩B=∅**，与打分函数形式无关。
- 解法：**demand-weighted facility-location 目标**（单调次模，贪心 1−1/e 近似保证），用 **Sinkhorn–Wasserstein 边际增益代理**实现。
- 数字：6 个 QA benchmark 上 **EM 比 top-k 截断平均 +6.5 ~ +7.5**，HotpotQA 与 ASQA 最高 **+9.7**；消融 Axis A（多维需求分布）+2.7 EM、Axis B（集合感知选择）+3.4 EM。

[来源: https://ar5iv.labs.arxiv.org/html/2606.29328 ]

**与 MMR 的关系**：MMR（Carbonell & Goldstein, SIGIR 1998）是这套思路的最小实现——

```
MMR = argmax_{D_i ∈ R \ S} [ λ · Sim1(D_i, Q) − (1−λ) · max_{D_j ∈ S} Sim2(D_i, D_j) ]
```

迭代：每次从候选集 R 里选 MMR 最大的加入结果集 S，直到 |S|=k。λ=1 退化为纯相关性，λ=0 退化为纯多样性。原文示例 λ=0.5 时牺牲了总相关性 2.44→2.31 换取多样性（两两相似度 0.87→0.63）。

[来源: https://cloud.tencent.cn/developer/article/1748334 ]（MMR 公式与 Python/Java 实现的逐字说明；原始出处 Carbonell & Goldstein, SIGIR 1998）

**本项目的 MMR 特化版【推断】**：不需要向量库——`Sim2(D_i, D_j)` 用**词袋 Jaccard** 或"同 doc_id / 同 chapter 二值惩罚"就够。台账证据是"同 doc 兄弟块占掉前 20 名额的 25 题、共 46 个名额"，而兄弟块的字面重叠度天然极高，词袋 Jaccard 能直接抓住。

### 4.6 本章小结：cross_chunk 的真正修法

`docs/分析-cross_chunk判据.md` 已经用逐题证据把根因钉死：

- `_chapter_answer` 的收录条件是 `name in unit["text"]` = 在上下文子集上跑 `C_text` 口径，而 gold 是 `G_name` 口径。
- 两档合计 63 个多列章节，**`unit_entities_has_focus` 无一例外全是 False**。
- 分类：`unattributed_standalone` 14（B=6000）/ 42（B=12000）、`substring_other_entity` 3/4、`alias_only` 0、`gold_gap` 0、**`unrelated` 0**。
- **不是 gold 漏列，也不是无关章节，而是"名字字面出现但实体归属不成立"**（普通名词 / 说话人标签 / 泛称 / 被更长实体名包含）。

文献侧的对应解法（这些都是**能在零依赖下做**的）：

1. **ConRAG 的 `df(e) ≥ 2`**：一个只出现在一章里的实体名不可能是跨章实体（对本项目不适用——`_chapter_answer` 本来就在多章之间挑）。
2. **ConRAG 的"同 doc 内若 A 是 B 的连续 token 子串，只保留更长的那个"**：**直接命中 `substring_other_entity`（`帕特` ⊂ `帕特里奇昂`、`勾吴` ⊂ `勾吴城`）**。
3. **说话人标签识别**：台账里 `收音机：…`、`“雄辩家”：…` 这类是 `行首 = 名字全长 + 全角冒号`。**一条正则就能过滤**（`^\s*[「“]?{name}[」”]?\s*[:：]`）。
4. **实体归属判据**（台账已在建议）：该章入选 iff 上下文中存在属于该实体的块（`chunk_id ∈ entity["chunks"]`）。台账说试过但否决（多列 34→0，通过 19/38→13/38），原因是 `unit["entities"]` 只记被采纳断言的主宾名 —— **这不是"归属判据错"，而是"`unit["entities"]` 这个字段本身不完整"**。所以正确顺序是**先补全归属数据，再用归属判据**，而不是放弃归属判据。

## 5. 判定口径与评测方法论

### 5.1 字符串共现式判据的偏差

**(a) 共现判据会奖励捷径——这是有硬证据的。**

**"Compositional Questions Do Not Necessitate Multi-hop Reasoning"**（ACL 2019 short，arXiv:1906.02900）：

- **单跳 BERT-based RC 模型在 HotpotQA 上达到 67 F1**，与 SOTA 多跳模型相当；
- 不展示全部必要段落时**人类仍能答 > 80%**。

[来源: https://arxiv.org/abs/1906.02900 ]

这句话在 2019 年是"多跳评测被污染"的指控；对本项目的含义是：**"答案里出现 gold 串"这类判据，单跳系统也能刷到很高**。本项目台账里三套被否证的错口径全部是这条的实例：

1. "答案含 gold 串" → MAX_CLAIMS 5→12 假涨 15 题（`隶属` 出现在 102/350 题答案里）；
2. cross_chunk 超集判据 → 大预算虚增 3–5pt（12000 档 236 vs 225）；
3. **问句自带答案** → single_chunk 76 题里 **46 题 gold 就写在题干书名号里**，零检索抄标题就过 46/76（16.14%）。

**(b) EM / F1 对冗长答案不可靠——有原文。**

**Adlakha et al.**（TACL, arXiv:2307.16877v2, 2024-04 修订）原文：**"the additional verbosity makes traditional QA evaluation metrics such as exact match (EM) and F1 unreliable for accurately quantifying model performance"**；提出 token-overlap 与 model-based 指标，分 **correctness / faithfulness** 两维。

[来源: https://arxiv.org/abs/2307.16877 ]

**(c) reference-free 三件套（可用于自检，不替代 gold）**

**Ragas**（arXiv:2309.15217, 2023/2025）：faithfulness / answer relevance / context relevance，三者都不需要 gold 标注。 [来源: https://arxiv.org/abs/2309.15217 ]

**本项目可以直接借这个思路做一个"内部体检"**：`context relevance` 在本项目就是"上下文里真 gold 块占的比例"（台账已有：multihop gold 进 context 53/57，cross_chunk gold 章节可达率 62/97 或 74/97）。

### 5.2 在 dev 上过拟合：这条有专门论文

**Cawley & Talbot, "On Over-fitting in Model Selection and Subsequent Selection Bias in Performance Evaluation", JMLR 11(70):2079−2107, 2010**：

- **在同一个 CV 估计上反复调参 = 对 model selection criterion 过拟合**；
- 其效应量**常与算法间差异同量级**；
- 低方差比无偏更重要；
- 常见评测实践因此有 selection bias 而不可靠。

[来源: https://jmlr.org/papers/v11/cawley10a.html ]

**这正是本项目正在做的事**：在 dev 285 题上连续几十轮调参（`MAX_CLAIMS` 5/8/12/16/20/24、`COOC_BOOST_WEIGHT` 0.1/0.3、`CANDIDATE_POOL_MULT` 3/5/10/20、`TITLE_ANSWER_PATH`、`CHAPTER_ANSWER_PATH`、`hop0.5`、`truncation continue→break`……）。

文献给的两个现成解药：

1. **50:50 分割 dev/test，重复 30 次取 test 折平均**（ECIR'22 QPP 论文 arXiv:2202.06306 的标准调参协议）[来源: https://arxiv.org/html/2202.06306v1 ]。
2. **nested CV**（Varma & Simon, *BMC Bioinformatics* 7:91, 2006）—— 内层调参、外层评估。⚠️ **本次调研未能抓取到原文**（BMC 与 Springer 均重定向到登录墙），只能作为二手引用，落地时请自行核对。

### 5.3 可直接用的统计检验方案（零依赖）

本项目现在用的是 **bootstrap 4000 次配对 p 值**（seed=1107）。这没问题，但**不是最优**。文献给的正确做法：

**推荐协议（三层，从便宜到贵）**

**第一层：McNemar 精确检验（配对二元，最贴切）**

只统计**标签不一致的配对**：`n+` = A 对 B 错，`n−` = A 错 B 对；忽略 `(A,A)` 与 `(B,B)`。H₀: `n+` 与 `n−` 等概率。

```
精确 p = 2 · Σ_{i=0}^{k} C(N, i) / 2^N,   k = min(n+, n−),  N = n+ + n−
N > 25 时可用连续性校正近似：Z = (|n+ − n−| − 1) / √N  ~  N(0,1)
```

[来源: https://lesn.appstate.edu/olson/stat_directory/Statistical%20procedures/McNemars%20Tst/mcnemars_test.htm ]

纯标准库实现（可直接放进 `scripts/`）：

```python
from math import comb

def mcnemar_exact(pairs):
    """pairs: [(pass_A, pass_B), ...]，同一批题两次配置的逐题 pass/fail。"""
    n_plus  = sum(1 for a, b in pairs if a and not b)
    n_minus = sum(1 for a, b in pairs if b and not a)
    N = n_plus + n_minus
    if N == 0:
        return 1.0
    k = min(n_plus, n_minus)
    p = 2 * sum(comb(N, i) for i in range(k + 1)) / (2 ** N)
    return min(1.0, p)
```

**第二层：配对差值的 bootstrap CI（现有做法，保留）**

差值 d = acc_B − acc_A 的 95% CI 用 4000 次重采样（现有 seed=1107）。这一步保留，因为**CI 下界是否触 0 是决策依据**（台账里 `8→20` 的 holdout `p=0.1345`、clean `p=0.1303` 就是靠这个否掉的）。

**第三层：多重比较校正（BH-FDR）**

Benjamini & Hochberg 1995, JRSS-B 57(1):289–300 [来源: https://academic.oup.com/jrsssb/article/57/1/289/7035855 ]。

把本轮所有试过的配置的 p 值按升序排 `p_(1) ≤ … ≤ p_(m)`，找最大 k 使 `p_(k) ≤ (k/m)·q`（q=0.05），拒绝前 k 个。

**为什么这一步对本项目特别重要【推断】**：本项目单轮会试 6–10 个配置，m 轮下来累计试了上百个。以 m=20 计，**至少一个假阳性的期望 = 1 − (1−0.05)^20 ≈ 64%**。也就是说"某一档看起来显著"很可能只是多重比较的产物。BH 校正后，本项目的实际判定门槛应该从 p<0.05 提到 p<0.0025（m=20, k=1 时）左右。

**统计功效：能检出多大的差【推断/计算】**

用 McNemar 的近似式 `Z = (n+ − n−)/√N`，α=0.05 双侧、power=80% 需要 `|n+ − n−| ≥ 2.80·√N`。

- 若两次配置的不一致率约 16%（285 题 → N ≈ 46），则最小可检出净增 = `2.80·√46 ≈ 19` 题 = **+6.7pt**。
- **这意味着本项目在 285 题上根本检不出 +5pt 的改动**（需要不一致率降到 ~10% 或题目量翻倍）。
- 台账里"8→20 claims 得 +1.43pt、p=0.0055"之所以显著，是因为 bootstrap 用的是**逐题配对差值的分布**而非二元不一致对；这也解释了为什么 holdout（195 题）和 clean（120 题）上都不显著——**样本量不够**。

参考：**Adding Error Bars to Evals**（arXiv:2411.00640, 2024, Evan Miller / Anthropic）把评测题视为从未观测 super-population 抽样，给出均值/差值标准误公式、配对比较、以及"要检测 d 点差异需要多少题"的实验设计公式，并建议**报告置信区间而非单点**。[来源: https://arxiv.org/abs/2411.00640 ]

**Dror et al., ACL 2018 (P18-1128, pp.1383–1392)** 给的是"怎么选检验"的实用协议：区分配对 vs 非配对、指标类型、样本量小 → **推荐近似随机化检验（approximate randomization）/ bootstrap 而非 t 检验**；并指出 2017 年 ACL/TACL 论文中显著性检验常被忽略或误用。[来源: https://aclanthology.org/P18-1128/ ]

**落地建议（具体到命令级）**：给 `scripts/eval_answer_quality.py` 的 `--json` 输出补三样东西：`n_plus / n_minus / mcnemar_p`、`bootstrap_ci`（已有）、以及一个 `--baseline-json` 参数用来批量跑 BH 校正。

### 方案 2：桥接实体显式打分（本项目版 bridge finder）

**① 一句话原理**
对问句里的每一对锚点 `(u, v)`，在邻接表上算 `Γ(u) ∩ Γ(v)`，用 **AA/RA 度归一 + λ 零假设归一**排名，top-1 即"唯一中间实体"；同时用 CCPA 处理"两跳够不到、需要三跳"的情况。

**② 改哪个模块**
新增 `src/arkrag/bridge.py`（纯函数，~120 行），由 `retrieve.expand()` 在 `depth=1` 结束后调用；产出的桥接实体作为**追加 seed** 再跑一次 BFS。

**③ 预估能捞回多少题 + 推理依据**

- 依据 `docs/会话交接-20261107.md` 漏斗：multihop 的 **gold 进 context 53/57，但"两跳同时挂上"只有 13/57**，judge 通过 8/57。
- 【推断】当前 8/57 里，**"问唯一中间实体"这一类**（题面："「云兽」通过唯一一个中间实体与「变形者集群」相连，中间实体是谁？"）的中间实体如果就是 gold，那么桥接打分能直接把它拉进答案：
  - 21/57 是"gold 与任何一个锚点都没有共现句" —— 这批最可能被桥接打分救回（gold 进 context 53，说明它只在候选池/上下文里但没连上）；
  - 28/57 是"只连上一部分锚点" —— 桥接打分能补上另一半。
- 但**上限被"两跳同时挂上 13/57"钉住**：桥接打分不能凭空造出断言。所以即便完美，也只在 13 题里兑现。**保守估计 +3 ~ +6**，乐观 +8。
- 外部佐证：ConRAG 的任务定义与本项目同构，其 BCM（bridge contains match）指标就是本项目 multihop 判据；HippoRAG 的 node specificity 与 λ 是同一个抑制 hub 的思路。

**④ 实现成本**
4–6 小时。核心约 60 行：

```python
# Γ 建 dict 加速
adj_out = {eid: {it["neighbor_id"]: it for it in rec["out"]} for eid, rec in adj.items()}

def bridge_score(u, v):
    gu, gv = adj_out.get(u, {}), adj_out.get(v, {})
    if not gu or not gv:
        return []
    small, large = (gu, gv) if len(gu) <= len(gv) else (gv, gu)
    out = []
    for w in small:                       # O(min(deg))
        if w in large and w not in (u, v):
            deg_w = len(adj_out.get(w, {}))
            ra = 1.0 / deg_w if deg_w else 0.0
            aa = 1.0 / math.log(deg_w) if deg_w > 1 else 0.0
            out.append((w, ra, aa))
    # λ 归一：λ = mean_deg**2 / N
    lam = (2 * E / N) ** 2 / N
    return sorted(out, key=lambda r: -r[1])
```

- **必须做 λ 归一**（3.3 节：`λ = ⟨k⟩²/N ≈ 0.0029`），否则 `阿米娅` 这种 hub 会垄断所有答案。
- **必须做 hub 抑制**：`deg > p_hub` 分位数（ConRAG 做法）的实体直接不进候选。
- **必须做 df≥2**（ConRAG）：只出现在 1 个 chunk 的实体不能当桥。

**⑤ 风险**

- **hub 实体污染**：这是本项目已经踩过的坑（`hop_line` 信号 19.15 块点亮但只有 1 个真 gold）。缓解：λ 归一 + `deg` 分位数截断 + **只在"题面明确说'唯一中间实体'"时才启用**。
- **误把"关系谓词"当"桥接实体"**：`Γ(u) ∩ Γ(v)` 会包含问句里已经提到的实体，要排除 `u`、`v` 本身以及 `entity_candidates` 里已有的全部 name。
- **可能压掉已有的 direct 通路**：必须做成"**只追加、不替换**"，即新增的桥接实体走额外 seed，不改现有 hit 排序。

### 方案 3：`build_context` 的 MMR 去冗余

**① 一句话原理**
同 doc 的兄弟块字面重叠极高（同一场景的连续对白），用词袋 Jaccard 当 `Sim2`，跑 MMR 把"同 doc 冗余块"的分数压低，让出前 20 名额给真正的第二跳承载块。

**② 改哪个模块**
`src/arkrag/retrieve.py::build_context` 的 `ordered = sorted(...)` 一行之前，插入 MMR 重排（约 40 行）。

**③ 预估能捞回多少题 + 推理依据**

- 依据 `docs/a阶段_失败样本分层.md`：multihop 48 题失败分层 = 「上下文未采用 21 / 找到未进前部 17 / 引用或拒答 7 / 回答未覆盖 2 / 检索未找到 1」；`找到但未进前部` 62 题里**同 doc 兄弟块占掉前 20 名额的 25 题、共 46 个名额**。
- 【推断】如果这 46 个名额里有一半换成真正的第二跳承载块，按漏斗（载块进 hits 35 → 进 ctx 28）估算，**"两跳同时挂上"可从 13 升到 18 左右** ⇒ judge 通过从 8 升到 **11–13** ⇒ **+3 ~ +5**。
- 另外 cross_chunk 的 `ceiling`（B=6000 时 15/38）也直接受名额分配影响，可能**顺带 +2 ~ +4**。
- 合计 **+3 ~ +9**，取中位 +5。

**④ 实现成本**
3–5 小时。零依赖实现：

```python
def _bag(text):  # 词袋（中文用 2-gram 更稳）
    s = re.sub(r"\s+", "", text)
    return {s[i:i+2] for i in range(len(s) - 1)}

def mmr_order(units, k, lam=0.7):
    pool = sorted(units, key=lambda u: -u["score"])
    bags = {u["chunk_id"]: _bag(u["text"]) for u in pool}
    out, rest = [], list(pool)
    while rest and len(out) < k:
        best, best_v = None, -1e9
        for u in rest:
            sim2 = max((len(bags[u["chunk_id"]] & bags[d["chunk_id"]])
                        / max(1, len(bags[u["chunk_id"]] | bags[d["chunk_id"]])))
                       for d in out) if out else 0.0
            # 同 doc 额外惩罚：同 doc 兄弟块几乎必然是同一场景
            if any(d["doc_id"] == u["doc_id"] for d in out):
                sim2 = max(sim2, 0.6)
            v = lam * u["score"] - (1 - lam) * sim2
            if v > best_v:
                best, best_v = u, v
        out.append(best); rest.remove(best)
    return out
```

**⑤ 风险**

- **λ 必须调，且调法要防过拟合**（第 5.2 节）：建议用 50:50 重复分割 30 次，而不是在完整 dev 上扫。
- **可能挤掉同一 doc 的必要多块**：cross_chunk 恰恰需要"同一 doc 的多个 chapter"（doc 级 ≠ chapter 级）。所以**同 doc 惩罚要按 chapter 细分**：同 doc 同 chapter 才重罚（0.6），同 doc 不同 chapter 不罚。
- **`direct` 优先的排序键不能丢**：现有 `(0 if direct(u) else 1, -score, chunk_id)` 里的 `direct` 语义（BM25/entity 直出 vs 纯图扩展）要保留在最外层，MMR 只在 `direct` 组内和 `graph_only` 组内各自做。

### 方案 4：两跳联合检索

**① 一句话原理**
拿第一跳的 gold 候选反过来查第二个锚点的边（ConRAG 的"两侧各有 seed" + MDR 的"hop 顺序信息 + beam search"）。

**② 改哪个模块**
`src/arkrag/retrieve.py::expand`（新增 `hop2` 阶段）。

**③ 预估能捞回多少题 + 推理依据**

- 台账已给死数：**multihop 天花板 13/57 = 22.8%**，现在 8，**若 13 全兑现 dev 198→203（+1.75pt）**。
- 这是**唯一有明确量级的 multihop 改动**，但**上限只有 +5**。
- 加上方案 3（MMR 把天花板从 13 抬到 18）才有 +10 的空间。

**④ 实现成本**
1–2 天（要处理预算爆炸、去重、以及 `build_context` 里"图扩展锚点必须用锚点自己的 chunk_id"那个硬约束）。

**⑤ 风险**

- **预算爆炸**：两跳的路径数是 `Π deg`。必须按 ConRAG 的 `L_max` + hub 抑制 + 分桶 k_path 三件套控。
- **台账已记录同类失败**：`hop0.5` 那次是「优化指标不优化系统」（R@20 +3.03pt 但进 ctx 净 0、覆盖 −3）。**这次必须先量"进 ctx 的净增"再谈 R@20。**

### 方案 5：装填顺序「两端黄金区」

**① 一句话原理**
`Lost in the Middle`（TACL 2023, arXiv:2307.03172）：**相关信息在 context 开头或结尾时性能最高，在中间显著下降**，长上下文模型也一样。把 `graph_only` 单元插到尾部而非中段。

**② 改哪个模块**
`build_context` 的单元排序 + 序列化顺序。

**③ 预估收益**
+1 ~ +3【推断】。依据：现在 `direct` 在前、`graph_only` 在后，方向是对的；但 `graph_only`（正是第二跳承载块的主要来源）全堆在尾部之后被 token 预算从**尾部**截断（`truncated.append; continue`）。把 `direct` 的两端各放一半、`graph_only` 紧跟第一个 `direct` 之后，能让必被保留的单元落在黄金区。

**④ 成本** 1 小时。

**⑤ 风险**
`build_context` 的预算**非单调**（跨档 6000↔12000↔24000 = 193/350 违规，`xfail(strict=True)` 钉着）。改顺序会让这个已知缺陷的表现形态变化，**必须重跑 `tests/test_context_budget.py` 并更新 xfail 依据**。

**补充文献依据**：PathRAG 的提示词排序式(6) `M(q; R) = concat([q; t_{P_K}; …; t_{P_1}])` —— **最可信路径放最末尾**，实测比随机序/升序显著更好。它就是这么用 lost-in-the-middle 的。 [来源: https://arxiv.org/html/2502.14902v1 ]

---

### 方案 6：实体表 `df ≥ 2` + 同块子串归并

**① 一句话原理**
ConRAG 的两条预处理：`df(e) < 2` 的实体直接丢弃（"a mention confined to one document cannot connect two documents"）；同一 doc 内若 A 是 B 的连续 token 子串，只保留更长的那个。

**② 改哪个模块**
检索侧实体候选生成（`retrieve` 的 entity channel 输入）+ `answer._chapter_answer`（共用同一份规则）。

**③ 预估收益**
+1 ~ +4【推断】。依据：`substring_other_entity` 在 cross_chunk 里 3/4 个多列章节；`unattributed_standalone` 里相当一部分是"只在单章出现的类名"（`轮胎`/`收音机`）。

**④ 成本** 3 小时。

**⑤ 风险**
`df ≥ 2` 会误删只在单章出现但确实是答案的实体（single_chunk 类）。**只能用于"跨章/桥接"判定，不能用于答案候选。**

### 方案 7：统计口径升级（不改生产代码，0 题收益但防假涨）

**① 一句话原理**
用 McNemar 精确检验（配对二元）替代/补充 bootstrap；对一轮内试过的所有配置做 BH-FDR 校正；调参用 50:50 重复分割 30 次取 test 折平均。

**② 改哪个模块** `scripts/eval_answer_quality.py`（加 `--baseline-json` 与 `n_plus/n_minus/mcnemar_p` 输出）+ 新增 `scripts/stat_paired.py`。

**③ 预估收益**
**0 题**。价值在于：按第 5.3 节的功效计算，285 题上 McNemar 80% 功效的最小可检出净增是 **+6.7pt（19 题）**；少于这个量级的"改善"在统计上分成不出来。**这条会直接否掉一批看起来显著的小改动**，省下的时间是真收益。

**④ 成本** 2 小时。

**⑤ 风险**
McNemar 会**比现有 bootstrap 更严**（它只看不一致对），可能出现"以前算显著、现在算不显著"的翻案。这是对的，但要有心理准备：**`MAX_CLAIMS` 8→20 那次 dev p=0.0055，按 McNemar 重算可能就不再显著**。

### 方案 8：入库期 bridging facts 预计算（IndexRAG 式）

**① 一句话原理**
离线把"锚点对 → 共享桥接实体 → 承载原始句"预生成为**可独立检索的单元**，查询期单趟检索即可命中，不需要第二跳。

**② 改哪个模块** 索引构建（`index.py` + 新的离线批处理）。这是唯一需要**重建索引**的方案。

**③ 预估收益**
+5 ~ +10【推断】。外部依据是 IndexRAG 的 **F1 +4.6**（HotpotQA/2Wiki/MuSiQue，仅 flat 向量索引）与"与 IRCoT 组合后平均最好"。本项目对应的是把"两跳同时挂上 13/57"直接抬到接近"gold 进 context 53/57"。
**但注意 IndexRAG 自己记录的副作用**："The recall drops because bridging facts compete with original passages for retrieval slots" —— **新增单元会抢名额**，与本项目"同 doc 兄弟块占 46 个名额"是同一类问题，所以**必须和方案 3（MMR）一起上**。

**④ 成本** 3–5 天。

**⑤ 风险**
索引体积与候选池污染；`CANDIDATE_POOL_MULT=10` 的拐点会移动（要重调）；离线批处理的产出必须带原文偏移否则 `verify_citations` 硬闸会拦。

### 6.9 明确「不要做」的清单（有文献或台账证据）

| 不做的事 | 为什么不 |
|---|---|
| **显式查询分解（拆子问题再各检索）** | MDR Table 4 给了**人工 oracle 分解**的负结果：R@2 54.9→50.0，R@10 63.7→64.7（几乎不变）。本项目无 LLM 生成中间答案，分解连传导通道都没有。 |

| **继续抬 `MAX_CLAIMS`（8→20）** | 台账已量：+5 题但答案 +40.6 字/题、7.79% 断言是纯噪音；holdout p=0.1345、clean p=0.1303 不显著。且按方案 7 的 McNemar 口径大概率更不显著。 |

| **用"更严的同行共现"来提精度** | 台账："两端点同行 + 共同邻居同行"把 gold 命中从 84.8% 打到 23.9%。**加严信号不是解，加权排序才是解。** |
| **把 `_cooc_boost` 的 `all(n in line)` 合取当主信号** | Zenodo 21157390：合取式词法检索让 **78–95% 的 query 出现空结果集**。本项目实测同病（要么不亮，要么全亮）。 |
| **在完整 dev 285 上继续扫超参** | Cawley & Talbot JMLR 2010：在同一 CV 估计上反复调参 = 对 selection criterion 过拟合，效应量与算法间差异同量级。 |
