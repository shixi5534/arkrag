## 1. 术语词典的数据结构

业界主流是**两层**：一个「概念」，下挂「每种语言一个规范名 + 一簇别名」。差别只在用什么文件承载。

### 1.1 SKOS：prefLabel / altLabel / hiddenLabel 三件套

W3C SKOS 参考是这套区分最权威的出处（https://www.w3.org/TR/skos-reference/ ）：

- 三者都是 `owl:AnnotationProperty`（S10），都是 `rdfs:label` 的子属性（S11），值域是 RDF plain literal（S12）——即"标签是字面量，不是资源"（https://www.w3.org/TR/skos-reference/ ）。
- **三者两两互斥**（S13）：同一个字符串不能既是某概念的 prefLabel 又是它的 altLabel（https://www.w3.org/TR/skos-reference/ ）。
- **每种语言最多一个 prefLabel**（S14）（https://www.w3.org/TR/skos-reference/ ）。官方"一致"示例（Example 10）原文：

  ```
  <MyResource> skos:prefLabel "animals"@en ;
               skos:altLabel  "fauna"@en ;
               skos:hiddenLabel "aminals"@en ;
               skos:prefLabel "animaux"@fr ;
               skos:altLabel  "faune"@fr .
  ```
  （https://www.w3.org/TR/skos-reference/ ）

- `hiddenLabel` 的**存在理由就是查询期归一**，原文（5.1 Preamble）：「The hidden labels are useful when a user is interacting with a knowledge organization system via a text-based search function. The user may, for example, enter mis-spelled words … If the mis-spelled query can be matched against a hidden label, the user will be able to find the relevant concept, but the hidden label won't otherwise be visible to the user (so further mistakes aren't encouraged).」（https://www.w3.org/TR/skos-reference/ ）—— 这是"拼写变体/误写不进展示、只进匹配"的规范级依据。
- 语言标签粒度：`en`/`en-US`/`en-GB` 算**不同**语言标签，所以 Example 18 里 `<Colour> skos:prefLabel "color"@en , "color"@en-US , "colour"@en-GB` 是合法的三条 prefLabel 而不违反 S14；文档建议按 BCP 47 的 "lookup" 算法做语言回退匹配（https://www.w3.org/TR/skos-reference/ ）。
- 多书写系统同理：Example 11 给同一个概念在 `ja-Hani`/`ja-Hira`/`ja-Kana`/`ja-Latn` 下各一个 prefLabel 加一个 altLabel（https://www.w3.org/TR/skos-reference/ ）。
- 允许"只有别名没有规范名"（5.6.4，Example 17：`<Love> skos:altLabel "adoration"@en , "desire"@en .`），但文档自己承认「many applications will require a preferred lexical label in order to generate an optimum human-readable display」（https://www.w3.org/TR/skos-reference/ ）。

对我们的直接含义：**别名字符串必须是"概念"的属性，而不是"实体名"的属性**；且别名天然是一对多、分语言、分可见性三档。

### 1.2 SKOS-XL：给"标签"本身一个 URI

如果除了字符串还要描述标签本身（缩写关系、来源、可信度），SKOS 主命名空间不够，规范在附录 B 给了扩展（https://www.w3.org/TR/skos-reference/ ）：

- `skosxl:Label` 类，它的超类是「`skosxl:literalForm` 基数恰好为 1」的约束；与 `skos:Concept`/`skos:Collection`/`skos:ConceptScheme` 互斥（https://www.w3.org/TR/skos-reference/skos-xl.html ）。
- `skosxl:prefLabel` / `skosxl:altLabel` / `skosxl:hiddenLabel` 的值域都是 `skosxl:Label`，不再是字面量（https://www.w3.org/TR/skos-reference/skos-xl.html ）。
- `skosxl:labelRelation` 是 **Symmetric** 的、定义域值域都是 `skosxl:Label` 的关系，用来表达"这两个标签之间有关系（比如缩写/翻译）"（https://www.w3.org/TR/skos-reference/skos-xl.html ）。
- 官方还给了 "Dumbing-Down to SKOS Lexical Labels"（降级到普通 SKOS 标签）的规则（https://www.w3.org/TR/skos-reference/ ）。

**这是"术语条目要带元数据（来源、审核态、置信度）"时的标准做法**——而不是往别名字符串里塞标记。

### 1.3 TBX：概念 → 语言 → 术语，三层容器

TBX（TermBase eXchange）是 ISO 30042 的交换格式，官方定义原文：「TBX … is the international standard for archiving and exchanging terminological information exported from terminology databases (termbases)」（https://www.tbxinfo.net/ ），schema 在 https://github.com/LTAC-Global/TBX_Core_RNG 。

层级（元素参考页原文，命名空间 `urn:iso:std:iso:30042:ed-2`，https://www.tbxinfo.net/developer-resources/tbx-elements-reference/ ）：

- `<conceptEntry id="...">` —— "a container for concept level information, including all `<langSec>` elements belonging to that concept"；必须含 ≥1 个 `<langSec>`。
- `<langSec xml:lang="...">` —— "a container for language level information, including all `<termSec>` elements belonging to that language (within the same terminological concept)"。
- `<termSec>` —— "a container for term level information, including a single `<term>` any other elements which provide more information or context about that term"。
- `<term>` —— "contains a single term"。
- 术语级元数据全部走带 `type` 属性的元素：`<termNote type="...">`、`<admin type="...">`（termType / administrativeStatus）、`<descrip type="...">`（definition）、`<transacGrp>`/`<transac>`（谁在什么时候改的）、`<ref>`（文档内引用）/`<xref>`（URI 外部引用）（https://www.tbxinfo.net/developer-resources/tbx-elements-reference/ ）。
- 还有一条很实用的**降级惯例**原文：「it has become best practice to store the contents of unsupported data categories as `<note>` elements using the following convention: `<note>[DataCategoryName]::[Data Category text content]</note>` Example: `<note>partOfSpeech::noun</note>`」（https://www.tbxinfo.net/developer-resources/tbx-elements-reference/ ）。

与 SKOS 的结构差异：SKOS 是「概念 → 每语言一个 prefLabel + 若干 altLabel」（扁平标签），TBX 是「概念 → 语言 → 若干 termSec」（每个 term 能单独挂元数据、能标术语类型如 preferredTerm/admittedTerm/deprecatedTerm）。**"术语本身要分级（首选/可接受/废弃）"时 TBX 的结构更合适**。

### 1.4 Wikibase / Wikidata JSON：label 是对象，aliases 是数组

官方 JSON 文档原文（https://github.com/wikimedia/mediawiki-extensions-Wikibase/blob/master/docs/topics/json.md ）：

> "Labels, descriptions and aliases are represented by the same basic data structure. For each language, there is a record using the following fields: `language` — The language code. `value` — The actual label or description." … "**In the case of aliases, each language is associated with a list of such records, while for labels and descriptions the record is associated directly with the language.**"

文档里的完整例子（Q60 New York City）：

```json
{
  "labels": {
    "en": { "language": "en", "value": "New York City" },
    "ar": { "language": "ar", "value": "نيويورك سيتي" }
  },
  "descriptions": { "en": { "language": "en", "value": "..." } },
  "aliases": {
    "en": [ { "language": "en", "value": "New York" } ],
    "fr": [ { "language": "fr", "value": "New York City" },
            { "language": "fr", "value": "NYC" },
            { "language": "fr", "value": "The City" },
            { "language": "fr", "value": "La grosse pomme" } ]
  }
}
```
（https://github.com/wikimedia/mediawiki-extensions-Wikibase/blob/master/docs/topics/json.md ）

注意 `fr` 的别名数组里连 "New York City" 自己都复述了一遍——**Wikidata 并不要求 alias 与 label 互斥**，这与 SKOS S13（prefLabel/altLabel disjoint）是两种不同取向：SKOS 要求干净划分，Wikidata 容忍冗余。工程上按 SKOS 划分更省事，按 Wikidata 那样只做"候选名集合"也能跑。

### 1.5 检索引擎的 synonyms 文件：等价式 vs 显式式

Elasticsearch 的 synonym token filter 支持两种规则格式（https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-tokenfilter ）：

- **Solr 格式 · 等价式**：`ipod, i-pod, i pod` / `computer, pc, laptop`（逗号分隔的一组可互换词）。
- **Solr 格式 · 显式式**：`personal computer => pc`、`sea biscuit, sea biscit => seabiscuit`（左边全部映射到右边）。
- **WordNet 格式**：多行同 set id，每行 `s(100000002,1,'come',v,1,0).`，字段依次是「同义词集数字 id / 该词在集内的序号 / 词 / 词性 n·v·a·b / 在网中的深度」（https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-tokenfilter ）。

载体三选一：`synonyms_set`（Synonyms Management API 建的集合，单个 filter 最多挂 100 个 set）、`synonyms_path`（相对 config 目录的文件，「The file must be available on every node in the cluster」）、`synonyms`（inline 数组）；默认每个 set 上限 100,000 条规则，由 `synonyms.max_synonym_rules` 调（https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-tokenfilter ）。

官方给的同义词文件样例（可直接照抄当格式参照）：

```text
# Blank lines and lines starting with pound are comments.
# Explicit mappings
i-pod, i pod => ipod
sea biscuit, sea biscit => seabiscuit
# Equivalent mappings
ipod, i-pod, i pod
universe, cosmos
```
（https://www.elastic.co/docs/solutions/search/full-text/search-with-synonyms ）

**这套"每行一条规则、`#` 注释"的纯文本格式的工程价值**：它是事实标准，Solr、Elasticsearch、Azure AI Search 都吃同一份文件（Azure 侧原文：唯一支持的格式是 `solr`，https://learn.microsoft.com/en-us/azure/search/search-synonyms ），所以一份术语表可以同时喂多个检索栈。

### 1.6 顺带：图数据库里术语怎么放

Neo4j 没有"术语表"这个概念，做法是把**别名列表塞进实体的一个 `LIST<STRING>` 属性**，再对该属性建全文索引。官方原文（https://neo4j.com/docs/cypher-manual/current/indexes/search-indexes/full-text-indexes/ ）：

> "If the indexed property contains a list of `STRING` values, each entry is analyzed independently and all produced tokens are associated to the same property name. This means that when querying such an indexed node or relationship, there is a match if any of the list elements matches the query string. **For scoring purposes, the full-text index treats it as a single-property value**, and the score will represent how close the query is to matching the entire list."

关键代价官方自己写明了：**整张别名表共享一个"字段"的统计量**，别名之间没法各自拿 IDF，也做不了按别名加权。全文索引底层是 Lucene（原文 "Full-text indexes are powered by the Apache Lucene indexing and search library"，https://neo4j.com/docs/cypher-manual/current/indexes/search-indexes/full-text-indexes/ ）。

### 1.7 四种结构对照

| 结构 | 一对多别名 | 每语言一个规范名 | 标签自带元数据 | 落地成本 |
| --- | --- | --- | --- | --- |
| SKOS prefLabel/altLabel/hiddenLabel | 是（altLabel 可多个） | 是（S14 强制） | 否（要 SKOS-XL） | 需 RDF 工具链；也可只借语义不借格式 |
| SKOS-XL | 是 | 是 | 是（label 是资源） | 更重，一般只在要审计标签时用 |
| TBX | 是（多个 termSec） | 是（术语类型可标 preferredTerm） | 是 | XML schema + 命名空间，解析成本高 |
| Wikibase JSON | 是（每语言一个数组） | 是（labels 每语言一个对象） | 部分（可在 statements 里） | 最贴近普通 JSON 工程 |
| ES/Solr synonyms 文件 | 是（等价式/显式式） | 靠"显式式右侧唯一"模拟 | 否（纯字符串） | 最低，但无元数据槽位 |

## 2. 查询期归一与扩展

两条方向要分开谈，很多项目把它们混成一个"同义词"概念，结果埋坑：

- **归一（alias → canonical）**：用户写了「W」「大爹」「Winter」→ 映射到规范实体/规范术语。
- **扩展（canonical → aliases）**：用户写对了规范名，但正文里可能用的是别名 → 检索时把别名一起查。

### 2.1 为什么是 graph 而不是 flat（多词别名）

Solr 官方参考里同一段落把问题说透了（https://solr.apache.org/guide/solr/latest/indexing-guide/filters.html ）：

- 旧 Synonym Filter 已被弃用，原文：「Synonym Filter has been deprecated in favor of Synonym Graph Filter, which is required for multi-term synonym support.」
- Synonym Graph Filter 原文：「This filter maps single- or multi-token synonyms, producing a fully correct graph output. This filter is a replacement for the Synonym Filter, which produces incorrect graphs for multi-token synonyms.」
- 索引期与查询期的取舍原文：「If you use this filter during indexing, you must follow it with a **Flatten Graph Filter** to squash tokens on top of one another like the Synonym Filter, because **the indexer can't directly consume a graph**. To get fully correct positional queries when your synonym replacements are multiple tokens, you should instead **apply synonyms using this filter at query time**.」
- 还有个坑：「NOTE: Although this filter produces correct token graphs, it cannot consume an input token graph correctly.」

Elasticsearch 侧同义（https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-graph-tokenfilter ）：「In order to properly handle multi-word synonyms this token filter creates a **graph token stream** during processing.」，并明确「This token filter is designed to be used as part of a **search analyzer only**. If you want to apply synonyms during indexing please use the standard synonym token filter.」

**为什么 flat 会错**：Solr 文档给了可直接对照的输入输出示例——`mysynonyms.txt` 里写 `small => tiny,teeny,weeny`，输入 "teh small couch" 输出是 `the`(位置1)、`tiny`(位置2)、`teeny`(位置2)、`weeny`(位置2)、`couch`(位置3)、`sofa`(位置3)、`divan`(位置3)（https://solr.apache.org/guide/solr/latest/indexing-guide/filters.html ）。**三个替换词落在同一位置号上 = 同位置并列 token（graph）**；flat 的做法是把它们当"依次相邻的新 token"，位置号会往后顺延，于是短语查询 `"small couch"` 变成 `"tiny couch"`/`"teeny couch"`/`"weeny couch"` 之外还会错误命中 `"tiny teeny"` 这类根本不存在的相邻关系。**中文这种没有空格、别名长度又不固定的语言，这个位置错乱问题更严重。**

同页还有一条工程建议值得抄：「Use multiple synonym sets in a single filter instead of chaining multiple `synonym_graph` filters. Chaining can produce indeterminate search-time behavior.」（https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-graph-tokenfilter ）

### 2.2 `expand: true/false` —— 双向扩展 vs 单向归约

这是"归一 vs 扩展"在检索引擎里的开关（三处文档口径一致）：

- Elasticsearch 原文（https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-tokenfilter ）：`foo, bar, baz` 在 `expand: true`（默认）下展开成 9 条 `foo=>foo, foo=>bar, foo=>baz, bar=>foo, … baz=>baz`；在 `expand: false` 下「the first synonym is treated as the canonical representation」，等价于 `foo=>foo, bar=>foo, baz=>foo`；并且「The `expand` parameter does not affect explicit synonym rules, like `foo, bar => baz`.」
- Solr 原文（https://solr.apache.org/guide/solr/latest/indexing-guide/filters.html ）：`expand` 默认 true（展开成全部等价同义词），false（归约到列表第一个）。
- Azure AI Search 原文（https://learn.microsoft.com/en-us/azure/search/search-synonyms ）：「Explicit mapping only applies in the direction specified, and doesn't rewrite the query _WA_ to _Washington_ in this case.」——即 `Washington, Wash., WA => WA` 这条规则**只把前三个归一到 WA，不会把 WA 反向扩成 Washington**。

另一种更细的两种规则语义，Azure 页面说得最干净（https://learn.microsoft.com/en-us/azure/search/search-synonyms ）：「**Explicit mappings** use `=>` to specify one-way replacements … **Equivalent mappings** use commas to group interchangeable terms」。同一页给的可运行示例：`USA, United States, United States of America\nWashington, Wash., WA => WA\n`。

**一条必须知道的副作用**（Azure 官方原文，https://learn.microsoft.com/en-us/azure/search/search-synonyms ）：「Internally, the synonyms feature rewrites the original query with synonyms **by using the OR operator**. For this reason, **hit highlighting and scoring profiles treat the original term and synonyms as equivalent.**」——也就是说同义词扩展之后，你**没法再区分"用户原话命中"和"同义词命中"**，任何"原词加分"的设计都会失效。另外同一条原文里还有：「Synonyms apply to free-form text queries only and aren't supported for filters, facets, autocomplete, or suggestions.」「Synonym expansions don't apply to wildcard search terms; prefix, fuzzy, and regex terms aren't expanded.」

### 2.3 索引期 vs 查询期：官方都建议查询期

Elasticsearch 原文（https://www.elastic.co/docs/solutions/search/full-text/search-with-synonyms ）：「Synonyms can be applied at search time or index time. **Search time is recommended because you can update your synonym sets without reindexing.**」；且「Synonym sets created through the API or the Kibana UI **can only be used at search time**.」

查询期的代价也写在官方：同义词只对 `match` / `query_string` / `simple_query_string` 生效（同页 Step 5）；`inline` 大量同义词「increases cluster size unnecessarily and can lead to performance issues」（同页 Warning）；同义词集必须先存在，否则引用它的索引「becomes inoperable and must be deleted and re-created, or closed and re-opened」（同页 Warning）。索引期同义词还有一个隐蔽代价：**同义词文件本身会被 synonym 之前的 token filter 处理**——原文「Elasticsearch will also use the token filters preceding the synonym filter in a tokenizer chain to parse the entries in a synonym file or synonym set.」（https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-tokenfilter ）；以及 stacked positions 冲突：`multiplexer`/`word_delimiter_graph`/`ngram` 会直接报错、`asciifolding` 只保留折叠版（同页 Warning）。

### 2.4 gazetteer 路线：spaCy PhraseMatcher / EntityRuler

官方文档（https://spacy.io/usage/rule-based-matching ）：

- `PhraseMatcher` 的定位原文：「is useful if you already have a large terminology list or gazetteer consisting of single or multi-token phrases that you want to find exact instances of in your data. As of spaCy v2.1.0, you can also match on the `LOWER` attribute for fast and case-insensitive matching.」——**这就是"术语表整词匹配"的工业实现，且明确说大小写不敏感靠换成 `LOWER` 属性来换**。
- 与 `Matcher` 的取舍原文：`Matcher`「isn't as blazing fast as the `PhraseMatcher`, since it compares across individual token attributes」。
- 性能建议：造 pattern 时用 `nlp.make_doc` / `nlp.tokenizer.pipe`，别用 `nlp(...)` 跑整条 pipeline（同页）。
- 重叠匹配：`EntityRuler` 内置处理，「It also takes care of handling overlapping matches」（同页）。
- 顺带做消歧：「You can also associate patterns with entity IDs, to allow some basic entity linking or disambiguation.」（同页）
- 模糊匹配：v3.5 起有 `FUZZY`（默认 Levenshtein 距离至少 2、最多占 pattern 长度 30%）与 `FUZZY1`..`FUZZY9`（同页）——**拼写容错不必自己写编辑距离**。
- 正则的边界：`REGEX` 只在单个 token 上生效；跨 token 要用 `re.finditer(doc.text)` + `Doc.char_span`，而「If the matched characters don't map to one or more valid tokens, `Doc.char_span` returns `None`」（同页）——**这正是"字符 span → token span"映射会丢东西的官方承认**。

### 2.5 Rasa：synonym 块 + lookup table，以及它的硬限制

Rasa 1.x 训练数据格式（https://legacy-docs-v1.rasa.com/1.6.2/nlu/training-data-format/ ）：

- 同义词写法两种：`## synonym:New York City` 下列 `NYC` / `nyc` / `the big apple`；或在实体标注里写 `[NYC](city:New York City)`，值不同于文本即视为同义。需要 pipeline 里有 `EntitySynonymMapper` 组件。
- **关键限制原文**：「this only happens _after_ the entities have been extracted」；「adding synonyms using the above format does not improve the model's classification of those entities. **Entities must be properly classified before they can be replaced with the synonym value.**」——**同义词只能"抽取后归一"，不能帮抽取**。这是"归一"与"识别"必须分开设计的官方证据。
- lookup table 写法：`## lookup:plates` + 外部文件 `data/test/lookup_tables/plates.txt`（换行分隔词或短语，可多 token 如 `lettuce wrap`）；加载时「combined into a large, case-insensitive regex pattern」，与手写 regex feature 同等对待。
- lookup table 的三条教训原文：「For lookup tables to be effective, there must be a few examples of matches in your training data. Otherwise the model will not learn to use the lookup table match features.」；「if there are false positives or other noise in the table, this can hurt performance. So make sure your lookup tables contain clean data.」；「creating synthetic examples usually leads to overfitting, it is a better idea to use Lookup Tables instead if you have a large number of entity values.」
- 纯 JSON 形态（同一页）：`{"rasa_nlu_data": {"common_examples": [], "regex_features": [], "lookup_tables": [], "entity_synonyms": []}}`。

**DeepPavlov 侧纠正**：其 NER 文档（https://docs.deeppavlov.ai/en/master/features/models/NER.html ）里**没有 lookup table 机制**；DeepPavlov 的等价物是 entity linking 走 SQLite FTS5 倒排索引（见 4.4）。

### 2.6 Microsoft 侧：Azure AI Search synonyms 是"查询期改写"的成品实现

原文要点（https://learn.microsoft.com/en-us/azure/search/search-synonyms ）：

- 同义词映射是**顶层资源**，建一次可被多个索引复用；「Synonyms apply to string fields」；可随时增删且「doesn't require the index to be rebuilt」；**一个字段只能挂一个 synonym map**。
- 唯一支持的格式是 `solr`。
- 配额（真实数字，可引）：free 服务每个 map 最多 **5,000** 条规则，其它 tier 上限 **20,000** 条；每条规则最多 **20** 个 expansion（https://learn.microsoft.com/en-us/azure/search/search-synonyms ）。
- 「Query parsers automatically lower-case any upper or mixed case terms.」（同页）

Microsoft Learn 上**没有**「advanced RAG 的 glossary / query expansion」专节——该页（https://learn.microsoft.com/en-us/azure/foundry/concepts/retrieval-augmented-generation ）只有 keyword/semantic/vector/hybrid 四类检索模式和 agentic retrieval（模型把问题拆成子查询并行检索），未见术语表相关章节。**结论：这一项标「未查到」**；能代表微软口径的只有 Azure AI Search 的同义词页。

## 3. 术语怎么进检索索引：三种做法的真实案例与代价

### 3.1 做法 A：整词 token（把术语当成一个不可分的 token 加入索引）

外部最接近的官方表述是**自定义 tokenizer / 词典分词**这一类：Solr 的 synonym 文件解析默认用 `WhitespaceTokenizerFactory`（`tokenizerFactory`，https://solr.apache.org/guide/solr/latest/indexing-guide/filters.html ），意味着"术语里带空格就被切开，除非你换 tokenizer"；spaCy 的 `PhraseMatcher` 则是"把术语表编译成 token 序列匹配器"（https://spaCy.io/usage/rule-based-matching ）。**没有一个主流项目把"最大匹配整词化"当成默认能力**，它基本都出现在中文/日文这类无空格语言的工程里——这一点我**未查到**权威外部规范，只能作方法学判断。

SQLite FTS5 侧的**结构性事实**（这是我们要对接的后端，https://sqlite.org/fts5.html ）：默认 `unicode61` tokenizer 把「Unicode 6.1 中的 L*（字母）/N*（数字）/Co（私用）」类字符算作 token 字符，其余算分隔符。**汉字属于 L\*，因此一串连续汉字在 FTS5 里会成为一个完整 token**——这意味着：
- 不加任何处理时，「罗德岛制药公司和罗德岛」是**一个** token，什么都搜不到；
- 想让术语整词命中，就得自己切词后再喂给 FTS5（本项目的 `tokenize_t1`/`tokenize_t2` 正是在做这件事）；
- 反过来说，`trigram` tokenizer（每三个连续字符一个 token，支持子串匹配，https://sqlite.org/fts5.html ）能绕过切词但会把索引放大，且丢掉词边界语义。

`tokenize_t2(name_terms=...)` 这种"候选词表 → 只在文本中实际出现的名字整词入索引"的写法，在外部对应的正是 spaCy 文档说的 gazetteer 思路（"large terminology list … exact instances"，https://spacy.io/usage/rule-based-matching ）。

代价（分析，非实测）：词表越大，最长匹配的候选集越大（本项目 `NameTable.spans_in_run` 的开销）；整词 token 的 IDF 单独计算，会与原词的 IDF 脱钩；一旦术语表变化，索引必须重建（这正是本项目 `index_build_fingerprint` / `content_digest` 存在的理由）。

### 3.2 做法 B：同义词扩展进索引（index-time expansion）

真实案例与代价都写在官方文档里：

- ES 的 `synonym` token filter（非 graph 版）就是给索引期用的：`synonym_graph` 文档明确「If you want to apply synonyms during indexing please use the standard synonym token filter.」（https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-graph-tokenfilter ）
- Solr 的索引期写法必须补 `FlattenGraphFilter`，原文「the indexer can't directly consume a graph」+「This filter must be included on index-time analyzer specifications that include at least one graph-aware filter」（https://solr.apache.org/guide/solr/latest/indexing-guide/filters.html ）。
- 代价一：**改词表就要重建索引**（这正是 ES 官方推荐查询期的理由，https://www.elastic.co/docs/solutions/search/full-text/search-with-synonyms ）。
- 代价二：**索引体积**。Azure 官方原话「A large number of inline synonyms increases cluster size unnecessarily and can lead to performance issues.」（https://learn.microsoft.com/en-us/azure/search/search-synonyms ）
- 代价三：**同义词条目本身会被前置 filter 变形**（stemmer 等），原文见 2.3。
- 代价四：**同义词与 stop word 的顺序问题**会造成"规则里有 stop word 就报错"或"静默丢弃"，取决于 `lenient`（默认等于 `updateable`），`lenient: false` 时「the affected index enters a red state」；构词表时还有堆内存熔断（默认 95% 触发）（https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-tokenfilter ）。

Solr 官方给的索引/查询分离模板（可直接当参照实现）：

```xml
<analyzer type="index">
  <tokenizer name="standard"/>
  <filter name="synonymGraph" synonyms="mysynonyms.txt"/>
  <filter name="flattenGraph"/> <!-- required on index analyzers after graph filters -->
</analyzer>
<analyzer type="query">
  <tokenizer name="standard"/>
  <filter name="synonymGraph" synonyms="mysynonyms.txt"/>
</analyzer>
```
（https://solr.apache.org/guide/solr/latest/indexing-guide/filters.html ）

### 3.3 做法 C：同义词只做查询期扩展（不碰索引）

官方首选，原文见 2.3。代价清单见 2.2 末尾（OR 改写导致原词/同义词不可区分、只对 `match` 类查询生效、通配/前缀/正则/fuzzy 不扩展）。

另一条硬代价：multi_match 类查询的子句数 = 字段数 × 词数，`indices.query.bool.max_clause_count` 默认 **4096**（https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-multi-match-query ）。同义词扩展会成倍放大子句数——**这是"扩展"最容易被低估的成本**。

### 3.4 做法 D：独立 term 字段 + 字段 boost（术语命中权重单独控制）

四种官方机制：

1. **Elasticsearch `multi_match` 的 `most_fields`**——官方动机原文（https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-multi-match-query ）：「The `most_fields` type is most useful when querying multiple fields that contain the same text analyzed in different ways. For instance, the main field may contain **synonyms, stemming and terms without diacritics**. A second field may contain the original terms, and a third field might contain **shingles**. By combining scores from all three fields we can match as many documents as possible with the main field, but use the second and third fields to push the most similar results to the top of the list.」——**这就是"同一段文本按不同方式分析成多个字段、再合并打分"的官方推荐做法**，术语字段完全可以当"第二个字段"。
2. **字段权重 `^`**：`"fields": ["subject^3", "message"]`（https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-multi-match-query ）。
3. **Azure AI Search scoring profile 的字段权重**：`scoringProfiles[].text.weights`，原文「Weighted fields are name-value pairs composed of a `searchable` field and a positive number that is used as a multiplier. If the original field score of HotelName is 3, the boosted score for that field becomes 6」；单索引最多 100 个 profile，一次查询只能指定一个；函数型 boost 有 `magnitude`/`freshness`/`distance`/`tag` 和 `constant|linear|quadratic|logarithmic` 插值；官方调参建议「Start conservative: boost in the 1.25–2.0 range」（https://learn.microsoft.com/en-us/azure/search/index-add-scoring-profiles ）。
4. **SQLite FTS5 的按列加权 bm25**：原文「The first argument passed to `bm25()` following the table name is the weight assigned to the leftmost column… If there are not enough arguments for all table columns, remaining columns are assigned a weight of 1.0.」；示例 `ORDER BY bm25(email, 10.0, 5.0)` 表示 "a hit in the sender column is considered equivalent to 10 hits in the body column"；k1 固定 1.2、b 固定 0.75（https://sqlite.org/fts5.html ）。**这意味着"独立 term 字段 + boost"在 FTS5 上是原生的，不需要引入任何依赖**。

还有一个更轻的变体：**加权同义词**。Solr 的 `DelimitedBoostFilter`（`solr.DelimitedBoostTokenFilterFactory`，默认分隔符 `|`）让同义词文件本身带权重，官方示例 `boostedSynonyms.txt`：`leopard, big cat|0.8, bagheera|0.9, panthera pardus|0.85` / `lion => panthera leo|0.9, simba|0.8, kimba|0.75`（https://solr.apache.org/guide/solr/latest/indexing-guide/filters.html ）——**"别名可信度不同"可以直接编码进词表，而不用另开字段**。

### 3.5 三种做法代价对照

| | 索引期成本 | 查询期成本 | 改词表成本 | 能否区分原词命中 | 能否给别名不同权重 |
| --- | --- | --- | --- | --- | --- |
| A 整词 token | 词表只影响出现的块；整词 ID；索引结构不变 | 最长匹配开销 | **必须重建索引** | 能 | 不能（除非别名各占一 token 并配 weight） |
| B 索引期同义词扩展 | 索引显著变大；flattenGraph 必需 | 低 | **必须重建索引** | 不能（同位置并列） | 靠 `DelimitedBoostFilter` 可以 |
| C 查询期同义词扩展 | 无 | 查询变慢；子句数膨胀（max_clause_count 4096） | 不重建 | 不能（OR 改写，官方明说） | 靠 boost 不能，靠字段权重可以 |
| D 独立 term 字段 + boost | 多一列 + 回填；索引变大 | 低 | 需重建该列 | 能 | 能（字段权重） |

## 4. 术语库与知识图谱实体的对齐

### 4.1 候选生成的三条真实路线

**路线 1：别名精确查表（最省，最脆）**
spaCy 的 `EntityLinker` 默认就是这样：官方原文「It requires a `KnowledgeBase`, as well as a function to generate plausible candidates from that `KnowledgeBase` given a certain textual mention, and a machine learning model to pick the right candidate」（https://spacy.io/api/entitylinker ）；其默认候选生成器 `CandidateGenerator` 的定义是「a function looking up **exact, case-dependent aliases** in the KB」（https://spacy.io/api/entitylinker ）。

KB 的接口本身就是"别名表"抽象：`KnowledgeBase` 是「A storage class for entities and aliases of a specific knowledge base (ontology)」，核心方法 `get_candidates(mention: Span)`、`get_alias_candidates()`（3.5 起从 `KnowledgeBase` 移到 `InMemoryLookupKB`），候选对象 `Candidate` 带 `alias`/`prior_prob`/`entity_freq`/`entity_vector`（https://spacy.io/api/kb ）。

关键工程细节：**`prior_prob`（别名指向实体的先验概率）+ `threshold`（低于阈值输出 NIL）+ `labels_discard`（自动丢弃）**（https://spacy.io/api/entitylinker ）。这直接回答"找不到怎么办"——**返回 NIL，而不是硬塞一个最像的**。

**路线 2：稠密检索 + 交叉编码器精排（BLINK）**
README 原文：「BLINK is an Entity Linking python library that uses Wikipedia as the target knowledge base.」；两阶段原文：「In the first stage, BLINK performs retrieval in a dense space defined by a bi-encoder that independently embeds the mention context and the entity descriptions. Each candidate is then examined more carefully with a cross-encoder, that concatenates the mention and entity text.」；KB 文件是 `entity.jsonl`（每行一个实体，含 Wikipedia url/title/text），索引可用 FAISS flat（精确）或 hnsw（近似）（https://github.com/facebookresearch/BLINK ）。论文摘要原文：「a two-stage zero-shot linking algorithm, where each entity is defined only by a short textual description」；「no explicit entity embeddings or manually engineered mention tables」；「much of the accuracy gain from the more expensive cross-encoder can be transferred to the bi-encoder via knowledge distillation」（https://arxiv.org/abs/1911.03814 ）。

**路线 3：受限解码 / 前缀树（GENRE）—— 从机制上保证"输出一定是 KG 里的真标识"**
README 原文：「(m)GENRE uses a sequence-to-sequence approach to entity retrieval (e.g., linking), based on fine-tuned BART … performs retrieval generating the unique entity name conditioned on the input text using **constrained beam search to only generate valid identifiers**」；前缀树实现文件是 `genre/trie.py`（`Trie`、`MariasaTrie`，后者注明「memory efficient prefix tree」），用法 `prefix_allowed_tokens_fn=lambda batch_id, sent: trie.get(sent.tolist())`；mGENRE 侧要额外维护 `(title, language_ID) -> Wikidata ID` 映射，`marginalize=True` 时把同一实体的多种语言写法合并打分（https://github.com/facebookresearch/GENRE ）。

**这条路线的方法论价值**：把"合法实体名集合"编译成一棵 trie 当约束，解码时逐 token 剪枝。它**不需要别名表就能保证不 hallucinate 实体名**，代价是要训练模型（对我们这种纯标准库、离线可复现的项目不适用，但"把候选集合编译成前缀树做匹配"这个结构本身不需要模型）。

### 4.2 "多少比例术语能在 KG 找到实体" —— 未查到

我在 BLINK、GENRE、spaCy、DeepPavlov 的官方文档里**没有找到任何"术语↔实体对齐覆盖率"的公开数字**，也未找到可引用的实测报告。**这一项标「未查到」，不得编造。**

能给出的只是「对齐率由什么决定」的结构性判断：spaCy 默认候选生成是「exact, case-dependent aliases」（https://spacy.io/api/entitylinker ）——这意味着**大小写差异、全半角差异、空格差异、简繁差异都会直接掉到 NIL**，所以对齐率的第一个决定因素是"别名表里有没有这一种写法"，而不是模型好坏。

### 4.3 找不到对应实体怎么处理（四种官方承认的做法）

1. **返回 NIL / 丢弃**：spaCy 的 `threshold`（低于阈值输出 NIL）与 `labels_discard`（https://spacy.io/api/entitylinker ）。
2. **保留为"仅术语、无实体"的条目**：SKOS 允许有 altLabel 而无 prefLabel 的概念（5.6.4，https://www.w3.org/TR/skos-reference/ ）——即"这个词是真的，但还没有规范名/还没有实体"是合法状态；TBX 同样允许只有 `<term>` 没有对应 `<descrip>`（https://www.tbxinfo.net/developer-resources/tbx-elements-reference/ ）。
3. **降级为"一串注释"**：TBX 的降级惯例 `<note>partOfSpeech::noun</note>`（https://www.tbxinfo.net/developer-resources/tbx-elements-reference/ ）——不支持的数据类别不要丢，塞进 note 保留。对"对齐不上的术语"同理：**别丢，标一个 unresolved 状态**。
4. **人工审核分档**：Wikibase 的 aliases 是自由数组（无审核态字段，https://github.com/wikimedia/mediawiki-extensions-Wikibase/blob/master/docs/topics/json.md ），而 SKOS-XL 允许把标签做成资源后挂任意描述（含审核态，https://www.w3.org/TR/skos-reference/skos-xl.html ）——**要审核态就得用 SKOS-XL 那种"标签是资源"的结构，纯字符串别名表放不下状态**。

### 4.4 最贴近我们后端的一张现成 schema：DeepPavlov 的 `inverted_index`

原文（https://docs.deeppavlov.ai/en/master/features/models/entity_extraction.html ）：

> 「The database filename is defined with the **entities_database_filename** in entity linking configs. The file is in **SQLite format with FTS5 extensions for full-text search of entities by entity mention**. The database file should contain the **inverted_index** table with the following columns: `title` — entity title (name or **alias**) in the knowledge base; `entity_id` — entity ID in the knowledge base; `num_rels` — number of relations of the entity with other entities in the knowledge graph; `ent_tag` — entity tag of the entity detection model (for example, CITY, PERSON, WORK_OF_ART, etc.); `page` — page title of the entity (for Wikidata entities - the Wikipedia page); `label` — entity label in the knowledge base; `descr` — entity description in the knowledge base.」

它另外还有两个字段能直接对应"排序"需求：`num_rels`（KG 里连边数，当先验热度用）和 `ent_tag`（类型约束）。官方列出的候选排序四步原文：「extraction of candidate entities from SQLite database; candidate entities sorting by entity tags (if entity tags are provided); ranking of candidate entities by connections in Wikidata knowledge graph …; candidate entities ranking by context and descriptions using Transformer model」（同页）——**注意第一步就是 FTS5 查表，模型只用在前 3 步筛完的少量候选上。**

同页还有两个可借的配置项：`alias_coef: float` —「The coefficient which is multiplied by the substring matching score of the entity if the entity mention in the text matches with the entity title」（**精确别名命中给一个乘子**，正是"术语命中应该加权"的工程化写法）；`use_tags` / `lemmatize` —「whether to search only those entity IDs in the inverted index, which have the same tag as the entity mention」/「whether to lemmatize entity mentions before searching candidate entity IDs in the inverted index」（https://docs.deeppavlov.ai/en/master/features/models/entity_extraction.html ）。

**这张表的价值**：它是"术语库 ↔ KG 对齐"能落成一张普通表的最小 schema，而且后端就是 FTS5——和本项目 `fts_backend.py` 同一技术栈，**不需要任何新依赖**。

## 5. 对本项目的可借鉴清单

1. **把别名分成三档（规范名 / 可见别名 / 隐藏别名），只让隐藏别名进匹配、不进展示。**
   → 对应位置：`src/arkrag/index.py` 的 `build_alias_index`（现在是 `on`/`setdefault` 一对多、先到先得）与 `name_terms_from_graph`（只读 `entities[].name` 与 `aliases`）；消费端 `src/arkrag/query.py` 的 `_alias_owner_map`。
   → 代价：schema 要新增一档字段（`hidden_aliases`），且 `build_alias_index` 必须能区分"这条别名只用于匹配"；`norm_entity.py::merge_names` 合并时要跳过隐藏档，否则会把拼写变体当权威名。语义参照 SKOS hiddenLabel（https://www.w3.org/TR/skos-reference/ ）。**零新依赖。**

2. **`build_alias_index` 从"一对一、先到先得"改成"文本 → 候选列表"，把冲突显式暴露出来，而不是静默丢弃。**
   → 对应位置：`src/arkrag/index.py::build_alias_index`（现在 `out.setdefault(text, eid)` 会丢掉"同一文本被第二个实体认领"）；消歧复用 `src/arkrag/norm_entity.py::ambiguous_aliases`（已经能算出"一个别名对应多个实体"）。
   → 代价：返回类型由 `dict[str, str]` 变 `dict[str, list[str]]`，所有调用点（`query.py::_alias_owner_map` 的兼容分支、`index.py` 的 `probe_digest` 基准）都要跟；好处是不用再靠 `norm_entity` 那一层的 `UnionFind` 事后补救。参照 spaCy Candidate 列表 + `prior_prob` 的多候选模型（https://spacy.io/api/kb ）。**零新依赖。**

3. **查询期做"双向但要分方向"：别名 → 规范名（归一）与规范名 → 别名（扩展）用两套表，别混成一张。**
   → 对应位置：`src/arkrag/query.py` 的 `_relation_lookup`（已区分 canonical 自映射与 `RELATION_SYNONYMS`，可照此给实体词做同样两段）与 `analyze_query` 输出；`src/arkrag/index.py` 的 `tokenize_t2(name_terms=...)` 只提供"文本里出现过的名字"，不提供反向扩展。
   → 代价：扩展会成倍放大查询 term 数（官方明说 `max_clause_count` 4096 与子句数 = 字段数 × 词数，https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-multi-match-query ），且扩展后"原词命中 vs 别名命中"不可区分（Azure 原文 https://learn.microsoft.com/en-us/azure/search/search-synonyms ）——所以本项目如果要保留"原词加分"，只能走"独立字段"而不是"同义词改写"。**零新依赖。**

4. **术语表不参与索引期，只在查询期生效；索引只存"文本中确实出现的整词"。**
   → 对应位置：`src/arkrag/index.py` 的 `name_terms_from_graph` + `tokenize_t2`（已经是"候选词表 → 只整词化真实出现的名字"），加上 `index_build_fingerprint` / `content_digest` 作为词表变更的失效信号。
   → 代价：查询期多一层最长匹配（`NameTable.spans_in_run`），换来"改词表不重建索引"——这正是 ES 官方推荐查询期的理由（https://www.elastic.co/docs/solutions/search/full-text/search-with-synonyms ）。**零新依赖。**

5. **给术语命中单开一列并走 FTS5 的按列加权 bm25，而不是把术语混进正文列。**
   → 对应位置：`src/arkrag/fts_backend.py`（建表与查询）配合 `src/arkrag/index.py::LexicalIndex.search`。
   → 代价：多一列要回填、索引体积上升，且 `content_digest` 变化会触发一次全量重建；好处是权重可调（`bm25(fts, 10.0, 5.0)` 的语义见 https://sqlite.org/fts5.html ），不需要引入 ES 那套 `most_fields` 多字段合并（https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-multi-match-query ）。**零新依赖。**

6. **用 `fts5vocab` 做"术语到底有没有进索引"的自检探针。**
   → 对应位置：`src/arkrag/index.py` 的 `probe_digest` / `freshness_check`（现有探针只比 top-k 排序，看不出"某个术语根本没进词表"）。
   → 代价：`fts5vocab` 是 FTS5 自带的虚拟表模块（https://sqlite.org/fts5.html ），只适合测试期与诊断期，别进生产路径。**零新依赖。**

7. **术语↔实体的对齐结果落成一张普通表（title / entity_id / tag / 热度 / 状态），别只放在内存 dict 里。**
   → 对应位置：`src/arkrag/index.py::build_alias_index` 的产出目前是内存 dict；可参照 DeepPavlov 的 `inverted_index` 表（title 含 alias、entity_id、num_rels 当热度、ent_tag 当类型约束、label、descr，https://docs.deeppavlov.ai/en/master/features/models/entity_extraction.html ）。
   → 代价：查询期多一次 SQL；好处是可以直接带"对齐状态"字段（对齐上/未对齐），把 4.3 里的"找不到就 NIL"显式化；如果只想修 dict 也可以在 `build_alias_index` 里加一个 `unresolved` 输出。**零新依赖**（FTS5 是标准库 `sqlite3` 自带的）。

8. **给"精确别名命中"一个乘子，并把"未对齐术语"的阈值参数化，别硬编码成一个 if。**
   → 对应位置：`src/arkrag/query.py::analyze_query` 的 span→owner 查找与 `src/arkrag/vocab.py`（可新增一组阈值常量，与 `TYPE_SYNONYMS` / `RELATION_SYNONYMS` 同层）。
   → 代价：任何阈值都要用 `goldset.py` 的题集回归，且 `gates.py` 现有门限可能被带崩；外部先例是 DeepPavlov 的 `alias_coef`（精确别名命中的乘子）与 spaCy 的 `threshold`（低于阈值输出 NIL）（https://docs.deeppavlov.ai/en/master/features/models/entity_extraction.html 、https://spacy.io/api/entitylinker ）。**零新依赖。**

> 需要标注「需新增依赖」的候选方案（本次清单里**没有采用**，仅记录）：spaCy `PhraseMatcher`/`EntityRuler`（需新增 `spacy` 依赖与语言包，https://spacy.io/usage/rule-based-matching ）；BLINK 式稠密检索（需 `torch`+`faiss`，https://github.com/facebookresearch/BLINK ）；GENRE 式受限解码（需模型与 `transformers`，https://github.com/facebookresearch/GENRE ）；ES/Solr 的 synonym_graph（需外部检索服务，https://www.elastic.co/docs/reference/text-analysis/analysis-synonym-graph-tokenfilter ）。
