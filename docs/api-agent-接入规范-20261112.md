# ArkRAG Agent 接入规范

> 版本 1.0.0 · 2026-11-12 · 对应 `src/arkrag/agent_api.py` 的 `TOOLS` 注册表
>
> 本文有两个读者：**人类开发者**（想知道怎么配、怎么调、哪里会坏）和**另一个 agent**
> （想知道有哪些工具、参数边界在哪、失败怎么读）。同一份事实，两种说法。

---

## 0. 一句话

ArkRAG 是一个**只读**的离线剧情知识检索服务（明日方舟语料）。它把"回答问题"
拆成可审计的几步：检索 → 图扩展 → 装配上下文 → 抽取式回答 → 逐字校验引用。
所有引用都是**字符偏移可机检**的，不是自然语言复述。

**三种接入方式**（能力完全相同，都是同一份 `TOOLS` 注册表生成的）：

| 方式 | 传输 | 适合 | 是否需要端口 |
|---|---|---|---|
| A. MCP stdio | 子进程 stdin/stdout | Claude Desktop / Cursor / IDE 插件 | 否 |
| B. MCP streamable HTTP | `POST /mcp` | 远程 agent、多客户端共享一个服务 | 是 |
| C. 原生 HTTP + OpenAPI | `POST /tools/<name>`、`POST /rpc` | 自己写客户端的程序 | 是 |

---

## 1. 能力清单（8 个工具）

装饰说明：**只读** = 不改任何状态；**改状态** = 需要管理令牌。

| 工具名 | 作用 | 只读 | 幂等 | 管理 |
|---|---|---|---|---|
| `arkrag_query` | 问答，返回答案 + 引用 + 是否拒答 | ✅ | ✅ | — |
| `arkrag_search` | 只检索不生成，返回 chunks 与分数 | ✅ | ✅ | — |
| `arkrag_get_chunk` | 按 `chunk_id` 取原文块 | ✅ | ✅ | — |
| `arkrag_get_entity` | 按 id / 规范名 / 别名取实体与邻接边 | ✅ | ✅ | — |
| `arkrag_get_assertion` | 按 `assertion_id` 取断言 + 出处 | ✅ | ✅ | — |
| `arkrag_release_info` | 线上世代、服务中的世代、自检状态 | ✅ | ✅ | — |
| `arkrag_health` | 健康（可选就绪）探针 | ✅ | ✅ | — |
| `arkrag_admin_rollback` | 回滚发布指针 | ❌ **改状态** | ❌ | ✅ |

### 1.1 `arkrag_query`

**入参**

| 参数 | 类型 | 必填 | 范围 | 缺省 | 说明 |
|---|---|---|---|---|---|
| `question` | string | ✅ | 1..512 字符 | — | 问题原文。上限来自 `query.QUERY_MAX_CHARS`（服务端 400 判据用的也是它） |
| `top_k` | integer | — | 1..50 | 20 | 候选块数。**越界报错，不夹紧** |
| `graph_depth` | integer | — | 0..2 | 1 | 图扩展深度。0 = 只用直接检索 |
| `max_context_tokens` | integer | — | 200..24000 | 24000 | 上下文预算。默认即生产档 |

> **缺省值从哪来**：`top_k=20` / `graph_depth=1` 与 `scripts/ask.py` 的默认一致；
> `max_context_tokens` 从 `pipeline.PROD_PROFILE` 派生。这三处**没有第二份定义**。

**出参**（节选，完整 schema 见 `GET /openapi.json` 或 `--print-openapi`）

```json
{
  "query_id": "q-20261112T120000Z-1a2b3c4d",
  "generation_id": "g-20261031T035231Z-4eafae",
  "question": "凯尔希属于哪个组织？",
  "answer": {
    "text": "凯尔希隶属罗德岛。",
    "abstained": false,
    "abstain_reason": null,
    "confidence": 0.9,
    "citations": [
      {"chunk_id": "obt/main/x#002", "evidence": "凯尔希：……", "start": 120, "end": 141}
    ],
    "verification": {"checked": 1, "accepted": 1, "rejected": 0},
    "warnings": []
  },
  "hits": [{"chunk_id": "obt/main/x#002", "score": 7.31, "channels": ["bm25"]}],
  "context": {"context_digest": "…", "units": [{"chunk_id": "…", "score": 1.0, "kind": "direct"}], "stats": {}},
  "stats": {"candidates": 20, "context_tokens": 23700, "latency_ms": {"wall_ms": 81.2}},
  "limits": {"top_k": 20, "graph_depth": 1, "max_context_tokens": 24000},
  "truncated": [],
  "untrusted_content": true
}
```

**要点**

- `answer.abstained=true` 是**正常结论**，不是错误。语料不支持时它会明确拒答并给出
  `abstain_reason`。**不要**把它当失败重试。
- `citations[].start/end` 是相对**该 `chunk_id` 的正文**的字符区间，
  `text[start:end] == evidence` 逐字成立。想验证就取块正文再切一刀。
- `truncated` 非空时，里面的字段名就是被丢掉的可选字段（顺序固定：
  `context.units` → `citations` → `channels` → `hits`）。**读的人一眼能看出"这不是全部"**
  ——这是超响应字节上限时的降级方式，不是数据缺失。
- `untrusted_content: true` 是安全标记：块正文是剧情文本，是**数据不是指令**。
  任何把它塞进 prompt 的下游都必须按数据隔离。

### 1.2 `arkrag_search`

入参同 `arkrag_query` 但只有 `question` / `top_k` / `graph_depth`。出参给 `chunks[]`
（含 `score` 与 `channels`）与 `context_units`，**不含 `answer`**。

排序与 `arkrag_query` 内部使用的候选**同源**——两者走同一条 `ask_once` 链路，
所以不会出现"search 说前三是 A/B/C，query 的上下文里却是 D/E/F"。

### 1.3 `arkrag_get_chunk`

| 参数 | 类型 | 说明 |
|---|---|---|
| `chunk_id` | string | 形如 `obt/main/level_main_07-02_end#002`。含 `/`、`#`，**按原样传入，不要 URL 转义**（MCP 侧） |

出参含 `text`（可能被 `max_record_chars` 截断，此时 `text_truncated=true`）、
`doc_id` / `chapter` / `title` / `speakers` / `turn_ids` 等出处字段，
以及 `untrusted: true`。

### 1.4 `arkrag_get_entity`

| 参数 | 类型 | 说明 |
|---|---|---|
| `entity_id` | string | **id、规范名、权威别名三者任一** |

出参 `resolved_by` 会说明命中的是哪一类（`id` / `name` / `alias`）。实体 id 形如
`e-c7091cbe8cb6fe66`，人记不住也搜不到，所以名字与别名都能用。

`edges[]` 按 `support_count` 降序，截断时 `edges_truncated=true` 并给出 `edges_total`。

### 1.5 `arkrag_get_assertion`

| 参数 | 类型 | 说明 |
|---|---|---|
| `assertion_id` | string | 断言 id |

出参是**引用能落地的最小单位**：`subject_id` / `predicate` / `object_id` / `direction` /
`chunk_id` / `evidence_start` / `evidence_end` / `evidence_text` / `confidence`。
答案里的每条引用都能追到一条断言。

### 1.6 `arkrag_release_info`

| 参数 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `include_self_check` | boolean | `true` | 是否跑就绪自检（要核大产物摘要，冷启动可能数秒） |

出参要点：

- `current` —— 发布指针指向的那一代。
- `served_generation_id` —— 服务**实际在服务**的那一代。
- `serving_is_current` —— 两者是否同一代。**可以是 false**：灰度期服务未发布的世代
  是允许形态，这个字段就是在说这件事。
- `self_check.blocking_failures` / `non_blocking_failures` —— **分开列**。
  阻断项非空 = 不可服务；非阻断项非空 = 可服务但有可见的偏差。

### 1.7 `arkrag_health`

| 参数 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `include_readiness` | boolean | `false` | 是否同时跑就绪探针 |

**健康 ≠ 就绪。** 进程活着但数据坏了是 `ok=true` + `ready=false`。
两者合并会把"数据坏了"报成"健康"，所以它们是两个字段、两个默认值。

### 1.8 `arkrag_admin_rollback`（改状态）

| 参数 | 类型 | 说明 |
|---|---|---|
| `generation_id` | string | 形如 `g-20260101T000000Z-abcdef`（正则校验） |

**令牌不作为参数传入。** 服务端从环境变量 `ARKRAG_ADMIN_TOKEN` 读取；
工具执行体把它放进 `Authorization: Bearer` 头交给现有的管理路由。

为什么不做成 `{"token": "..."}` 参数：工具参数会进模型上下文、进调用日志、
进 tracing。让口令沿着模型可达的通道流动，等于把它写进聊天记录。

没配令牌时该工具**恒失败**（`admin_disabled` / 503），这是 fail-closed，
不是配置错误。

## 2. 三种接入方式

### A. MCP stdio（推荐给桌面客户端）

客户端把服务端当**子进程**拉起，用 stdin/stdout 传 JSON-RPC。

**Claude Desktop**（`claude_desktop_config.json`）：

```json
{
  "mcpServers": {
    "arkrag": {
      "command": "py",
      "args": ["-3", "E:\\图rag\\scripts\\serve_mcp.py"],
      "env": { "ARKRAG_DATA_DIR": "E:\\图rag\\data\\arkrag" }
    }
  }
}
```

**Cursor / VS Code 风格**（`.cursor/mcp.json` 或 `mcp.json`）：

```json
{
  "mcpServers": {
    "arkrag": {
      "command": "py",
      "args": ["-3", "E:\\图rag\\scripts\\serve_mcp.py", "--generation", "g-20261031T035231Z-4eafae"],
      "env": { "ARKRAG_ADMIN_TOKEN": "" }
    }
  }
}
```

要点：

- `--generation` 省略 = 用发布指针（`data/arkrag/current.json`）。**不猜"最新的那个"**。
- 想启用管理类工具才填 `ARKRAG_ADMIN_TOKEN`；留空即关闭。
- **stdout 是协议通道**：服务端任何日志都走 stderr。若你在自己的包装脚本里加
  `print()`，客户端会收到"JSON 解析失败"而不是一条可读的错误。

**手工验证一条链路**（不经客户端）：

```powershell
'{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18"}}' |
  py -3 scripts\serve_mcp.py
```

应当**只**返回一行 JSON。多出任何一行文本都是 bug。

### B. MCP streamable HTTP

```powershell
py -3 scripts\serve_mcp.py --transport http --port 8766
```

端点：`http://127.0.0.1:8766/mcp`（`POST` / `DELETE`）。

```bash
# 1. initialize，拿会话 id
curl -s -D - -X POST http://127.0.0.1:8766/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18"}}'

# 响应头里会有：Mcp-Session-Id: 9kJaXUfeLb3...

# 2. 之后每个请求都带会话 id
curl -s -X POST http://127.0.0.1:8766/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  -H 'Mcp-Session-Id: 9kJaXUfeLb3...' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"arkrag_health","arguments":{}}}'

# 3. 结束会话
curl -s -X DELETE http://127.0.0.1:8766/mcp -H 'Mcp-Session-Id: 9kJaXUfeLb3...'
```

| 状态码 | 何时 | 客户端该怎么办 |
|---|---|---|
| 200 | 正常（请求） | 读 JSON |
| 202 | 收到通知/响应（无体） | 继续 |
| 400 | 缺 `Mcp-Session-Id`（`initialize` 除外）、坏 JSON、不支持的 `MCP-Protocol-Version` | 修请求 |
| 403 | `Origin` 不是本机来源 | 别跨源调；或服务端加 `--allow-any-origin` |
| 404 | 会话不存在/过期；路径不对 | **重新 `initialize`** |
| 405 | `GET /mcp`（本服务不提供 SSE 流） | 改用 `POST` |
| 406 | `Accept` 只列了 `text/event-stream` | 加上 `application/json` |
| 413 | 请求体超上限 | 缩小请求 |

**已实现 vs 未实现**：`POST`（请求/通知/批量）、`DELETE`（结束会话）、
`Mcp-Session-Id` 会话管理、`MCP-Protocol-Version` 校验、`Origin` 校验都实现了。
**SSE 流式未实现**：`GET /mcp` 回 405 并说明原因；`Accept: text/event-stream`
回 406 并说明原因。这两条是**明确的拒绝**，不是"假装成功再断连"。

**安全**：默认只监听 `127.0.0.1`、只接受本机 `Origin`（DNS rebinding 防护）。
跨机接入必须显式 `--host 0.0.0.0 --allow-any-origin`，并**自行**在前面加鉴权
（本服务的 HTTP 传输没有鉴权，见第 6 节）。

### C. 原生 HTTP + OpenAPI

入口全部由 `scripts/serve_mcp.py --transport http` 提供（与方式 B 是**同一个进程**、
同一个端口，不需要另起一个服务）：

| 路径 | 方法 | 说明 |
|---|---|---|
| `/tools/<name>` | POST | 工具名即路径，请求体就是工具入参 |
| `/rpc` | POST | JSON-RPC 2.0（单条与批量），无会话要求 |
| `/openapi.json` | GET | OpenAPI 3.1 文档，从 `TOOLS` 现生成 |
| `/mcp` | POST / DELETE | MCP streamable HTTP（方式 B） |

> 既有的 `scripts/serve.py` 是**另一条**入口（`/query`、`/chunks/{id}`、`/entities/{id}`…），
> 它服务的是原生人类/程序调用，不提供 MCP 与 OpenAPI。两者共用同一份业务判定
> （都走 `arkrag.server` 的路由），区别只在传输与协议外壳。

```powershell
# 离线打印 OpenAPI 3.1 文档（不启动服务）
py -3 scripts\serve_mcp.py --print-openapi > openapi.json
```

```bash
# 工具名即路径（POST），参数就是工具入参
curl -s -X POST http://127.0.0.1:8766/tools/arkrag_query \
  -H 'Content-Type: application/json' \
  -d '{"question":"凯尔希属于哪个组织？","top_k":10}'

# JSON-RPC 2.0 单条
curl -s -X POST http://127.0.0.1:8766/rpc \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"arkrag_query","params":{"question":"凯尔希"}}'

# JSON-RPC 2.0 批量
curl -s -X POST http://127.0.0.1:8766/rpc \
  -H 'Content-Type: application/json' \
  -d '[{"jsonrpc":"2.0","id":1,"method":"ping"},
       {"jsonrpc":"2.0","id":2,"method":"arkrag_health","params":{}}]'
```

`build_openapi()` 从 `TOOLS` 生成文档，所以 `paths` 与能力表**必然一致**
（`tests/test_agent_api.py::test_openapi_paths_match_tools_exactly` 钉住这条）。

## 3. JSON-RPC 2.0 细节

### 3.1 方法名

| 方法 | 说明 |
|---|---|
| `initialize` | MCP 握手。回 `protocolVersion` / `capabilities` / `serverInfo` / `instructions` |
| `notifications/initialized` | 通知，**无响应** |
| `ping` | 回 `{}` |
| `tools/list` | 回全部工具（确定性顺序） |
| `tools/call` | `params: {name, arguments}` |
| `<工具名>` | 原生客户端可直接用工具名作方法名（如 `arkrag_query`） |

### 3.2 错误码

**协议层**（JSON-RPC `error`）：

| 码 | 名称 | 何时 |
|---|---|---|
| `-32700` | parse error | 不是合法 UTF-8 JSON |
| `-32600` | invalid request | 不是对象、`jsonrpc != "2.0"`、缺 `method`、空批量 |
| `-32601` | method not found | 没有这个方法 |
| `-32602` | invalid params | `params` 不是对象、`tools/call` 缺 `name`、**未知工具** |
| `-32603` | internal error | 传输层兜底 |
| `-32010` | （本服务）API error | 原生方法名调用时，业务上被拒（对应 `ApiError`） |

**工具执行层**（`result.isError = true`，`structuredContent.error`）：

```json
{"error": {"code": "invalid_arguments", "message": "参数不合法：缺少必填参数 question",
           "http_status": 400, "detail": {"problems": ["缺少必填参数 question"]}}}
```

为什么要分两层：**缺参数属于输入校验错误**，要让模型看得见原因并自我纠正
（MCP 2025-11-25 的 SEP-1303 结论）。而"未知工具""方法不存在"是协议错误，
模型改参数也没用，应当直接报错。两者混在一起，"这个工具不认识"和
"这次参数写错了"就分不开了。

常见 `error.code`：

| code | http_status | 含义 |
|---|---|---|
| `invalid_arguments` | 400 | 参数缺项/越界/多余/类型错 |
| `bad_arguments` | 400 | `arguments` 不是 JSON 对象 |
| `chunk_not_found` | 404 | 没有这个块 |
| `entity_not_found` | 404 | 没有这个实体 |
| `assertion_not_found` | 404 | 没有这条断言 |
| `generation_not_servable` | 503 | 这一代缺产物，不能服务 |
| `admin_disabled` | 503 | 未配置管理令牌（fail-closed） |
| `unauthorized` | 401 | 管理令牌无效 |
| `rollback_refused` | 409 | 回滚被拒（世代不存在/状态不允许） |
| `rate_limited` | 429 | 超过速率上限（HTTP 侧带 `Retry-After`） |
| `timeout` | 504 | 单请求超墙钟上限 |
| `internal` | 500 | 内部错误——**只给异常类型名，不含堆栈与路径** |

## 4. 限流、超时、幂等

| 项 | 值 | 出处 |
|---|---|---|
| 问句长度上限 | 512 字符 | `query.QUERY_MAX_CHARS` |
| `top_k` 上限 | 50 | `server.DEFAULT_MAX_TOP_K` |
| `graph_depth` 上限 | 2 | `server.DEFAULT_MAX_GRAPH_DEPTH` |
| 上下文预算上限 | 24000 tokens | `pipeline.PROD_PROFILE` |
| 单请求墙钟上限 | 20 s（`ARKRAG_SERVE_TIMEOUT_S`） | `server.DEFAULT_TIMEOUT_S` |
| 并发上限 | 4（`ARKRAG_SERVE_CONCURRENCY`） | `server.DEFAULT_CONCURRENCY` |
| 速率 | 每 60 s 60 次（`ARKRAG_SERVE_RATE_LIMIT_*`） | `server.DEFAULT_RATE_LIMIT_*` |
| 请求体上限 | 64 KiB（`ARKRAG_SERVE_MAX_BODY_BYTES`） | `server.DEFAULT_MAX_BODY_BYTES` |
| 响应上限 | 256 KiB（超了按固定顺序降级） | `server.DEFAULT_MAX_RESPONSE_BYTES` |
| 单条记录字符上限 | 4096（`ARKRAG_SERVE_MAX_RECORD_CHARS`） | `server.DEFAULT_MAX_RECORD_CHARS` |

**参数越界一律报错，不夹紧。** 夹紧会让调用方以为自己的参数生效了——
而真相是"你要的 100 条我只给了 50 条，且没告诉你"。

**幂等性**：除 `arkrag_admin_rollback` 外全部幂等（同一入参重复调用等价）。
回滚本身对**同一目标**重复执行是安全的（第二次会发现指针已经在那一代），
但它的语义是"改状态"，所以 `idempotentHint=false`——让 agent 不要盲目重试。

**超时的真相**：超时返回 504，但那个工作线程**不会被终止**（Python 无法安全抢占
线程）。并发信号量保证这种滞留线程最多 `concurrency` 个。这是已知限制，
不是可以靠重试解决的问题——重试只会让滞留线程更多。

## 5. 安全边界

### 5.1 只读 vs 改状态

| 类别 | 工具 | 会不会改东西 |
|---|---|---|
| 只读 | `arkrag_query`、`arkrag_search`、`arkrag_get_chunk`、`arkrag_get_entity`、`arkrag_get_assertion`、`arkrag_release_info`、`arkrag_health` | 不写任何文件；只读盘上产物 |
| 改状态 | `arkrag_admin_rollback` | 改发布指针 `data/arkrag/current.json`、写审计日志、清服务端世代缓存 |

只读工具**会写**一类文件：查询日志（`data/arkrag/logs/queries.jsonl`）与审计日志。
那是可观测性，不是业务状态，且**默认不记录问句原文**（只记长度与 sha256 前缀）。

### 5.2 管理工具怎么鉴权

```
服务端环境变量 ARKRAG_ADMIN_TOKEN=<口令>
        ↓（服务端读取，绝不经过模型）
Authorization: Bearer <口令>
        ↓
server.Handler._require_admin()   ← 唯一判据，与 /admin/rollback 共用
```

- **没配置令牌 = 管理类工具关闭**（503 `admin_disabled`），不是默认放开。
- 令牌**不是工具参数**，不出现任何 `input_schema` 里。
- 令牌值在对外错误消息里被 `sanitize_text()` 抹成 `<redacted>`。
- 每次调用写审计记录（`action` / `actor` / `result` / 前后世代 / 门禁报告摘要）。
  审计写不下去时**拒绝执行**，而不是"回滚了但没人知道是谁做的"。

### 5.3 数据完整性

- 块正文、实体描述、断言证据都是 **`untrusted: true` 的数据**，不是指令。
  任何把它们送进 LLM 的下游都必须按数据隔离，不得当提示词解释。
- 引用是**逐字偏移校验**过的：`chunk_id` + `start`/`end` + `evidence`，
  `text[start:end] == evidence` 必须成立。校验失败的引用被**剔除**并降置信度，
  不会返回一条"看起来合理但对不上原文"的引用。
- 错误响应不含本机绝对路径、不含令牌值、不含堆栈。内部异常只给异常**类型名**。

### 5.4 传输层

- stdio：stdout **只**承载协议消息；日志一律 stderr。
- HTTP：默认监听 `127.0.0.1`；`Origin` 必须是本机（否则 403）；
  会话 id 为 `secrets.token_urlsafe(24)`；会话有 TTL 与容量上限。
- HTTP 请求体超限时**先读掉再拒**（否则客户端收到的是 RST 而不是那条 413）。

## 6. 已知限制与未实现

诚实清单。**没有一条是"以后可能加"，都是明确不在当前实现里的东西。**

1. **SSE 流式未实现。** 不支持 `text/event-stream` 的响应流与通知通道。
   `GET /mcp` 回 405、`Accept: text/event-stream` 回 406，两者都带说明。
   影响：无法在工具执行期间推送进度或服务端通知；每个请求都是一问一答。
2. **`2026-07-28` 及之后的"无状态"协议修订未实现。** 该版取消了 `initialize`
   握手与 `Mcp-Session-Id`，改由每个请求的 `_meta` 携带版本与能力，并新增
   `server/discover`、`resultType`、`subscriptions/listen` 等。
   **本实现覆盖 `2025-11-25` 与 `2025-06-18`**（两者都属 `initialize` 握手时代，
   语义相同）。按新协议来的客户端会在 `initialize` 上收到明确的 `-32601`，
   而不是被静默按旧语义处理。
3. **HTTP 传输没有鉴权。** 只有管理类工具用了令牌；只读工具对任何能连上端口的
   客户端开放。跨机部署必须自己在前面加一层（反向代理 + mTLS / API key）。
   这也是默认只绑回环的原因。
4. **没有 OAuth / 细粒度授权。** 只有一个管理口令，够用于本地/单机灰度。
   多用户、按工具授权、按数据域授权都不在范围内。
5. **超时不能中断已在执行的请求。** 见第 4 节"超时的真相"。
6. **响应字节上限不是硬上限。** 超过 `max_response_bytes` 时按固定顺序丢可选字段
   并置 `truncated`；这是**一次性构造**，不是流式截断。所以极端情况下仍可能
   略微超出。
7. **`arkrag_search` 与 `arkrag_query` 共享链路。** 这意味着 `search` 也会跑完整条
   `ask_once`（含装配上下文与生成），只是把答案丢掉。它的"只检索"是**语义承诺**，
   不是性能优化——真要省掉生成那一步，就得另起一条通路，而那会让两者的候选
   各说各话（本项目已因"同一判定写两处"出过三次事故）。所以选择了慢但一致。
8. **没有 `resources/` 与 `prompts/` 能力。** 只声明了 `tools`。
   块正文通过工具取，不通过资源订阅。
9. **`tools/list_changed` 通知不发。** 工具表是编译期常量，
   `capabilities.tools.listChanged = false` 是**声明**而非省略。
10. **单进程、无水平扩展。** 会话表、速率计数、世代缓存都在进程内存里。
    多实例部署需要外部化这三样，当前没做。

## 7. 自检与排障

```powershell
# 能力表是否自洽（名字/描述/schema/权限标记/OpenAPI 可序列化）
py -3 scripts\serve_mcp.py --print-tools

# OpenAPI 文档（path 与 TOOLS 必然一致）
py -3 scripts\serve_mcp.py --print-openapi

# 接口层测试（74 个，离线，不需要真实 data/ 产物）
py -3 -m pytest tests\test_agent_api.py -q
```

**常见现象与原因**

| 现象 | 原因 | 处理 |
|---|---|---|
| 客户端报"JSON 解析失败" | stdout 被污染（多半是包装脚本里的 `print()`） | 所有日志改 stderr |
| `initialize` 回 `-32601` | 客户端在用 `2026-07-28+` 的无状态协议 | 见限制 2；改用 `2025-06-18`/`2025-11-25` |
| HTTP 400 缺会话 | `initialize` 之外没带 `Mcp-Session-Id` | 用响应头里的会话 id |
| HTTP 404 | 会话过期（TTL 30 min）或被 `DELETE` | 重新 `initialize` |
| HTTP 403 | `Origin` 不是本机 | 本机调用，或 `--allow-any-origin`（并自行加鉴权） |
| `admin_disabled` 503 | 没配 `ARKRAG_ADMIN_TOKEN` | 这是 fail-closed，属预期 |
| `generation_not_servable` 503 | 该世代缺产物（graph/assertion/adjacency/index/chunks） | 查 `arkrag_release_info` 的 `self_check` |
| `ready=false` 但 `ok=true` | 进程活着，数据不齐 | 查 `self_check.blocking_failures` |

`test_tool_handlers_delegate_to_named_routes` 钉住这条。
