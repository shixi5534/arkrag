# W0 体检产物说明：`data/diag_rank_24000.json`

- 生成脚本：`scripts/diag_rank_24000.py`
- 生成命令：`py -3.14 scripts/run_guarded.py -- py -3.14 scripts/diag_rank_24000.py`
- 对应计划：`docs/计划-W0到W4-检索宽度解耦与决策兑现-20261108.md` §W0
- schema 版本：`arkrag.diag_rank_24000/1`

## 这个文件回答什么

生产档跑 **24000** token、均 19.5 个单元，但现存断崖数据只有 6000/8000/12000
三档（`data/diag_context_positions.json` 的 `budget_arms` 只到 12000）。
W1 要定的 cap 值直接依赖「24000 档下 rank>10 的 gold 还有多少能进上下文」，
而这张表此前**不存在**。

## 为什么 `tmp_prod_*.json` 补不了这个缺口

`tmp_prod_*.json` 的 `rows` 每题只有
`abstained / answer / arms / category / citations_ok / judge / n_citations /
question / question_id / split` —— **全是答案级字段**。
没有 `hit_rank`、`n_units`、`ctx_tokens`，也没有单元列表，
所以无法事后复算「名次 → 上下文」的对应关系。

## 顶层字段

| 字段 | 含义 |
|---|---|
| `schema` | `arkrag.diag_rank_24000/1` |
| `purpose` | 一句话说明用途 |
| `generated_at` | UTC 时间戳，**不参与 `run_digest`** |
| `python` / `os` | 运行环境 |
| `command` | 生成命令原文 |
| `generation` | 世代 ID（`g-20261103T132152Z-06a741`） |
| `baseline_sha` | 三份 `tmp_prod_{split}.json` 的联合 SHA，用于锚定对比基线 |
| `config_digest` | `{budget, options, top_k, graph_depth}` 的规范化 SHA |
| `gold_set` / `gold_set_sha` | 用的 gold set 路径与 SHA |
| `splits` | 本次覆盖的 split 列表 |
| `elapsed_ms` | 测量总耗时，**不参与 `run_digest`** |
| `n_per_question` | 逐题记录条数 |
| `summary.<split>` | 分 split 汇总（见下） |
| `per_question` | 逐题记录，按 `(split, question_id)` 排序 |
| `run_digest` | `config_digest` + 规范化 `per_question` 的 SHA |

**可复算的定义（A2）**：同一命令跑两次，`run_digest` 必须相等。
它只由 `config_digest` 与剔掉 `elapsed_ms` / `generated_at` 的规范化
`per_question` 决定，所以时间戳变化不影响它。

## `summary.<split>` 字段

### `denominators` —— 分母逐个报出（A3 要求）

| 键 | 含义 |
|---|---|
| `全部输入` | 该 split 的全部 gold 题数 |
| `有 gold` | `gold_chunk_ids` 非空的题数 |
| `应答题（有 gold 且非结构类）` | 再排除 `should_abstain` |
| `gold 在 hits` | gold 至少有一块进了检索命中 |
| `gold 进上下文` | gold 至少有一块进了最终上下文 |

**任何比率的分母都是 `有 gold`**，不是 `全部输入`。结构类题（`time_conflict` /
`negative_abstain` / `adversarial`）没有 gold，单列，不混进分母。

### `by_rank_bucket` —— 逐名次 × 进上下文

| 键 | 含义 |
|---|---|
| `bucket` | `1` / `2-3` / `4-5` / `6-10` / `11+` / `无 gold 在 hits` |
| `n` | 落在这个区间的题数（**按本题 hits 实测，不沿用 12000 档的 32**） |
| `in_context` | 其中 gold 真的进了上下文的题数 |
| `rate` | `in_context / n` |

分桶口径与 `diag_context_positions.json` **同名同义**（A1 要求）。

### `cumulative_presence` —— 累计 presence

| 键 | 含义 |
|---|---|
| `k` | 名次阈值 |
| `gold_rank_le_k` | gold 名次 ≤ k 的题数 |
| `in_context` | 其中进了上下文的题数 |
| `rate_within_k` | `in_context / gold_rank_le_k` |

### `rank_gt_10` —— W1 cap 值的直接依据

| 键 | 含义 |
|---|---|
| `n` | 名次 > 10 的题数 |
| `in_context` | 其中进了上下文的题数 |
| `rate` | 比率 |
| `question_ids` | 具体是哪几道（可逐题复核） |

**这是 W0 反证条件 2 的分子**：若 `in_context / n` > 16.25%，
说明 24000 档下深名次仍大量可达，**不得直接 cap=10**，须重新评估 cap=12/14。

### `units` —— 单元成本

| 键 | 含义 |
|---|---|
| `n_units_median` / `n_units_mean` / `n_units_min` / `n_units_max` | 上下文单元数 |
| `ctx_tokens_median` / `ctx_tokens_mean` | 实际用掉的 token |
| `gold_unit_tokens_median` | gold 单元自身的 token 中位（cap 的直接依据） |
| `n_direct_units_mean` | 直接证据单元数均值 |
| `n_graph_only_units_mean` | 纯图扩展单元数均值 |

**W0 反证条件 1**：`n_units_mean < 12` ⇒ 标为「配置疑似未生效」，
先核 `Retriever.budget`、实际 `token_budget` 与可装载候选数，W1 暂停。

## `per_question` 逐题字段

| 字段 | 含义 |
|---|---|
| `question_id` / `split` / `category` / `question` | 身份 |
| `status` | `ok` / `gold_in_hits_not_in_context` / `gold_not_in_hits` / `no_gold` / `run_error` |
| `n_gold` / `gold_chunk_ids` / `should_abstain` | gold 信息 |
| `hit_rank` | **前插之后**的 `found["hits"]` 里 gold 的最好名次；无则 `null` |
| `in_hits` / `in_context` | 布尔 |
| `ctx_pos` | gold 在上下文里的最好位置 |
| `n_units` / `ctx_tokens` / `token_budget` / `n_candidates` / `n_hits` | 规模 |
| `gold_unit_tokens` | gold 单元 token 中位 |
| `channels` | gold 单元的来源通道 |
| `n_direct_units` / `n_graph_only_units` | 直接 vs 纯图单元数 |
| `n_truncated` / `any_truncated` | 被预算砍掉的单元数 |
| `rank_bucket` | 名次分桶 |
| `quote_locate_hits` | 逐字定位命中并前插的块（空 = 未触发） |
| `reserve_applied` / `graph_reserve_tokens` | 图预留额度是否生效及实际值 |

**`status` 的语义**（缺一不可，否则等于静默丢分母）：

- `no_gold` —— 结构类题，本就没有 gold，不进任何比率的分母；
- `gold_not_in_hits` —— 有 gold 但检索没召回到，是**检索层**问题；
- `gold_in_hits_not_in_context` —— 召回到了但没装进上下文，是**装配层**问题；
- `ok` —— gold 进了上下文；
- `run_error` —— 单题抛异常，`error` 字段留痕，**不从分母删除**。

## 链路保真：为什么必须照抄 `ask_once`

`scripts/diag_context_positions.py` 是 6000 档模板，**不能直接复用**：
它写死 `TOKEN_BUDGET = 6000`、不走 `quote_locate` 前插、不区分桥接题的
`bridge_search_top_k=40`。照抄它测出来的是**另一条链路**。

`diag_rank_24000.py` 严格照 `ask_once(options=prod_options())` 的顺序：

1. `analyze_query`
2. `search(top_k = 40 if 桥接题 else 20)`
3. `quote_locate.locate` **前插**，分数 `max(hits)+1.0`
4. `expand`
5. `build_context(graph_reserve_tokens=12000)`（仅桥接题）
6. 预算 24000

**名次在前插之后算**：前插会改变名次，若在插之前算 rank，
测出的不是生产链路上真实生效的名次。

## 纪律

- 本文件**只测量，不改任何实现**。不碰 `judge.py`、不碰 `data/goldset/`。
- 不覆盖任何历史基线：只写 `data/diag_rank_24000.json` 这一个新文件。
- 运行必须走 `scripts/run_guarded.py`（内核硬上限 + 轮询监督 + 跑前预估），
  见 `docs/事故-内存耗尽与熔断器-20261110.md`。
